# jix bug hunt

A setup for finding hard bugs in jix - unsafe / UB, silent wrong results, panics on valid input,
untrusted-input hazards - with a fleet of Claude sub-agents, each reviewing a small slice of the
library with pre-generated context, followed by adversarial verification with executable repros.

## Why sub-agents and not one inline scan

jix is about 40k non-test lines of Rust, and its unsafe code is spread over ~15 files whose
correctness depends on contracts defined elsewhere (`read_data`'s push / pull modes, `StridedBuf`'s
unaligned usize strides, pooled buffers, `noalias` pointers). An inline scan in one context
either skims (and misses the subtle bugs) or runs out of room after a few files. Splitting the
work gives each reviewer a narrow scope and a full budget for reasoning about it.

But splitting naively by file misses the most interesting class of bugs here: a caller in one
file breaking a precondition that an `unsafe` block in another file relies on. So the hunt runs
on three axes:

| kind | count | what it does |
|------|-------|--------------|
| module  | 44 | reads one slice (600-1500 lines) line by line, with the contracts it depends on, and settles the mapping-stage suspicions in it |
| concept | 12  | traces ONE invariant (push / pull contract, aliasing, alignment, integer width, degenerate shapes, untrusted archives, the Python boundary, ...) across every module, to catch bugs at the seams |
| dynamic | 2   | writes differential tests (Rust vs an ndarray reference, Python vs NumPy) and explains each failure from the code |

Every agent starts from the same briefing instead of rediscovering the architecture:
`PRIMER.md` (mission, severity, key contracts, checklist, how to test, the bar for a finding)
plus `context/<subsystem>.md` (contracts with file:line, unsafe inventory, edge-case surface,
**intentional behaviors** - so deliberate NumPy deviations are not reported - and hot spots).

Hunters are wrong often, so their findings are deduplicated and then checked by an adversarial
verifier per finding, which tries to refute it first and then builds a minimal repro: a Rust
integration test (debug build, so overflow and `debug_assert!`s fire), Miri for memory-safety
claims (sparingly - it is slow), or a Python script. Serious findings that the first verifier
could not settle get a second, independent verifier. What remains goes into a report.

Inline work in the main session is still the right tool *after* the run: triaging the report,
reading repros, fixing.

## Layout

```
bug-hunt/
  README.md          this file
  PRIMER.md          shared briefing every agent reads first
  KNOWN.md           triaged issues; hunters skip them, dedup drops them
  context/*.md       per-subsystem context (generated by the bug-hunt-map workflow, then reviewed)
  setup.sh           prebuilds everything the agents use
  templates/         repro template; dry_run_workflow.mjs (runs a workflow script with fake agents)
  tools/             cargo-i686: build and run a test as 32-bit i686-musl
  runs/<run-id>/     REPORT.md, findings/<ID>.md, repros/  (one directory per run)
.claude/workflows/
  bug-hunt.js        the hunt: Hunt -> Dedup -> Verify -> Report (unit list lives here)
  bug-hunt-map.js    regenerates context/*.md from the current code
```

## Running a hunt

1. **Prepare the checkout** (once per machine / after code changes):

   ```bash
   bash bug-hunt/setup.sh            # --no-miri / --no-python / --no-i686 to skip parts
   ```

   It builds the jix library and unit-test binary, warms the Miri cache, installs a debug
   build of the Python bindings into `.venv`, and builds the library for 32-bit
   `i686-unknown-linux-musl` (zig compiles zstd, clang + lld link; the static test binaries run
   natively, so 32-bit truncation bugs can be demonstrated, not just argued). Agents share these
   build caches and never rebuild them; a new repro test then compiles in ~2 s (~30 s for i686).

2. **Check the context is current.** The docs in `context/` describe the code at the commit
   they were generated from. If the code has moved, ask Claude Code to "run the bug-hunt-map
   workflow", review `git diff bug-hunt/context`, and update `MODULE_UNITS` in
   `.claude/workflows/bug-hunt.js` from the units it proposes. Reviewing these docs is the
   single highest-leverage thing a maintainer can do: every hunter trusts their "Contracts" and
   "Intentional behaviors" sections.

3. **Run.** In Claude Code: "run the bug-hunt workflow with runId 2026-10-21". Arguments:

   | arg | default | meaning |
   |-----|---------|---------|
   | `runId` | `"run"` | output directory `bug-hunt/runs/<runId>/`; also prefixes scratch files |
   | `units` | all | unit-id prefixes, e.g. `["reduction", "concept-alignment", "py-"]` |
   | `skip` | - | unit-id prefixes to leave out, e.g. units a previous run already covered |
   | `kinds` | all | subset of `["module", "concept", "dynamic"]` |
   | `verify` | `true` | `false` reports raw hunter output without verification |
   | `minConfidence` | `"low"` | only verify findings at or above this hunter confidence |
   | `focus` | - | extra instructions for every hunter, e.g. `"memory safety only"` |
   | `effort` | inherit | reasoning effort for hunters and verifiers |

   A pilot first is a good idea: `units: ["util-memory", "concept-alignment"]`, then read the
   report and adjust the primer before the full run. (Done: run `2026-10-21-pilot`, see below.)

   Subagents may not write report files, so the workflow returns the report as `reportMarkdown`
   and the session that ran it saves it to `bug-hunt/runs/<runId>/REPORT.md`.

   After editing a workflow script, check its control flow for free with fake agents:
   `node bug-hunt/templates/dry_run_workflow.mjs .claude/workflows/bug-hunt.js '{"runId":"x"}'`
   (`PRINT_PROMPT=hunt:<unit-id>` prints a rendered prompt).

4. **Triage** `bug-hunt/runs/<runId>/REPORT.md`. Each confirmed / plausible finding has a
   write-up in `findings/<ID>.md` and, usually, a repro in `repros/`. To re-run a Rust repro,
   copy it back into `jix/tests/` and run
   `cargo test --manifest-path jix/Cargo.toml --all-features --test <name>`. Record every triaged
   finding (fixed, won't fix, intended) in `KNOWN.md` so later runs skip it. Read the
   "Refuted and intended" section too: a pattern of false positives means the primer or a
   context doc is missing a fact.

## Cost and time

Measured on the pilot (4 hunters -> 16 raw / 13 distinct findings -> 13 verifiers + dedup +
report = 19 agents): about 3.0M subagent tokens (~160k per agent) and 61 minutes at 2 agents at a
time. A full run is 58 hunters plus one or two verifiers per distinct finding - extrapolating,
roughly 200-250 agents and 30-40M tokens. The workflow runs at most `min(16, CPUs - 2)` agents at
once, so on a 4-core cloud container it runs 2 at a time and takes on the order of 10-12 hours; on
a 16+ core machine, 1-2 hours. To go faster on a small machine, split the run into batches with `units` and
different `runId`s and launch them concurrently (scratch file names are run-scoped, so batches do
not collide). Memory is the other limit: building the Python extension needs several GB, so do
not run `setup.sh` next to a hunt.

An interrupted run can be resumed: re-invoke the workflow with `resumeFromRunId` and the same
arguments; finished agents return their cached results.

## Rules the agents follow (and why)

- They never modify tracked files - many agents share one checkout and one build cache, and an
  edit under `jix/src` would invalidate everyone's build mid-run. They only create new files:
  `jix/tests/hunt_<run>__*.rs` / `repro_<run>__*.rs` (gitignored; the report stage moves the
  repros into `runs/<run>/repros/` and deletes the scratch) and files under `runs/<run>/`.
- Repros use the public Rust API or Python. A defect no public path can reach is reported as a
  latent hazard (low severity).
- Miri only via `python jix/run_miri.py ...`, on one tiny test, at most once or twice per finding.

## Runs so far

- `2026-10-21-pilot` - units `util-memory-*` + `concept-alignment`: 13 findings, all confirmed
  with repros (6 high). Recorded as K1-K13 in `KNOWN.md`. Lessons folded into the primer:
  one repro convention (assert the correct behavior), "crate-internal" must account for public
  associated types, re-run hunter claims instead of quoting them, and the i686 test runner.
  Next: the remaining units with `skip: ["util-memory", "concept-alignment"]`.
