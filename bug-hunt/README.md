# jix bug hunt

A setup for finding hard bugs in jix - unsafe / UB, silent wrong results, panics on valid input,
untrusted-input hazards - with a fleet of Claude sub-agents, each reviewing a small slice of the
library with pre-generated context, followed by adversarial verification with executable repros.

The results of the scans run so far (2026-10-21 to 2026-11-16) are consolidated in
`report/REPORT.md`: one list of the issues that are still open. This file explains how to run the
next scan.

## Why sub-agents and not one inline scan

jix is about 40k non-test lines of Rust, and its unsafe code is spread over ~15 files whose
correctness depends on contracts defined elsewhere (`read_data`'s push / pull modes, `StridedBuf`'s
unaligned usize strides, pooled buffers, `noalias` pointers). An inline scan in one context
either skims (and misses the subtle bugs) or runs out of room after a few files. Splitting the
work gives each reviewer a narrow scope and a full budget for reasoning about it.

But splitting naively by file misses the most interesting class of bugs here: a caller in one
file breaking a precondition that an `unsafe` block in another file relies on. So the hunt runs
on three axes:

| kind | count | what it does |
|------|-------|--------------|
| module  | 46 | reads one slice (600-1500 lines) line by line, with the contracts it depends on, and settles the mapping-stage suspicions in it |
| concept | 12  | traces ONE invariant (push / pull contract, aliasing, alignment, integer width, degenerate shapes, untrusted archives, the Python boundary, ...) across every module, to catch bugs at the seams |
| dynamic | 2   | writes differential tests (Rust vs an ndarray reference, Python vs NumPy) and explains each failure from the code |

Every agent starts from the same briefing instead of rediscovering the architecture:
`PRIMER.md` (mission, severity, key contracts, checklist, how to test, the bar for a finding)
plus `context/<subsystem>.md` (contracts with file:line, unsafe inventory, edge-case surface,
**intentional behaviors** - so deliberate NumPy deviations are not reported - and hot spots).

Hunters are wrong often, so their findings are deduplicated and then checked by an adversarial
verifier per finding, which tries to refute it first and then builds a minimal repro: a Rust
integration test (debug build, so overflow and `debug_assert!`s fire), Miri for memory-safety
claims (sparingly - it is slow), or a Python script. Serious findings that the first verifier
could not settle get a second, independent verifier. What remains goes into a report.

Inline work in the main session is still the right tool *after* the run: triaging the report,
reading repros, fixing.

## Layout

```
bug-hunt/
  README.md          this file
  PRIMER.md          shared briefing every agent reads first
  KNOWN.md           triaged issues (open and intended); hunters skip them, dedup drops them
  context/*.md       per-subsystem context (generated by the bug-hunt-map workflow, then reviewed)
  setup.sh           prebuilds everything the agents use
  templates/         repro template; dry_run_workflow.mjs (runs a workflow script with fake agents)
  tools/             cargo-i686 (+ zig-i686-cc / -ar): build and run a test as 32-bit i686-musl
                     save_report.py: save a finished run's REPORT.md
                     disk_janitor.sh: delete stale repro builds while a run is going
                     cost.py: token cost per agent of a finished run
  report/            consolidated report of all scans so far: REPORT.md, findings/, repros/
  runs/<run-id>/     one directory per new run: REPORT.md, findings/<ID>.md, repros/
.claude/workflows/
  bug-hunt.js        the hunt: Hunt -> Dedup -> Verify -> Report (unit list lives here)
  bug-hunt-map.js    regenerates context/*.md from the current code
```

## Running a hunt

1. **Prepare the checkout** (once per machine / after code changes):

   ```bash
   bash bug-hunt/setup.sh            # --no-miri / --no-python / --no-i686 to skip parts
   ```

   It builds the jix library and unit-test binary, warms the Miri cache, installs a debug
   build of the Python bindings into `.venv`, and builds the library for 32-bit
   `i686-unknown-linux-musl` (zig compiles zstd, clang + lld link; the static test binaries run
   natively, so 32-bit truncation bugs can be demonstrated, not just argued). Agents share these
   build caches and never rebuild them; a new repro test then compiles in ~2 s (~30 s for i686).

   Memory: building the Python extension needs several GB. On a 15 GB machine it is OOM-killed
   when it runs next to other Rust builds (seen twice while consolidating the report), so never
   run `setup.sh` or `maturin develop` next to a hunt or a batch of repro builds; if it must share
   the machine, set `CARGO_BUILD_JOBS=2`.

2. **Check the context is current.** The docs in `context/` describe the code at the commit
   they were generated from (they were last regenerated for main after #105 and do not know #106
   / #107, which the scan of 2026-11-16 read from the diff instead; their suspicion bullets carry
   `[CONFIRMED in <run> as Kn]` / `[RULED OUT in <run>: ...]` tags from triage).
   If the code has moved, ask Claude Code to "run the bug-hunt-map workflow" with
   `since: <commit of the last scan>`, review `git diff bug-hunt/context`, and update
   `MODULE_UNITS` in `.claude/workflows/bug-hunt.js` from the units it proposes. Reviewing these
   docs is the single highest-leverage thing a maintainer can do: every hunter trusts their
   "Contracts" and "Intentional behaviors" sections.

3. **Run.** In Claude Code: "run the bug-hunt workflow with runId 2026-12-01-batch1 and units
   [...]". Arguments:

   | arg | default | meaning |
   |-----|---------|---------|
   | `runId` | `"run"` | output directory `bug-hunt/runs/<runId>/`; also prefixes scratch files |
   | `units` | all | unit-id prefixes, e.g. `["reduction", "concept-alignment", "py-"]` |
   | `skip` | - | unit-id prefixes to leave out, e.g. units a previous run already covered |
   | `kinds` | all | subset of `["module", "concept", "dynamic"]` |
   | `verify` | `true` | `false` reports raw hunter output without verification |
   | `minConfidence` | `"low"` | only verify findings at or above this hunter confidence |
   | `focus` | - | extra instructions for every hunter, e.g. `"memory safety only"` |
   | `effort` | inherit | reasoning effort for hunters and verifiers |

   A good `focus` for a scan after code changes names the commit range to concentrate on
   (`git diff -M <last scan> HEAD -- <your files>`), the K-ids recorded most recently with a
   one-phrase summary each ("do not re-report them, but look for the same pattern at other
   sites"), and the experiment limits: "Miri is very slow: use it very little, only through
   `python jix/run_miri.py`", "On i686, K8 (8-byte alignment debug_assert for 64-bit dtypes)
   blocks debug experiments: use --release or 4-byte dtypes there", "Python tests must run under
   pytest-xdist (`--numprocesses auto`)".

   Subagents may not write report files, so the workflow returns the report as `reportMarkdown`
   and the session that ran it saves it: `python3 bug-hunt/tools/save_report.py <workflow task
   output file> <runId>`.

   After editing `bug-hunt.js` (e.g. remapping unit ranges after a rebase), launch it with
   `scriptPath: ".claude/workflows/bug-hunt.js"` rather than by name: a launch by name can run an
   older copy of the file (run 2026-10-29-batch6 started with stale unit ranges this way).

   **Keep batches small (about 6 units) and commit each before starting the next.** A cloud
   container can restart at any time (it is also reclaimed when the disk fills), and a restart
   wipes both the workflow's resume cache (in the session directory) and the uncommitted run
   directory: run `2026-11-14-batch7` lost 36 units' worth of hunting this way. A 6-unit batch
   takes 1-2 h, so a restart costs at most that. Commit the raw output first, then triage it in a
   second commit (see "After a run"). A restart can also leave the session directory intact (it
   did during the 2026-11-16 scan): then re-invoking with `resumeFromRunId` replays the hunters
   that had finished, but only with byte-identical arguments, so save the `focus` text to a file
   before launching and pass the same text again.

   Disk: each repro is its own test binary, and a batch builds hundreds of them. Keep only line
   tables in debug builds (an untracked `.cargo/config.toml` with `[profile.dev] debug =
   "line-tables-only"`, listed in `.git/info/exclude`) and run the janitor next to the workflow:
   `bash bug-hunt/tools/disk_janitor.sh 9000` in the background (it deletes
   `{repro,hunt}_*` test binaries, fingerprints and incremental caches older than ~90 minutes; a
   later run of that test just relinks it). `df` misreports a cloud container's per-session disk
   allowance; trust the janitor's free-space log.

   To add units to a running batch, stop it and re-invoke with `resumeFromRunId`, the same `runId`
   and the longer `units` list. Finished hunters replay from the cache only if their prompts are
   byte-identical, so do not change the definitions of units that already ran.

   After editing a workflow script, check its control flow for free with fake agents:
   `node bug-hunt/templates/dry_run_workflow.mjs .claude/workflows/bug-hunt.js '{"runId":"x"}'`
   (`PRINT_PROMPT=hunt:<unit-id>` prints a rendered prompt).

4. **After a run** (the order used for every batch of the last scans):
   1. Save `REPORT.md` with `tools/save_report.py`.
   2. Delete the run's leftover build output (`jix/target/{debug,release}/{deps,.fingerprint,
      incremental}/*<run>*`, the Miri and `target-i686` equivalents, scratch crate copies and
      `scratch/target-*`) and say so in REPORT.md's header, so the paths it cites are not a
      surprise.
   3. Check the ASCII-only rule: `grep -rlP '[^\x00-\x7F]' bug-hunt/runs/<run>` and
      `python scripts/check_only_ascii.py` (hunters write literal non-ASCII test strings; replace
      them with escapes and note it in REPORT.md).
   4. Commit "bug-hunt: raw output of run <run>" and push.
   5. Re-run every confirmed / plausible repro by hand. Python: from a scratch directory,
      `.venv/bin/python -I <repro>`. Rust: copy it into `jix/tests/`, run
      `cargo test -q --manifest-path jix/Cargo.toml --all-features --test <name> -- --nocapture
      --test-threads=1`, then delete the copy and its incremental cache. 32-bit:
      `bug-hunt/tools/cargo-i686 test ...` with the same arguments.
   6. Record each finding in `KNOWN.md` (next free K-id; an intended one gets `Status: intended -
      <why>`). A note on an existing entry goes at the end of its Notes line, not on a new line,
      and every `## K` heading keeps a blank line before it.
   7. Tag the context-doc suspicion bullets the run settled with `[CONFIRMED in <run> as Kn]` or
      `[RULED OUT in <run>: <evidence>]`, and fold verifier corrections into the "Intentional
      behaviors" sections: a pattern of refuted findings means a doc is missing a fact.
   8. Add a row to the cost table below (`python3 bug-hunt/tools/cost.py <transcript dir of the
      workflow run>`).
   9. Commit "bug-hunt: triage run <run> (Kx-Ky)" and push.

   Each confirmed / plausible finding has a write-up in `runs/<run>/findings/<ID>.md` and, usually,
   a repro in `runs/<run>/repros/`. When the scans of a campaign are done, consolidate them into
   `report/` (one list of the still-open items, re-checked against the current main, with fixed
   items dropped from `KNOWN.md`), as was done for the 2026-10/11 scans.

## Cost and time

Measured, in input-token equivalents (cache reads weighted 0.1, cache writes 1.25; output is
negligible), from the subagent transcripts with `tools/cost.py`. A transcript logs an assistant
message once per content block, every copy carrying the same usage, so count each message id once
(the numbers recorded before batch4 summed every copy and were ~1.8x too high).

| run | units | agents | findings | cost | per unit | wall time (2 at a time) |
|-----|------:|-------:|---------:|-----:|---------:|------------------------:|
| pilot (util-memory, concept-alignment) | 4 | 19 | 13 | 13.4M | 3.4M | 61 min |
| trial2 (mixed complexity) | 8 | 38 | 28 | 21.1M | 2.6M | 125 min |
| batch3 (#87 code, 2 untouched subsystems) | 8 | 34 | 23 (+1 intended) | 26.2M | 3.3M | 138 min |
| batch4 (#90 code, module units only) | 8 | 28 | 18 | 18.8M | 2.4M | 91 min |
| batch5 (#91 code, module units only) | 12 | 37 | 23 | 26.8M | 2.2M | 122 min |
| batch6 (#92 code, last 11 module + all 9 concept units) | 20 | 70 | 44 (1 plausible) | 75.7M | 3.8M | ~5 h |
| batch7-1 (#94-#105 read path, 5 module + 1 concept unit) | 6 | 15 | 7 | 16.5M | 2.75M | 66 min |
| batch7-2 (#94-#105 read path, 6 module units) | 6 | 11 | 3 | 15.0M | 2.5M | 59 min |
| batch7-3 (#94-#105 read path, 5 module + 1 concept unit) | 6 | 13 | 5 | 14.5M | 2.4M | 81 min |
| batch7-4 (#94-#105 read path, 5 module + 1 concept unit) | 6 | 12 | 2 (+2 intended) | 17.3M | 2.9M | 85 min |
| batch7-5 (#94-#105, the 6 Python-binding module units) | 6 | 20 | 10 | 15.2M | 2.5M | 70 min |
| batch7-6 (#94-#105, 2 module + 2 concept + both dynamic units) | 6 | 9 | 1 | 27.8M | 4.6M | 110 min |
| scan-106-107 (the #106 / #107 diff, 6 module units) | 6 | 18 | 7 (+1 intended) | 17.9M | 3.0M | 49 min after a resume |
| scan-106-107-b (rest of the #106 / #107 diff, 4 module + 2 concept units) | 6 | 17 | 9 | 15.0M | 2.5M | 57 min |

The scan-106-107 row includes 2.3M for two hunters that a container restart interrupted and the
resume ran again.

- A module hunter costs 0.7-2.4M (util-test-infra 4.4M); a concept hunter 1.2-8.2M; the
  differential testers 5-6M (150-170 turns). The cost follows how much code it traces, not how
  "complex" the code is: concept hunters and the differential testers cost the most, Python
  wrappers and shape ops the least.
- A verifier costs ~0.1-0.9M, one per distinct finding, so verification is 30-40% of a run.
  Bug density was 3.3, 3.5, 2.9, 2.25, 1.9 and 2.2 per unit in the first six runs, and fell to
  0.2-1.7 per unit in the six batches of the re-scan after #94-#105 (most code had been hunted
  once already). The units that are "simple" to hunt are not much cheaper overall:
  py-ops-shape-ops had the cheapest hunter and 8 findings.
- Each agent takes ~6.5 min of wall time at 2 agents in parallel.
- Yield per token differs a lot by kind (findings / hunter cost): module units are the best value
  (codec-archive-archive-io 8 / 0.9M, py-ops-shape-ops 8 / 0.7M, shape-ops-slice-reshape 5 /
  1.0M, py-core-read-path 5 / 1.7M); concept units 0-4 each for 1.2-8.2M
  (concept-python-boundary 4 / 2.4M, concept-tiling-coverage 0 / 2.6M); the dynamic testers are
  bimodal (Python 11 / 2.8M on fresh code, 1 / 5.6M on re-scanned code; Rust 2 / 6.0M, then 0).
  A re-scan of already-hunted code is best spent on module units over the changed files.
- Builds leave GBs behind (incremental caches, per-repro test binaries): batch3 ended with 3 GB of
  disk free. setup.sh, the janitor and the post-run cleanup delete them.

Coverage so far: every unit (46 module, 12 concept, 2 dynamic) ran once in the first six runs
(60 hunters, 226 agents, 182M tokens); after #94-#105 the 36 units over new or changed code ran
again in six 6-unit batches (36 hunters, 80 agents, 106M tokens); two 6-unit scans over the #106 /
#107 diff followed (12 hunters, 35 agents, 33M tokens).

The workflow runs at most `min(16, CPUs - 2)` agents at once. To go faster on a small
machine, split the run into batches with `units` and different `runId`s and launch them
concurrently (scratch file names are run-scoped, so batches do not collide). Memory is the other
limit (see step 1).

An interrupted run can be resumed: re-invoke the workflow with `resumeFromRunId` and the same
arguments; finished agents return their cached results - as long as the container that holds the
session directory survives (see the batch rule above).

## Rules the agents follow (and why)

- They never modify tracked files - many agents share one checkout and one build cache, and an
  edit under `jix/src` would invalidate everyone's build mid-run. They only create new files:
  `jix/tests/hunt_<run>__*.rs` / `repro_<run>__*.rs` (gitignored; the report stage moves the
  repros into `runs/<run>/repros/` and deletes the scratch) and files under `runs/<run>/`.
- Repros use the public Rust API or Python. A defect no public path can reach is reported as a
  latent hazard (low severity).
- Miri only via `python jix/run_miri.py ...`, on one tiny test, at most once or twice per finding.

## Lessons from the 2026-10/11 scans

- Fixes need a second look. A large share of findings were incomplete or regressed earlier
  fixes (e.g. K177 came from the K131 fix, K178 from the K146 fix, K157 re-opened K120). After a
  fix lands, re-run its repro AND hunt the same pattern at other sites; listing the recent K-ids
  in `focus` does this. Example: #107 fixed 22 of the 44 open items at once, and a 6-unit scan of
  its diff (with the claimed fixes in `focus`) found three of those fixes incomplete or
  overreaching (K185, K186, K188) plus an archive-format break from #106 (K184); a second batch
  over the rest of the diff found four more storages whose #106 ReadTiling level is cheaper than
  their read (K192-K194, K198). Fresh code is where the yield is: 16 findings in 12 units.
- Repros rot. Rust repros written against an older API stop compiling after refactors (#94-#105
  broke most repros written before them); Python repros survive much better. When consolidating,
  port the open items' Rust repros to the current API (as `report/repros/` now is) instead of
  keeping dead files.
- 32-bit bugs are real bugs here: `as usize` truncations of u64 sizes produced the only high
  findings of the re-scan. The i686 runner shows them natively; keep the 32-bit concept unit and
  i686 experiments in every scan of code that sizes buffers.
- Re-verify the hunters' "intended" judgments against the docs and tests, and record intended
  behaviors in the context docs, or the next run re-files them.
- `jix/Cargo.lock` is gitignored, so dependency versions drift between scans (fearless_simd
  resolved 1.1.0, then 1.2.0): say which version a SIMD differential ran against.
- The Python extension in `.venv` is an editable install of one checkout: after switching
  worktrees or commits, rebuild it (`maturin develop` from that checkout's `jix-py`) before
  re-running Python repros, and check `jix.__file__`.
