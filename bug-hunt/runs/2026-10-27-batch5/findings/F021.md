# F021: A widening element-wise view keeps the source's explicit block shape (in elements, all fixed), so compact()/write_to() with default params fails with InvalidArgument when that block exceeds 1 GiB at the wider itemsize

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/ops/op1.rs:36 (related: jix/src/ops/op2.rs:72, jix/src/storage/params.rs:279-290, jix/src/storage/params.rs:349-372, jix/src/storage/params.rs:405-414, jix/src/array.rs:1315-1316)
- Reachability: public Rust API (`cast`, `map`, any widening Op1/Op2 view, then `compact`, `compact_with(ArrayParams::new(), ..)`, `write_to`, `write_to_file`) and Python API (`jix.cast` + `jix.compact`)
- Reported by: elementwise-ops-kernel-framework

## What goes wrong
`Op1::new` clones the input's `ArraySpecDynamic` verbatim, including `block_shape` (counted in
elements) and `block_shape_fixed_dims`, even when the kernel's output itemsize is larger than the
input's (`Op2::new` does the same through `combine_block_layout`). An explicitly set block shape is
all-fixed by default. When the view is materialized with default params,
`override_from_storage` inherits that fixed block shape and `tune` keeps it unchanged, then rejects
it because `block_shape * new_itemsize > MAX_BLOCK_SIZE_BYTES` (1 GiB, added in #87 for K18). A
valid lazy view of a valid array thus cannot be compacted or written without passing explicit
params, although `compact_with`'s docs say unset fields are inherited "if possible". This is a
clean `Err` with an explanatory message (no panic, no wrong data), and it needs an unusually large
explicit block (more than 1 GiB / output itemsize elements), hence low.

The hunter's second point (below the limit the derived array gets blocks k times larger in bytes)
is not counted as a defect here: the `ArrayParams::block_shape` docs say a fixed shape "will be
preserved as-is" when used as a propagation source, and keeping the element grid aligned with the
source is a defensible choice.

## Trigger
```rust
let n = (1usize << 26) + 8;                       // 64 MiB of u8 in one explicit block
let mut p = ArrayParams::new(); p.block_shape(&[n as u32]);
let a = Array::compact_ndarray_with(&ndarray::Array1::<u8>::zeros(n), p)?;   // OK
a.view().cast::<Complex<f64>>().compact()          // Err: 67108872 * 16 B > 1 GiB
a.view().cast::<Complex<f64>>().write_to(&mut Cursor::new(vec![]))   // same Err
```
Same with `f32` source, explicit block of > 2^27 elements, `.cast::<f64>()`; or `u8 -> f64` with a
block of > 2^27 elements; or a user `map` to a wider type. Python:
`jix.compact(jix.cast(jix.compact(np.zeros(n, np.uint8), params={"block_shape": [n]}), np.complex128))`.

## Root cause
- jix/src/ops/op1.rs:36 `let mut spec = array.spec().dynamic().clone();` - the block layout is
  carried over unchanged regardless of `K::Output::DTYPE.itemsize()` vs the input itemsize (and
  jix/src/ops/op2.rs:72-75 via `combine_block_layout`, which keeps a dim fixed when all inputs agree).
- jix/src/storage/params.rs:286-289 `override_from_storage` copies both the block shape and its
  fixed flags (the shared `block_size`, in bytes, is copied too and no longer matches
  `block_shape * itemsize` of the view).
- jix/src/storage/params.rs:349/372: an all-fixed shape skips rescaling, so nothing brings it back
  under the limit before the hard check at jix/src/storage/params.rs:405-414.
- Entry point jix/src/array.rs:1315-1316 (`compact_into_builder_dyn`), shared by `compact`,
  `compact_with`, `write_to`, `write_to_with` and `write_to_file`.

## Suggested fix
Treat an inherited block shape as a hint: in `override_from_storage` / `tune`, when the inherited
(not user-given) fixed block exceeds `MAX_BLOCK_SIZE_BYTES` at the target itemsize, clear the fixed
flags (or scale the inherited shape down) instead of erroring. Alternatively, have `Op1::new` /
`Op2::new` drop the fixed flags when the output itemsize grows enough to push the block past the
limit. Keep the hard error for block shapes the caller passed explicitly.
