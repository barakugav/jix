# F016: read_from rounds untrusted header dims up with unchecked next_multiple_of: a dim near u64::MAX panics in debug builds instead of returning InvalidArchive

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/archive/array.rs:490 (related: jix/src/archive/array.rs:511-515, jix/src/storage/params.rs:512, jix/src/error.rs:186)
- Reachability: public Rust API (`Array::read_from_reader`, `read_from_file`, `read_from_file_section`, `read_from_file_mmap`) and Python API (`jix.read_array`, default options)
- Reported by: codec-archive-array-format-dtype

## What goes wrong
`ArrayBlockTableStorageBase::read_from` works out the expected padded item count as
`s.next_multiple_of(b)` per dim, on header values read straight from the file. The only earlier
check is `0 < b <= max(s, 1)` (array.rs:472-481), and nothing caps `s` at i64::MAX until
`into_spec` -> `check_shape_overflow` (params.rs:512, error.rs:186) runs much later. When `s` is
within `b - 1` of u64::MAX and not a multiple of `b`, the rounding overflows. Debug builds,
including the dev Python extension, panic with "attempt to add with overflow". Release builds
wrap the padded dim to 0. In the second trigger below, the unchecked `nblocks` product at
array.rs:511-515 also wraps to 0, so every archive consistency check passes. The file is then
rejected only by `check_shape_overflow`, with `InvalidShapeOperation` instead of
`InvalidArchive`. The shipped release build therefore returns an error and nothing unsafe
happens. The defect is a debug panic on malformed input, plus the wrong error kind in release.
It is the same pattern as K55 and K83. The bug predates #91: the removed `Idx::ceil_to_multiple`
(`div_ceil(m) * m`) overflowed the same way.

## Trigger
Take a valid ArrayV1 archive and replace its ArrayHeader, shifting the TOC offsets by the change
in header length:
1. `shape = [u64::MAX], block_shape = [2]` over the archive of `compact_fn([2], |_| 7u8)`.
   Debug: panic. Release: `InvalidArchive` ("array blocks nitems 2 does not match shape
   product 0"), because the padded dim wraps to 0.
2. `shape = [u64::MAX, 2], block_shape = [2, 1]` over the archive of a `[0, 2]` u8 array with
   block `[1, 2]` (empty block table, nitems 0, block_size 2). Debug: panic. Release: the padded
   nitems wraps to 0 and the nblocks product `2^63 * 2` wraps to 0. All archive checks pass, and
   the error is `InvalidShapeOperation`.
Then call `Array::read_from_reader(Cursor::new(bytes), Some(len), ArrayParams::default(),
ArchiveValidation::Strict)` or `jix.read_array(io.BytesIO(bytes))`.

## Root cause
array.rs:483-499 does unchecked `u64` arithmetic on dims from the file, before the library-wide
invariant "dims <= i64::MAX" (error.rs:186-188) is applied to them. `try_shape_product` guards
only the product, not the per-dim rounding that feeds it. The `nblocks` product at 511-515 is a
plain `.product::<u64>()`. It cannot overflow once the per-dim padding is correct, because each
factor is at most the padded dim, but it wraps along with a wrapped padded dim.

## Suggested fix
Reject `s > i64::MAX` with `InvalidArchive` right after the block-shape check, or call
`check_shape_overflow` on the header shape and map its error to `InvalidArchive`. Either one makes
`next_multiple_of` safe, since `i64::MAX + u32::MAX < u64::MAX`. Alternatively, use
`checked_next_multiple_of` and turn `None` into `InvalidArchive`.
