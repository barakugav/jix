# F020: The f32 read-cost hint `element_cost` is never saturated; past f32::MAX it becomes +inf, a zero-length concatenate member turns that into NaN (0 * inf), and the next multi-input constructor panics in max_cost_layout_order (partial_cmp().unwrap())

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/storage/params.rs:896 (0 * inf weighted cost), panic at jix/src/storage/params.rs:912 (related: jix/src/storage/params.rs:897, jix/src/storage/params.rs:826, jix/src/storage/params.rs:878, jix/src/ops/reduction.rs:177, jix/src/ops/shape_ops/concatenate.rs:121-135, jix/src/array.rs:1662)
- Reachability: public Rust API and Python API (release wheels panic at params.rs:912; debug builds, including the Python dev extension, panic at array.rs:1662 already on the op whose cost becomes inf)
- Reported by: shape-ops-join

## What goes wrong
Every op derives an f32 `element_cost` read hint from its inputs, and nothing caps it: element-wise
combines add costs (params.rs:897, `+ 1.0`), `Op1` adds 1 (params.rs:826), reductions multiply by the
reduced length + 4 (reduction.rs:177). Once the estimate passes f32::MAX (~2^128) it is +inf, which
`Array::from_storage` treats as an invariant violation (`debug_assert!(element_cost.is_finite())`,
array.rs:1662) - a panic in debug builds, silently carried in release. Concatenate weights each
input's cost by its share of the concat dim (concatenate.rs:131-135 -> `combine_select_hints`), so a
zero-length member with inf cost contributes `0 * inf = NaN` (params.rs:896) and the Concatenate's own
cost is NaN. The next constructor that combines hints (Concatenate, Stack, Op2, cmp, where,
map_multiple) calls `max_cost_layout_order`, whose `a.partial_cmp(b).unwrap()` (params.rs:912) panics
on the NaN - inside Result-returning constructors such as `Concatenate::new_array`, so no `Err`.

## Trigger
Either way of reaching an inf cost, then two joins:

- `x = compact(zeros::<f32>(0))`; 130 times `x = x + x` (cost c -> 2c + 1, inf after ~125 steps).
  The array is empty, so it is trivially evaluable.
- or `compact([[1u8]]).broadcast([1, 2^62]).sum(1)`, then twice `.insert_dim(1).broadcast([1, 2^60]).sum(1)`
  (cost 8 -> ~2^65 -> ~2^125 -> ~2^185 = inf), then `.slice((0..0,))`.

Then `c = Concatenate::new_array(vec![x, other_len1], 0)` returns Ok with cost NaN, and
`Concatenate::new_array(vec![c.into_any(), other_len1], 0)` (or `c + other`) panics.
Python: `x = jix.compact(np.zeros(0, np.float32))`; `x = x + x` 130 times;
`c = jix.concatenate([x, o])`; `jix.concatenate([c, o])`.

## Root cause
`element_cost` is a heuristic but is computed with unbounded f32 arithmetic, while
`Array::from_storage` asserts it stays finite (array.rs:1662) and `max_cost_layout_order` assumes it
is never NaN (params.rs:912). The only producer of NaN is `combine_hints`' `weight * cost`
(params.rs:896) with weight 0 (a zero-length concatenate member, or every member zero-length:
`total.max(MIN_POSITIVE)` at params.rs:878 then makes all weights 0) and cost +inf; every other
combine keeps an inf as inf. Severity is low: building the inf cost needs an estimated per-element
cost above ~3.4e38 (125 self-doublings or nested reductions over >2^128 elements) and, in release,
a zero-length join member on top. The cost is only a read-tile hint, so inf/NaN have no other effect
(ScaleWeight::new maps NaN to its smallest non-zero weight without panicking).

## Suggested fix
Saturate costs where they are produced - e.g. clamp to `f32::MAX` in `ArraySpecDynamic::new` /
`add_elementwise_cost` and at reduction.rs:177 / params.rs:904 - so they stay finite as the debug
assertion expects, and make the combine NaN-proof anyway: skip zero-weight inputs in
`combine_hints` (or treat `0 * inf` as 0) and compare with `f32::total_cmp` in
`max_cost_layout_order`.
