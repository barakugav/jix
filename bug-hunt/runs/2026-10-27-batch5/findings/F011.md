# F011: RemoveDim::new / new_array panics (dim_arr NDIM_MAX assert) on a DimsArg with more than 8 entries instead of returning Err

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix/src/ops/shape_ops/remove_dim.rs:58 (related: jix/src/dimension.rs:526, jix/src/ops/common.rs:66, jix/src/ops/shape_ops/flip.rs:40, jix/src/ops/shape_ops/insert_dim.rs:58)
- Reachability: public Rust API (Python not affected)
- Reported by: pipeline-nodes, shape-ops-forwarders

## What goes wrong
`RemoveDim::new` (and `RemoveDim::new_array`), documented as fallible (`-> Result<Self>`), collects
the dims with `dim_arr(dim.len(), |i| dim.get(i))` before any validation. `dim_arr` asserts
`ndim <= NDIM_MAX` (dimension.rs:526), so any `DimsArg` with more than 8 entries - e.g. nine
repeated `0`s, or a `Vec`/slice of 9 indices - panics with `assertion failed: ndim <= NDIM_MAX`
instead of returning `Err(InvalidShapeOperation)` ("duplicate dim" / "out of bounds"). The sibling
`DimsArg` consumers return `Err` for the same input: `Flip::new` loops over `dim.get(i)` and rejects
the duplicate, `InsertDim::new` calls `check_ndim` first. A caller who uses the fallible
constructor precisely to handle bad user-supplied dims gets a panic.

## Trigger
```rust
let a = Array::compact_ndarray(&array![[1.0f32]])?;
jix::ops::RemoveDim::new_array(a, &[0usize; 9][..]); // panics
jix::ops::RemoveDim::new_array(a2, vec![0usize, 1, 2, 3, 4, 5, 6, 7, 8]); // panics
```
`&[usize]` and `Vec<usize>` are library-provided `DimsArg` impls; no custom impl needed.
`Array::remove_dim` unwraps and is documented to panic on invalid dims, so it is not itself a bug;
only the `Result`-returning constructors are affected. The Python binding is guarded:
`normalize_dims` rejects more than 8 dims (jix-py/src/util.rs:208) before reaching
`RemoveDim::new_array` (jix-py/src/ops/shape_ops.rs:530); the other jix-py caller
(shape_ops.rs:216) passes at most ndim <= 8 entries.

## Root cause
remove_dim.rs:58 materializes the caller's dims into a capacity-8 `DimArray` via `dim_arr`, whose
documented contract is "Panics if `ndim > NDIM_MAX`", before the loop at 59-75 that would reject an
out-of-range or duplicate dim. Any list of more than 8 entries must contain a duplicate or an
out-of-range dim (input ndim <= 8), so the validation loop would always return Err if it ran first.
Same class as K12 / K32 / K79, at a site those fixes did not cover (also noted in
bug-hunt/context/shape-ops.md "Hot spots", line 213).

## Suggested fix
Drop the intermediate `DimArray` and iterate `for i in 0..dim.len() { let d = dim.get(i); ... }`
as `Flip::new` does (the existing loop already rejects duplicates and out-of-range dims, so it
returns Err by the 9th entry at the latest), or add an explicit
`ensure!(dim.len() <= input_ndim, InvalidShapeOperation, ...)` before line 58. Add an in-tree test
with 9 dims.
