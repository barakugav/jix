# F006: Array.numpy_dtype holds the per-Array std::sync::Mutex while dtype_to_numpy runs Python code; Python code there that yields the GIL to a thread using the same Array, or that uses the same Array itself, hangs the process forever

- Severity: medium  Verdict: confirmed  Category: hang
- Location: jix-py/src/array.rs:301-311 (`numpy_dtype`: `self.cache.lock()` held across `dtype_to_numpy(py, ..)` at :308) (related: jix-py/src/dtype.rs:67 `py.import("numpy")` + `numpy.dtype(.., align=True)` call; lock takers that block while attached: jix-py/src/array.rs:544 `numpy()`/`__getitem__` -> `numpy_dtype`, :429 `dtype` getter, :165 `read_ctx` on the attached small-plain-read path :638 and the attached file-like `write_array` path jix-py/src/archive.rs:249, :1753 `ContextGuard::drop`)
- Reachability: Python API
- Reported by: py-core-read-path

## What goes wrong
`Array.numpy_dtype` locks `self.cache` (a plain `std::sync::Mutex`) while attached and keeps the guard
across `dtype_to_numpy`, which calls into Python. For a struct dtype that jix classifies as aligned it runs
`py.import("numpy").getattr("dtype").call(..)`; pyo3's `py.import` is `PyImport_Import`, which calls
`builtins.__import__`. Any Python code that runs there (a Python-level `__import__` override) is run with the
Mutex held. Two hangs follow, both permanent: no exception, no timeout, Ctrl-C does not help.
(1) Two threads, GIL build: if the Python code under the lock gives up the GIL (sleep/I/O, or just running
bytecode past the switch interval), another thread can call `arr.dtype` / `arr[...]` / `arr.numpy()` on the
same Array. That thread blocks in `Mutex::lock` with the GIL held, while the lock holder waits for the GIL in
`PyEval_RestoreThread`. (2) Same thread: Python code under the lock that reads the same Array re-locks the
non-reentrant Mutex and hangs. (3) Free-threaded builds (3.14t/3.15t wheels ship, module is `gil_used=false`):
a thread blocked on the std Mutex while attached never reaches a stop-the-world safe point, so a GC/STW request
while the holder sits at a safe point inside `dtype_to_numpy` deadlocks. This is the hazard that pyo3's
`MutexExt::lock_py_attached` exists for. Case (3) is argued from the code only (no free-threaded interpreter here).

## Trigger
```python
import builtins, threading, time, numpy as np, jix
dt = np.dtype([('a', 'i4'), ('b', 'i4')], align=True)   # aligned struct -> py.import path
arr = jix.compact(np.zeros(4, dtype=dt))                  # numpy dtype not cached yet
orig = builtins.__import__
started = threading.Event()
def hook(name, *a, **kw):
    if name == "numpy" and threading.current_thread() is threading.main_thread() and not started.is_set():
        started.set(); time.sleep(0.3)                    # or: a pure-bytecode loop of ~100 ms
    return orig(name, *a, **kw)
threading.Thread(target=lambda: (started.wait(), arr[0])).start()
builtins.__import__ = hook
arr.dtype            # hangs forever
```
Single-thread variant: the hook itself evaluates `arr[0]`, and `arr.dtype` hangs.
Preconditions: the Array's numpy dtype is not cached yet. That is the case for arrays from `jix.compact`,
`read_array` and `asarray` without `dtype=`, until the first `.dtype`/`.numpy()`/`[]`. Python code must also
run inside `dtype_to_numpy`. In a default GIL interpreter that happens only through a Python-level
`builtins.__import__` override and only for aligned struct dtypes. Scalar dtypes go through the numpy C API
only.

The script asserts that every scenario finishes, so it exits 1 while the bug exists.

In scenario B the hook only runs a pure-Python loop: there is no sleep or I/O, and the switch interval alone
hands over the GIL. The control (the second thread reads a different Array) finishes. A matching busy-loop
control was also run, and there the other thread completes while main is still inside the hook. gdb on the
hung scenario-A process shows:
```
Thread 2: Mutex<jix::array::ArrayCache>::lock -> lock_contended <- Array::numpy_dtype <- Array::numpy <- __getitem__   (holds the GIL)
Thread 1: PyEval_RestoreThread <- PyImport_Import <- jix::dtype::dtype_to_numpy <- Array::numpy_dtype <- Array::dtype (holds the Mutex)
```

## Root cause
At jix-py/src/array.rs:302-309 the cache Mutex guard is kept across `dtype_to_numpy(py, ..)`, which can run
arbitrary Python code (jix-py/src/dtype.rs:67: `PyImport_Import` -> `builtins.__import__`, then
`numpy.dtype(...)`). Other code paths take the same Mutex while attached with a plain `lock()`: array.rs:544,
:429, :165 (attached at :638 for small plain reads and at archive.rs:249 for file-like `write_array`), and
:1753. "Never run Python under a Rust lock that attached threads block on" is broken in both directions.
Both lock-order hangs (GIL vs Mutex) and same-thread re-entry are therefore possible.

## Suggested fix
Do not call Python while holding the lock. Read the cached value under the lock and drop the guard. Run
`dtype_to_numpy` unlocked, then re-lock and store the result if the slot is still empty (a racing duplicate
computation is harmless). Separately, take the cache Mutex with `pyo3::sync::MutexExt::lock_py_attached`
(or detach before locking) wherever it is locked while attached, so a waiter never blocks with the GIL held
or outside an STW safe point. `lock_py_attached` alone does not fix the same-thread re-entry. Moving the
numpy dtype out of the Mutex into an unlocked compute-then-store slot does fix it.
