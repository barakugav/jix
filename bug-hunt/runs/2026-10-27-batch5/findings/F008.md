# F008: jix.log(x, base), jix.log2 and jix.log10 round three times: exact powers come out 1 ulp low (log10(1000) = 2.9999999999999996, f16 log2(32) = 4.996), up to 2.7 ulp error in f64

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix-py/src/ops/op1.rs:361-362 (related: jix-py/src/ops/op1.rs:378, jix-py/python/jix/__init__.py:39-46, jix-py/python/tests/test_op1.py:111-127)
- Reachability: Python API (the Rust core has no log2 / log10 / log-with-base op; the Python wrapper builds it from `Ln` + `map`)
- Reported by: elementwise-ops-op1-unary-classify-complex

## What goes wrong
`jix.log(a, base=b)` computes `Ln(a)` rounded to T, then multiplies by `1/ln(b)`, which is computed in
f64 (itself two roundings) and then cast to T, and the product is rounded once more. The result is not
correctly rounded and is biased low. `jix.log2` / `jix.log10` are plain aliases for `log(x, base=2/10)`,
so they look like `np.log2` / `np.log10` but give `log10(1000) = 2.9999999999999996` and
`log2(8) = 2.9999999999999996`. Anything that turns the result into an integer is then off by one:
`floor(jix.log10(1e6))` is 5, `int(jix.log2(8.0))` is 2. For f16 all three roundings happen in f16 (the
multiplier is cast to f16), so a third of the exact powers of two are wrong (`log2(32) = 4.996`) and the
error reaches 1.6 ulp. For f64 `log10` the multiplier's rounding error is systematic: jix differs from
numpy on 87% of random inputs, with a mean error of 0.97 ulp and a maximum of 2.7 ulp (numpy: 0.5 ulp).

## Trigger
```python
jix.log10(np.array([1000.0]))                     # 2.9999999999999996, numpy 3.0
jix.log2(np.array([8.0]))                         # 2.9999999999999996, numpy 3.0
jix.log2(np.array([32.0], dtype=np.float16))      # 4.99609375, numpy 5.0
np.floor(jix.log10(np.array([1000.0, 1e6, 1e15])).numpy())   # [2, 5, 14], numpy [3, 6, 15]
```

## Root cause
jix-py/src/ops/op1.rs:378 computes `1.0 / b.ln()` (two f64 roundings), op1.rs:361 casts it to T (a
third rounding for f16 / f32), and op1.rs:362 multiplies the already-rounded `ln(x)` by it (one more
rounding). The relative error of the multiplier scales with the result, so it can reach several ulp
when the result's mantissa is large, and for exact powers it lands just below the integer. The Python
tests (test_op1.py:111-127) compare with `rtol=1e-5` / `1e-12`, which hides a few-ulp error, and never
test f16 with a base. Python's `math.log(x, base)` has the same 1-ulp behavior, but `math.log10` /
`math.log2` and numpy's `log10` / `log2` are exact on powers, and jix presents `log2` / `log10` as their
equivalents. Not listed under the context doc's "Intentional behaviors" nor in KNOWN.md.

## Suggested fix
Add dedicated `Log2` / `Log10` op1 kernels in jix core (`f64::log2/log10`, `f32::log2/log10`, f16 via
the f32 function rounded once, as the other f16 op1 kernels do) and have `jix.log2` / `jix.log10`, and
`jix.log(x, base=2|10)`, dispatch to them. For a general base, compute in a wider type and round once
(f16 / f32: `(x as f64).ln() / base.ln()` rounded to T; f64: at least divide by `ln(base)` instead of
multiplying by its rounded reciprocal, or use `log2(x) / log2(base)`, which is exact for powers of two
bases). Tighten the tests to require exact results on exact powers and add f16 cases.
