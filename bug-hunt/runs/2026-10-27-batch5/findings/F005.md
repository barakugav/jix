# F005: Array.numpy() / __getitem__ / plain() panic (ArrayVec capacity) when the array's ndim plus its dtype's inner ndim exceeds 8

- Severity: medium  Verdict: confirmed  Category: panic
- Location: jix-py/src/util.rs:103 (related: jix-py/src/util.rs:130, jix-py/src/util.rs:133, jix-py/src/array.rs:545-549, jix-py/src/array.rs:576, jix-py/src/array.rs:733 (plain), jix-py/src/array.rs:748 (__getitem__))
- Reachability: Python API
- Reported by: py-core-read-path

## What goes wrong
Since #91 (the K66 fix), `Array.numpy()` builds the numpy result shape as the selected outer
shape followed by the dtype's inner shape (array.rs:545-549), so it can have up to
NDIM_MAX + DTYPE_MAX_NDIM = 12 entries. It then allocates through
`numpy_empty_ordered(np_dtype.base(), &np_shape, &order)` (array.rs:576), and both
`numpy_empty` (util.rs:103) and `numpy_empty_ordered` (util.rs:130, 133) collect that shape into
`DimArray = ArrayVec<_, 8>` with `dim_arr`. With more than 8 entries the collect panics
("ArrayVec: capacity exceeded in extend/from_iter"; arrayvec panics in release too) and Python
gets `pyo3_runtime.PanicException` instead of the array. Every allocating read goes through
this: `numpy()` without `out`, `a[...]` / any `__getitem__`, and `plain()`. `numpy(out=)` on the
same array does not allocate and returns the right values, so the read itself is fine. NumPy
handles such arrays without issue (NPY_MAXDIMS is 32 / 64), so the input is valid.
(`item()`, also named in the report, is NOT affected: it requires ndim 0, so the numpy shape has
at most 4 entries.)

## Trigger
```python
dt = np.dtype([('a', 'i4', (2, 2, 2)), ('b', 'i4')])
x = np.zeros((1, 1, 1, 1, 1, 2), dtype=dt)
f = jix.dtype_sub_field(jix.compact(x), 'a')   # shape (1,1,1,1,1,2), dtype ('<i4', (2,2,2))
f.numpy()                                      # PanicException (util.rs:103)
f[...]                                         # PanicException (util.rs:103)
f.plain()                                      # PanicException
jix.permute_dims(f, (5, 4, 3, 2, 1, 0)).numpy()  # PanicException (util.rs:130)
f.numpy(out=np.empty(x['a'].shape, 'i4'))      # works, equals x['a']
```
Any outer ndim + inner ndim > 8 triggers it: 6+3, 7+2, 8+1, 5+4 all panic; 5+3 = 8 passes.

## Repro
`bug-hunt/runs/2026-10-27-batch5/repros/F005.py`, run with
`.venv/bin/python bug-hunt/runs/2026-10-27-batch5/repros/F005.py`. It asserts each read equals
numpy's `x['a']` (or its transpose) and fails while the bug exists:
```
outer ndim 5 + inner ndim 3 = 8: numpy(): ok            (and [...], permuted, out=: ok)
outer ndim 6 + inner ndim 3 = 9: numpy(): FAIL pyo3_runtime.PanicException: ArrayVec: capacity exceeded in extend/from_iter
outer ndim 6 + inner ndim 3 = 9: [...]: FAIL pyo3_runtime.PanicException: ...
outer ndim 6 + inner ndim 3 = 9: permuted numpy(): FAIL pyo3_runtime.PanicException: ...
outer ndim 6 + inner ndim 3 = 9: numpy(out=): ok
... same pattern for 8+1, 7+2 and 5+4 ...
AssertionError: 12 case(s) failed
```
With RUST_BACKTRACE=1 the panicking frames are `jix::util::numpy_empty` (identity layout,
called directly or via `numpy_empty_ordered`) and `jix::util::numpy_empty_ordered` (permuted
layout). A separate run confirmed `f.plain()` on the 6+3 array raises the same PanicException.

## Root cause
`numpy_empty` / `numpy_empty_ordered` (util.rs:92-141) were written when the numpy shape always
equalled the jix shape (<= NDIM_MAX dims) and use the NDIM_MAX-capacity `dim_arr` for the shape
(util.rs:103, 130) and the transpose permutation (util.rs:133). The #91 fix (array.rs:545-576)
started passing the outer shape plus the dtype's inner shape (<= 12 dims) without widening these
buffers. Nothing between `dtype_sub_field` (or an archive dtype with an inner shape) and
`numpy()` limits outer ndim + inner ndim to 8.

## Suggested fix
Size the shape / permutation buffers in `numpy_empty` and `numpy_empty_ordered` for
`NDIM_MAX + DTYPE_MAX_NDIM` (e.g. `ArrayVec<_, { NDIM_MAX + DTYPE_MAX_NDIM }>`, or a `Vec`), and
add a 6+3 / 8+1 case to the sub-dtype tests. Side note (separate issue, not this finding):
`plain()` of an inner-shape dtype returns an array with the base dtype and the inner dims
appended to the shape (5+3 case: shape (1,1,1,1,2,2,2,2) int32, source (1,1,1,1,2) of
('<i4',(2,2,2))), contrary to its "same dtype as self" docstring; once this panic is fixed the
9+ dim case of `plain()` will hit the 8-dim limit of `asarray` instead.
