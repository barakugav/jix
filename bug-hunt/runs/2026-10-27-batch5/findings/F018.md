# F018: Archive reader truncates u64 header fields to u32 before validating them, so a block dim or block_size of 2^32 + 2 is silently read as 2

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/archive/array.rs:471 (related: jix/src/archive/block.rs:365, jix/src/archive/block.rs:366-372, jix/src/archive/array.rs:472-481, jix/src/archive/array.rs:513-519)
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file` / `read_from_file_mmap`, both validation modes) and Python API (`read_array`)
- Reported by: codec-archive-array-format-dtype

## What goes wrong
`ArrayHeader.block_shape` and `BlockTableHeader.block_size` are `uint64` on the wire. The reader
casts them to `BlockSize` (`u32`) with `as` first and only then validates them. A value of 2^32 or
more is therefore checked and used as its low 32 bits. The result is a malformed archive that
loads without an error, while every other header field is parsed strictly. One example is a block
dim larger than its array dim. Another is an `nitems` that is not a multiple of the declared
`block_size`. Writing the loaded array back emits a different header that holds the truncated
values. Because every check after the cast runs on the truncated value, the geometry that is used
is self-consistent. The read data is correct, and no panic or UB follows. That keeps the severity
at low.

## Trigger
Start from a valid archive of a `[4]` u8 array (values 0..4) with block shape `[2]`, then do one of:
- (a) rewrite `ArrayHeader.block_shape` to `[2^32 + 2]`. The dim is larger than the dim length 4
  and does not fit u32.
- (b) rewrite `BlockTableHeader.block_size` (proto field 3) to `2^32 + 2`. Then `nitems = 4` is
  not a multiple of it.

Read the result with `Array::read_from_reader(Cursor::new(bytes), Some(len), ArrayParams::default(), ArchiveValidation::Strict)`.

## Root cause
- `jix/src/archive/array.rs:471` has `dim_arr(ndim, |dim| header.block_shape[dim] as BlockSize)`.
  The range check `b > 0 && b as u64 <= s.max(1)` at `:472-481` and every later product (padded
  nitems, block size, nblocks) see only the truncated `b`.
- `jix/src/archive/block.rs:365` has `let block_size = header.block_size as BlockSize;`. The
  `block_size > 0` and `nitems.is_multiple_of(block_size)` checks at `:366-372`, and the
  `blocks.block_size == expected_block_size` check at `array.rs:513-519`, compare truncated values.

Nothing else catches the condition. `BlockTable::new` and `tune` get the already-truncated value,
which is small and valid. The block volume bound (`MAX_BLOCK_SIZE_BYTES = 2^30`,
`storage/params.rs:10,410`) also applies only to the truncated value. The context doc lists this
under "Suspicions (unverified)". It is not in KNOWN.md and is not documented as intentional.

## Suggested fix
Convert with `BlockSize::try_from(v)` and return `InvalidArchive` on failure, in both places.
Alternatively, validate the u64 value (`b <= s.max(1)`, `nitems % block_size == 0`) before
narrowing it.
