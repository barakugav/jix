# F023: jix.log silently accepts an invalid base (1, 0, -0.0, negative): every element becomes inf / NaN / a signed zero with no error, although the docstring says the base must be positive and not 1

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix-py/src/ops/op1.rs:378 (related: jix-py/src/ops/op1.rs:361-363, jix-py/src/ops/op1.rs:307-308 (docstring precondition), jix-py/src/array.rs:1431 (Array.log), jix-py/python/jix/__init__.py:39-46 (log2/log10 aliases, unaffected: fixed valid bases))
- Reachability: Python API (`jix.log(a, base=...)`, `Array.log(base=...)`); the Rust core has no log-with-base
- Reported by: elementwise-ops-op1-unary-classify-complex

## What goes wrong
`jix.log` turns `base` into `multiplier = 1.0 / base.ln()` without validating it, then applies it
with a plain `Array::map(|x| x * multiplier)`, a closure that has no status channel. For base 1
the multiplier is +inf, for base 0 / -0.0 it is -0.0, for a negative base it is NaN, so the whole
result is inf / NaN / signed zeros and nothing passes through `jix.errstate`. The docstring states
"Must be a positive number other than 1" but nothing enforces it, while under the same default
errstate a single negative ELEMENT raises `FloatingPointError: invalid operation` and Python's own
`math.log(2, base)` raises ZeroDivisionError / ValueError for these bases. A user who passes a
computed base (e.g. from data) that happens to be 1 or <= 0 gets garbage silently.

## Trigger
`jix.log(np.array([2.0, 1.0, 0.5]), base=b)` (same through `jix.compact(x).log(base=b)`, and for
f32 / f16 inputs), default errstate:
- b = 1.0 -> `[inf, nan, -inf]`
- b = 0.0 or -0.0 -> `[-0.0, -0.0, 0.0]`
- b = -2.0 -> `[nan, nan, nan]`

Related corner from the same pre-computed multiplier (valid base, f16 only): the multiplier is
cast to the element type before the multiply, so for f16 a valid base within ~1.5e-5 of 1
overflows the multiplier to inf: `jix.log(np.array([1.0009765625, 0.9990234375], np.float16),
base=1.00001)` gives `[inf, -inf]` where the true values are `[97.6, -97.7]` (finite in f16), again
with no Overflow report.

(Not counted as bugs: base=NaN -> all NaN matches NaN propagation and `math.log(2, nan)`; base=inf
-> 0.0 matches the limit and `math.log(2, inf)`.)

## Root cause
jix-py/src/ops/op1.rs:378 computes `base.map(|b| 1.0 / b.ln())` with no domain check, and
jix-py/src/ops/op1.rs:361-363 casts it to `T` and applies it with `res.map(move |x| x * multiplier)`
(`jix/src/ops/map.rs:16`, `F: Fn(S::Item) -> R`, no `ArithmeticErrorKind` status), so neither the
bad multiplier nor the inf/NaN it produces can be reported through errstate. The documented
precondition (op1.rs:307-308) is assumed, not checked. The f16 variant comes from casting the
multiplier to `T` (op1.rs:362) before multiplying, instead of dividing by `ln(base)` or
multiplying in a wider type.

## Suggested fix
In `log`, before dispatch: `if let Some(b) = base { if !(b > 0.0) || b == 1.0 { return
Err(PyValueError::new_err("log: base must be a positive number other than 1")) } }` (decide
whether NaN should be rejected too; `!(b > 0.0)` rejects it). Optionally, for f16, compute
`ln(x) * multiplier` in f32 (or divide by `ln(base)` cast to T) so a base close to 1 does not
overflow the multiplier.
