# F017: An empty array that jix writes cannot be read back when its padded shape product (zero dims counted as 1) overflows u64

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/archive/array.rs:483-499 (the `.try_shape_product()` at :493) (related: jix/src/util/mod.rs:213-223, jix/src/error.rs:186, jix/src/storage/params.rs:512, jix/src/array.rs:1318-1331)
- Reachability: public Rust API (`compact_fn_with` / `write_to` / `read_from_reader`) and Python API (`broadcast` / `write_array` / `read_array`)
- Reported by: codec-archive-array-format-dtype

## What goes wrong
The writer and the reader check an array's size in different ways. Construction and the writer
need only `check_shape_overflow`: the shape product with zero dims counted as 1, times itemsize,
must fit in u64. The writer then writes `nitems = nblocks * block_size`, which is 0 for an empty
array. The reader instead builds the PADDED shape (each nonzero dim rounded up to a multiple of its
block dim) and calls `try_shape_product` on it. That function also counts zero dims as 1 for its
overflow guard. Padding can grow a dim by up to `b - 1`. So for an empty array whose other dims
multiply to nearly 2^64, the reader returns `InvalidArchive "... has too many items"`, even though
the stored nitems is 0 and jix wrote the file itself. The archive round trip is meant to be
lossless, but this one fails: the file is written and then rejected. An in-memory `compact()` of
the same array works. Non-empty arrays this big (about 2^64 elements) cannot really be written, so
only empty arrays are affected. The error is clean (no panic, no UB) and the shapes are contrived.

## Trigger
- Rust: `Array::compact_fn_with([0u64, 3, 0x5555_5555_5555_5555], params.block_shape(&[1, 2, 1]), |_| 0u8)`.
  Here `3 * 0x5555_5555_5555_5555 == u64::MAX`, and block dim 2 pads the 3 up to 4. Then call
  `write_to(Cursor)` and `Array::read_from_reader(.., Some(len), ArrayParams::default(), Strict)`.
- Same with the auto block shape: `Array::compact_fn([0u64, 2^32 - 1, 2^32 + 1], ..)` gets block
  shape `[1, 1, 49152]`, which pads the last dim.
- Python: `a = jix.broadcast(jix.compact(np.zeros((0, 1, 1), np.uint8)), (0, 3, 0x5555555555555555))`,
  then `jix.write_array(a, buf)` (writes 91 bytes) and `jix.read_array(buf)`.

## Root cause
`try_shape_product` (util/mod.rs:213) is designed to guard shape ops: a zero dim must not hide an
overflowing product of the other dims (the K13 fix). In #86 (5b3a9f5) the K13 fix mechanically
replaced `try_product` with `try_shape_product` at archive/array.rs:493. At that point the product
is taken over the padded shape, not the logical one. The quantity being validated there is the
stored item count, which really is 0 when any dim is 0. The overflow guard, though, applies the
zeros-as-1 rule to the padded dims, and those can be larger than anything the writer checked. The
writer (jix/src/array.rs:1318-1331) never forms the padded product. It only checks the block-grid
product, and `check_shape_overflow` on the logical shape (params.rs:512). So the reader is stricter
than the writer and rejects some files the writer produces. Before #86, `try_product` returned
`Some(0)` when the first dim was 0, so this exact trigger read back fine then. A zero in a later
position was already rejected.

## Suggested fix
Validate the stored nitems with the ordinary product semantics: zero dims give 0, and overflow is
checked only on the real product. For example, compute `expected_nitems` as a plain checked
product, or as `expected_nblocks * expected_block_size` with checked arithmetic. Then rely on
`into_spec`'s `check_shape_overflow` (params.rs:512) for the logical-shape guard that the rest of
the library depends on, or call it explicitly before the padding loop. Run that check (dims <=
i64::MAX) before `next_multiple_of` as well, so a crafted huge dim cannot overflow the padding
arithmetic.
