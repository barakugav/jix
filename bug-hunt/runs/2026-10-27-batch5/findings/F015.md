# F015: Array.plain() of a dtype with an inner shape returns a different array - the inner dims become array dims and the dtype becomes the base dtype, contradicting its docstring and compact()

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/array.rs:733-734 (`plain()` = `asarray_simple(&self.numpy(index))`) (related: jix-py/src/array.rs:692 and 712-715 (docstring: "same dtype as `self`", shape from the index, and also "Equivalent to `jix.asarray(self.numpy(index))`"), jix-py/src/array.rs:543-549 (numpy() appends the inner dims since #91), jix-py/src/ops/common/operand.rs:164-196 (asarray wraps the numpy array with its own ndim and base dtype))
- Reachability: Python API
- Reported by: py-core-read-path

## What goes wrong
Since #91, `numpy()` returns an array whose dtype has an inner shape as a numpy array of the
base dtype with the inner dims appended to the shape. That is what NumPy itself does, and it
is pinned by `test_sub_array_field_reads_as_trailing_dims`. `plain()` is built on top of
`numpy()`, so it inherits the expansion. But unlike numpy, a jix Array can hold an inner-shape
dtype. `plain()` therefore returns a jix Array with `ndim + inner_ndim` dims and the base dtype.
`compact()` keeps the shape and dtype. The docstring presents `plain()` as the uncompressed
counterpart of `compact()` for breaking a lazy chain, and it promises "the same dtype as `self`
and shape determined by the `index` argument (or `self.shape`...)". So swapping `.compact()`
for `.plain()` (or the reverse) silently changes shape, ndim, dtype, which ops are accepted,
and what end-anchored indexing selects. The docstring also contradicts itself: it says
`plain()` is "Equivalent to `jix.asarray(self.numpy(index))`", which is the expanding behavior.

## Trigger
```python
dt = np.dtype([("a", "i4", (3,)), ("b", "i4")])
x = np.zeros((2, 2), dtype=dt); x["a"] = np.arange(12, dtype=np.int32).reshape(2, 2, 3)
f = jix.dtype_sub_field(jix.compact(x), "a")   # shape (2, 2), dtype ('<i4', (3,))
p = f.plain()                                  # shape (2, 2, 3), dtype int32
f.compact()                                    # shape (2, 2), dtype ('<i4', (3,))
f[..., 1]  # (2, 3) [3,4,5, 9,10,11]   - x["a"][:, 1]
p[..., 1]  # (2, 2) [1,4,7,10]         - x["a"][..., 1]: a different selection, silently
f.plain(1) # shape (2, 3) int32, expected shape (2,) dtype ('<i4', (3,))
```
Other differences the verifier observed. `f.sum()` raises TypeError, but `p.sum()` returns 66.
`jix.permute_dims(p, [1, 0])` raises RuntimeError (ndim 3), but it works on `f`.
`jix.reshape(p, (4,))` raises RuntimeError. `jix.stack([f, p])` raises TypeError (dtype
mismatch), but `jix.stack([f, f.compact()])` works. `p[:, :, 0]` is accepted, but `f[:, :, 0]`
is an IndexError.

Indices with no ellipsis, valid on `f` (`p[1]`, `p[1, 0]`, `p[0:1]`, `p[()]`), give the same
numpy result as on `f`. The hunter's "p[1] vs f[1] select differently" is not accurate. The
silent divergence comes from end-anchored indices (`[..., k]`), negative dims in later ops, and
ndim-dependent code.

Edge consequence: an array with ndim 8 (the maximum) and an inner dim has a valid `compact()`.
Its `plain()` needs a 9-dim jix array. Today that is the F005 PanicException in
`numpy_empty`. Once F005 is fixed, `asarray` will reject it ("Number of dimensions 9 exceeds the
maximum supported 8", checked with `jix.asarray(np.zeros((1,)*8 + (2,)))`). So `plain()` can
never work on such arrays while it routes through numpy.

## Root cause
`plain()` (jix-py/src/array.rs:733-734) round-trips through a numpy array and re-wraps it with
the generic `asarray` (operand.rs:164-196). That path takes shape, strides and dtype from the
numpy object. For an inner-shape dtype, numpy cannot represent the jix dtype at the top level, so
the information is lost at the numpy boundary. #91 changed `numpy()` to expand the inner dims, and
`plain()` was not adjusted. No test covers `plain()` on an inner-shape dtype, and the
docstring's "same dtype as `self`" claim was not updated.

## Suggested fix
In `plain()`, keep the allocation from `numpy()`. `numpy_empty_ordered` puts the inner dims last
and C-contiguous. Then build the `Plain` storage directly instead of calling `asarray`:
`Plain::new(np_arr.unbind(), data_ptr, out_shape, np_arr.strides()[..out_shape.len()] (as in
operand.rs, with the len <= 1 rule), self.arr.dtype(), params)`, and cache `np_dtype`. This keeps
shape and dtype, and it also covers the ndim-8-plus-inner case. Then fix the docstring's
"Equivalent to `jix.asarray(self.numpy(index))`" sentence (true only for dtypes with no inner
shape), and add a `plain()` case to `test_sub_array_field_reads_as_trailing_dims`.
Alternatively, if the expansion is the intended behavior, document it in `plain()` and stop
calling it the uncompressed counterpart of `compact()` for such dtypes.
