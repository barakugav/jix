# F003: MapMultiple::new panics (index out of bounds) on an empty array sequence instead of returning Err

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/ops/map.rs:256 (related: jix/src/storage/params.rs:895, jix/src/storage/params.rs:923, jix/src/ops/map.rs:277, jix/src/ops/map.rs:399, jix/src/ops/map.rs:410, jix/src/ops/shape_ops/stack.rs:65, jix/src/ops/shape_ops/concatenate.rs:73)
- Reachability: public Rust API (`jix::ops::MapMultiple::new`, `jix::ops::map_multiple`). Not reachable from Python: jix-py never builds a MapMultiple.
- Reported by: pipeline-nodes

## What goes wrong
`MapMultiple::new` returns `Result`, but an empty array sequence makes it panic before it can
return. The shape and overflow checks sit inside `if narrays > 0 { ... }` (map.rs:256), so an
empty sequence gets through them. Construction then calls `combine_elementwise_hints(&[])`
(map.rs:277), and `combine_hints` indexes `inputs[0]` (params.rs:895). `combine_block_layout`
does the same at params.rs:923. The other `ArraySequence` consumers, `Stack::new` and
`Concatenate::new`, reject an empty sequence with
`ensure!(narrays > 0, InvalidShapeOperation, ...)`. If construction did succeed, `shape()`
(map.rs:399) and `spec()` (map.rs:410) would also index array 0. No memory-safety impact: the
panic comes from a safe bounds check, so it happens in release builds too.

## Trigger
```rust
let arrays: Vec<Array<Compact<Ty<f32>>>> = Vec::new();
jix::ops::MapMultiple::new(arrays, |xs: &[f32]| xs.len() as f32); // panics
```
The same happens with `&arrays[..]` and with `[A; 0]`, and through `jix::ops::map_multiple`.
That wrapper unwraps anyway, but its `# Panics` doc names only a shape mismatch, and it panics
with an index-out-of-bounds message instead of a clear one.

## Root cause
At map.rs:256, `MapMultiple::new` treats `narrays == 0` as a case that needs no validation. It
then passes the empty list to helpers that assume at least one input: `combine_hints`
(params.rs:895, `inputs[0].1.len()`) and `combine_block_layout` (params.rs:923,
`inputs[0].0.len()`). The storage methods also assume one input exists (`self.arrays.shape(0)`,
`self.arrays.spec(0)`). Nothing defines a shape for zero inputs, so the case cannot be supported
and has to be rejected.

## Severity note
The hunter rated this medium. An empty sequence is not valid input for this op, because there is
no output shape to take. The defect is that a fallible constructor panics on invalid input
instead of returning `Err`, and only Rust callers can reach it. That matches K79 (SliceSpec
panics before the fallible `Slice::new` can return `InvalidIndex`), which was rated low.

## Suggested fix
Replace the `if narrays > 0` guard in `MapMultiple::new` with
`ensure!(narrays > 0, InvalidShapeOperation, "cannot map over zero arrays")`, as in
stack.rs:64-68 and concatenate.rs:72-76. Then run the shape / overflow checks unconditionally.
Optionally, add `debug_assert!(!inputs.is_empty())` to `combine_hints` and
`combine_block_layout`, and add the empty case to the `map_multiple` `# Panics` doc.
