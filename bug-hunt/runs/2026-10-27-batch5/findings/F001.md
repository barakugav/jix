# F001: 32-bit: the reduction's temp state buffer size `out_nitems * size_of::<State>()` wraps, so var/std states are written far past a few-byte pool buffer (heap overflow, SIGSEGV from safe code)

- Severity: high  Verdict: confirmed  Category: overflow
- Location: jix/src/ops/reduction.rs:516 (related: jix/src/ops/reduction.rs:410, jix/src/ops/reduction.rs:169-170, jix/src/ops/reduction.rs:597, jix/src/error.rs:274, jix/src/storage/buf.rs:314, jix/src/array.rs:1403)
- Reachability: public Rust API (32-bit targets: i686 / armv7). Likely also Python on the x86 / armv7 wheels (`jix.var(...)` on a broadcast f16 array, then `.compact(params={"block_shape": [...]})`), not run.
- Reported by: reduction-driver, util-nd-iter-unordered

## What goes wrong
When the reduction states cannot live in the output buffer (always for Var/Std, whose Welford
state is 24 bytes - 32 for complex - against a 2-8 byte output), `read_data_impl` allocates a
temporary state buffer of `out_nitems * kernel_state_sizeof` bytes with an unchecked usize
multiply (reduction.rs:516). On 32-bit targets the only bound on the region is
`check_region_size` (error.rs:274, called from `check_out_buf`, buf.rs:314), which uses the
OUTPUT itemsize; `ReductionOp::new` checks `shape * max(output, state)` only in u64
(reduction.rs:169-170). So for var(f16) any region with more than 2^32 / 24 cells (358 MB of
f16 output) passes every check and the state size wraps. The fold then writes 24-byte states at
offsets up to ~4.3 GB into a buffer of a few bytes (`get_unchecked_mut(state_offset..)` at 597 and
the fold loops): heap corruption, SIGSEGV in release, an overflow panic in debug.

## Trigger
On i686 (or armv7):

```rust
let a = Array::compact_ndarray(&array![[f16::from_f32(1.0)]])?;
let v = a.broadcast(&[178_956_971, 1]).var(1, 0.0);   // 178_956_971 * 24 = 2^32 + 8 -> 8
// either a direct read:
v.storage().read_data(&[0..178_956_971], &ReadContext::default(), None);
// or the ordinary compaction path (one push-mode read per chunk, array.rs:1403):
let mut p = ArrayParams::new();
p.block_shape(&[178_956_971]);                         // 358 MB block, under the 1 GiB cap
v.compact_with(p, &ReadContext::default());
```

Other wrapping kernels (state / output size): var/std of f32 (24/4), f64 / ints / bool8 (24/8),
Complex<f32> (32/4), Complex<f64> (32/8) - all with an output region that still fits
`check_region_size`. Where the state size lands in (isize::MAX, 2^32) instead (e.g. argmax of
f64, 16/8), the multiply does not wrap but the allocation is larger than any 32-bit process can
have.

## Root cause
The region-size check that guards every `read_data` on 32-bit (`check_region_size`,
error.rs:274) is parameterized by the output itemsize only, and the reduction driver allocates a
second, larger per-output-cell buffer (the state buffer) whose size is derived from the same
region without its own check (reduction.rs:516). The u64 check in `ReductionOp::new`
(reduction.rs:169-170) covers `max(output, state)` for the full shape but never compares it with
`usize` / `isize::MAX`, and a sub-region read would need its own check anyway.

## Suggested fix
In `read_data_impl`, when the states do not live in `out`, size the buffer with
`out_nitems.checked_mul(kernel_state_sizeof)` bounded by `isize::MAX` and return
`InvalidShapeOperation` otherwise - e.g. call
`check_region_size(index, max(output itemsize, kernel_state_sizeof))` up front. Alternatively,
allocate the state buffer per bulk (bulks already partition the outputs), which also bounds peak
memory.
