# F002: 32-bit: the reduction driver computes reduced-stream positions in usize, so a reduction over 2^32+ items silently drops everything before the last tile at position k*2^32 (sum/mean/max/all/any/argmax...), and argmax indices are truncated mod 2^32

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/reduction.rs:588-593 (`tile_base_reduced_idx` summed in usize) and jix/src/ops/reduction.rs:486-497 (`reduced_shape_logical_strides`, `logical_stride *= ... as usize`) (related: jix/src/ops/reduction.rs:818 one-cell merge iff `base_item_idx > 0`, jix/src/ops/reduction.rs:655 multi-cell init iff `base_item_idx == 0`, jix/src/ops/reduction.rs:750 per-run base, jix/src/ops/reduction.rs:991 `item_idx`, jix/src/ops/reduction.rs:463-466 `full_reduction_size` (u64, correct) used by finalize)
- Reachability: public Rust API (32-bit targets); Python API on the shipped x86 / armv7 wheels through the same driver (not run)
- Reported by: reduction-driver, util-nd-iter-unordered

## What goes wrong
`read_data_impl` derives each tile's position in the reduced stream from usize arithmetic: the
row-major logical strides over the reduced sub-shape (486-497) and the tile's base position
`(tile.start - range.start) as usize * stride`, summed in usize (588-593). On a 32-bit target the
position wraps mod 2^32. The fold uses this position as its only "first visit" signal: the
one-cell path merges with the stored state iff `base_item_idx > 0` (818) and the multi-cell path
re-initializes iff `base_item_idx == 0` (655). A tile that starts at stream position k*2^32
therefore overwrites the accumulated state, and every item folded before it is lost. Every kernel
is affected (Sum, Product, Mean, Var/Std, Max/Min, All/Any, ArgMax/ArgMin, reduce_unordered);
Mean/Var then divide the partial result by the correct u64 `full_reduction_size`; ArgMax/ArgMin
additionally report indices mod 2^32. No UB: the first visit of a cell always has base 0, so no
uninitialized state is read. Debug builds panic instead (multiply overflow at 492 for multi-dim
reductions, `debug_assert_eq` at 495 for one dim longer than 2^32).

## Trigger
On i686 (release), with lazy broadcasts that cost no memory:
- `Array::compact_ndarray(&array![1u8])?.broadcast(&[(1<<32)+16]).sum(0)` -> 16, expected 4294967312
- `Array::compact_ndarray(&array![1.0f32])?.broadcast(&[(1<<32)+16]).mean(0)` -> 3.7252903e-9, expected 1.0
- `Array::compact_ndarray(&array![[1u8]])?.broadcast(&[65537, 65536]).sum(&[0usize, 1][..])` -> 65536, expected 4295032832 (each dim small; only the product exceeds 2^32)
- `Array::compact_ndarray(&array![[1u8, 1]])?.broadcast(&[(1<<32)+16, 2]).sum(0)` (multi-cell fold path) -> [16, 16], expected [4294967312, 4294967312]
- `concatenate((zeros.broadcast(&[(1<<32)+16]), one.broadcast(&[1])), 0).argmax(0)` -> 16, expected 4294967312
The same holds for highly compressible Compact / mmap arrays of more than 2^32 elements.

## Root cause
Stream positions are u64 quantities (shapes are u64, `full_reduction_size` is a u64 product,
`base_item_idx` is u64), but the driver computes them through usize: `logical_stride` and
`reduced_shape_logical_strides` are usize (486-497), and the tile base casts each u64 offset with
`as usize` and multiplies / sums in usize before converting back to u64 (588-593). The fold then
conflates "position 0" with "first visit of this cell" (655, 818), so a wrapped position silently
turns a merge into a re-initialization. Nothing bounds the reduced element count to usize on
32-bit (`check_out_buf` / `check_region_size` only bound the output region).

## Suggested fix
Compute the logical strides and the tile base in u64 (checked), and pass a u64 base into the fold.
For the in-tile logical offsets that `NdIterUnordered` computes in usize, either rebase them per
tile (they only need to fit the tile) or, since only ArgMax/ArgMin need indices and they are
single-dim, use the single dim's offset directly. Better still, decide init vs merge from an
explicit "first tile along the reduced dims" flag rather than from `position == 0`. A minimal
alternative: on 32-bit return an error from `ReductionOp::new` / `read_data` when
`full_reduction_size > usize::MAX`.
