# F022: f16 tan(+-177.5) overflows to +-inf with no Overflow report (Tan's error set has no overflow condition, but the f16 kernel rounds the f32 result to f16)

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/ops/op1.rs:674 (related: jix/src/ops/op1.rs:539-553 f16 variant of `float_op1!`, jix/src/ops/op1.rs:632 Exp's error set, jix/src/ops/op1.rs:1780-1789 trig status tests, jix-py/src/ops/op1.rs:447-478 Python `tan`)
- Reachability: public Rust API (`Array::tan`, `jix::scalar::Tan::tan`) and Python API (`jix.tan` on float16)
- Reported by: elementwise-ops-op1-unary-classify-complex

## What goes wrong
The f16 kernel of every `float_op1!` op computes in f32, rounds the result to f16, and then tests
the op's error conditions. For Tan that rounding can overflow: tan(177.5) = -66347.4, past the f16
overflow threshold (65520), so the f16 result is -inf (and +inf for -177.5). The value is the
correctly rounded result. But Tan's only error condition is `InvalidOperation: x.is_infinite()`, so the
overflow is never reported. It reads `Ok` even with the Overflow mode set to Error. In Python it neither
raises under `jix.errstate(over="raise")` nor warns under the default errstate. numpy reports
"overflow encountered in tan" for the same float16 input. jix's own f16 Exp reports the analogous
rounding overflow, and a unit test pins that (`exp(11.1)` -> Overflow for f16). So within one
dtype, two ops of the same kernel family disagree on whether an f16 rounding overflow is an error.
An exhaustive scan of all finite f16 inputs finds exactly two silent overflows: 177.5 and -177.5.
f32/f64 tan cannot overflow from finite input.

## Trigger
Rust: `Array::compact_ndarray(&array![f16::from_f32(177.5), f16::from_f32(-177.5)])?.tan()`, read
with `ctx.set_arithmetic_error_mode(ArithmeticErrorKind::Overflow, ArithmeticErrorMode::Error)`.
Scalar: `Tan::tan(f16::from_f32(177.5), &mut status)` leaves `status` without Overflow.
Python: `jix.tan(np.array([177.5, -177.5], dtype=np.float16))` under `jix.errstate(over="raise")`
(no error), or under the default errstate (no warning).

## Root cause
The error sets in `float_op1!` were written for f32/f64, where tan of a finite input is always finite
(the closest float to an odd multiple of pi/2 gives |tan| around 1e7 / 1e16). The f16 variant
(op1.rs:539-553) reuses the same `errors = |x, r| {...}` set on the f16-rounded result. That adds a
new failure mode, rounding overflow, which only Exp's set covers (op1.rs:632, where the overflow
condition exists for f32/f64 anyway). Tan's set (op1.rs:674) has no Overflow condition, so the f16
rounding overflow is dropped. The trig status test (op1.rs:1780-1789) checks only inf, NaN, 0, pi/2
and 60000 for tan, so the f16 overflow inputs are never tested. Nothing documents this as
intentional. KNOWN.md K60 (Square drops Overflow) is a separate, explicitly accepted decision about
x ** 2 and does not cover tan. Tan's docs list only the InvalidOperation case, and the Python
docstring says errors are reported "as numpy".

## Suggested fix
Add `Overflow: r.is_infinite() && x.is_finite()` to Tan's error set (op1.rs:674). It is never
true for f32/f64, so it costs nothing there. Add `(177.5, &[Overflow])` as an f16-only case in the
trig status test. A more general alternative: have the f16 variant of `float_op1!` set
Overflow whenever the f32 result is finite but its f16 rounding is infinite, so any future op is
covered. Mention the overflow case in the Rust and Python tan docs.
