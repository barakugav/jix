# F010: std of f16 / f32 / complex64 rounds the f64 variance to the narrow output dtype before sqrt: inf, 0 or tens of ulps off where the correctly rounded std is representable

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/ops/reduction.rs:2853 (related: jix/src/ops/reduction.rs:1932-1941, jix/src/ops/reduction.rs:2768, jix/src/ops/op1.rs:607-610, jix-py/src/ops/reduction.rs:427-436)
- Reachability: public Rust API (`Array::std`, `StandardDeviation`) and Python API (`jix.std`)
- Reported by: reduction-scalar-traits

## What goes wrong
Var/Std keep a Welford state in f64 for every real input (`MeanT = f64`, reduction.rs:1965-2069),
but `StandardDeviationKernel::finalize_state` (reduction.rs:2852-2858) gets the variance from
`Variance::finalize`, which ends with `Cast<Self::Output>::cast(res)` (reduction.rs:1940). For
f16, f32 and Complex<f32> inputs the variance is therefore rounded to f16 / f32 first, and only
then square-rooted. The variance range is twice as wide (in exponent) as the std range, so:
(1) var overflows the output dtype while std fits (var > 65504 for f16, > 3.4e38 for f32): std is
+inf; (2) var underflows to 0 or lands in the subnormal range while std is a normal number
(var < 6.1e-5, i.e. std < 0.0078, for f16; var < 1.2e-38 for f32): std is 0 or off by many ulps.
For f16 this hits ordinary data - a few consecutive f16 values near 1.0 give a std 26 ulps
(1.6 %) off, two adjacent values near 0.01 give std 0. The overflow is silent (no
`ArithmeticOpStatus`, no Python warning; NumPy at least warns "overflow encountered in square").
It is also inconsistent across dtypes: std on the f64 copy, rounded to f16 / f32, is correct.

## Trigger
- f16 `[1.0, 1.0+2^-10, 1.0+2^-9].std(0, 0.0)`: var = 2^-19/3 = 6.36e-7, an f16 subnormal.
- f16 `[0.01, nextafter(0.01)]`: var = 1.4e-11, rounds to 0 in f16.
- f16 `[-300, 300]`: var = 90000 > f16::MAX.
- f32 `[-2e19, 2e19]`, complex64 `[-2e19+0j, 2e19+0j]`: var = 4e38 > f32::MAX.
- f32 `[1e-25, 2e-25]`: var = 2.5e-51, below the smallest f32 subnormal.

## Root cause
`StandardDeviationKernel::finalize_state` (reduction.rs:2852-2858) is literally
`Sqrt::sqrt(Variance::finalize(...))`, and `Variance::finalize` (reduction.rs:1932-1941) casts
the f64 `m2 / denom` to `Self::Output` (f16 / f32) before returning. The f16 `Sqrt` then widens
to f32 (op1.rs:607-610), but the precision is already gone. The f64 accumulation that Var/Std
deliberately use (context doc "Intentional behaviors") is thrown away at the last step.

Mitigating context, why low and not higher: NumPy returns the same inf / 0 / imprecise values
for these inputs (it squares and sums in the narrow dtype), and the Rust doc says "Equivalent to
`sqrt(variance)`" (reduction.rs:2768), which taken literally allows it. Not covered by K67 / K84
(those are about overflow of the f64 `m2` and NaN inputs) nor listed as intentional.

## Suggested fix
Split `Variance::finalize` into an f64 part (e.g. `finalize_f64(state, ddof, nitems) -> f64`,
including the `m2 >= 0` handling) and the final cast; have std compute `f64::sqrt` of that and
cast to `Output` once. Var keeps its current behavior. Add the triggers above as tests.
