# F004: Widening cast of a huge lazy array raises PanicException instead of RuntimeError: jix-py cast_impl calls the panicking convenience Array::cast

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix-py/src/ops/mod.rs:116 (related: jix/src/ops/cast.rs:485, jix/src/ops/op1.rs:35, jix-py/src/ops/common/operand.rs:231, jix-py/src/ops/common/dispatch.rs:224 and :242/:254, jix-py/src/ops/as_array.rs:65, jix-py/src/ops/mod.rs:97, jix-py/src/array.rs:1631)
- Reachability: Python API
- Reported by: py-ops-operand-broadcast

## What goes wrong
`cast_impl`, the single function jix-py uses to cast a whole array, builds the cast with core's
convenience method `array.cast::<T>()`. That method is `Cast::new_array(self).unwrap()`. Since the
K2 fix (#86), `Op1::new` runs `check_shape_overflow(shape, output itemsize)`. It returns
`InvalidShapeOperation` when the widened byte size does not fit in u64. jix-py unwraps that `Err`.
So a valid lazy array whose byte size fits at its own itemsize but not at the wider one makes
Python raise `pyo3_runtime.PanicException`, in debug and release builds alike (no `panic = "abort"`
in any profile). PanicException derives from BaseException, so `except Exception` does not catch
it. The same overflow found through a fallible constructor raises `RuntimeError`, for example
`jix.add(1.5, big)`, where `Scalar::new` reports it, or `big + col`, where `Broadcast::new` does.
Which exception you get therefore depends on operand order. An error is the right outcome; only
the exception type is wrong.

## Trigger
`big = jix.broadcast(jix.asarray(np.zeros(1, np.uint8)), (2**62,))` is a valid lazy u8 array
(2**62 bytes). Then any of these:
- `jix.cast(big, np.float64)`
- `jix.asarray(big, dtype=np.float32)` or `jix.compact(big, dtype=np.float64)`
- `big + 1.5` or `big == np.float32(1)` (dispatch casts the array operand)
- `int8_big * np.int64(3)`
- `jix.where(True, big, 1.5)`, `jix.concatenate([big, np.zeros(1, np.int32)])` or `jix.stack([big, 1.5])`
  (`operands_dtype_promotion`)

Not affected: `-big` (negating an unsigned array casts u8 to i8, the same width, which cannot
overflow; the hunter's claim about `negative` is wrong).

The backtrace shows `Array<IntoType<..., u8>>::cast::<f64>` called from `jix::ops::cast_impl`. The
panic location `src/ops/mod.rs:165` is the `cast_typed!` expansion site, because `Array::cast` is
`#[track_caller]`.

No Rust repro: core's `Array::cast` panicking is the intended behavior of its convenience methods
(`Cast::new_array` returns the `Err`, which core's own test `cast_rejects_widened_shape_overflow`,
jix/src/ops/cast.rs:493, already covers). The defect is that jix-py uses the panicking variant.

## Root cause
jix-py/src/ops/mod.rs:113-118 (`cast_typed!`):
```rust
let array = array.into_typed::<$src_type>().unwrap();
let array = array.cast::<$dst_type>();   // = Cast::new_array(self).unwrap(), jix/src/ops/cast.rs:485
return Ok(array.into_any());
```
`Cast::new` became fallible when the K2 fix added `check_shape_overflow` with the output itemsize
to `Op1::new` (jix/src/ops/op1.rs:35). jix-py kept the unwrapping wrapper, although its other
core-op call sites use `X::new_array(..).into_py_result()?`. All array casts go through
`cast_impl`: `Operand::cast` (operand.rs:231), which serves dispatch (dispatch.rs:224) and
`operands_dtype_promotion` (dispatch.rs:242/254: where, concatenate, stack); `jix.cast`
(mod.rs:97); and `asarray(dtype=)` (as_array.rs:65), which `jix.compact(dtype=)` also uses
(array.rs:1631). I checked the other unwrapping calls in jix-py ops (op1.rs:52-55 negate, log's
`res.map`) and none changes the itemsize, so none can fail. `cast_impl` is the only such site.

Severity is low, down from the hunter's medium. An error is the correct outcome, and only its type
is wrong (BaseException PanicException instead of RuntimeError). The trigger also needs a lazy
array of at least about 2^61 elements. This matches the precedent for panic-instead-of-error
findings on unusual inputs (K32, K79: low).

## Suggested fix
In `cast_typed!` replace `array.cast::<$dst_type>()` with
`jix_core::ops::Cast::<_, $dst_type>::new_array(array).into_py_result()?`. Optionally add a
`# Panics` section to core `Array::cast` (jix/src/ops/cast.rs:477), as `map` / `sub_dtype` /
`where_op` have, and add the repro cases to the Python tests.
