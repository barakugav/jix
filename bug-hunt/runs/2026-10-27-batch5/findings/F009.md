# F009: NdIterExtBlockOffsetSize doc prescribes block_end = end.div_ceil(b), which visits a phantom size-0 block for an empty range with an unaligned begin; every caller uses calc_block_end instead (latent, crate-internal)

- Severity: low  Verdict: confirmed  Category: latent-hazard (stale internal doc contract)
- Location: jix/src/util/iter/block.rs:9-16 (the `# Usage` doc of `NdIterExtBlockOffsetSize`; the wrong formula is on line 12) (related: jix/src/util/mod.rs:625-633 `calc_block_end`, the bound the extension really needs; jix/src/util/iter/nd.rs:497-513 `with_block_offset_size_ext`, which takes the element-space begin/end separately from the builder's block-space bounds and never checks them; jix/src/util/iter/block.rs:102-125 `on_increase`/`on_decrease`, which assume the walk starts at `low.index`)
- Reachability: crate-internal. `NdIterExtBlockOffsetSize`, `NdIterBuilder` and `calc_block_end` are all `pub(crate)`, and no public trait or associated type exposes them. All six callers compute the bounds correctly: compact.rs:453-466, array.rs:1062-1073, array.rs:1385-1391 and 1415-1423 (begin 0, where div_ceil and calc_block_end agree), reduction.rs:454-474 and 551-566.
- Reported by: util-nd-iter-ordered

## What goes wrong
The usage doc tells callers to iterate block space over `[begin/b, end.div_ceil(b))`. The extension is only exact over `[begin/b, calc_block_end(begin, end, b))`. The two differ in exactly one case: `begin == end` with `begin % b != 0`. There, the documented bounds visit one block per dim combination, and that block has inner offset `begin % b` and size 0 in the empty dim. The region is empty but the walk is not.

Following the doc does no harm to memory. The phantom block index `begin/b` is always inside the block grid, because an unaligned `begin <= shape` implies `begin/b < shape.div_ceil(b)`. Its size is 0, so a consumer copies nothing. The visible cost is decoding a block that no element needs, or running any other per-block side effect.

The second half of the report is a design remark, not a separate defect. The builder takes the element-space range and the block-space bounds independently. If they disagree, the extension reports wrong `(offset, size)` pairs: the low-border values on the wrong block, or a full `(0, b)` after a wrap. In debug builds the `debug_assert_ne!` at block.rs:105/118 caught this in all three cases tried. Release builds would pass the wrong sizes on. No caller mismatches the bounds today.

## Trigger
This is crate-internal: a new caller that follows the doc.

- 1-d: `NdIter::builder_with_begin([5/4], [5u64.div_ceil(4)]).with_block_offset_size_ext(&[5], &[5], [4])` yields `([1], ([1], [0]))`. The correct result is no items, which is what the `calc_block_end` bounds give.
- 2-d: element range `[5,5) x [0,8)`, block `[4,4]` yields `([1,0],[1,0],[0,4])` and `([1,1],[1,0],[0,4])`.

Mismatched bounds (observation only): an NdIter over block space `[0,2)` with element range `[5,8)` and b=4. The first item, block 0, reports `(1, 3)`, although block 0 does not touch the range. The next step trips `debug_assert_ne!(1, 1)` at block.rs:105.

## Root cause
The doc at block.rs:11-12 states the general `div_ceil` formula. It omits the empty-range exception that `calc_block_end` (util/mod.rs:625-633) exists to handle; its comment says "div_ceil always works for all cases, except for empty ranges where begin is not aligned with block_size". The extension's border math (block.rs:59-80) gives the low border `length = min(b - begin%b, end - begin) = 0` and leaves it to the NdIter bounds to skip that block. Nothing in `with_block_offset_size_ext` (nd.rs:497-513) derives or checks those bounds. Every caller gets them right by calling `calc_block_end` itself, and the module's own unit tests do the same (block.rs:161-166). Each caller also returns early on an empty region; for example, Compact read_data returns when `nitems == 0` (compact.rs:303-304).

## Suggested fix
Fix the doc so that `block_end[d] = calc_block_end(begin[d], end[d], block_shape[d])`. A sturdier fix is to have `with_block_offset_size_ext` (or a dedicated `NdIter::blocks(begin, end, block_shape)` constructor) compute the block-space bounds from the element range itself. The extension then cannot be paired with mismatched bounds. If the separate API stays, add a `debug_assert` in the builder that the bounds equal `begin/b .. calc_block_end(...)`.
