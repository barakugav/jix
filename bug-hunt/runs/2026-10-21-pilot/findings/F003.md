# F003: Padded struct dtypes: nd_copy moves elements as `[u32; 2]` / `[u64; 2]`, reading uninitialized padding as integers (UB from the safe API)

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/util/nd_copy.rs:35 (`(8, 4) => scalar_fn::<[u32; 2]>`) and :37 (`(16, 8) => scalar_fn::<[u64; 2]>`)
  (related: jix/src/util/nd_copy.rs:416-438 `fill_contiguous` dispatches on itemsize alone;
  jix-macros/src/lib.rs:113-122 accepts padded `#[repr(C)]`; jix/src/dtype.rs:1147-1152 `Dtyped`
  safety contract does not forbid padding; jix/src/storage/plain.rs:476; jix/src/storage/buf.rs:229-238;
  jix/src/storage/compact.rs:392; jix/src/storage/scalar.rs:111,125; jix/src/storage/elementwise_pipeline.rs:544;
  jix/src/codec/filter/byte_shuffle.rs:128 (reads every byte as a `u8` value))
- Reachability: public Rust API (safe `#[derive(Dtyped)]` + `Array::plain_ndarray` / `compact_ndarray` / `to_ndarray`). Not Python: numpy and file bytes are initialized from Rust's point of view.
- Reported by: util-memory-helpers

## What goes wrong
`#[derive(Dtyped)]` accepts padded `#[repr(C)]` structs, and the dtype docs describe the padded
"Aligned" layout as a supported variant. `NdCopier::new` picks its copy routine from
`(itemsize, alignment)` only, so a padded struct with (8, 4) (e.g. `{a: u8, b: u32}`) is copied as
`[u32; 2]` and one with (16, 8) (e.g. `{a: u8, b: u64}`) as `[u64; 2]`. In a Rust value the padding
bytes are uninitialized, so a typed integer load over them is UB. Every read of such an array goes
through `NdCopier` (Plain push, Compact gather/scatter, Broadcast/Scalar/Tile/Repeat/Flip copies), so
the UB happens on the plainest `to_ndarray()`. Natively the copy just moves garbage padding bytes and
the test passes; no miscompile was observed.

## Trigger
```rust
#[derive(Clone, Copy, Debug, PartialEq, Dtyped)]
#[repr(C)]
struct Padded { a: u8, b: u32 }   // itemsize 8, alignment 4, 3 padding bytes at 1..4

let a = Array::plain_ndarray(Array1::from(vec![Padded { a: 1, b: 2 }; 4])).unwrap();
a.to_ndarray::<Ix1>().unwrap();   // NdCopier -> inner_loop_contiguous_const_len::<[u32; 2], 4, true>
```

## Root cause
The byte-level storage layer assumes every byte of an element is an initialized value, while the
type layer lets a Rust type with padding (uninitialized bytes) be a `Dtyped`:
- `NdCopier::new` (nd_copy.rs:30-39) treats `(8, 4)` / `(16, 8)` as "plain integer array" layouts,
  which is false for padded structs. The removed `copy_struct` path (commit 763a701) did not cover
  this either: `create_scalar_fn` already ran first for `(8, 4)`. The doc comment on `NdCopier` still
  mentions a field-by-field struct copy that no longer exists.
- `fill_contiguous` (nd_copy.rs:416-438) dispatches on itemsize alone and reads `u16`/`u32`/`u64`/
  `[u64; 2]` for any 2/4/8/16-byte struct, including padded ones with smaller alignment (e.g.
  `{a: u8, b: u16}` (4, 2)). It is reached from broadcast staging (elementwise_pipeline.rs:544).
- Untyped copies alone would not make it sound: the Compact write path then runs the default
  byte-shuffle filter, which reads each byte as a `u8` value (byte_shuffle.rs:128, SIMD loads at :82),
  and hands the bytes to zstd. A compressed or written padded-struct array also stores whatever
  stale heap bytes sat in the padding.

## Suggested fix
Make "no uninitialized bytes" part of the type contract instead of patching each copy: state in the
`unsafe trait Dtyped` safety section that implementors must have no padding bytes, and have
`#[derive(Dtyped)]` emit a compile-time check that the field sizes add up to `size_of::<Self>()`
(users add explicit `_pad: [u8; N]` fields, as with `bytemuck::NoUninit`). Runtime padded dtypes
from `Dtype::from_fields` / numpy / files can stay, because their bytes are initialized. If padded
Rust types must stay supported, ingestion (`plain_ndarray`, `compact_ndarray`, `Scalar`) would need a
field-wise copy into a zeroed buffer before the bytes reach nd_copy, the filters or zstd.
