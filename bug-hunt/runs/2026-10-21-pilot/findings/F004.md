# F004: Array::read_from_reader hands uninitialized buffers to the caller's safe Read impl (UB from safe code, stale heap leak)

- Severity: high  Verdict: confirmed  Category: unsound-api
- Location: jix/src/util/mod.rs:571-583 (`value_from_io`) (related: jix/src/archive/common.rs:204-215 `ArchiveReader::read_slice`, jix/src/archive/block.rs:452-458 `Owned::read_section`, callers jix/src/archive/common.rs:125, jix/src/archive/block.rs:360, jix/src/archive/common.rs:161, entry point jix/src/archive/array.rs:145)
- Reachability: public Rust API (`Array::read_from_reader`, safe fn, any `impl Read + Seek`). Not reachable from Python: `PyReader::read` (jix-py/src/archive.rs:302-326) calls the Python `read(n)` and only writes `buf`, and the path-based readers wrap `File`.
- Reported by: util-memory-helpers

## What goes wrong
Three places in the archive reader create a `&mut [u8]` over uninitialized memory and pass it to
`read_exact` on the user's reader (wrapped in `std::io::Take`):
- `value_from_io` uses `MaybeUninit::<T>::uninit()`. It reads the `Header` and the `[Section; 2]` table of contents.
- `read_slice` calls `Vec::set_len` after `reserve`. It reads every protobuf message.
- `Owned::read_section` uses `Vec::<MaybeUninit<T>>::with_capacity` + `set_len` + `cast_slice_mut`. It reads the block data and the block locations.

`Read` is a safe trait. The std docs for `Read::read` say: "It is your responsibility to make
sure that `buf` is initialized before calling `read`. Calling `read` with an uninitialized `buf`
... is not safe, and can lead to undefined behavior." So a safe `Read` impl that looks at `buf`
before it fills `buf` causes UB through the safe `read_from_reader`. In practice that impl
receives stale heap contents, which leak to safe code. These include freed data from other
allocations and malloc free-list pointers.

## Trigger
Any safe `Read + Seek` impl that reads `buf` before writing to it. For example:

```rust
fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
    for &b in buf.iter() { self.copy.push(b); }   // or self.x ^= b, a hex-dump logger, ...
    self.inner.read(buf)
}
```

Pass that impl to `Array::read_from_reader(reader, None, ArrayParams::default(),
ArchiveValidation::default())` on a valid archive, for example `Array::compact_ndarray(&[1u8, 2, 3, 4])`
written with `write_to`.

## Root cause
The three helpers assume that `read_exact` only writes to `buf`. Nothing in the signatures
enforces that: `R` is an arbitrary caller type, `read_from_reader` is safe, and its docs do not
restrict what the reader does. The `unsafe` blocks at util/mod.rs:577-580, common.rs:210-213 and
block.rs:453-457 therefore rely on an assumption that the `Read` contract does not give. The
code-level comment at block.rs:432-433 ("Allocates uninitialized capacity, reads the raw bytes
from `reader` directly into the buffer") describes exactly the pattern that std calls unsound.

## Suggested fix
Initialize every buffer before handing it to `Read`:
- `value_from_io`: use `MaybeUninit::<T>::zeroed()`. T is a POD for which all-zero bytes are valid,
  and the size is at most 32 bytes.
- `read_slice`: use `self.tmp_buf.clear(); self.tmp_buf.resize(len, 0)` instead of `reserve` +
  `set_len`. Alternatively use `(&mut self.reader).take(len).read_to_end(&mut self.tmp_buf)`, which
  uses std's initialized-length tracking.
- `Owned::read_section`: allocate zeroed memory, e.g. `vec![MaybeUninit::<T>::zeroed(); len]`, or
  read into a zeroed `Vec<u8>` / `vec![0u8; n]`, which uses calloc and is free for large sections.

The memset cost is negligible next to the I/O. Separately, `read_slice` also trusts the uleb128
message length from the file for `reserve(len)` without checking it against `total_size`. That is
a resource issue, not part of this finding.
