# F008: On i686 Linux, jix hard-codes alignment 8 for f64/i64/u64/c128 but the ABI aligns them to 4, so Python `.dtype`/`.numpy()`/shape ops raise and derived structs with 8-byte fields write archives that cannot be read back

- Severity: medium  Verdict: confirmed  Category: portability
- Location: jix/src/dtype.rs:967-984 (`ScalarKind::alignment()`), jix-py/src/dtype.rs:78-85 (exact
  `(itemsize, alignment)` check in `dtype_to_numpy`) (related: jix-py/src/array.rs:288-297
  (`numpy_dtype`, callers array.rs:222, 416, 551, ops/shape_ops.rs:100,192,426,498,613,761,878,963,1031,1097,1157,1227,
  ops/where_op.rs:74), jix-py/src/dtype.rs:127,198 (numpy's alignment passed to `Dtype::new_struct`),
  jix/src/dtype.rs:653-688 (`is_aligned_struct`), jix-macros/src/lib.rs:185,203 (derive lays out
  fields with `align_of`), jix/src/archive/schema/conversions.rs:113 (`new_struct` on archive read),
  jix/src/util/nd_copy.rs:90 and jix-py/src/dtype.rs:207 (debug asserts))
- Reachability: Python API (manylinux / musllinux x86 wheels from release.yaml) and public Rust
  API (`#[derive(Dtyped)]` + `write_to_file` / `read_from_file`), on i686 Linux only
- Reported by: concept-alignment (two reports, same root cause)

## What goes wrong
`ScalarKind::alignment()` returns 8 for I64, U64, F64 and ComplexF64 on every target. The i386
SysV psABI (i686 Linux, glibc and musl) aligns `double`, `long long` and `double _Complex` to 4.
Rust's `align_of` and numpy's descriptor alignment both follow the ABI. Every place that compares
the two values breaks on i686 Linux:
1. Python: `dtype_to_numpy` requires numpy's `(itemsize, alignment)` to equal jix's exactly, which
   fails with `(8, 4) != (8, 8)`. The result is a ValueError from `.dtype`, `.numpy()`, `a[...]`,
   every shape op, `where`, and `numpy(out=...)` on any f8/i8/u8/c16 array that does not already
   carry a cached numpy descr. Those dtypes are numpy's defaults.
2. Python, struct input: numpy's aligned struct layouts (e.g. `[('a','f8'),('b','i4')]`,
   align=True: itemsize 12, alignment 4) are passed to `Dtype::new_struct`, which rejects them.
3. Rust: `#[derive(Dtyped)]` places fields by `align_of`. For `struct S { a: u8, b: u64 }` it gives
   `b@4`, itemsize 12, align 4. That dtype is written to the archive header. On read,
   `new_struct` rejects it, so an archive written on i686 cannot be read back on i686 itself, or on
   any other platform.
4. Debug builds on i686 panic in `NdCopier::scalar_fn::<u64>` (nd_copy.rs:90) for every 8-byte
   scalar copy. The Python-binding debug build also panics in `dtype_from_numpy` (dtype.rs:207).

No memory-safety impact: jix's 8 is stricter than Rust's 4 on i686, and release builds return
errors, never wrong data.

## Trigger
- Python, on the i686 manylinux/musllinux wheel with numpy 2 built for i686: `a = jix.asarray(np.zeros(3)); a.numpy()`.
  The same failure comes from `a.dtype`, `a[1:]`, `jix.compact(np.zeros(3)).numpy()`,
  `(jix.asarray(np.arange(4)) + 1).numpy()`, and `jix.reshape(jix.asarray(np.zeros(6)), (2, 3)).numpy()`.
  Also `jix.asarray(np.zeros(3, dtype=np.dtype([('a','f8'),('b','i4')], align=True)))`.
  PyPI has no numpy 2 i686 Linux wheel, so numpy comes from the distro (Debian i386, Alpine x86) or
  a source build. jix's own x86 Linux wheels are shipped.
- Rust, on i686-unknown-linux-{gnu,musl}: `#[derive(Copy, Clone, Dtyped)] #[repr(C)] struct S { a: u8, b: u64 }`,
  then `Array::compact_ndarray(&arr1(&[S{..}; 5]))?.write_to_file(p)?; Array::read_from_file(p, ArrayParams::default())`.

`numpy_i686_struct_layouts` fails on every host. It is a host-side simulation of the
`Dtype::new_struct` call that `dtype_from_numpy` makes with numpy's i686 descriptors.

numpy's value on i686: in the numpy 2.5.4 sdist, the builtin descrs set
`.alignment = NPY_ALIGNOF(type)` (arraytypes.c.src). `NPY_ALIGNOF` is C11 `_Alignof` (common.h:236-244).
The comment there says numpy avoids GCC bug 52023 deliberately, so that it reports the ABI
alignment and not the "preferred" one. `_Alignof` of `double`, `long long`,
`unsigned long long` and `double _Complex` (npy_cdouble) compiles to 4 with `gcc-13 -m32` and with
`clang --target=i686-unknown-linux-{gnu,musl}`. It compiles to 8 for x86_64 and armv7. The
aligned struct `{double; int}` is 12 bytes, alignment 4, on i686. rust-numpy's
`PyArrayDescr::of::<f64>()` is `PyArray_DescrFromType(NPY_DOUBLE)`, i.e. that builtin descr.

Python failure itself was not executed. It follows directly from the unconditional equality at
jix-py/src/dtype.rs:78-85 with numpy alignment 4 against jix alignment 8.

## Root cause
`ScalarKind::alignment()` (jix/src/dtype.rs:967-984) encodes the x86_64 alignment as a
platform-independent constant. The Dtype model then assumes it equals the platform's alignment in
three places:
- the numpy bridge (jix-py/src/dtype.rs:78-85 exact match; :127/:198 forwards numpy's alignment
  into `new_struct`; :207 debug assert);
- the struct validators: `is_aligned_struct` (dtype.rs:653-688) requires
  `alignment == max(field.DTYPE.alignment())` and field offsets that are multiples of the field
  DTYPE alignment. The derive (jix-macros/src/lib.rs:185,203) instead uses `align_of`, which is 4
  on i686;
- `NdCopier::scalar_fn` (nd_copy.rs:90) asserts `align_of::<T>() == dtype.alignment()`.

The constant has to stay target-independent, because archive decode checks scalar alignment
against it (conversions.rs:78). The bug is in the consumers that compare it with the platform value.

## Suggested fix
- jix-py: in `dtype_to_numpy`, check only that itemsize matches and that
  `numpy_alignment <= jix_alignment` (or skip the alignment check for scalars). In
  `dtype_from_numpy`, drop the scalar alignment debug assert.
- Struct layouts: let `is_aligned_struct`/`new_struct` accept the i386 "aligned" layout, either
  with a per-field alignment of `min(field alignment, 4)` for 8-byte scalars or as a generic
  explicit-offset layout. Alternatively, have the derive emit a dtype that `new_struct` accepts
  and is still portable, and add a derive test that round-trips the dtype through `new_struct`.
- Make the `nd_copy.rs:90` assert `align_of::<T>() <= dtype.alignment()`.
- Add a CI job that at least builds and runs the core tests for i686-unknown-linux-musl. It runs
  natively on x86_64 runners.
