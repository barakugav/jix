# F011: ArrayVec::extend_from_iter drops each ZST element and also counts it in len, a double drop that safe public code can reach through Dimension::vec

- Severity: high  Verdict: confirmed  Category: unsound-api
- Location: jix/src/util/arrayvec.rs:416-418 (related: jix/src/util/arrayvec.rs:367-369, jix/src/util/arrayvec.rs:470-473, jix/src/util/arrayvec.rs:443, jix/src/util/arrayvec.rs:47-50, jix/src/util/arrayvec.rs:332-335, jix/src/util/arrayvec.rs:571-572, jix/src/util/arrayvec.rs:517-524, jix/src/dimension.rs:76, jix/src/dimension.rs:127, jix/src/dimension.rs:162, jix/src/dimension.rs:516)
- Reachability: public Rust API. The `arrayvec` module is pub(crate), but the public, documented
  `Dimension::vec` (dimension.rs:127) returns `<DimDyn as Dimension>::Vec<T>`, which is
  `DimArray<T> = ArrayVec<T, 8>` (dimension.rs:162, 516), for any user-chosen `T`. That value's
  std trait impls (`Extend`, `FromIterator` via `collect()` into the inferred type,
  `Clone::clone_from`, `IntoIterator` then `IntoIter::clone`) can be called from safe code outside
  the crate. jix itself never stores a ZST in an `ArrayVec`.
- Reported by: util-memory-arrayvec-bitmap-cache

## What goes wrong
When `size_of::<T>() == 0`, `extend_from_iter` skips `ptr.write(elt)` but still increments
`guard.data`, which becomes `len`. Because `elt` is only conditionally moved, it is dropped at the
end of the `if let` scope. The vector still counts the element as live, so it is dropped a second
time later, in `truncate`/`clear`/`Drop` or in `IntoIter::drop`. Each element of a ZST type with
a `Drop` impl is therefore dropped twice. Rust's ownership contract allows exactly one drop per
value. A ZST with `Drop` is normally a uniquely-owned token or guard, and safe user code that
relies on that contract turns the second drop into memory corruption. The repro shows a double
free caused by this pattern. The code already knows about the hazard: `ArrayVec::clone`
`mem::forget`s the ZST value for exactly this reason (arrayvec.rs:517-524). `extend_from_iter`
does not.

## Trigger
Safe code outside the crate:

```rust
use jix::{DimDyn, Dimension};
struct Z; impl Drop for Z { fn drop(&mut self) { /* count */ } }
let mut v = <DimDyn as Dimension>::vec(0, |_| Z);   // ArrayVec<Z, 8>
v.extend([Z, Z, Z]);                                 // 3 drops here...
drop(v);                                             // ...and 3 more here
```

The bug is also reachable through `v = iter.collect()`, through `dst.clone_from(&src)` (which
calls `extend_from_slice`) and through `v.into_iter()` -> `next()` -> `.clone()` (which also calls
`extend_from_slice`). `ArrayVec::from_slice` (:47-50) takes the same path, but outside the crate
only an unnameable type can name it.

frees it in `Drop`. That is sound user code, because each allocation has exactly one `Token`. The

## Root cause
At arrayvec.rs:416-418, `if mem::size_of::<T>() != 0 { ptr.write(elt); }` treats skipping the
write as "nothing to do" for a ZST. Skipping the write also skips the move, so `elt`'s drop flag
stays set. Line 420 (`guard.data += 1`) still records the element as stored. The pattern was
copied from upstream `arrayvec`. The local `Clone` impl was patched with `mem::forget`
(arrayvec.rs:517-524), but this function was not. `Dimension::vec` / `Dimension::Vec<T>`
(dimension.rs:76, 127, 162) expose the container for arbitrary `T`, which makes the flaw
reachable from outside the crate. The `pub(crate) DimVec` bound only stops users from
implementing `Dimension`. It does not stop them from using the returned value.

## Suggested fix
In `extend_from_iter`, add the same `else { mem::forget(elt) }` branch that `Clone` has. Do not
make the write unconditional: for a ZST, `ptr` advances with `wrapping_byte_add`, so it can be
misaligned for an over-aligned ZST. Optionally, also restrict `Dimension::vec`/`Vec<T>` to
`T: Copy` or make it `#[doc(hidden)]`. Neither is needed once the drop is fixed. A unit test with a
drop-counting ZST over extend/collect/clone_from/IntoIter::clone would cover this.

## Severity note
The hunter rated this low as crate-internal. Verification found that the public `Dimension::vec`
hands out the container, so safe external code can cause a double drop, and from there a double
free. That fits the PRIMER's "UB reachable only with unusual-but-valid input" row, which is high.
The input is unusual: it needs a `Drop` ZST stored in a per-dim helper container. No jix API
consumes such a container, so the practical risk is small.
