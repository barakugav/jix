# F006: ArrayParams::tune panics (divide by zero / multiply overflow) on an invalid fixed block dim when another dim is auto-scaled, instead of returning InvalidArgument

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/storage/params.rs:427 (related: jix/src/storage/params.rs:400, jix/src/storage/params.rs:347-360, jix/src/storage/params.rs:361-369, jix/src/array.rs:275, jix/src/array.rs:1289, jix-py/src/array.rs:1663-1668)
- Reachability: public Rust API (`Array::compact_ndarray_with`, `compact_with`, and the other `tune` callers at array.rs:312/495) and Python API (`jix.compact(x, params=...)` and anything else that takes `params`)
- Reported by: util-memory-arrayvec-bitmap-cache, util-memory-helpers

## What goes wrong
`tune` validates the block shape (`b > 0 && b <= max(s, 1)`, params.rs:361-369) only after
`scale_block_shape` has run. If at least one dim is not fixed, `scale_block_shape` runs first with
the user's fixed lengths. It multiplies them into `volume` without checking (params.rs:400), then
divides by that volume in `block_len_heuristic` (params.rs:427). A fixed length of 0 makes
`volume == 0`. Integer division by zero panics in every build profile. With all dims fixed,
scaling is skipped and the same block shape gives a clean `Err(InvalidArgument)`, so two paths
that should agree do not. A second trigger at the same site: fixed lengths far larger than the
array overflow the unchecked `product::<u64>()`. That panics in debug. In release it wraps, and
if it wraps to exactly 0 it reaches the same division by zero. In Python the panic surfaces as
`pyo3_runtime.PanicException` (a `BaseException`) where a `RuntimeError` is expected.

## Trigger
- Rust: `let mut p = ArrayParams::new(); p.block_shape(&[0, 4]).block_shape_fixed_dims(&[true, false]);`
  then `Array::compact_ndarray_with(&Array2::<f32>::zeros((3, 5)), p)`. `[4, 0]` with fixed
  `[false, true]` on `(8, 4)` behaves the same, and so does
  `compact_with(p, &ctx)` on an existing compact array.
- Python: `jix.compact(np.zeros((3, 5), np.float32), params={"block_shape": [0, 4], "block_shape_fixed_dims": [True, False]})`.
- Overflow variant: `block_shape = [1<<31, 1<<31, 4, 1]`, fixed `[T, T, T, F]`, on a
  `(3, 3, 3, 5)` f32 array. Debug: multiply-overflow panic. Release: the product is
  2^31 * 2^31 * 4 = 2^64, which wraps to 0, then divide-by-zero. The release case was worked out
  from the arithmetic and not run.
- The scaled dim must have length > 1. `block_len_heuristic` returns 1 early for `dim_len <= 1`
  (params.rs:423-425). In that case the 0 survives to the validation and becomes a clean `Err`.

## Root cause
- params.rs:347-360: when `!fixed_block_shape`, the user's fixed lengths go straight into
  `scale_block_shape`, before the entry validation at params.rs:361-369.
- params.rs:400: `volume` is an unchecked `product::<u64>()` of those lengths, so it can be 0 or
  overflow. At :408, `volume / max(1) * block_len` keeps it 0 for every later dim.
- params.rs:427: `max_volume / inner_block_volume` divides with no guard against zero.
- Nothing earlier rejects 0. `ArrayParams::block_shape` (params.rs:120-124) checks only ndim,
  and the Python `resolve_array_params` (jix-py/src/array.rs:1663-1668) forwards the list as is.

Why severity is low and not medium: no valid input reaches the panic. A 0 block length, or a
fixed length larger than the array, is always rejected by `tune` in the end. Internally propagated
block shapes are clamped with `.max(1)` (ops/shape_ops/slice.rs:93, tile.rs:83-85,
reshape.rs:88-90, repeat.rs:70-73), and a loaded archive is validated with `b > 0`
(archive/array.rs:469-477). So `override_from_storage` cannot feed in a 0. Reaching the panic
takes an explicit invalid user parameter plus an explicit `block_shape_fixed_dims` with at least
one `false`. The only consequence is a panic in place of `Err(InvalidArgument)`: no UB and no
wrong result. It is an error-handling inconsistency between the all-fixed path and the
partly-scaled path.

## Suggested fix
In `tune`, before the scaling step, validate the fixed entries:
`block_shape_fixed_dims.get(d) => 0 < block_shape[d] <= max(shape[d], 1)`. Return the same
`InvalidArgument` as :361-369. That rules out both the 0 and the overflow, because a valid fixed
volume is at most the product of the shape dims. To be safe, also compute `volume` at :400 with
`try_product()` (or saturating mul) and guard `inner_block_volume.max(1)` at :427.
