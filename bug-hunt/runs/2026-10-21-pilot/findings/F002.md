# F002: Pull-mode buffer size `product(shape) * itemsize` wraps after an itemsize-widening op (no shape-overflow re-check), so a too-small buffer is written at full-shape strides

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/storage/buf.rs:312 (related: jix/src/ops/op1.rs:28-41, jix/src/error.rs:186,
  jix/src/array.rs:1022-1063, jix/src/storage/elementwise_pipeline.rs:869-878,
  jix/src/storage/elementwise_pipeline.rs:891, jix/src/util/mod.rs:86-88, jix/src/util/mod.rs:159,
  jix/src/storage/compact.rs:281)
- Reachability: public Rust API (`Array::to_ndarray_buf(.., None)`); on 32-bit targets also any
  materializing pull read over 4 GiB
- Reported by: util-memory-helpers, util-memory-alloc-pool

## What goes wrong
`materialize_out_buf` (storage/buf.rs:310-316) sizes the pull-mode buffer as
`out_shape.iter().product::<usize>() * itemsize` with unchecked arithmetic, and then derives
strides for the full shape with `strides_for_layout_order`. The only guard against a too-large byte
size, `check_shape_overflow` (error.rs:186), runs in broadcast/tile/repeat/stack/concatenate with the
*input* itemsize. Ops that widen the itemsize afterwards (`Op1::new`, used by `cast`; also Op2 and Map)
never re-check. So an array whose `shape * itemsize` is larger than `u64` can be built from safe code.
A pull read of it wraps the size, gets a tiny pooled allocation, and
`to_ndarray_buf_slow_dyn` (array.rs:1052-1061) pushes each tile into it at full-shape strides through
unchecked `PtrMutNoalias` cursors. That is a heap buffer overflow in release builds, where overflow
checks are off. Debug builds panic at the multiplication.

## Trigger
```rust
let n: u64 = (1 << 61) + 1;                  // n * 1 fits u64, so broadcast's check passes
let big = Array::compact_ndarray(&array![7u8])?.broadcast(&[n]).cast::<f64>();
let ctx = big.read_ctx();
big.to_ndarray_buf(&[0..n], &ctx, None)       // (2^61 + 1) * 8 wraps to 8 bytes
```
Variant from util-memory-alloc-pool: `broadcast(&[1<<31, 1<<31, 2])` on u8 then `.cast::<f64>()`.
2^63 * 8 wraps to 0, so the buffer is a 0-capacity (dangling) allocation, or a stale small pooled
buffer if the context's pool is warm. On 32-bit targets no widening op is needed: any pull read
whose byte size exceeds 4 GiB wraps the same way.

```
attempt to multiply with overflow
   3: jix::storage::buf::materialize_out_buf
   4: jix::array::to_ndarray_buf_slow_dyn::<jix::dimension::Dim<1>>
```
The debug build shows the size computation wrapping. Release builds have overflow checks off. From
there the code path is unambiguous: `allocate_buf(8)` gets an 8-byte allocation
(`BufferPool::get`, buf_pool.rs:40-49, fresh exact-size alloc). The strides are `[8]` for the full
shape. The first tile (out_offset 0) is pushed through `StridedBuf::from_slice_mut` (no length
check) into the pipeline driver, which writes `chunk_len * 8` bytes through a `PtrMutNoalias` whose
span comes from the strides (elementwise_pipeline.rs:278-284), not from the allocation. The hunter
reported that the release build dies with SIGSEGV. I did not re-run release or Miri: Miri also has
overflow checks on, so it would stop at the same panic.

## Root cause
- jix/src/storage/buf.rs:312: the size of a pull-mode allocation is computed with an unchecked
  `product * itemsize`, while the strides at :314 describe the full shape. Nothing reconciles the two.
- jix/src/ops/op1.rs:28-41 (and Op2 / Map constructors): no `check_shape_overflow` with the
  *output* itemsize. This breaks the invariant that broadcast etc. establish for the input itemsize
  ("shape * itemsize fits u64").
- On 32-bit, `u64 -> usize` truncation also appears in the same paths: `(end - start) as usize`
  (array.rs:1022, compact.rs:281, elementwise_pipeline.rs:869) and `Idx::from_u64` (util/mod.rs:86-88).
  The same unchecked size product appears in `materialize_pipeline_out_buf`
  (elementwise_pipeline.rs:875-878) and `pick_output_layout` (:891).

## Suggested fix
Make the size computation fallible at the allocation site. In `materialize_out_buf` and
`materialize_pipeline_out_buf`, compute the byte size with `checked_mul` over the `u64` extents plus
a `usize::try_from` (or `try_product`), and return an error (both are called from functions that
return `Result`). Also run `check_shape_overflow(shape, output_itemsize)` in `Op1::new` / Op2 / Map
constructors, so an array whose byte size cannot be represented is rejected when it is built.
Replace the `as usize` casts of extents with checked conversions, so 32-bit targets fail cleanly.
