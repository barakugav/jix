# F005: mmap reader bounds archive sections by the caller's `len`, not by the mapping: a safe Python read of a truncated file segfaults

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/archive/block.rs:478-498 (related: jix/src/archive/common.rs:265-271, jix/src/archive/array.rs:217-240, jix/src/storage/block.rs:445, jix/src/storage/block.rs:188-192, jix-py/src/archive.rs:105-124)
- Reachability: Python API (`jix.read_array(path, len=..., mmap=True)`, a safe call); public Rust API through `unsafe Array::read_from_file_mmap` while meeting its documented `# Safety` contract
- Reported by: concept-alignment

## What goes wrong
`Mmap::read_section` checks a section only with `ArchiveReader::check_section_bounds`. That check
compares `offset + size` with `total_size`, which is the `len` the caller passed, not the length
of the mapping. `self.mmap[offset..]` then bounds-checks only the start of the section, and the
returned `MmapData` carries `len = section.size / size_of::<T>()`. `MmapData::as_ref` builds a
`&[T]` with `slice::from_raw_parts` over that length, and the slice can extend past the end of the
mapping. `ArchiveValidation::Strict` checks block locations against this over-long slice, so it
passes. `BlockTable::read_block` then hands zstd a source pointer outside the mapping. The result
is an out-of-bounds read: SIGSEGV, or decoding of whatever memory happens to be mapped after the
file. The heap reader catches the same file (`UnexpectedEof`), and so does the mmap reader when
`len` is left at its default. Only an explicit `len` larger than the file reaches the bug.

## Trigger
Write `jix.compact(np.random.default_rng(0).random(2_000_000))` to a file (14042966 bytes; 489
blocks of 4096 f64). Truncate the file to 65536 bytes. Header, TOC and block locations stay
intact; this simulates a partial download, an interrupted copy, or a stale `(offset, len)` from an
external index of a multi-array file. Then call `jix.read_array(p, offset=0, len=14042966,
mmap=True)[-1:].numpy()`. The Rust equivalent is `Array::read_from_file_mmap(&p, 0, full, ...)`,
followed by `to_ndarray_sub(&[n-1..n])`.

## Root cause
- `jix/src/archive/block.rs:478-498`: the only bound on `[base_offset + section.offset,
  + section.size)` is `check_section_bounds` against the caller's `len`
  (`jix/src/archive/common.rs:267`, with `total_size = len`). Nothing compares the section with
  `self.mmap.len()`. `&self.mmap[offset..]` at :489 proves only `offset <= mmap.len()`.
- `jix/src/archive/array.rs:217-240`: `read_from_file_mmap` passes `Some(len)` through without
  comparing `offset + len` with the file size or the mapping length. Its `# Safety` section
  (:185-191) names only modification of the file, so a caller who meets the documented contract
  still gets UB. The contract leaves out the precondition "`[offset, offset+len)` lies within
  the file".
- `jix-py/src/archive.rs:105-124`: the safe Python `read_array` uses a user-supplied `len`
  unchanged. It clamps nothing and computes the length from the file only when `len` is `None`.
- `jix/src/storage/block.rs:445`: `MmapData::as_ref` trusts `(ptr, len)`. Strict validation
  (`jix/src/archive/block.rs:392-410`) checks block locations against `block_data.len()`, which
  comes from the same unchecked section size, so it cannot catch this.

Related (read from the code, not run): the same unchecked path is reachable without an explicit
`len` in release builds. `section.offset as u64 + section.size` in `common.rs:267` is a plain
`+`, which wraps when overflow checks are off. A crafted TOC with `size` near `u64::MAX` therefore
passes the check, and `MmapData` gets a length beyond `isize::MAX`. This is UB in
`from_raw_parts`, and every block offset then counts as "in bounds". In the debug build this panics
on the overflow instead. The fix below covers both.

## Suggested fix
In `Mmap::read_section`, check the absolute range against the mapping with checked arithmetic:
`base_offset.checked_add(section.offset)?.checked_add(section.size)? <= self.mmap.len()`. Return
`InvalidArchive` or `UnexpectedEof` otherwise. Optionally, also reject
`offset + len > mmap.len()` up front in `read_from_file_mmap`, and make `check_section_bounds`
use `checked_add`.
