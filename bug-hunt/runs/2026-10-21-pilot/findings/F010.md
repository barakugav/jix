# F010: RawAlignedBytes::shrink_to reallocs to size 0 (UB), does not null-check the realloc result, and leaks the block when capacity becomes 0

- Severity: low  Verdict: confirmed  Category: memory-safety
- Location: jix/src/util/aligned_vec/raw.rs:155 (related: jix/src/util/aligned_vec/raw.rs:158, jix/src/util/aligned_vec/raw.rs:20, jix/src/util/aligned_vec/mod.rs:277-290)
- Reachability: crate-internal (`AlignedBytes::shrink_to` / `shrink_to_fit` have no caller outside the inline tests; `AlignedBytes` is `pub(crate)`, util/mod.rs:2)
- Reported by: util-memory-alloc-pool

## What goes wrong
`RawAlignedBytes::shrink_to(len)` always calls `realloc(old_ptr, old_layout, len)`. When `len == 0`, that
breaks `GlobalAlloc::realloc`'s "`new_size` is greater than zero" precondition. Miri reports it as UB
("creating allocation with size 0"). Nothing checks the result for null (raw.rs:158 does
`NonNull::new_unchecked(ptr)`), unlike the grow paths, which call `handle_alloc_error`. So a legal null
return from a failed shrink, even with `len > 0`, becomes a null `NonNull`. Drop would later
`dealloc(null, ..)`. When the shrink is to 0, `capacity` becomes 0 while `ptr` holds a real heap block.
Drop (raw.rs:20) and the cap-0 branch of `grow_*` both treat cap 0 as "nothing to free", so the block
leaks. This also breaks the invariant that a cap-0 `ptr` is the dangling `align` address.

## Trigger
Inside the crate (no public path):
- `let mut v = AlignedBytes::with_capacity_exact(16, 10); v.shrink_to_fit();` (len 0, cap 10). This
  calls `buf.shrink_to(0)` (mod.rs:288).
- `AlignedBytes::with_capacity_exact(128, 64).shrink_to(0)` (mod.rs:278-280; `max(0, len=0) = 0`).
- Null-result variant: any shrink (for example len 3, cap 10) where the global allocator's `realloc`
  returns null. With the System allocator and align > 16 (for example the 128-byte padded alignment),
  shrinking goes through `realloc_fallback`, a fresh `posix_memalign` plus a copy, which can fail when
  memory runs out.

## Root cause
raw.rs:144-159 copies the realloc logic of the grow paths but drops two of their guards. First, it does
not special-case a new capacity of 0. std's `RawVec::shrink` deallocates and resets to dangling when
`cap == 0`. Second, it does not check for null; compare `grow_unchecked`, raw.rs:232-237. The only stated
precondition is `debug_assert!(len < self.capacity())` (raw.rs:145). Both `AlignedBytes::shrink_to`
(mod.rs:278) and `shrink_to_fit` (mod.rs:288) pass `len == 0` when the vector is empty. The context doc
already lists the needed precondition `0 < len < capacity` (util-memory.md, RawAlignedBytes contracts)
as "NOT established".

## Suggested fix
In `RawAlignedBytes::shrink_to`:
- If `len == 0`, call `dealloc(old_ptr, old_layout)` and set `*self` to `new_unchecked(align)` (the
  dangling cap-0 state).
- Otherwise, call `realloc` and, on a null result, call
  `handle_alloc_error(Layout::from_size_align_unchecked(len, align))` before updating `ptr` or `capacity`.

Alternatively, delete the unused `shrink_to` / `shrink_to_fit` methods.
