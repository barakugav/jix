# F013: A 0 dim hides an overflowing shape product: [0, 2^40, 2^40] is accepted, then unchecked C-order stride products overflow (debug panic), and reducing the 0 dim away gives an unrepresentable shape (release unwrap panic)

- Severity: medium  Verdict: confirmed  Category: overflow
- Location: jix/src/error.rs:186 (`check_shape_overflow`) and jix/src/util/mod.rs:217-222 (`try_product`)
  - the hole; jix/src/util/mod.rs:145 (`default_strides_from_iter`) - where the reported panic fires
  (related: jix/src/util/mod.rs:171 `strides_for_layout_order`, jix/src/util/mod.rs:182
  `default_strides_slice`, jix/src/ops/shape_ops/reshape.rs:57-66, jix/src/ops/shape_ops/broadcast.rs:65,
  jix/src/array.rs:1299-1303, jix/src/array.rs:1609, jix/src/ops/reduction.rs:160-164,
  jix-py/src/ops/shape_ops.rs:724)
- Reachability: public Rust API and Python API
- Reported by: util-memory-helpers

## What goes wrong
The library's shape invariant is "the u64 product of the shape fits" (`check_shape_overflow`,
`Reshape::new`'s nitems check, and the `debug_assert!` in `Array::from_storage`, array.rs:1609, all
use `try_product`). `try_product` folds left with `checked_mul`, so once a 0 has been seen the
product stays 0. The check is therefore order dependent: `[0, 2^40, 2^40]` is accepted, while
`[2^40, 2^40, 0]` is rejected with `InvalidShapeOperation`. An accepted shape like `[0, 2^40, 2^40]`
breaks code that assumed the invariant:
1. (reported) The C-order stride helpers multiply the trailing dims without a check
   (util/mod.rs:145, :171, :182). `Reshape::new` (reshape.rs:66) and `compact_into_builder_dyn`
   (array.rs:1303, over the block grid) call them, so `reshape`, `compact`, and `compact_fn` with
   such a shape panic in debug builds. In release builds the product wraps silently. The wrapped
   strides are only used to match dims in `Reshape::new` and for the block-grid index math, and the
   array has no blocks or readable elements, so all three return `Ok` in release (verified).
2. (same root cause, release-reachable) Reducing over the 0 dim (`sum` sets `SUPPORTS_EMPTY`, see
   reduction.rs:141) gives a NON-empty `[2^40, 2^40]` array. Its element count (2^80) does not fit
   in u64, and reduction.rs:160-164 builds the output shape without checking it. Debug builds trip
   the `from_storage` `debug_assert!` (array.rs:1609). Release builds panic in `.compact()` at
   array.rs:1300 (`nblocks ... try_product().unwrap()`), and `nitems()` (array.rs:525) wraps.

Severity is medium because of item 2, a release-build panic reached through the public API. Item 1
alone, the reported defect, is a debug-only panic with harmless wrap in release, which would be
low. Both items need a contrived but accepted degenerate shape.

## Trigger
- Rust (reported): `Array::compact_ndarray(&Array1::<f32>::zeros(0))?.reshape([0u64, 1<<40, 1<<40])`
- Rust: `Array::compact_ndarray(&Array3::<f32>::zeros((0,1,1)))?.broadcast(&[0, 1<<40, 1<<40]).compact()`
- Rust: `Array::compact_fn_with([0u64, 1<<40, 1<<40], ArrayParams::default(), |_| 0f32)`
- Rust (release panic): `...broadcast(&[0, 1<<40, 1<<40]).sum(0).compact()`
- Python: `jix.reshape(np.zeros(0, np.float32), (0, 2**40, 2**40))`,
  `jix.compact(jix.broadcast(np.zeros((0,1,1), np.float32), (0, 2**40, 2**40)))`.
  `jix.reshape(np.zeros(0, np.float32), (2**40, 2**40, 0))` also panics in debug, at a second unchecked
  product in the Python wrapper (jix-py/src/ops/shape_ops.rs:724, `known_size *= dim as u64`), before
  it reaches Rust's clean rejection of that order.

## Root cause
`try_product` (util/mod.rs:217-222) short-circuits through a 0, so an overflow check built on it
(error.rs:186-188, reshape.rs:58, array.rs:1609) proves nothing about the non-zero dims. Code
downstream assumes that any partial product of a valid shape fits in u64:
- the stride helpers (util/mod.rs:145/171/182) multiply unchecked;
- reductions (reduction.rs:160-164) drop dims and assume the result still fits;
- `compact_into_builder_dyn` unwraps `nblocks` (array.rs:1300).

## Suggested fix
Define and enforce the invariant as "the product of the NON-zero dims (times itemsize) fits in u64"
(ndarray's `size_of_shape_checked` rule): change `check_shape_overflow` and the nitems check in
`Reshape::new` to fold over `filter(|&d| d != 0)`, and make the `from_storage` debug_assert match. Every
partial product, including the stride products and a reduction that drops a 0 dim, then fits, and
`[0, 2^40, 2^40]` is rejected cleanly whatever the dim order. Also replace
`known_size *= dim as u64` in jix-py's `reshape` with `checked_mul` (raise ValueError on overflow).
