# F007: mmap reader rejects valid archives whose block-locations section is not 8-aligned in the file (relocated/embedded archives, files from the i686 Linux wheel)

- Severity: low  Verdict: confirmed  Category: portability
- Location: jix/src/archive/block.rs:487-494 (related: jix/src/archive/block.rs:171-182, jix/src/archive/block.rs:107,115, jix/src/storage/block.rs:28-35, jix/src/archive/array.rs:217-240, jix-py/src/archive.rs:105-125)
- Reachability: public Rust API (`Array::read_from_file_mmap`), Python API (`jix.read_array(path, offset=..., mmap=True)`)
- Reported by: concept-alignment

## What goes wrong
`Mmap::read_section` casts `mmap[base_offset + section.offset..]` to `*const BlockLocation2` and
returns `InvalidArchive("data section offset is not properly aligned")` unless the pointer is
aligned. The mapping starts at file offset 0 (page-aligned), so the check passes only when the
locations section's ABSOLUTE file offset is a multiple of `align_of::<BlockLocation2>()` (8 on
64-bit hosts). The writer pads to that alignment relative to the stream position it was writing at,
while the TOC records offsets relative to the archive start, so the format is otherwise
position-independent and the heap reader (`read_from_file_section` / `mmap=False`) reads it at any
offset. As a result, the two readers disagree about whether a file is valid. Valid archives fail
with `mmap=True` in two cases. (a) The archive is moved to a different offset mod 8: embedded after
a header, `cat a.jix b.jix`, written to `BytesIO`/`Cursor` and saved elsewhere, or stored inside an
uncompressed zip. (b) The archive was written by the i686 Linux (gnu and musl) wheels. On those
targets `align_of::<u64>() == 4`: the data layout has no `i64` entry, so LLVM's default `i64:32:64`
applies. The writer then pads only to 4, which contradicts the "8-byte boundary" in the wire-layout
docs (block.rs:107,115). Whenever the pre-padding position is 1-4 mod 8, the section ends up at
4 mod 8, and every non-i686 mmap reader rejects the file: x86_64, aarch64, armv7, ppc64le and
Windows x86 all need 8. No memory-safety impact: the check is real and runs before any typed access.
The error is clean, and `mmap=False` is a workaround.

## Trigger
- Relocation: write `Array::compact_ndarray(&array![10.0f64, 20.0, 30.0, 40.0])` to a
  `Cursor::new(Vec::new())`. Write `k` bytes (k in 1..=7) followed by those bytes to a file. Then
  `read_from_file_mmap(&path, k, len, ..)` fails, while `read_from_file_section(&path, k, len, ..)`
  succeeds. The same happens with `cat a b`, where `a` is a 127-byte archive, when `b` is read at
  offset 127. In Python: `jix.write_array(x, bytes_io)`, write `b"H"*k + blob` to a file, then call
  `jix.read_array(p, offset=k, len=len(blob), mmap=True)`.
- i686: a 1-D f64 array of length 128. On x86_64 the TOC ends at offset 81 (1 mod 8), so padding is 7
  and the locations start at 88. On i686, padding is 3 and they start at 84
  (4 mod 8). The repro builds the exact i686 byte image: the x86_64 bytes minus 4 padding bytes,
  with both TOC offsets reduced by 4. `Section` (16 B) and `BlockLocation2` (24 B) have the same
  size on both targets, so nothing else differs.

## Root cause
- block.rs:171-182: the writer pads to `align_of::<BlockLocation2>()`. That value is
  target-dependent (4 on i686 Linux, 8 elsewhere), and the padding is measured from the absolute
  stream position. The on-disk layout therefore depends on the writer's target and on where the
  writer happened to be positioned.
- block.rs:487-494: the mmap reader needs a host-aligned typed pointer
  (`MmapData<BlockLocation2>`, turned into `&[BlockLocation2]` at storage/block.rs:445). It treats
  "misaligned in this mapping" as "invalid archive", even though the bytes are well-formed and the
  heap reader accepts them.
- `BlockLocation2` (storage/block.rs:28-35) is `#[repr(C)]` with `u64` fields, so its alignment
  follows the target's `u64` ABI alignment.

## Suggested fix
Make the mmap reader independent of the section's alignment. Either give `BlockLocation2`
alignment 1 (store the fields as `[u8; 8]` / `[u8; 4]` with `from_le_bytes` accessors, or use
`repr(C, packed)` with by-value reads) and drop the check, or fall back to copying the small
locations section (12 B per block) into an owned aligned `Vec` when the mapped pointer is
misaligned. Separately, pad with a fixed constant 8 instead of `align_of::<BlockLocation2>()`, so
the layout written on i686 matches the documented wire format.
