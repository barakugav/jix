# F009: RuntimeAlign::new accepts align 0, so safe AlignedBytes constructors build NonNull(null) / Layout with align 0

- Severity: low  Verdict: confirmed  Category: unsound-api
- Location: jix/src/util/aligned_vec/mod.rs:28 (related: jix/src/util/aligned_vec/mod.rs:96-102, jix/src/util/aligned_vec/mod.rs:117-127, jix/src/util/aligned_vec/mod.rs:325-330, jix/src/util/aligned_vec/mod.rs:343-345, jix/src/util/aligned_vec/raw.rs:44-46, jix/src/util/aligned_vec/raw.rs:162-167, jix/src/util/aligned_vec/raw.rs:192-199, jix/src/util/aligned_vec/raw.rs:245-249, jix/src/util/aligned_vec/mod.rs:46-48)
- Reachability: crate-internal (`AlignedBytes` is re-exported `pub(crate)` at jix/src/util/mod.rs:2; no current caller passes 0)
- Reported by: util-memory-alloc-pool

## What goes wrong
`RuntimeAlign::new` rejects only non-zero values that are not powers of two (`align != 0 &&
!align.is_power_of_two()`). It lets `0` through. The safe `AlignedBytes` constructors
`new_exact`, `with_capacity_exact`, `from_slice` and `from_iter` validate their alignment only
through `RuntimeAlign::new`, and then call `RawAlignedBytes` unsafe functions whose documented
precondition is "align is a power of two" (raw.rs:39-42, 48-51). With `align = 0`:
- `new_exact(0)`, and `with_capacity_exact(0, 0)` (which takes the same path), compute
  `null_mut().wrapping_add(0)`, which is null, and pass it to `NonNull::new_unchecked`.
- `with_capacity_exact(0, n>0)`, `from_slice(0, ..)` and `from_iter(0, ..)` reach
  `is_valid_alloc`. There `align - 1` underflows, and the only guard is a `debug_assert`. In
  release the subtraction wraps and the check passes. Then `Layout::from_size_align_unchecked(n, 0)`
  runs, followed by `alloc`.

Both are UB from safe functions. The doc comment at mod.rs:46-48 says that 0 "uses the minimum
alignment". That text is stale, copied from the aligned-vec crate.

## Trigger
Crate-internal only: `AlignedBytes::new_exact(0)`, `AlignedBytes::with_capacity_exact(0, 16)`
or `AlignedBytes::from_slice(0, &[1])`.

No production caller does this today. All live callers pass an `Alignment`-derived value. The
`Alignment` type is a power of two in 1..=32768 (dtype.rs:65-95). The callers are
codec/mod.rs:126, array.rs:1346-1348, storage/block.rs:649 and util/test_util.rs:31,813. The
other path is `max(_, CACHE_LINE_SIZE)` in `new_padded` / `with_capacity_padded`, and in
buf_pool.rs:45 the alignment is at least `CACHE_LINE_SIZE`. So this is a latent hazard: a
future caller that passes, say, an unvalidated or defaulted `0` alignment gets UB rather than a
panic.

## Root cause
`RuntimeAlign::new` (mod.rs:27-36) keeps aligned-vec's "0 means minimum alignment" exemption.
But it no longer maps 0 to any minimum: it stores 0 as is. Everything downstream (raw.rs:45,
raw.rs:248, the `Layout::from_size_align_unchecked` calls at raw.rs:25, 198, 212, 232, 237)
assumes `align >= 1`, and the only enforcement is a `debug_assert!` at raw.rs:246.

## Suggested fix
Make `RuntimeAlign::new` reject 0, by panicking on `!align.is_power_of_two()`, which is false
for 0. Alternatively, map 0 to 1. Update the stale doc comment at mod.rs:46-48. Optionally,
make `is_valid_alloc` use a real `assert!`, or take a validated `RuntimeAlign` / `Alignment`
instead of a bare `usize`.
