# F001: Short zstd block decode is only debug_asserted; release reads return unwritten (uninit or stale) destination bytes as data

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/storage/block.rs:193 (related: jix/src/codec/mod.rs:293-319, jix/src/storage/compact.rs:324-327, jix/src/storage/compact.rs:396-401, jix/src/codec/mod.rs:276-279, jix/src/array.rs:767-800)
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file_section` + `to_ndarray*`), Python API (`jix.read_array(...)` + `.numpy()`)
- Reported by: util-memory-alloc-pool

## What goes wrong
`BlockTable::read_block` checks the number of bytes the decoder produced only with
`debug_assert_eq!(nbytes, b_size_bytes)`. `Decoder::decode` returns whatever zstd reports, and
zstd accepts a frame that holds fewer bytes than the block (for example a short frame followed by
a skippable frame, which keeps every offset and length in the archive valid). In release builds
(the shipped wheels) the read succeeds and the unwritten bytes `[nbytes, block_size)` of the
destination are returned as array data. Depending on the path, that destination is:
1. `ndarray::Array::uninit` memory, which `to_ndarray_sub` then `assume_init`s (array.rs:800). This is
   UB and leaks freed heap contents.
2. The pooled `tmp_buf` in `read_data_slow`. This is stale data from an earlier read on the same
   `ReadContext`, which can belong to a different array.
3. The pooled decompression scratch used when filters are present, whose stale or uninitialized
   tail then passes through the filter decode.

No other check catches it. `ArchiveValidation::Strict` checks only that block locations are in
bounds (archive/block.rs:392-410), and the archive has no checksum.

## Trigger
Write a `u8` array with `filters=[]` and `block_shape=[64]` using `write_to`. In the archive
bytes, replace one block's zstd frame in place with a frame of the same total length:

`28 B5 2F FD | 20 | 08 | 41 00 00 | EE x8` (single-segment frame, one raw block of 8 bytes),
followed by a skippable frame `50 2A 4D 18 | u32 pad | 00 x pad`.

Then read it back with `read_from_reader(..., ArchiveValidation::Strict)` and `.into_typed::<u8>()`,
and read it in one of three ways:
- `to_ndarray()` on a 64-element array (fast path, decodes straight into the uninit ndarray).
- `to_ndarray_sub(&[64..127], &ctx)` on a 128-element array, after `ctx` was used to read another
  array (`read_data_slow`, stale pool).
- The same as the second, but with `Filter::ByteShuffle` and an aligned `[0..64]` read (stale
  decompression scratch).

## Repro
`jix/tests/repro_2026_10_21_pilot__f001.rs` (3 tests; each test asserts the correct behavior, an
`Err`, so it fails while the bug is present).

```
cargo test --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_21_pilot__f001 -- --nocapture --test-threads=1
```
Debug: all 3 tests panic at `src/storage/block.rs:193:9`, `assertion left == right failed, left: 8, right: 64`.

```
cargo test --release --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_21_pilot__f001 -- --nocapture --test-threads=1
```
Release: all 3 reads return `Ok`:
- `f001_uninit_ndarray_tail`: `[238 x8, 0 x8, 119 x48]`. The `119 = 0x77` bytes come from a
  `vec![0x77u8; 64]` that the test freed just before the read. Freed heap memory came back as
  array data through `assume_init`.
- `f001_stale_pool_bytes_from_other_array`: `[238 x8, 90 x55]`. The `90 = 0x5A` bytes are the
  contents of a different array (`[0x5A; 64]`) read earlier on the same `ReadContext`.
- `f001_byteshuffle_stale_pool_tail`: `[238 x8, 90 x56]`. Same leak through the filter
  decompression scratch.

Python: `bug-hunt/runs/2026-10-21-pilot/repros/F001.py` (`.venv/bin/python`).
`jix.read_array(io.BytesIO(corrupt))` accepts the file with the default strict validation. `.numpy()`
then raises `PanicException: assertion left == right failed, left: 8, right: 64` from
`jix/src/storage/block.rs:193:9` in the debug build installed in `.venv`. Release wheels compile
the assert out and take the same path as the Rust release run above.

Miri was not used. Under `cfg(miri)` the decode is `decompress_out.copy_from_slice(src)`
(codec/mod.rs:308-311), which cannot produce a short decode, and the frame lookup uses zstd FFI. The
release run, which returns freed heap bytes, is the direct evidence.

## Root cause
`read_block` (storage/block.rs:192-193) treats "decoded length == block size" as an internal
invariant (`debug_assert_eq!`). It actually depends on untrusted file contents. Every destination
it decodes into relies on the decode writing all bytes:
- the uninit ndarray in the compact.rs:324-327 fast path, then array.rs:800 `assume_init`;
- the pooled `tmp_buf` at compact.rs:396-401 (pool contents are uninit or stale by contract,
  buf_pool.rs:34-39);
- the pooled filter scratch at codec/mod.rs:276-279, which the filter decode (codec/mod.rs:314-317)
  reads before `decode` even returns `nbytes`.

## Suggested fix
Make the check a real error. In `Decoder::decode`, right after `decompress_to_buffer` and before
the filters run, return `CodecError`/`InvalidArchive` when `nbytes != decompress_out.len()`. Turn
the `debug_assert_eq!` in `read_block` into an `ensure!` as defense in depth. Optionally also reject
frames whose header content size differs from the block size, or that are followed by trailing
(skippable) frames.
