# F006: K28 fix is incomplete: f64 -> f16 still mis-rounds on every shipped target except macOS arm64, now ~8x as often as before the fix

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/cast.rs:55 (related: jix/Cargo.toml:28, jix/src/ops/cast.rs:806-816,
  jix/src/ops/cast.rs:578-581, jix/src/ops/cast.rs:286-296, jix-py/src/ops/common/operand.rs:286,
  jix-py/src/ops/common/operand.rs:428, half-2.7.1/src/binary16/arch.rs:14-81, 99-111, 617-679)
- Reachability: public Rust API (`Array::cast::<f16>`, `<f64 as Cast<f16>>::cast`,
  `Complex<f64> -> Complex<f16>`) and Python API (`jix.cast`, `jix.asarray(dtype=float16)`,
  Python float scalars combined with float16 arrays)
- Reported by: elementwise-ops-bitwise-cast

## What goes wrong
K28 (f64 -> f16 double rounding through f32) was marked fixed in c009869 (#87) by switching the
scalar cast to `half::f16::from_f64` (cast.rs:55). In the build jix actually ships, `from_f64` is
not correctly rounded either. jix pulls in `half` with `default-features = false`
(jix/Cargo.toml:28), and nothing in the jix / jix-py graph enables half's `std` feature
(`cargo tree -e features -i half` lists only `num-traits`). Without `std`, half's `convert_fn!`
only uses hardware when the target enables `f16c` / `fp16` at compile time. Among the wheel
targets, only aarch64-apple-darwin does (`fp16`). Every other target (x86_64 and x86 Linux,
Windows and macOS, aarch64 Linux and Windows, armv7, ppc64le) runs `f64_to_f16_fallback`. That
fallback drops the low 32 mantissa bits before rounding, so any f64 within about 2^-32 (relative)
of an f16 halfway point is rounded as an exact tie (ties-to-even), which is 1 ulp off when the
value is above the tie and the even neighbour is the lower one. That happens about 5 times per
10,000 uniform random values, about 8 times as often as the pre-fix f32 double rounding. The
original K28 trigger still fails on x86_64 Linux, the only platform CI tests on.

## Trigger
- `x = 1 + 2^-11 + 2^-40` (just above the midpoint of 1.0 and 1 + 2^-10):
  `Array::compact_ndarray(&array![x, -x])?.cast::<f16>()`, `<f64 as Cast<f16>>::cast(x)`,
  `<Complex<f64> as Cast<Complex<f16>>>::cast(Complex { re: x, im: -x })`;
  Python `jix.cast(np.array([x]), np.float16)`, `jix.asarray(np.array([x]), dtype=np.float16)`,
  `jix.add(np.zeros(2, np.float16), x)`.
  Expected 1.0009765625, got 1.0.
- Subnormal branch: `2^-25 + 2^-60`. Expected 2^-24 (5.96e-08, the smallest subnormal), got 0.0.
- Random: uniform f64 in +-200, e.g. -33.9531448090642: expected -33.96875, got -33.9375.

## Root cause
- cast.rs:55 delegates to `half::f16::from_f64` on the assumption that it rounds once. In
  half-2.7.1 `f64_to_f16` (arch.rs:99-111) is correctly rounded only on the aarch64 `fp16` path
  (`fcvt h, d`). Its x86 `f16c` path does `f as f32` first (the same double rounding as K28), and
  the software fallback (arch.rs:617-679) does `let x = (val >> 32) as u32`, so the round/sticky
  test `(man & round_bit) != 0 && (man & (3 * round_bit - 1)) != 0` never sees the low 32 bits.
  This happens in both the normal branch and the subnormal branch.
- With `default-features = false` (jix/Cargo.toml:28) half has no `std`, so `convert_fn!`
  (arch.rs:14-81) cannot detect features at run time and uses the fallback unless the target
  enables `f16c` / `fp16` at compile time. `rustc --print cfg` shows only `neon` for
  aarch64-unknown-linux-gnu and aarch64-pc-windows-msvc, and no `f16c` for x86_64 Linux or macOS.
  The release workflow (.github/workflows/release.yaml) passes no target-cpu flags. armv7 and
  ppc64le have no hardware path at all. So enabling `std` would not fix this: x86 with F16C
  would go back to K28's double rounding, and armv7 / ppc64le would still use the fallback.
- Why the tests miss it: the only correctness test, `cast_f64_to_f16_rounds_once`
  (cast.rs:806-816), is `cfg(target_arch = "aarch64")`, so it never runs in CI (x86_64). Its
  comment says that on x86 `from_f64` "also goes through f32", which is wrong for this build. The
  test would also fail on aarch64 Linux. The property-test oracle `CastTo<f16> for f64`
  (cast.rs:578-581) calls the same `f16::from_f64`, so it agrees with the bug.
- The same path is used by `Complex<f64> -> Complex<f16>` (cast.rs:286-296, per component), by
  jix-py `Scalar::Float` with f16 precision (operand.rs:286, `f16::from_f64` directly), and by
  `Scalar::cast` to F16 (operand.rs:428, through core `Cast<f16>`).

## Suggested fix
Do not rely on `half::f16::from_f64`. Implement a correctly rounded f64 -> f16 in jix. One way:
round the full 64-bit pattern to 11 significant bits with an integer sticky bit over all 52
mantissa bits, handling the subnormal and overflow branches. Another way: go through f32 with
round-to-odd (`y = x as f32`; if `y as f64 != x`, step `y` toward zero by one ulp if needed and
set its low mantissa bit), then `f16::from_f32(y)`. 24 >= 11 + 2 bits makes the second rounding
exact, and `from_f32` is correct on both the F16C and fallback paths. Make
`cast_f64_to_f16_rounds_once` unconditional, and give the `CastTo<f16> for f64` oracle an
independent reference such as the one in the repro.
