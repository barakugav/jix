# F009: Complex mean divides the sum by Complex(n, 0) with num-complex's textbook division, so sum * n overflows: mean([1.7e308+0j, 0j]) = inf+0j, mean of 1e6 copies of 1e302+1e302j = inf+infj

- Severity: low  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/reduction.rs:1766 (related: jix/src/ops/reduction.rs:1785-1787 (the
  `impl_mean!` lines for `Complex<f32>` / `Complex<f64>`, finalize type `Complex<f64>`);
  jix/src/ops/reduction.rs:2646 (`MeanKernel::finalize_state`); num-complex 0.4 src/lib.rs:812-823
  (the `Div` impl it calls); jix/src/ops/op2.rs:787 (K27, the same formula in the `Div` op, a
  different call site); jix/src/ops/reduction.rs:4202 (the unit test's reference mean uses the same
  formula, with `op_safe_strategy` values that never reach the range))
- Reachability: Python API (`jix.mean` on complex128 numpy or compact arrays) and public Rust API
  (`Array::mean` / `ops::Mean` on `Complex<f64>`)
- Reported by: reduction-op-kernels

## What goes wrong
`Mean::finalize` casts both the running sum and the item count to `Complex<f64>` and evaluates
`state / nitems` with num-complex's `Div`, i.e. `re = (a*n + b*0) / (n*n)`,
`im = (b*n - a*0) / (n*n)`. The products `a*n` and `b*n` overflow to inf whenever a sum component
exceeds `f64::MAX / n`, although the mean (`a / n`) is finite and the sum itself did not overflow.
The result is silently `inf` (no status, no warning), while NumPy (Smith's division) and jix's own
real `f64` mean (a direct `sum / n`) return the finite mean. The bad window is
`MAX / n^2 < |mean component| < MAX / n`, so it widens as `n` grows (n = 1e6: means above ~1.8e296),
but it always needs values within a factor `n` of overflowing the sum. Only complex128 is affected:
complex64 accumulates in `Complex<f64>`, which never gets near `f64::MAX`.

## Trigger
```python
jix.mean(np.array([1.7e308 + 0j, 0j]))                  # inf+0j, numpy 8.5e+307+0j
jix.mean(np.array([1.7e308 - 1.7e308j, 0j]))            # inf-infj, numpy 8.5e+307-8.5e+307j
jix.mean(np.full(1_000_000, 1e302 + 1e302j))            # inf+infj, numpy 1e+302+1e+302j
jix.mean(np.array([1.7e308, 0.0]))                      # control: 8.5e+307 (real path is fine)
```
Rust: `Array::compact_ndarray(&array![Complex::new(1.7e308, -1.7e308), Complex::new(0.0, 0.0)])?.mean(0)`
gives `inf-infi`; `Broadcast::new_array(compact([1e302+1e302i]), &[1_000_000])?.mean(0)` gives
`inf+infi`.

## Root cause
reduction.rs:1764-1766 generalizes the real-valued `sum / n` to complex by casting `n` into the
finalize type, so for `Complex<f64>` the division is num-complex's unscaled
`(a + bi)(c - di) / (c^2 + d^2)` (num-complex lib.rs:812-823). That formula forms `a*c` before
dividing, which needs headroom the sum may not have. The divisor is always real, so complex
division is not needed at all. This is the same num-complex formula as K27 (open, op2.rs:787), but
reached directly through `std::ops::Div` on `num_complex::Complex`, not through jix's
`scalar::Div` op, so fixing K27 in op2.rs would not fix this. The unit-test reference
(reduction.rs:4202) uses the identical formula and draws only moderate values, so it cannot catch
it. Not intended: no doc or context entry describes it (the context doc lists it as an
unverified suspicion), and the Rust and Python docs promise NumPy-matching mean semantics.

## Suggested fix
Divide each component by the real count instead of dividing by `Complex(n, 0)`: for the complex
`impl_mean!` arms finalize as `Complex::new(state.re / n, state.im / n)` with `n = nitems as f64`
(e.g. a small `DivByCount` helper trait, or a separate macro arm for complex). This is exact
(one rounding per component, like the real path) and never overflows when the mean is finite.
Side effect to decide on: per-component division turns `mean([inf+1j])` into `inf+1j` instead of
the current (and NumPy's) `inf+nanj`; pin the chosen behavior with a test. Update the test
reference at reduction.rs:4202 the same way.
