# F003: Rust range -> SliceItem conversion: an inclusive end of -1 (`..=-1`, `0..=-1`) silently gives an empty slice and `-k..=-1` errors/panics; u64/usize bounds above i64::MAX wrap to end-relative indices

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/shape_ops/slice.rs:324 (`Bound::Included(&e) => Some(e as i64 + 1)` in `impl_from_range!`) (related: jix/src/ops/shape_ops/slice.rs:319, jix/src/ops/shape_ops/slice.rs:325, jix/src/ops/shape_ops/slice.rs:367-385 `DimSlice::resolve`, jix/src/ops/shape_ops/mod.rs:73 `Array::slice` unwrap)
- Reachability: public Rust API (`Array::slice`, `Slice::new` / `Slice::new_array` with any `RangeInclusive` / `RangeToInclusive` / range of `u64` / `usize`). Python is not affected: jix-py builds `SliceItem`s directly from already-resolved absolute bounds (jix-py/src/ops/shape_ops.rs:312-373).
- Reported by: shape-ops-slice-reshape (also listed as an unverified suspicion in bug-hunt/context/shape-ops.md)

## What goes wrong
`SliceItem` uses Python-style end-relative negatives, and the `Slice` docs advertise both
inclusive ranges (`1..=3`) and negative range literals. The `From<range>` conversion turns an
inclusive end `e` into the exclusive end `e + 1`, which is wrong for `e == -1`: "through the last
element" becomes the absolute end 0. So `..=-1` and `0..=-1` silently select nothing (shape `[0]`),
and `-k..=-1` resolves to `start = len-k, end = 0`, which `Slice::new` rejects ("slice start 2 must
be <= end 0") and `Array::slice` turns into a panic. Other negative inclusive ends (`..=-2`) work.
Separately, every bound is cast with a plain `as i64`, so a `u64`/`usize` bound >= 2^63 becomes
negative and is silently taken as end-relative: `0..u64::MAX` is accepted as `0..-1` (drops the
last element) and `..=usize::MAX` becomes `..0` (empty), where an out-of-bounds error is expected
(dims are capped at i64::MAX since #87, so such a bound is always out of range). `..=i64::MAX`
overflows the `+ 1` inside the `From` impl (debug panic; release wraps to i64::MIN, then errors).

## Trigger
```rust
let a = Array::compact_ndarray(&array![0i32, 1, 2, 3, 4])?;
Slice::new_array(a, (..=-1i64,).into())      // Ok, shape [0]        (expected [0,1,2,3,4])
Slice::new_array(a, (0i64..=-1,).into())     // Ok, shape [0]        (expected [0,1,2,3,4])
Slice::new_array(a, (-3i64..=-1,).into())    // Err "slice start 2 must be <= end 0" (expected [2,3,4])
a.slice((-3i32..=-1,))                       // panics (same Err unwrapped)
Slice::new_array(a, (0u64..u64::MAX,).into())// Ok, shape [4] = [0,1,2,3] (expected out-of-bounds Err)
Slice::new_array(a, (..=usize::MAX,).into()) // Ok, shape [0]        (expected out-of-bounds Err)
SliceItem::from(..=i64::MAX)                 // debug panic "attempt to add with overflow"
```

## Root cause
`impl_from_range!` (jix/src/ops/shape_ops/slice.rs:314-330) maps `Bound::Included(&e)` to
`Some(e as i64 + 1)`. For a non-negative `e` this is the right exclusive end, but for negative
(end-relative) `e` the exclusive end of "through index -1" is "past the end" (`None`), not the
absolute index 0 that `DimSlice::resolve` (slice.rs:367-372) makes of `0`. The `+ 1` is also
unchecked. Independently, `s as i64` / `e as i64` (slice.rs:319, 324, 325) reinterpret `u64`/`usize`
values >= 2^63 as negative numbers, which `resolve` then normalizes as end-relative instead of
rejecting. ndarray, which jix depends on, special-cases exactly this: its
`From<RangeInclusive<_>> for Slice` maps an inclusive end of -1 to `end: None`
(ndarray-0.17.2/src/slice.rs:200-209). No test in slice.rs covers a negative inclusive end.

## Suggested fix
In `impl_from_range!`, map `Bound::Included(&e)` to `None` when `e == -1` (signed types),
otherwise `e + 1` with a checked add. Convert unsigned bounds with `i64::try_from` and, since
`From` cannot fail, either saturate to `i64::MAX` (which `resolve` then rejects as out of bounds) or
move the conversion into a fallible path. Add tests for `..=-1`, `-k..=-1` and `0u64..u64::MAX`.
