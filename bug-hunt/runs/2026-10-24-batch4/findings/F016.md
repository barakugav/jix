# F016: to_ndarray_sub sizes its ndarray with a per-dim `as usize` and bounds the region only on 32-bit, via the element product (0 for an empty region): empty regions with huge dims get a truncated shape on 32-bit and panic inside ndarray on 64-bit

- Severity: low  Verdict: confirmed  Category: wrong-result
- Location: jix/src/array.rs:774 (related: jix/src/array.rs:771 `check_region_size` call,
  jix/src/error.rs:274-287 `check_region_size` (a no-op on 64-bit, checks the element product on
  32-bit), jix/src/array.rs:786 and :795 `ndarray::Array::uninit`, jix/src/error.rs:186
  `check_shape_overflow` (accepts these shapes), jix/src/util/mod.rs:219 `try_shape_product`,
  jix/src/array.rs:1130 `to_plain`, ndarray-0.17.2 impl_constructors.rs:602 (the panic))
- Reachability: public Rust API (`Array::to_ndarray`, `to_ndarray_sub`, `to_plain`). Python is
  not affected: `Array.numpy()` allocates through numpy (jix-py/src/array.rs:535-557), and on
  x86_64 the same `[0, 2^62, 3]` array raises `ValueError: array is too big` there.
- Reported by: storage-core-array-read-paths

## What goes wrong
`to_ndarray_sub` (behind `to_ndarray` and `to_plain`) checks the region with
`check_region_size(index, itemsize)` (array.rs:771). On 64-bit that check does nothing. On 32-bit
it bounds `prod(extents) * itemsize`, which is 0 for any empty region. Then each extent is cast
with `(end - start) as usize` (array.rs:774) and handed to `ndarray::Array::uninit`. For an empty
region:
- On 32-bit, an extent >= 2^32 truncates. The call returns `Ok` with the wrong shape, for example
  `[0, 5]` for `[0, 4294967301]` or `[0, 0, 3]` for `[0, 2^62, 3]`. `to_plain` then builds a Plain
  array whose `shape()` differs from its source.
- On 64-bit, when the product of the non-zero extents exceeds `isize::MAX`, ndarray panics:
  `Shape too large, product of non-zero axis lengths overflows isize`.

The read itself touches no memory because the region is empty, so this is a wrong shape or a
panic, not corruption. The K16 fix (c009869) added `check_region_size` here, but that check does
not cover empty regions. A related secondary case: on 64-bit, a non-empty region over
`isize::MAX` bytes panics with `capacity overflow` in the `Vec` allocation, while 32-bit returns
`Err(InvalidShapeOperation)` from the same check.

## Trigger
All shapes below pass `check_shape_overflow`. Each dim is at most i64::MAX, and the byte product of
the non-zero dims fits in a u64.
```rust
// i686: Ok, shape [0, 5]
Array::compact_ndarray(&array![[7u8]])?.broadcast(&[0, (1u64 << 32) + 5]).to_ndarray::<IxDyn>();
// x86_64: panic in ndarray; i686: Ok, shape [0, 0, 3]
Array::compact_ndarray(&array![[[7u8]]])?.broadcast(&[0, 1u64 << 62, 3]).to_ndarray::<IxDyn>();
// The array does not have to be empty, only the region: [1, 2^62, 3] read at [0..0, 0..2^62, 0..3]
let a = Array::compact_ndarray(&array![[[7u8]]])?.broadcast(&[1, 1u64 << 62, 3]);
a.to_ndarray_sub::<IxDyn>(&[0..0, 0..1 << 62, 0..3], &a.read_ctx());
// secondary, x86_64 only: panic "capacity overflow" (i686 returns Err)
Array::compact_ndarray(&array![7i32])?.broadcast(&[1u64 << 61]).to_ndarray::<IxDyn>();
```

## Root cause
- array.rs:774: `out_shape[dim] = (index[dim].end - index[dim].start) as usize` is an unchecked
  `u64 -> usize` per dim.
- error.rs:274-287: `check_region_size` only runs on 32-bit, and it compares the *element* product
  `prod(extents) * itemsize` with `isize::MAX`. That product is 0 whenever one extent is 0, so it
  proves nothing about the other extents. ndarray needs more than that: every extent must fit in a
  `usize`, the product of the non-zero extents must be at most `isize::MAX` (checked in
  `Array::uninit`), and the allocation in bytes must be at most `isize::MAX` (`Vec::with_capacity`).
- `check_shape_overflow` (error.rs:186) only proves that the non-zero byte product fits in a u64,
  so shapes valid in jix can still be unrepresentable as an ndarray.
- `to_ndarray_slice` and `to_ndarray_buf` are not affected. They use the exact u64 length check and
  return early for empty regions.

## Suggested fix
In `to_ndarray_sub`, on all targets, before calling `Array::uninit`: convert each extent with
`usize::try_from` and check that `prod(max(extent, 1)) * itemsize <= isize::MAX`. This is the
"safe" product that `try_shape_product` already computes internally. Return
`InvalidShapeOperation` otherwise. That one check covers the 32-bit truncation, the 64-bit ndarray
panic and the 64-bit `capacity overflow`. Document the error under `# Errors` for `to_ndarray` /
`to_ndarray_sub`.
