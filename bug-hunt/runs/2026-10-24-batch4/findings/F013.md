# F013: Slice plain fast path computes inner_stride * step unchecked: a step larger than the dim (output length 1) overflows - debug panic, release returns a wrapped stride on the extent-1 dim

- Severity: low  Verdict: confirmed  Category: overflow
- Location: jix/src/ops/shape_ops/slice.rs:161 (related: slice.rs:148-163 fast-path block,
  storage/plain.rs:145 and storage/scalar.rs:70 set PLAIN_READ, storage/core_trait.rs:139 default
  read_as_elementwise_pipeline pulls through this path, array.rs:978 to_ndarray_buf small-read path)
- Reachability: public Rust API (Python cannot reach it: jix-py/src/ops/shape_ops.rs:340 rejects any
  step other than 1)
- Reported by: shape-ops-slice-reshape

## What goes wrong
In pull mode over an inner with the PLAIN_READ flag (Plain, Scalar, InsertDim/RemoveDim over them), Slice
reads the inner bounding box and turns it into a strided view by multiplying each inner stride by the
step: `inner.strides()[dim] * self.slice[dim].step as usize`. `DimSlice::resolve` accepts any step >= 1,
so a step larger than the dim is valid and gives an output dim of length 1, but then stride * step can
exceed usize::MAX. Debug builds (tests, dev builds) panic with "attempt to multiply with overflow" on a
valid request. Release builds wrap to a meaningless stride (observed 18446744073709551612). The values are
still correct, because that dim has extent 1 and no consumer steps through it. This is the same defect
class as K36 (Repeat, fixed in c009869), at a site that fix did not cover.

## Trigger
- `Array::plain_ndarray(array![0i32,1,2,3,4])?.slice((SliceItem::new(Some(3), None, i64::MAX),))`, then
  either `.to_ndarray_buf(&[0..1], &ctx, None)` or `.neg().to_ndarray()` (an elementwise op pulls its
  input).
- The product scales with the inner stride, so wider rows need smaller steps. For a `[5, 1000]` f32 Plain
  sliced with `SliceItem::new(Some(1), None, step)` on dim 0, the threshold is step > ~4.6e15 on 64-bit
  and step > ~1.07e6 on 32-bit (i686/armv7 wheels). For example, step = 2_000_000 panics on i686.
- The general path (push mode, e.g. a plain `s.to_ndarray()` without a pipeline op) never multiplies
  strides and is not affected.

## Root cause
slice.rs:160-162 assumes stride * step fits in usize. That holds only when the output dim has length >= 2:
then step <= dim_len - 1, so stride * step <= the inner's memory span. When the output length is 1, the step
is unbounded (up to i64::MAX), and the product is computed even though that stride is never used.
`step as usize` also truncates on 32-bit, but that is harmless because only extent-1 or stride-0 dims can
see a step that large.

## Suggested fix
Use stride 0 (or the inner stride) for any output dim of extent 1, the same fix K36 applied to Repeat,
e.g. `if out_shape[dim] == 1 { 0 } else { inner.strides()[dim] * step as usize }`. Alternatively use
`wrapping_mul` or `checked_mul`, though stride 0 also keeps the returned buffer's strides meaningful.
