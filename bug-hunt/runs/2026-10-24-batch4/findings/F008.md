# F008: ReductionOp::new adds 4 to the reduced element count unchecked; a valid lazy shape with > 2^64 - 5 reduced elements panics in debug builds instead of returning Ok

- Severity: low  Verdict: confirmed  Category: overflow
- Location: jix/src/ops/reduction.rs:177 (related: jix/src/ops/reduction.rs:173-176, jix/src/error.rs:186-201)
- Reachability: public Rust API (`Sum/Max/Min/Product/Mean/Variance/StandardDeviation/All/Any::new[_array]`, `Reduce::new_array`, and the `Array::sum/...` methods) and Python API (`jix.sum`, `jix.max`, `jix.all`, ... with `dim=None` or a tuple of 2+ dims)
- Reported by: reduction-op-kernels

## What goes wrong
`ReductionOp::new` computes the output spec's cost heuristic as
`(spec.element_cost() as f64 * (reduced_prod + 4) as f64) as f32`, where `reduced_prod` is the
`u64` product of the reduced extents. `check_shape_overflow` accepts any shape whose dims are each
<= i64::MAX and whose byte size fits in u64, so for a 1-byte dtype (u8, i8, bool8) a lazily
broadcast input can have up to 2^64 - 1 elements, and reducing 2+ dims can make `reduced_prod`
exceed u64::MAX - 4. The `+ 4` then overflows: in debug builds (including downstream crates'
`cargo test` and the `maturin develop` Python extension) the constructor panics with
"attempt to add with overflow" instead of returning its `Result`. In release builds the sum wraps to
a tiny value and only skews `element_cost`, a pure read-size / layout heuristic; the constructed op
is otherwise correct, so shipped wheels are unaffected. Single-dim reductions cannot trigger it
(each dim <= i64::MAX, so `reduced_prod + 4` < 2^63 + 4).

## Trigger
Rust: `Broadcast::new_array(Array::compact_ndarray(&array![[1u8]])?, &[i64::MAX as u64, 2])?`
(2^64 - 2 one-byte elements), then `Sum::new_array(a, (0, 1))` (same for `Max`, and `All` over a
`bool8` input).
Python: `jix.sum(jix.broadcast(jix.asarray(np.ones((1, 1), np.uint8)), (2**63 - 1, 2)))`, also
`jix.max(...)` and `jix.all(...)` over a `np.bool_` input.

  each after `panicked at .../jix/src/ops/reduction.rs:177:58`.

Both assert the correct behavior (an Ok 0-d lazy result) and pass once fixed.

## Root cause
reduction.rs:173-177 assumes the reduced element count is small enough that adding a constant is
safe. The product itself cannot overflow (it is a sub-product of a shape already validated by
`check_shape_overflow` with `try_shape_product`, which ignores zeros only for the overflow check),
but nothing bounds it away from u64::MAX for 1-byte dtypes.

## Suggested fix
Do the addition in floating point: `(reduced_prod as f64 + 4.0)`, or use
`reduced_prod.saturating_add(4)`. Either keeps the heuristic and never panics.
