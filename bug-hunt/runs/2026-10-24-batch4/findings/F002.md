# F002: Welford variance goes negative/NaN when |x - mean| overflows f64; std trips debug_assert (panic) or silently returns NaN

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/reduction.rs:1871-1874 (related: jix/src/ops/reduction.rs:1966-1987 `welford_update_bulk`, jix/src/ops/reduction.rs:1901-1925 `merge_states`, jix/src/ops/reduction.rs:2847-2853 `StandardDeviationKernel::finalize_state`, jix/src/ops/op1.rs:592-598 `Sqrt`)
- Reachability: public Rust API (`Array::var` / `Array::std`) and Python API (`jix.var` / `jix.std`)
- Reported by: reduction-op-kernels

## What goes wrong
For finite f64 or complex128 inputs whose spread exceeds f64::MAX, the Welford update's
`delta = x - mean` overflows to +-inf. The running mean becomes +-inf, `delta2 = x - mean` becomes the
opposite infinity, and `m2 += delta * delta2` adds `-inf`. The result is a negative variance
(`-inf`), or `NaN` when later terms add `+inf`. NumPy returns `+inf` with an overflow warning.
`std` then takes `sqrt` of that negative variance. In debug builds this fails
`debug_assert!(status.is_ok()); // variance is never negative`, a panic (`PanicException` in the
Python dev build). In release builds `std` silently returns `NaN`, with no FloatingPointError or
warning, because the local status is dropped.

## Trigger
- `Array::compact_ndarray(&array![1e308f64, -1e308]).var(0, 0.0)` gives `-inf`; `.std(0, 0.0)` panics in debug and gives `NaN` in release.
- `[1e308, -1e308, 0.0]` gives `NaN`; `[1e308]*40 + [-1e308]*40` gives `NaN`.
- complex128 `[1e308j, -1e308j]` gives `-inf`.
- `[[1.7e308, -1.7e308]]*3` reduced over dim 1 gives `[-inf, -inf, -inf]`.
- Python: `jix.var(jix.asarray(np.array([1e308, -1e308])))` gives `-inf`; `jix.std(...)` raises
  `pyo3_runtime.PanicException: assertion failed: status.is_ok()`.

Only f64 and complex inputs can trigger it, because every other dtype accumulates in f64 from a
narrower range.

## Root cause
The Welford recurrence (reduction.rs:1871-1874; the same formula is vectorized in
`welford_update_bulk`, 1966-1987) assumes `delta` and `delta2` have the same sign, so
`delta * delta2 >= 0`. That holds in exact arithmetic. Once `x - mean` overflows, the mean jumps to
+-inf and `delta2` flips sign, so the product is `-inf`. The Chan merge (1901-1925) uses
`delta * delta`, which stays non-negative. It gives `+inf` or `NaN` for the same data, so the
result also depends on which fold path runs (the hunter saw 64 alternating values give `+inf`).
`StandardDeviationKernel::finalize_state` (2847-2853) relies on "variance is never negative".
It enforces this only with a `debug_assert` and never passes the Sqrt status to
`ctx.check_op_status`.

## Suggested fix
Keep m2 non-negative when the deviation overflows. Options:
- compute the m2 term as `delta * delta * (n-1)/n`, which is the same in exact arithmetic and never negative;
- or clamp: if `delta` is not finite but `x` and the old mean are, set `m2 = +inf`;
- or scale the inputs, e.g. by 0.5, and the variance by 4, when |x| is near f64::MAX.

In `std`, also clamp `var` with `max(var, 0.0)` (keeping NaN) before `sqrt`, or replace the
`debug_assert` with a status that is propagated, so a negative variance can never panic.
