# F005: `ElementType` is a safe, unsealed trait, but Plain/BlockTable/SubDtype/Transmute take their dtype from `ET::dtype()` without checking it: a user impl gives a heap OOB read (Plain, SubDtype) and `assert_unchecked(false)` (BlockTable::decoder_config) from safe code

- Severity: medium  Verdict: confirmed  Category: unsound-api
- Location: jix/src/element_type.rs:16 (`pub trait ElementType`: safe, unsealed, no `# Safety` section). Related: jix/src/storage/plain.rs:504 (`element_type_change` stores `NewET::from_dtype(..)` without comparing its `dtype()`), jix/src/storage/plain.rs:446-476 (read_data sizes `from_raw_parts` / `copy_from` with `self.dtype()` = `element_type.dtype()`), jix/src/storage/block.rs:133 (`BlockTable::new`) and :232 (`BlockTable::element_type_change`), jix/src/storage/block.rs:223 (`assert_unchecked_eq!(element_type.dtype(), decoder_config.dtype)`), jix/src/archive/block.rs:84 (`write_content` -> `decoder_config()`), jix/src/ops/sub_dtype.rs:95 and :192 (`SubDtype::new` / `element_type_change`), jix/src/ops/sub_dtype.rs:154-166 (field copy sized by `dst_type.dtype()`), jix/src/ops/transmute.rs:148, jix/src/array.rs:1693 (safe `Array::into_type`), jix/src/array.rs:568-571 (`Array::dtype()` returns `ET::DTYPE` when it is `Some`)
- Reachability: public Rust API. It needs a user `impl ElementType` whose `dtype()` differs from the dtype it was built from. No `unsafe` is needed. Python cannot implement `ElementType`, so the Python API does not reach it.
- Reported by: storage-core-leaf-backends, storage-core-array-read-paths, elementwise-ops-where-transmute-subdtype

## What goes wrong
`ElementType` is a public, safe trait, re-exported at the crate root, and nothing seals it. Its docs say there are two implementors (`Ty<T>`, `TypeDyn`), but nothing enforces that. Four storages keep an `ET` value and answer `dtype()` with `element_type.dtype()`: Plain, BlockTable (Compact / CompactMmap), SubDtype and Transmute. Their `element_type_change` (reached by the safe `Array::into_type`) builds that value with the user's `NewET::from_dtype(old_dtype)`. `SubDtype::new` and `BlockTable::new` do the same. None of them checks that the returned value's `dtype()` equals `old_dtype`.

jix's unsafe code then trusts the user's answer:
- `Plain::read_data` takes the itemsize for `slice::from_raw_parts(src_ptr, span)` and for the `NdCopier` copy from it. This is a heap over-read, and the bytes are returned to the caller.
- SubDtype's push copy reads `dst_type.dtype()`-sized items out of the field view. This is also an over-read.
- `BlockTable::decoder_config` asserts `element_type.dtype() == decoder_config.dtype` with `assert_unchecked_eq!`. In release this becomes `assume(false)`, which is UB, on every `write_to` of such a Compact array.

This is the same class as K50, which was fixed by sealing `ArrayStorage`. `ElementType` was left open. `IntoType` is not affected: it uses only the associated const `ET::DTYPE` and checks it against the inner dtype in `IntoType::new` (ops/into_type.rs:58-61).

## Trigger
User element types without `unsafe`, with `DTYPE = None` and `from_dtype` always `Ok`:
- `Wide`: `dtype()` returns `&u64::DTYPE`.
- `Narrow`: `dtype()` returns `&u8::DTYPE`.

The three calls:
1. `Array::plain_ndarray_ref(&array![1u8, 2, 3])?.into_type::<Wide>()?`, then `to_ndarray_slice(&[0..3], &mut [0u8; 24], &ctx)`. The 3-byte buffer is read as 3 x 8 bytes at a 1-byte stride: the span is 10 bytes.
2. `Array::compact_ndarray(&array![1u32, 2, 3])?.into_type::<Narrow>()?.write_to(Cursor::new(&mut v))`.
3. `SubDtype::<_, Wide>::new_array(Array::plain_ndarray_ref(&array![Pair { x: 1, y: 2 }])?, "y")?`, then `to_ndarray_slice(&[0..1], &mut [0u8; 8], &ctx)`. Here `Pair` is `#[repr(C)] { x: i32, y: i32 }`. The copy reads bytes 4..12 of the 8-byte element.

## Root cause
The `ElementType` contract is only prose on a safe trait. `from_dtype` "validates against `DTYPE`" and `dtype()` "returns the element dtype". Yet unsafe code treats `element_type.dtype()` as the true layout of the stored bytes:
- **Plain::read_data** (plain.rs:446-476) sizes `from_raw_parts` and `copy_from` with it.
- **SubDtype::read_data** (sub_dtype.rs:154-166) copies `dst_dtype`-sized items from `get_unchecked(offset..)`.
- **BlockTable::decoder_config** (block.rs:223) makes the equality an optimizer assumption.

The only place that sets the value is a user call: `from_dtype` at plain.rs:504, block.rs:133/232, sub_dtype.rs:95/192 and transmute.rs:148. Its result is never compared with the dtype that was passed in. `Array::dtype()` also returns a user `ET::DTYPE`. The hunters found that mismatch is caught by the K14 span check in `check_out_buf` and by the codec length check, so it is not a separate trigger.

## Suggested fix
Seal `ElementType` with a private supertrait, as K50 did for `ArrayStorage`: only `Ty<T>` and `TypeDyn` are meant to exist. Another option is `pub unsafe trait ElementType` with a `# Safety` section ("`dtype()` returns the dtype passed to `from_dtype`, and equals `DTYPE` when that is `Some`").

As defense in depth, the four `element_type_change`s, `SubDtype::new` and `BlockTable::new` could also check `new.dtype() == old_dtype` after `from_dtype` (one `Dtype` compare, off the hot path) and return `UnsupportedDtype` on a mismatch.
