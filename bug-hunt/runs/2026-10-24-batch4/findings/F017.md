# F017: Array::to_ndarray docs promise a contiguous row-major (C-order) result, but the result follows read_layout_order (F-order for permuted views / F-order Plain sources)

- Severity: low  Verdict: confirmed  Category: questionable-semantics (stale API contract)
- Location: jix/src/array.rs:576-579 (docstring of `Array::to_ndarray`) (related: jix/src/array.rs:594-597 contradicting paragraph of the same docstring, jix/src/array.rs:651-654 `to_ndarray_sub` docs, jix/src/array.rs:777-797 allocation in `read_layout_order`, jix/src/array.rs:2374-2387 test `to_ndarray_allocates_in_the_hinted_layout`)
- Reachability: public Rust API
- Reported by: storage-core-array-read-paths

## What goes wrong
The first paragraph of `Array::to_ndarray`'s docs says the elements "are returned in a contiguous
row-major (C-order) ndarray". Since #52 (217ced2, "avoid unnecessary transpose, like numpy
`order='K'`") `to_ndarray_sub` allocates the result in the storage's `read_layout_order`, so a
permuted view or an F-order `Plain` source (and lazy ops on top of it) comes back F-contiguous.
#52 added a paragraph saying "The returned array is not necessarily C-contiguous" (array.rs:594)
but left the older C-order sentence (array.rs:576-579, from the initial commit 592a991) in place,
so the docstring now contradicts itself. Values are always correct. Only callers that rely on the
first paragraph break: `nd.as_slice().unwrap()` panics, and `into_raw_vec_and_offset()` or a raw
pointer handed to C/FFI as row-major reads the elements transposed. This is the Rust counterpart of
K40 (the Python `numpy()` docstring, fixed in #87). The layout behavior itself is intentional
(storage-core context doc, "Intentional behaviors"; test array.rs:2374); only the C-order promise
is wrong.

## Trigger
```rust
let a = Array::compact_ndarray(&array![[1i32, 2, 3], [4, 5, 6]])?;
let nd = a.view().permute_dims(&[1, 0]).to_ndarray::<Ix2>()?;   // strides [1, 3]
nd.as_slice().unwrap();                                           // panics: not C-contiguous

let mut f = Array2::<i32>::zeros((2, 3).f()); f.assign(&array![[1, 2, 3], [4, 5, 6]]);
Array::plain_ndarray_ref(&f)?.to_ndarray::<Ix2>()?;               // strides [1, 2]
Array::plain_ndarray_ref(&f)?.map(|x| x + 1).to_ndarray::<Ix2>()?; // strides [1, 2]
```

## Root cause
`to_ndarray` (array.rs:628-638) calls `to_ndarray_sub`, which (array.rs:777-797) allocates
`Array::uninit` in the C-order shape only when `spec.read_layout_order()` is the identity, and
otherwise allocates in the permuted shape and `permuted_axes(inv_order)` back - a deliberate
order='K'-style optimization from #52. The docstring sentence at array.rs:577-579 predates #52 and
was never updated (git blame: 592a991), while #52 appended the contradicting paragraph at 594-597.
No other Rust doc in `jix/src` makes the C-order promise (`to_ndarray_slice` at array.rs:819
correctly says it writes row-major, since its destination is packed).

## Suggested fix
Doc-only: in array.rs:577-579 replace "a contiguous row-major (C-order) ndarray" with something like
"a contiguous ndarray (in the source's memory order, like NumPy `order='K'`; see below)", and point
callers that need C order at `to_ndarray_slice` / `to_ndarray_buf` or `as_standard_layout()`.
Alternatively offer an explicit C-order variant. Keep the test at array.rs:2374 as the pin.
