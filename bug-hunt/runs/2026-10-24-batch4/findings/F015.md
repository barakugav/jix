# F015: Negative strides on never-stepped (length 0/1) dims are rejected on input, so valid views that NumPy and ndarray report as C-contiguous fail in asarray/compact/ops while numpy(out=) accepts the same layout

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/storage/plain.rs:520 (related: jix-py/src/ops/common/operand.rs:175-176, jix-py/src/array.rs:267-268, jix-py/src/array.rs:583-593, jix/src/storage/plain.rs:522, jix/src/storage/plain.rs:569-574)
- Reachability: Python API (`jix.asarray`, `jix.compact`, any op with a numpy operand) and public Rust API (`Array::plain_ndarray(_with)`, `plain_ndarray_ref(_with)`, `plain_ndarray_view(_with)`, `compact_ndarray(_with)`)
- Reported by: storage-core-leaf-backends (two reports: plain.rs:520 rejection, plain.rs:522 multiply overflow)

## What goes wrong
The #90 fix for K45 rejects every negative ndarray stride with InvalidArgument (plain.rs:520), and the
Python operand path does the same (operand.rs:175-176). That includes the stride of a dim of length 0
or 1. Such a dim is never stepped, so its stride has no direction. NumPy keeps a negative stride on a
length-1 axis after `x[::-1]` or `np.flip`, and still flags the array C_CONTIGUOUS. As a result
`np.ascontiguousarray(x)` returns `x` itself, and the obvious workaround for reversed views fails only
in this case.

ndarray's `invert_axis` also negates a length-1 stride. So does the `numpy` crate's `as_array`, which
calls `invert_axis` on every negative-stride axis. ndarray itself still reports standard layout, and its
own slicing sets the stride of any dim of length <= 1 to 0.

jix-py's `numpy(out=)` path accepts this layout on purpose: `check_output_array` skips dims with
extent <= 1, and the read path replaces such a stride with the C-order value, with a comment saying it
is harmless. So the same buffer is accepted as an output and rejected as an input. No values are wrong
and nothing is unsafe: valid input gets a clean error.

The second report is on the same line. `strides_from_ndarray` multiplies the stride of a length-1 dim
by `size_of::<T>()` unchecked (plain.rs:522). A huge stride, which ndarray accepts on a length-1 axis,
therefore panics in debug builds. In release the value wraps, which is harmless because the stride is
never stepped (`strided_span_bytes` multiplies it by `len - 1 = 0`). This one is Rust-only: the Python
path uses raw byte strides with no multiply.

## Trigger
Python:
- `x = np.arange(3, dtype=np.float32).reshape(1, 3)[::-1]` gives strides (-12, 4) and
  C_CONTIGUOUS True.
- Each of these then raises: `jix.asarray(x)`, `jix.compact(x)`,
  `jix.asarray(np.ascontiguousarray(x))`, and `jix.asarray(np.ones((1, 3), np.float32)) + x`.
- `jix.asarray(np.array([7.0])[::-1])` (strides (-8,)) and
  `jix.asarray(np.flip(a.reshape(1, 4), axis=0))` raise too.
- `src.numpy(out=np.zeros((1, 3), np.float32)[::-1])` is accepted.

Rust:
- `let mut v = array![[1i32, 2, 3]]; v.invert_axis(Axis(0));` gives strides [-3, 1]. Then
  `Array::plain_ndarray_view(v.view())`, `Array::compact_ndarray(&v)` and `Array::plain_ndarray(v)`
  all return `Err(InvalidArgument)`.
- `ArrayView2::from_shape((1, 3).strides((isize::MAX as usize, 1)), &[1i32, 2, 3][..])` followed by
  `Array::plain_ndarray_view(v)` panics in debug builds.

## Root cause
- `strides_from_ndarray` (plain.rs:516-524) and the operand conversion (operand.rs:171-178) test the
  sign of each stride without looking at the dim's length.
- Nothing downstream ever uses the stride of a dim of length <= 1:
  - `strided_span_bytes` multiplies it by `len - 1 = 0`.
  - The offset adds `start * stride` with start 0, or the region is empty and the base pointer is
    used.
  - `Plain::new` puts such dims in the "don't care" layout slot (plain.rs:150, 171-173).

  So rejecting the sign is stricter than the unsigned-stride model needs. The K45 write-up
  (batch3 F004) suggested normalizing this case, but #90 implemented only the rejection. The new unit
  test `negative_strides_are_an_error` (plain.rs:569-574) reuses that report's owned trigger, which
  happens to invert a length-1 axis. That test therefore pins the current behavior, and does not look
  like a deliberate decision about length-1 axes. The jix-py `out=` path makes the opposite, explicit
  choice (array.rs:583-593).
- plain.rs:522 multiplies before checking the length, so a never-stepped huge stride overflows.

## Suggested fix
In `strides_from_ndarray` and in operand.rs, map the stride of any dim with `shape[d] <= 1` to 0, or
to the C-order value as array.rs:589-593 does, before the sign check and the `* size_of::<T>()`. Also
pass the shape to `strides_from_ndarray`. Change the owned case in `negative_strides_are_an_error`
to invert an axis of length > 1, and add a length-1 case that expects success.
