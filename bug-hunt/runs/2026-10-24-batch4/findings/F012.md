# F012: Stepped Slice over a non-plain inner issues one inner read per output position of the stepped dims, decompressing whole blocks each time: step-2 slices read 200-1500x slower than the whole array

- Severity: medium  Verdict: confirmed  Category: pathological-performance
- Location: jix/src/ops/shape_ops/slice.rs:181-205 (related: jix/src/ops/shape_ops/slice.rs:148-164 plain fast path, the only path that avoids it; jix/src/storage/compact.rs:282-360 every Compact `read_data` decodes each touched block in full; jix/src/codec/mod.rs:401 `ReadContext` has no block cache, and jix/src/codec/mod.rs:224 lists one only as a future setting; jix/src/storage/core_trait.rs:129-141 elementwise ops over a Slice pull through the same path)
- Reachability: public Rust API (`Array::slice` / `Slice::new` with any `SliceItem` step > 1, e.g. the `SliceItem::new(None, None, 2)` example in the Slice docs at slice.rs:16). Python rejects steps other than 1 (jix-py/src/ops/shape_ops.rs:340-341), so Python cannot reach it.
- Reported by: shape-ops-slice-reshape

## What goes wrong
When any dim has step > 1, `Slice::read_data` uses its general path. The only exception is a
pull read (`out=None`) over an inner that has `PLAIN_READ` (Plain/Scalar). The general path
iterates over every output position of every stepped dim and issues a separate inner `read_data`
for each one. Each of those reads covers a single index along the stepped dims. A Compact inner
decodes every block it touches, and `ReadContext` has no block cache. So a stepped read decodes
each block about `(block extent along the stepped dims) / step` times when one decode would do.
The values are correct. The cost is not: stepping the innermost dim costs one whole-block
decompression per output element. Every materialization of such a view hits this:
`to_ndarray*`, `compact`, `write_to*`, and elementwise ops over it, which pull through the same
path. Nothing documents the cost. Only Reshape's docs warn about read amplification.

## Trigger
- `Array::compact_ndarray(&Array1::<f32>::from(0..262144))` (default params)
  `.slice((SliceItem::new(None, None, 2),)).to_ndarray::<Ix1>()`
- Compact f32 `[512, 512]` `.slice((SliceItem::new(None, None, 2), SliceItem::new(None, None, 2)))`;
  `[:, ::2]` is milder (one read per output column). `[::2, :]` is close to fine (one read per row).
- Any non-plain inner shows it, including lazy chains over Compact leaves. The inner-read count
  does not depend on the backend (see the broadcast counter below).

1 s for reading the whole array.

## Root cause
slice.rs:181-187 sets the iteration extent of every stepped dim to its full output length
(step-1 dims get 1 and are read as a range):
```rust
let iter_shape = dim_arr(ndim, |dim| {
    if self.slice[dim].step == 1 { 1 } else { out_shape[dim] }
});
```
slice.rs:191-205 then makes one push `read_data` per iteration, with `pos..pos + 1` on each stepped
dim. The bounding-box idea at slice.rs:148-164 (read `first..last + 1` once and re-stride by
`step`) is used only when `out.is_none()` and the inner has `PLAIN_READ`. That rules out every
`to_ndarray*` call (push mode) and every Compact or lazy inner. Each inner Compact read decodes
whole blocks into a temporary and copies out the part it needs (compact.rs:282-360). Nothing is
cached across calls (`ReadContext`, codec/mod.rs:401), so neighbouring elements decode the same
block again.

## Suggested fix
In the general path, read the bounding box of the stepped dims from the inner in one call (pull)
and copy it into `out` with NdCopier, using source strides multiplied by `step`. That is the plain
fast path extended to push mode and to non-plain inners. To bound the temporary for large steps
or large regions, process the bounding box in chunks along the outermost stepped dim, sized like
the cache-sized pieces of `to_ndarray_buf`. When step is large compared with the inner block
extent, fall back to per-position reads. At minimum, document the cost on `Slice` and
`Array::slice`, as Reshape's docs do.
