# F007: reduce_unordered over wide Dtyped elements overflows a 2 MiB thread stack and aborts: the one-cell fold keeps 16 (strided) / 8 (contiguous) lanes of T whatever the element width (K30 analog in the reduction fold)

- Severity: low  Verdict: confirmed  Category: resource
- Location: jix/src/ops/reduction.rs:768 (strided, `ONE_CELL_LANES = 16`, used at :814) and
  jix/src/ops/reduction.rs:836-842 (contiguous: `prev_power_of_two(S::u8s::LEN / size_of::<State>())`
  is `prev_power_of_two(0) == 1` for any state wider than one vector, then `const_max(.., 8)`)
  (related: jix/src/ops/reduction.rs:927-975 `fold_pairwise_leaf` (`[T; LANES]` items from
  `read_items_bulk` :1000, `[State; LANES]` from `init_state_bulk` / `update_state_bulk`);
  jix/src/ops/reduction.rs:1022-1040 `merge_states` (`[MaybeUninit<State>; LANES]`);
  jix/src/ops/reduction.rs:3081-3108 `ReduceKernel` (State = T, no `ONE_CELL_LANES` override);
  jix/src/storage/elementwise_pipeline.rs:689-704 (the K30 fix that caps lanes by width - the
  reduction fold got no such cap); jix/src/dtype.rs:1201-1216 (`[T; N]` is `Dtyped` up to
  65535 bytes); jix/src/storage/params.rs:428-432 (default read size = (max(l1d/2, l2/16), l2/2)))
- Reachability: public Rust API (`Array::reduce_unordered` / `Reduce::new` with a wide `T`, e.g.
  `[u8; 65000]` or a large `#[derive(Dtyped)]` struct). Not reachable from Python (jix-py exposes no
  `reduce_unordered`; the built-in kernels all have states of at most a few dozen bytes).
- Reported by: reduction-op-kernels

## What goes wrong
When the reduced dim is innermost (the one-cell fold), `fold_pairwise_leaf` holds `LANES` copies of
the item and of the state on the stack: the `[T; LANES]` returned by `read_items_bulk`, the
`[State; LANES]` built by `init_state_bulk` / `update_state_bulk`, and the
`[MaybeUninit<State>; LANES]` in `merge_states`. LANES is a fixed 16 on the strided path and at least
8 on the contiguous path, because `S::u8s::LEN / size_of::<State>()` is 0 for any state wider than a
SIMD vector and `prev_power_of_two(0) == 1`. Nothing bounds `LANES * size_of::<T>()`. For `Reduce`,
`State = T` can be any `Dtyped` up to 65535 bytes. In a release build, a strided one-cell reduce
over 65000-byte elements needs about 5.6 MiB of stack and a contiguous one about 2.1 MiB. The
multi-cell fold over the same data needs 396 KiB. On a thread with Rust's default 2 MiB
spawned-thread stack the process aborts with "has overflowed its stack" (SIGABRT). This is an abort,
not a catchable panic. K30 fixed exactly this lane-count-vs-width problem in the element-wise
pipeline (elementwise_pipeline.rs:689-704). The reduction fold reuses the same formula and was not
covered by that fix.

## Trigger
The fold only takes the lane path when a tile holds at least LANES items along the reduced dim, so
the element has to be wide while the read tile still holds 16 (strided) or 8 (contiguous) of them:
- contiguous, default read size: `Array::compact_ndarray_with(&Array1::from(vec![[1u8; 65000]; 32]),
  params.block_shape(&[16]))` then `.reduce_unordered(0, elementwise_wrapping_add).to_ndarray::<Ix0>()`.
  The default read-size floor is the block size in bytes (params.rs:429-430), so a tile holds 16
  items and 8 lanes are used.
- strided: a plain view `data.slice(s![..;2])` of 64 `[u8; 65000]` items with
  `read_size((1 << 20, 8 << 20))`, then the same `reduce_unordered(0, ..)`. That read size is exactly
  what `ArrayParams` picks automatically on a CPU reporting a 16 MiB L2 (Apple M-series P-cluster via
  `hw.perflevel0.l2cachesize`, cpu_cache.rs:193). There, `l2 / 16 = 1 MiB` holds 16+ wide items.
  On this 1 MiB-L2 host the default floor is 64 KiB, which holds a single 65000-byte item, so the
  override stands in for that machine.
In release, with the 16 MiB-L2 read size, strided elements of 24 KiB or more already abort on a
2 MiB thread. Measured minimum stack: 16 KiB -> 1452 KiB, 24 KiB -> 2188 KiB, 32 KiB -> 2892 KiB,
60000 B -> 5292 KiB. In debug builds the threshold is much lower: with fully default params on this
host, a strided 4 KiB-element reduce needs 3500 KiB and a contiguous 8 KiB-element reduce needs
3372 KiB, and both abort under `cargo test`. The multi-cell controls at those widths need 140-204 KiB.

## Repro
`jix/tests/repro_2026_10_24_batch4__f007.rs`. Each case runs in a child process on an explicit
2 MiB thread. The tests assert that the child exits 0, so they fail while the bug exists.
```
cargo test [--release] --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_24_batch4__f007 -- --nocapture
debug and release (same result):
  child_multi_cell_control: exit status: 0
  child_contiguous_one_cell: signal: 6 (SIGABRT) | thread '<unknown>' has overflowed its stack / fatal runtime error: stack overflow, aborting
  child_strided_one_cell:    signal: 6 (SIGABRT) | thread '<unknown>' has overflowed its stack / fatal runtime error: stack overflow, aborting
  test result: FAILED. 1 passed; 2 failed

cargo test [--release] ... -- --ignored measure --nocapture   (smallest stack that works)
               release      debug
  multi-cell     396 KiB     940 KiB
  contiguous    2172 KiB   26392 KiB
  strided       5724 KiB   54640 KiB
```
The hunter's original test (`jix/tests/hunt_2026_10_24_batch4__reduction_op_kernels_2.rs`,
60000-byte elements, `read_size((1<<26, 1<<27))`) also re-ran here: both one-cell cases SIGABRT in
debug, and the control exits 0. In release, 60000-byte contiguous needs 2028 KiB, just under 2 MiB,
so it passes. That is why the repro uses 65000-byte elements.

## Root cause
reduction.rs:836-842 sizes the contiguous lanes as `8 * prev_power_of_two(S::u8s::LEN /
size_of::<State>())`, clamped to at least 8. For a state wider than a vector the quotient is 0, so
the intended "8 vectors' worth of state" becomes "8 states of any size". The strided path
(reduction.rs:768/814) uses a fixed 16 lanes without looking at the width at all. `fold_pairwise_leaf`
(927-975) and `merge_states` (1022-1040) then put several `[T; LANES]` / `[State; LANES]` arrays
in one frame. Only the const assert `lanes.is_power_of_two() && lanes <= 512` (843) bounds them,
and it bounds the count, not the bytes. `ReduceKernel` (3081-3108) does not override
`ONE_CELL_LANES`, and its `T` is user-chosen. The element-wise pipeline had the same formula and
was fixed in c009869 (K30) by capping lanes by width (elementwise_pipeline.rs:689-704). The
reduction fold kept the old behavior.

## Suggested fix
Cap the one-cell lane count by bytes on both paths, as K30 did. Example: compute
`max_lanes = max(1, BUDGET / size_of::<State>().max(size_of::<T>()))` with a budget of a few KiB
(rounded down to a power of two). Use `min(lanes, max_lanes)` on the contiguous path, and also on
the strided path instead of the fixed 16. Alternatively, give `ReduceKernel` an `ONE_CELL_LANES`
derived from `size_of::<T>()`. With 1 lane for very wide `T`, `fold_pairwise_leaf` degenerates to
a sequential fold, which is what the multi-cell path already does.
