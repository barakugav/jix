# F007: Big-endian numpy dtypes are silently read and written as little-endian (asarray/compact/ops/write_array, and dtype='>f8' / cast)

- Severity: high  Verdict: confirmed  Category: wrong-result
- Location: jix-py/src/dtype.rs:101 (`dtype_from_numpy`; the scalar match at :139-176 and the struct-field recursion at :186 never look at byte order) (related: jix-py/src/ops/common/operand.rs:184 `Plain::new` zero-copy wrap; jix-py/src/ops/as_array.rs:64-69 and jix-py/src/ops/mod.rs:94-101 cache the user's descr; jix-py/src/array.rs:290-299 `numpy_dtype` / `.numpy()` allocation with the cached descr)
- Reachability: Python API
- Reported by: dynamic-python-differential

## What goes wrong
`dtype_from_numpy` maps a numpy descr to a jix `Dtype` by `(kind, itemsize)` only, so `'>i4'`
becomes `I32`, `'>f8'` becomes `F64`, and a struct with big-endian fields becomes a struct of
little-endian fields. Nothing in jix-py checks `byteorder` / native-ness (grep finds no byte-order
handling in jix-py/src). A non-native n-d numpy array is then wrapped zero-copy as `Plain` storage
and its bytes are interpreted as little-endian by core, so every consumer - `asarray().numpy()`,
`compact`, element-wise ops, reductions, `write_array` (which persists the wrong values to disk) -
silently returns byte-swapped values. In the other direction, `jix.asarray(x, dtype='>f8')` and
`jix.cast(a, '>f8')` cache the user's big-endian descr, so `.numpy()` allocates a `>f8` array and
core fills it with little-endian bytes. No error or warning in any case. Inconsistently, a 0-d
big-endian input is correct (it goes through numpy `.item()`, operand.rs:101-163), and `out=` with a
`>i4` buffer is rejected by `check_output_array`, so only the common n-d paths are wrong. All bit
patterns are valid for the affected int/float/complex types (bool/u8/i8 have no byte order), so
this is wrong values, not UB.

## Trigger
```python
be = np.array([1, 256, -2], dtype=">i4")   # e.g. FITS / HDF5 / np.frombuffer(net_bytes, ">i4")
jix.asarray(be).numpy()          # [16777216, 65536, -16777217]   expected [1, 256, -2]
jix.compact(be).numpy()          # [16777216, 65536, -16777217]
jix.add(be, 1).numpy()           # [16777217, 65537, -16777216]   expected [2, 257, -1]
jix.sum(be).numpy()              # 65535                          expected 255
jix.write_array(be, p); jix.read_array(p).numpy()   # [16777216, 65536, -16777217]
jix.asarray(np.array([1, 2], "<i4"), dtype=">f8").numpy()   # [3.03865e-319, 3.16e-322] (>f8)
jix.cast(np.array([1.5, 2.0]), np.dtype(">f8")).numpy()     # [3.13984e-319, 3.16e-322] (>f8)
jix.asarray(np.array([(1, 2.5)], [("a", ">i4"), ("b", ">f8")])).numpy()  # [(16777216, 5.375e-321)]
```

## Root cause
jix core has no byte-order notion (little-endian only), so the binding must ensure only
native-order data / descrs reach it. `dtype_from_numpy` (jix-py/src/dtype.rs:101-215) is the single
numpy -> jix dtype gate, but it matches only `numpy_base.kind()` and `itemsize` and recurses into
struct fields the same way, never consulting `byteorder` / `PyArrayDescrMethods::is_native_byteorder`.
Its callers then trust the result: `Operand::from_any_with_params` wraps the raw numpy buffer with
`Plain::new` (operand.rs:184-194), and `asarray(dtype=)` / `cast` attach the user's descr verbatim via
`Array::from_core_with_np_dtype` (as_array.rs:64-69, ops/mod.rs:98-101), which `numpy_dtype()`
(array.rs:290-299) then uses to allocate the `.numpy()` result. The `docs/module.md` "Little-endian
platforms only" limit is about the host, not data; nothing documents or tests that non-native
arrays are unsupported.

## Suggested fix
In `dtype_from_numpy` (and for every struct field), detect a non-native byte order. For input
arrays, either reject with a ValueError or (better) convert: `np.asarray(x, x.dtype.newbyteorder('='))`
/ `x.astype(x.dtype.newbyteorder('='))` before wrapping (a copy, like any other conversion
`asarray` may do). For `dtype=` / `cast` targets, either reject a non-native descr or normalize it to
native order before caching it (e.g. cache `dtype_to_numpy(&dtype)` instead of the user's descr).
Add tests with `'>i4'`, `'>f8'`, `'>c16'` and a struct with big-endian fields.
