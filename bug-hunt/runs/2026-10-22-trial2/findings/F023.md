# F023: Repeat multiplies the out stride by `repeats` even when the output dim has length 1, so it overflows (panics in debug builds) on valid `out=` buffers

- Severity: low  Verdict: confirmed  Category: overflow
- Location: jix/src/ops/shape_ops/repeat.rs:181 (related: repeat.rs:213-215 `g_count == 1` branch; jix-py/src/array.rs:566-590 passes the numpy stride through unchanged; jix/src/util/nd_copy.rs:66-67 drops size-1 dims, which is why release builds are unaffected)
- Reachability: public Rust API (`to_ndarray_buf` with an `out` built by `StridedBuf::from_raw_parts_mut` that meets its contract), Python API (`Array.numpy(..., out=)` with an ordinary numpy view)
- Reported by: shape-ops-copy-ops

## What goes wrong
`copy_region` splits output dim k into `(group, within-group)` and always computes the group stride
as `out_strides[k] * n as usize`, where `n` is the repeat count. When the requested output
range on dim k has length 1, the out stride on that dim is never stepped. It can therefore legally be
anything, and the group dim of the copy also has length 1, so its stride is never used either. If
`out_strides[k] * repeats >= 2^64`, the multiplication overflows. Debug builds, including
the default dev profile of any downstream crate and the dev Python build, panic with
`attempt to multiply with overflow` on valid input. Release builds wrap the value, but NdCopier
drops the size-1 dim, so the result is correct (verified). No UB and no wrong result.

## Trigger
- Huge stride, small count: `[[1u8,2,3,4]]` `.repeat(4, 0)` read at `[1..2, 0..4]` into an
  `out` of shape `[1,4]`, strides `[2^62, 1]`. In numpy, `np.zeros((8,4), np.uint8)[::2**60]`
  gives this buffer with no stride tricks.
- Ordinary stride, large lazy count: `.repeat(2^50, 0)` read at `[5..6, 0..4]` into one row of a
  wider buffer. The out has shape `[1,4]` and strides `[16384, 1]`, as from
  `np.zeros((2, 2**14), np.uint8)[0:1, 0:4]`. `16384 * 2^50 = 2^64`.

## Repro
- Rust: `jix/tests/repro_2026_10_22_trial2__f023.rs`. Run
  `cargo test --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_22_trial2__f023 -- --nocapture`.
  Both tests fail (debug) with
  `panicked at src/ops/shape_ops/repeat.rs:181:36: attempt to multiply with overflow`.
  With `--release`, both pass, so the result is correct once the overflow wraps.
- Python: `bug-hunt/runs/2026-10-22-trial2/repros/F023.py`. Run with `.venv/bin/python`. Both
  numpy-slice outs (`(1,4)` with strides `(16384,1)`, and `(1,4)` with strides `(2**62,1)`)
  raise `pyo3_runtime.PanicException: attempt to multiply with overflow` from
  `repeat.rs:181:36`.

## Root cause
At repeat.rs:181, `dst_strides_split[k] = out_strides[k] * n as usize` is computed
unconditionally. The product is only meaningful, and only guaranteed to fit, when the group dim
has `g_len > 1`. In that case the output dim spans more than `n` positions at that stride, so
the product is bounded by the out buffer's extent. With `g_len == 1`, which is always the case in the
`g_count == 1` branch and for head/tail regions, the value is dead, but the multiplication still
traps in builds with overflow checks. Nothing upstream constrains the stride of a length-1 out dim:
`check_out_buf` checks only the count and writability, `StridedBuf::from_raw_parts_mut` permits it,
and jix-py only normalizes negative strides on length-1 dims (array.rs:578-588).
`n as usize` also truncates on 32-bit, but that matters only when `g_len > 1`, which already
requires a region larger than the address space.

## Suggested fix
Use `wrapping_mul`, which is fine because the value is unused whenever it would overflow. Or set
`dst_strides_split[k] = if g_len > 1 { out_strides[k] * n as usize } else { 0 }`. The
`g_len > 1` product is bounded by the out extent, so it cannot overflow.
