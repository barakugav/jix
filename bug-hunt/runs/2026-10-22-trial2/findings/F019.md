# F019: permute_dims with more than 8 entries panics (ArrayVec capacity) instead of raising

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix-py/src/util.rs:193 (`normalize_dims` collects into `DimArray` with no length check) (related: jix-py/src/ops/shape_ops.rs:627 `dims: Option<Vec<i32>>`, jix-py/src/ops/shape_ops.rs:634 the call, jix-py/src/array.rs:1263-1267 `Array.permute_dims` method, jix-py/src/util.rs:266 `ItemOrTuple::into_dim_array`, which does bound the length)
- Reachability: Python API (`jix.permute_dims` and `Array.permute_dims`)
- Reported by: py-ops-shape-ops, dynamic-python-differential

## What goes wrong
`permute_dims` takes its `dims` argument as `Option<Vec<i32>>`, so a sequence of any length is
accepted. It then calls `normalize_dims(&dims, ndim)`, which maps each entry through
`normalize_dim` and collects into `DimArray<usize>` (an `ArrayVec` of capacity `NDIM_MAX = 8`).
The only guard in `normalize_dims` is on the array's `ndim`, not on `dims.len()`. When the list
has 9+ entries that are all in range for the array, the collect overflows the `ArrayVec` and
panics. From Python this surfaces as `pyo3_runtime.PanicException`, which derives from
`BaseException`, so `except Exception` / `except ValueError` does not catch it. A wrong-length
list of 8 or fewer entries gets a clean `RuntimeError` from the core length check
(jix/src/ops/shape_ops/permute_dims.rs:53-58), so the outcome depends only on whether the list
happens to exceed 8. No memory-safety impact (arrayvec panics before writing).

## Trigger
```python
a = jix.compact(np.arange(12, dtype=np.int32).reshape(3, 4))
jix.permute_dims(a, [0] * 9)       # or [0, 1] * 5, or a.permute_dims([0] * 9),
                                   # or jix.permute_dims(np.zeros((2, 3)), [0] * 9)
```
(An out-of-range entry before the 9th, e.g. `[5] * 9`, raises cleanly from `normalize_dim`
first, so the entries must be in range.)

## Root cause
`normalize_dims` (jix-py/src/util.rs:187-194) assumes its slice is already at most `NDIM_MAX`
long. Its other two callers satisfy that: `insert_dim` (shape_ops.rs:450-451) and the
shape_ops.rs:521 caller both pass the result of `ItemOrTuple::into_dim_array`, which rejects
sequences longer than `NDIM_MAX` (util.rs:266-272). `permute_dims` is the only caller that passes
an unbounded `Vec<i32>` (the deliberate exception to the "dims accept an int or a tuple only" rule,
py-ops context doc), so it skips that bound. The core `PermuteDims::new` length check
(permute_dims.rs:53-58) would reject the input, but it is never reached.

## Suggested fix
Check `dims.len() > NDIM_MAX` in `normalize_dims` (or check `dims.len() != ndim` there) and
return a `ValueError` before collecting; alternatively collect into a `Vec` and let the core
length check reject it.
