# F005: 32-bit: block byte size block_size * itemsize is never bounded to usize; every consumer wraps it identically, so size checks pass and block reads go out of bounds

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/storage/params.rs:321 (`ArrayParams::tune`, the missing bound) (related: jix/src/storage/compact.rs:395-396, jix/src/storage/compact.rs:411, jix/src/storage/compact.rs:477, jix/src/storage/block.rs:180, jix/src/storage/block.rs:366, jix/src/array.rs:1320, jix/src/array.rs:1371, jix/src/util/nd_copy.rs:341, jix/src/archive/array.rs:495-505)
- Reachability: public Rust API (safe `compact_with` on a lazy broadcast; safe `read_from_reader` with `ArchiveValidation::Strict`). Python is probably reachable the same way on the x86 / armv7 wheels (`jix.compact(..., params={"block_shape": [...]})`, `read_array`), not tested: no 32-bit Python here.
- Reported by: codec-archive-codec-pipeline

## What goes wrong
On 32-bit targets nothing checks that one block's byte size, `block_size * itemsize`, fits in `usize`.
The block element count is bounded by u32 (header check, `tune`) and the itemsize by u16, and
`check_shape_overflow` only checks the u64 product. Every consumer computes the product unchecked
in usize, and all of them wrap to the same small value. So `read_block`'s buffer-length check and
decoded-length check (block.rs:180-197) both pass against a scratch buffer that is far too small
(compact.rs:395-398). The offset of an element inside the block, `inner_offset * block_stride`
(compact.rs:404-411, 474-477), is not wrapped, though. So `tmp_buf.get_unchecked(active_start..)`
and the following `NdCopier` read go past the allocation: wrong data from the heap, then SIGSEGV.
On the write side, `compact_with` silently stores a block truncated to the wrapped size and returns
`Ok` (array.rs:1320, 1371, and the broadcast fill `total = len * itemsize` in nd_copy.rs:341).
The x86 and armv7 wheels ship with this. K2's fix does not cover it: K2 checks the pull-mode
`out` buffer with a u64 product, and here the `out` buffer is a single correctly sized element.

## Trigger
(b), no file needed: `Array::compact_ndarray(&Array1::from_elem(1, [7u8; 4096])).broadcast(&[(1<<20)+1])`,
then `compact_with` with `block_shape [(1<<20)+1]`, then `to_ndarray_sub(&[i..i+1])` for i = 0, 1, 2, 1000.
The block holds (2^20+1) * 4096 = 2^32 + 4096 bytes, which wraps to 4096.

(a), malformed file: a valid archive of 16385 x [u8; 4096] with `block_shape [16385]` and no
filters. Its four 3-byte header varints (shape, block_shape, nitems, block_size) 81 80 01 are
patched to 81 80 40 (1048577), and the zstd frame is replaced by a single RLE block that decodes
to 4096 x 0xCD, padded with a skippable frame. `read_from_reader(.., Strict)` accepts it.

## Root cause
`ArrayParams::tune` (storage/params.rs:321-420) validates the block shape against the array shape.
It derives `block_size` in u64, but it never requires `block_product * itemsize` to fit in usize,
let alone in `isize::MAX`. The archive header check (archive/array.rs:495-505) bounds the block
product by u32 only. Every byte-size computation downstream then uses unchecked `as usize * itemsize`:
- storage/block.rs:180 (read_block)
- storage/block.rs:366 (build_from_data)
- storage/compact.rs:395-396 (read_data_slow scratch)
- array.rs:1320 and 1371 (compaction block and chunk buffers)
- util/nd_copy.rs:341 (broadcast fill total)
In release they all wrap to the same value, so the size checks between them agree. But the
element offsets used in `get_unchecked` / `PtrNoalias::from_slice` (compact.rs:404-411, 474-477)
are computed per element and do not wrap.

## Suggested fix
Make "one block's bytes fit in memory" an invariant of the spec: in `tune`, which both
`compact_into_builder` and the archive load path (`ArrayBlockTableStorageBase::new`) go through,
compute `block_product * itemsize` in u64. Return `InvalidArgument` / `InvalidArchive` if it
exceeds `isize::MAX as u64` (or a saner cap). Optionally also use `checked_mul` / `usize::try_from`
at block.rs:180, compact.rs:396 and array.rs:1320 / 1371, so that a future caller that bypasses
`tune` gets an error and not a wrap.
