# F021: reshape with -1 rejects every zero-size array, even when the inferred length (0) is unambiguous

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/shape_ops.rs:768-769 (related: jix-py/src/ops/shape_ops.rs:818-821 `flatten`, jix-py/src/array.rs:1249-1253 `Array.reshape`)
- Reachability: Python API (`jix.reshape`, `Array.reshape`); the Rust core has no `-1` and is unaffected
- Reported by: py-ops-shape-ops, dynamic-python-differential

## What goes wrong
The `-1` inference in `jix.reshape` raises `ValueError: Cannot infer dimension size` whenever the
input has zero elements. When the explicit dims multiply to a nonzero `known_size`, the only
consistent value for the `-1` dim is 0, and numpy and torch both return that. Only
`known_size == 0` (e.g. `(0, -1)`) is ambiguous. jix disagrees with itself here too:
`jix.flatten(z)` and `jix.reshape(z, 0)` succeed on the same array, but `jix.reshape(z, -1)`
fails, even though it asks for the same thing. Generic code like `x.reshape(-1, d)` breaks on
empty batches (a filter or slice that selects nothing).

## Trigger
```python
z = jix.compact(np.zeros((0, 3), np.int32))
jix.reshape(z, (-1, 3))      # ValueError, expected shape (0, 3)
jix.reshape(z, -1)           # ValueError, expected shape (0,)
z.reshape((-1, 3))           # same, through the Array method
jix.reshape(z, (2, -1, 3))   # ValueError, expected (2, 0, 3)
jix.flatten(z)               # OK, shape (0,)
```

The genuinely ambiguous case `(0, -1)` raises in both numpy and jix, and should keep raising.

## Root cause
shape_ops.rs:768:
`if array_size == 0 || known_size == 0 || !array_size.is_multiple_of(known_size)`.
The `array_size == 0` term is unnecessary. When `known_size > 0`,
`0.is_multiple_of(known_size)` is true and `0 / known_size == 0` is the right inferred length.
The term seems to have been added to avoid ambiguity, but `known_size == 0` already covers
that case. Neither the reshape docstring (shape_ops.rs:694-733), the tests, nor the context
doc's "Intentional behaviors" list mention this restriction (py-ops.md lists it as a hot spot).
`flatten` (shape_ops.rs:818-821) passes the explicit size instead of `-1`, so it never hits
this check.

## Suggested fix
Drop `array_size == 0 ||` from the condition at shape_ops.rs:768 and keep `known_size == 0`
(the ambiguous case) plus the divisibility check. Add a test that `reshape(zeros((0, 3)), (-1, 3))`
gives shape `(0, 3)` and that `reshape(zeros((0, 3)), (0, -1))` still raises.
