# F009: Roll reduces shift with `rem_euclid(len as i64)`: wrong values for dims > i64::MAX, panic for len == u64::MAX with shift == i64::MIN

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/shape_ops/roll.rs:54 (related: jix/src/ops/shape_ops/roll.rs:94, jix/src/ops/shape_ops/roll.rs:132, jix-py/src/ops/shape_ops.rs:1182)
- Reachability: public Rust API (`Array::roll`, `Roll::new` / `Roll::new_array`) and Python API (`jix.roll`)
- Reported by: py-ops-shape-ops, shape-ops-copy-ops

## What goes wrong
`Roll::new` normalizes the shift with `shift.rem_euclid(len as i64) as u64`. When the rolled dim is
longer than `i64::MAX`, `len as i64` is negative (`len - 2^64`), and `rem_euclid` reduces modulo
`2^64 - len` instead of `len`. Any negative shift (and any positive shift >= `2^64 - len`) gets the
wrong normalized shift, so reads silently return wrong values. For `len == u64::MAX`,
`len as i64 == -1`, so every shift collapses to 0 (roll becomes identity), and
`i64::MIN.rem_euclid(-1)` panics with "attempt to calculate the remainder with overflow". Division
overflow is checked unconditionally in Rust (verified with `rustc -O -C overflow-checks=off`: still
panics), so release wheels raise `PanicException` too. Such shapes are valid: `check_shape_overflow`
only bounds `prod(shape) * itemsize` by u64, so 1-byte dtypes (u8/i8/bool) may have a dim up to
`u64::MAX` as a lazy tile/broadcast/repeat and be read in small sub-regions. Nothing in the
context docs marks this as intended (shape-ops.md lists it as a hot spot); the doc comment says
"`shift` is reduced modulo `L`, so any signed integer is accepted".

## Trigger
Rust:
- `Array::compact_ndarray(&array![0u8,1,2])?.tile(3074457345618258603, 0)` (len 2^63+1) `.roll(-1, 0)`, read `[0..1]`: expected `[1]`, got `[0]`.
- `...tile(u64::MAX / 3, 0)` (len u64::MAX) `.roll(1, 0)`, read `[0..1]`: expected `[2]`, got `[0]` (identity).
- `Roll::new_array(Array::compact_ndarray(&array![7u8])?.broadcast(&[u64::MAX]), i64::MIN, 0)`: expected `Ok`, panics.

Python:
- `t = jix.tile(jix.compact(np.array([0,1,2], np.uint8)), (2**64-1)//3)`;
  `jix.reshape(jix.roll(t, 1), (3, K))[0, 0:1]` gives `[0]` (expected `[2]`);
  `jix.roll(t, -2**63)` raises `pyo3_runtime.PanicException`.

## Root cause
roll.rs:54 casts the u64 dim length to i64 to use `i64::rem_euclid`, which is only correct for
`len <= i64::MAX`. The in-crate proptest reference (`roll_reference`, roll.rs tests) does the
reduction in i128 and the proptest only uses small shapes, so the gap is never exercised.

## Suggested fix
Reduce in a type that holds both ranges, e.g. `(shift as i128).rem_euclid(len as i128) as u64`, or
in u64: `let m = shift.unsigned_abs() % len; if shift >= 0 || m == 0 { m } else { len - m }`.
After that fix, roll.rs:94 (`s + l - shift`) and roll.rs:132 (`(s + l - shift)..l`) become reachable
with `s + l > u64::MAX` (e.g. len u64::MAX, shift 10, read starting at s = 5): debug overflow panic
(release wraps to the right value). Rewrite them as `s + (l - shift)` (valid since `shift < l`).
The same `len as i64` pattern exists in slice resolution (slice.rs:365-367, per shape-ops.md) and
may deserve the same treatment.
