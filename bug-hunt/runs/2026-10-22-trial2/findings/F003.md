# F003: 32-bit: read regions over 4 GiB / 2^32 elements are sized with truncating `as usize` and wrapping usize products, so reads overflow the heap (the 32-bit part of K2, which its fix did not cover)

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/storage/buf.rs:312 (`materialize_out_buf`) (related: jix/src/array.rs:960
  `nitems` truncation that picks the small-read fast path, jix/src/array.rs:1022 `out_shape_usize`,
  jix/src/array.rs:764 `to_ndarray_sub` shape, jix/src/error.rs:246-247 `check_get_buffer_size`,
  jix/src/storage/elementwise_pipeline.rs:200, :326, :869, :875-878, :891,
  jix/src/ops/shape_ops/tile.rs:127, :163, :205-229, repeat.rs:164-205)
- Reachability: public Rust API, safe code only, on 32-bit targets (i686 / armv7; the x86 and
  armv7 wheels ship). Python on those wheels most likely too (jix-py/src/array.rs:529 casts the
  same way), but there is no 32-bit Python to test it.
- Reported by: pipeline-driver, shape-ops-copy-ops, concept-integer-width

## What goes wrong
Shapes and index ranges are `u64`. Every read entry point turns the region extents into `usize`
with `as usize` and multiplies them in unchecked `usize`. The read itself then walks the full u64
region. The only shape guard, `check_shape_overflow` (error.rs:186), proves that `shape * itemsize`
fits a u64, not a usize. On 32-bit, a lazy array (broadcast, tile, repeat, map) can describe more
than 4 GiB without owning any memory, so the size computed for a read wraps or truncates:
- Pull reads (`to_ndarray_buf(.., None)`, `read_data(.., None)`) get a small pooled allocation,
  with strides for the full region.
- `to_ndarray_slice` accepts a caller buffer far shorter than the region.
- `to_ndarray` allocates an ndarray with the truncated shape.
All three then write the whole region past the end of the allocation. That is a heap overflow from
safe code. In release builds (what ships) every variant crashes. In debug builds the pull variants
panic on the multiplication, and the `to_ndarray_slice` / `to_ndarray` variants are heap overflows
even in debug.
A dim whose extent is a multiple of 2^32 truncates to 0. The element-wise driver then treats the
non-empty region as empty: it returns `Ok` with nothing computed, and `to_ndarray` returns an
ndarray of shape `[0]` for a `[2^32]` array.
K2 (fixed in 5b3a9f5) found the same `buf.rs:312` site through an itemsize-widening op, and its
write-up named the 32-bit truncation as part of the root cause. The fix only added `u64` shape
checks to op constructors, so on 32-bit `buf.rs:312` and the other sites below are unchanged.

## Trigger
All on i686 (`usize` = 32 bits). `D0 = 65536`, `D1 = 65600`; `D0 * D1 = 2^32 + 2^22` wraps to
4194304.
```rust
// (a) pull, slow path: materialize_out_buf allocates 4 MiB for a 4.3 GB region
let a = Array::compact_ndarray(&array![[7u8]])?.broadcast(&[D0, D1]);
a.to_ndarray_buf(&[0..D0, 0..D1], &ReadContext::default(), None);
// (b) pull, small-read fast path (array.rs:960 truncates nitems to 65536) into Tile::read_data
let t = Array::compact_ndarray(&Array2::<i8>::zeros((1, 65537)))?.tile(65536, 0).map(|x: i8| x ^ 1);
t.to_ndarray_buf(&[0..65536, 0..65537], &ReadContext::default(), None);
// (c) push: a 4 MiB buffer passes the "exact length" check for a 4.3 GB region
let mut buf = vec![0u8; 4194304];
a.to_ndarray_slice(&[0..D0, 0..D1], &mut buf, &a.read_ctx());
// (d) to_ndarray: shape [2^32 + 8] truncates to an 8-element ndarray; Tile case C fills 2^32 + 8
Array::compact_ndarray(&array![7u8])?.broadcast(&[(1 << 31) + 4]).tile(2, 0).to_ndarray::<Ix1>();
// (e) a 2^32 dim truncates to 0: the region is treated as empty
let m = Array::compact_ndarray(&array![3.0f32])?.broadcast(&[1 << 32]).map(|x: f32| x + 1.0);
m.to_ndarray::<Ix1>();                                     // Ok, shape [0]
m.to_ndarray_buf(&[0..1 << 32], &ReadContext::default(), None); // Ok, strides [4], nothing written
```

## Repro
`jix/tests/repro_2026_10_22_trial2__f003.rs` has 6 tests. Each test returns early on 64-bit and
asserts the correct behavior on 32-bit: an `Err`, or for a pull read a view whose strides fit the
address space and hold the right value. Several tests crash the process, so run them one at a time:
`bug-hunt/tools/cargo-i686 test [--release] --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_22_trial2__f003 -- --nocapture --test-threads 1 --exact <name>`

i686 debug:
- `pull_read_over_4gib_broadcast` (a) and `pull_read_over_4gib_tile_map_small_read` (b) both panic
  with `attempt to multiply with overflow` in `jix::storage::buf::materialize_out_buf at
  ./jix/src/storage/buf.rs:312:34`. For (a) it is called from `to_ndarray_buf_slow_dyn` at
  array.rs:1023, and for (b) from `Tile::read_data`.
- `to_ndarray_slice_rejects_wrapped_buffer_len` (c) gets SIGSEGV. gdb shows the frames
  `NdCopier::inner_loop_broadcast nd_copy.rs:292 <- StridedBuf::copy_from buf.rs:231 <-
  Broadcast::read_data broadcast.rs:157 <- to_ndarray_buf_slow_dyn array.rs:1063 <-
  to_ndarray_slice`. Outside gdb, Rust's handler prints a misleading "has overflowed its stack":
  the write runs past the heap into a guard page.
- `to_ndarray_tile_over_4gib` (d) dies with SIGSEGV (exit 139) at `NdCopier::inner_loop_broadcast

- `to_ndarray_pipeline_dim_2pow32` (e) fails with `got Ok with shape [0]`.

## Root cause
- The region extents are converted from `u64` with unchecked `as usize`: array.rs:764 (to_ndarray_sub
  shape), array.rs:960 (`nitems`, which also selects the small-read fast path), array.rs:1022,
  tile.rs:127, elementwise_pipeline.rs:200, :326 and :869, and error.rs:246.
- The extents are multiplied in unchecked `usize`: buf.rs:312, elementwise_pipeline.rs:875-878 and
  :891, and error.rs:247.
- `strides_for_layout_order` (buf.rs:314) and the copy loops (`NdCopier`, Tile/Repeat case C with u64
  extents, the slow-path tile loop) describe the real region, so the allocation and the writes
  disagree. Nothing checks the allocation against the strided span.
- `check_shape_overflow` (error.rs:186) is the only size guard, and it checks against `u64`.
  Nothing establishes that a region read from an array fits the target's `usize` / `isize::MAX`.

## Suggested fix
Make region sizing fallible and target-aware. Add one helper that converts a region (`&[Range<u64>]`,
itemsize) to `(DimArray<usize>, byte_len)` with `usize::try_from` per extent, `checked_mul` for the
products, and a `<= isize::MAX` bound, returning `Err(InvalidShapeOperation)` otherwise. Use it in
`materialize_out_buf` and `materialize_pipeline_out_buf` (have them return `Result`), in
`check_get_buffer_size`, in `to_ndarray_sub`, in `to_ndarray_buf_checked` (instead of the truncated
`nitems`), and in the element-wise driver's region shape. A pure broadcast pull may still return a
stride-0 view without allocating, so the check belongs at the allocation and copy sites, not at
array construction.
