# F016: slice_unpack resolves slice bounds through Py_ssize_t: on 32-bit CPython a dim longer than 2^31-1 gives a silently wrong slice; on 64-bit, stops >= 2^63-1 bypass the strict bounds check

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix-py/src/util.rs:30-31 (related: jix-py/src/util.rs:25 (`PySlice_Unpack` writes
  `Py_ssize_t` and clamps silently); jix-py/src/ops/shape_ops.rs:333-341 (`len = shape as i64`,
  `stop as i64`, a negative stop is taken as end-relative); jix-py/src/ops/shape_ops.rs:201
  (`jix.slice`); jix-py/src/array.rs:187 (`Array.__getitem__` / `numpy(index=...)` use the same
  parser); pyo3-ffi-0.30.1/src/pyport.rs:14 (`Py_ssize_t = libc::ssize_t`, i32 on the
  i686 / armv7 / win32 wheels))
- Reachability: Python API (`a[...]`, `jix.slice`, `Array.numpy(index=...)`)
- Reported by: py-ops-shape-ops

## What goes wrong
`slice_unpack` calls `PySlice_Unpack`, which returns start/stop as `Py_ssize_t` and silently clamps
any explicit value outside `[PY_SSIZE_T_MIN, PY_SSIZE_T_MAX]`. An omitted stop also comes back as
`PY_SSIZE_T_MAX`, so util.rs:30-31 replaces every stop equal to that sentinel, whether it was omitted
or clamped, with `length as Py_ssize_t`.
- 32-bit CPython (shipped x86 / armv7 / win32 wheels): `Py_ssize_t` is i32. `length` is the u64 dim
  length cast to i64, and the cast truncates it for any dim longer than 2^31-1. parse_basic_index then
  treats the negative truncated stop as end-relative and adds `len`. The slice resolves to a wrong but
  in-bounds range, which gives a wrong shape and wrong data with no error. Explicit start/stop values
  >= 2^31 are also clamped to 2^31-1 before any check. Such dims are valid on 32-bit because jix
  shapes are u64: they come from lazy broadcast / repeat / tile views or from highly compressible
  compact arrays.
- 64-bit: there is no truncation, but the clamp undercuts the documented strict bounds ("Slicing:
  strict bounds, no clamping", test_slice.py `test_slice_stop_out_of_bounds_raises`). `a[0:4]` on a
  length-3 dim raises, while `a[0:2**63]`, `a[0:2**100]` and `a[0:sys.maxsize]` are accepted as
  `a[:]`. The clamped value also leaks into error messages (`a[2**100:]` reports "slice start
  9223372036854775807").

## Trigger
64-bit (run):
```python
a = jix.compact(np.arange(12, dtype=np.int64).reshape(3, 4))
a[0:4]            # IndexError (correct)
a[0:2**63]        # returns shape (3, 4) - should raise IndexError
jix.slice(a, slice(1, 2**64))   # returns shape (2, 4)
```
32-bit CPython (derived from the code; not run, see Repro):
```python
b = jix.broadcast(np.zeros((1, 2), np.uint8), (2**31 + 10, 2))
b[:, 0].shape     # (20,) instead of (2147483658,)
c = jix.broadcast(np.zeros((1,), np.uint8), (3_000_000_000,))
jix.slice(c, slice(100, 2_500_000_000)).shape   # (1705032604,) instead of (2499999900,)
jix.slice(c, slice(-10, None))                   # bogus IndexError "start -10 must be <= stop -1294967296"
c[2_500_000_000:2_500_000_010]                   # bogus IndexError
# a dim of length 2**32 + 5: c2[:] has length 5
```

`.venv/bin/python bug-hunt/runs/2026-10-22-trial2/repros/F016.py`. It asserts the correct behavior.
Part A runs on any platform; Part B runs only when `sys.maxsize < 2**63 - 1` (32-bit CPython).
```

FAIL  a[0:2**63]: expected IndexError, got result with shape (3, 4)
FAIL  a[0:2**100]: expected IndexError, got result with shape (3, 4)
FAIL  a[0:sys.maxsize]: expected IndexError, got result with shape (3, 4)

FAIL  a.numpy(index=slice(0, 2**63)): expected IndexError, got result with shape (3, 4)
```

Part B could not be run here: there is no 32-bit CPython (no `/lib/ld-linux.so.2`). The extension is
a PyO3 module, so the i686-musl `cargo-i686` harness cannot run it. The 32-bit numbers above come from
an exact model of util.rs:19-34 plus shape_ops.rs:333-361, with i32 clamping and truncation. They
match the hunter's trace: `(0, 20)`, `(100, 1705032704)`, a start>stop error for `slice(-10, None)`,
and length 5 for a `2**32 + 5` dim.

## Root cause
util.rs:30-31 cannot tell an omitted stop from an explicit stop that `PySlice_Unpack` clamped to
`PY_SSIZE_T_MAX`, and it narrows the u64-derived `length` to `Py_ssize_t` with `as`. Integer indices
in the same parser are extracted as `i64` (shape_ops.rs:273) and are not affected. Only slices go
through the platform-width C API.

## Suggested fix
Do not go through `PySlice_Unpack`. Read `slice.start` / `slice.stop` / `slice.step` with
`getattr` and extract them as `Option<i64>`, or as Python ints compared against the u64 `len` (that
also covers dims > i64::MAX). `None` stop means `len`, and anything out of range raises IndexError.
That removes both the 32-bit truncation and the silent clamp.
