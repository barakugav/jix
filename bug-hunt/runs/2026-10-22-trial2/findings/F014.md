# F014: Complex division uses the textbook formula: NaN / inf / 0 or large error for finite operands when the divisor is far from 1

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/op2.rs:781 (related: jix/src/ops/op2.rs:786 (`Complex<f16>`, same formula);
  num-complex-0.4.6/src/lib.rs:816-824 (the `Div` impl it calls); jix/src/ops/op2.rs:377 (Rust doc:
  "errors are not reported yet"); jix-py/src/ops/op2.rs:200-245 (Python `divide` / `/`, docstring
  says only "full complex division"); jix/src/ops/op1.rs:357-367 (complex `Abs` uses the overflow-safe
  `hypot`, so jix is inconsistent with itself))
- Reachability: Python API (`jix.divide`, `Array.__truediv__` / `__rtruediv__`, compact arrays,
  numpy inputs, scalars) and public Rust API (`Array / Array` for `Complex<f32>` / `Complex<f64>`;
  `jix::scalar::Div::div` for `Complex<f16>`)
- Reported by: dynamic-python-differential

## What goes wrong
`impl Div for [Complex<f32>, Complex<f64>]` is `|a, b, _status| a / b`, i.e. num-complex's
`((ac + bd) + (bc - ad)i) / (c*c + d*d)`. The denominator `c*c + d*d` overflows to inf once
`|b|` exceeds ~sqrt(MAX) (~1.8e19 for complex64, ~1.3e154 for complex128) and underflows to a
subnormal / zero once `|b|` drops below ~sqrt(MIN_POSITIVE) (~1e-19 / ~1.5e-154). Finite operands
whose quotient is perfectly representable then come back as `nan+nanj`, `inf+nanj`, `0j`, or with
a relative error of ~5e-6 (complex64) / ~1e-5 (complex128) instead of half an ulp. Nothing is
reported (the status argument is ignored). NumPy (Smith's algorithm) and CPython's `complex`
division return the correctly rounded quotient for all these inputs. For `Complex<f16>` (Rust
scalar trait only) the threshold is sqrt(65504) ~ 256, so `(300+0i)/(300+0i)` is already NaN.

## Trigger
```python
c64 = np.complex64
a = np.array([1e20 + 1e20j], c64)
jix.divide(jix.compact(a), jix.compact(a)).numpy()          # [nan+nanj], expected [1+0j]
(jix.compact(a) / jix.compact(a)).numpy()                    # same via `/`
jix.divide(np.array([1+1j], c64), np.array([1e-23+1e-23j], c64)).numpy()  # [inf+nanj], expected 1e23
jix.divide(np.array([1+1j], c64), np.array([1e20+1e20j], c64)).numpy()    # [0j], expected 1e-20
jix.divide(np.array([3+4j], c64), np.array([1e-20+0j], c64)).numpy()      # 3.0000162e20+4.0000215e20j
# complex128: (1e160+1e160j)/(1e160+1e160j) -> nan+nanj; (1+1j)/(1e-170+1e-170j) -> inf+nanj;
#             (1+1j)/(1e160+1e160j) -> 0j; (3+4j)/(1e-160+0j) -> 3.0000334e160+4.0000445e160j
```
Special values also differ from numpy (informational, the "errors are not reported yet" part is
documented on the Rust trait at op2.rs:377): `(1+2j)/(inf+0j)` gives `nan+nanj` (numpy `0j`),
`(1+2j)/0j` gives `nan+nanj` (numpy `inf+infj` with a `divide` warning) and raises nothing under the
default errstate, while float `1.0/0.0` raises FloatingPointError.

## Root cause
op2.rs:781 and :787 delegate to `num_complex::Complex::div` (num-complex 0.4.6 lib.rs:816-824),
which forms `norm_sqr = c*c + d*d` in the element type with no scaling. That intermediate needs twice
the exponent range of the operands, so it overflows / underflows for half of the exponent range
even though the result fits. The Python test `test_divide` (jix-py/python/tests/test_op2.py:214-228)
only draws moderate non-zero values and allows rtol 1e-5 ("algorithms differ slightly"), so it
never reaches the failing range. The float `Div` impls (op2.rs:769, :1013) are IEEE-exact and report
errors; complex `Abs` uses `hypot` (op1.rs:359, :366); only complex division is unscaled.

## Suggested fix
Implement complex division directly instead of calling num-complex: Smith's algorithm as numpy does
(if `|c| >= |d|`: `r = d/c, t = 1/(c + d*r)`, `re = (a + b*r)*t`, `im = (b - a*r)*t`; else symmetric),
with numpy's special case for `c == d == 0` (divide the components by `|c|` to get inf/nan) - or the
more accurate Baudin-Smith variant. For `Complex<f16>` compute in f32 (or f64) and round once.
Optionally set the `ArithmeticOpStatus` flags (divide by zero / invalid / overflow) like the float
impl, and mention in the Python `divide` docstring whether complex errors are reported.
