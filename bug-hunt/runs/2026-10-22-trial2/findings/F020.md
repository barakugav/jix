# F020: Python bool index is silently taken as integer 0/1, while np.bool_ raises TypeError

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/shape_ops.rs:273 (related: jix-py/src/array.rs:187 `Array::parse_index`, used by `__getitem__` / `numpy(index)` / `plain(index)`; jix-py/src/ops/shape_ops.rs:200 `jix.slice`; jix-py/src/util.rs:158 `normalize_dim`, which accepts `dim=True` the same way)
- Reachability: Python API
- Reported by: py-ops-shape-ops

## What goes wrong
`parse_basic_index` classifies an index item as an integer whenever `item.extract::<i64>()`
succeeds. Python `bool` is an `int` subclass, so `True`/`False` pass that check and become
indices 1/0: `a[True]` returns row 1 and `a[False]` returns row 0, with the dim dropped.
`np.True_` has no `__index__` (NumPy removed it on purpose), so the same boolean value spelled as a
NumPy scalar raises TypeError. Two spellings of one value therefore give an integer selection in one
case and an error in the other, and the Python-bool case returns data silently. The usual source of
such a scalar - a comparison result or a flag variable - makes the mistake easy to make and hard to
see. NumPy treats a bool scalar index as a 0-d mask (shape `(1, ...)` / `(0, ...)`), and NumPy also
rejects bools where it really wants an integer (`np.sum(x, axis=True)` raises TypeError). The
docstrings of `numpy()` / `jix.slice` list only integers, slices and `...` as valid items, and no
test or "Intentional behaviors" entry covers bools. The context doc lists this only as an
unverified suspicion.

## Trigger
```python
a = jix.compact(np.arange(12, dtype=np.int32).reshape(3, 4))
a[True]             # -> [4 5 6 7], shape (4,)
a[False]            # -> [0 1 2 3], shape (4,)
jix.slice(a, True)  # -> lazy row 1
a.numpy((0, True))  # -> 1 (== a[0, 1]), shape ()
a[np.True_]         # -> TypeError
```

## Repro
`bug-hunt/runs/2026-10-22-trial2/repros/F020.py`, run with `.venv/bin/python` (exit 1 while the bug exists):
```
a[True]                jix=('ok', (4,), [4, 5, 6, 7])  numpy=('ok', (1, 3, 4), [0..11])
a[False]               jix=('ok', (4,), [0, 1, 2, 3])  numpy=('ok', (0, 3, 4), [])
jix.slice(a, True)     jix=('ok', (4,), [4, 5, 6, 7])  numpy=('ok', (1, 3, 4), [0..11])
a.numpy((0, True))     jix=('ok', (), [1])             numpy=('ok', (1, 4), [0, 1, 2, 3])
a[1, False]            jix=('ok', (), [4])             numpy=('ok', (0, 4), [])
a[np.True_]            jix=('error', 'TypeError')      numpy=('ok', (1, 3, 4), [0..11])
FAIL: ... a[True] -> ok but a[np.True_] -> TypeError (inconsistent)
```
Also checked (scratch/F020_verify_dims.py): `jix.sum(a, dim=True)` reduces dim 1, while
`np.sum(a_np, axis=True)` raises `TypeError: an integer is required`. This is the same pattern on the
dims path, through pyo3's `i32` extraction.

## Root cause
jix-py/src/ops/shape_ops.rs:273: `if let Ok(i) = item.extract::<i64>()` is used as the "is an integer
index" test. pyo3's integer extraction accepts any `int` subclass, `bool` included, so the type check
does not reject bools before the value is used as a position. `np.bool_` fails the extraction only
because NumPy removed `bool_.__index__`.

## Suggested fix
Before the integer branch, reject `PyBool` (and `numpy.bool_`, which the extraction already rejects)
with the existing TypeError, or explicitly add NumPy's 0-d mask semantics (insert a new dim of length
1 for True / 0 for False). Rejecting is simpler and matches the documented index grammar. Consider the
same `PyBool` guard for dim arguments (`normalize_dim` callers, util.rs:158).
