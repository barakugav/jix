# F013: Python comparisons of uint64 with int64 run in float64 and return wrong booleans above 2**53

- Severity: medium  Verdict: confirmed  Category: wrong-result (questionable-semantics)
- Location: jix-py/src/ops/cmp.rs:55 (related: cmp.rs:95, 135, 175, 215, 255 - the other five
  comparison tables; jix-py/src/ops/common/dtype_promote.rs:99-112 (u64 -> Int rejected) and
  :118-120 (any int -> f64 accepted); jix-py/src/ops/common/dispatch.rs:180-233 (first matching
  entry wins); jix-py/src/array.rs:1103-1129 (`<`, `<=`, `>`, `>=`, `==`, `!=` call the same functions))
- Reachability: Python API (`jix.equal/not_equal/less/less_equal/greater/greater_equal` and the
  comparison operators on `jix.Array`). Not reachable from Rust: core comparisons require both
  operands to have the same element type, so the caller casts explicitly.
- Reported by: elementwise-ops-cmp-clamp-approx, dynamic-python-differential

## What goes wrong
The six Python comparison functions pick an impl from a same-type table
`[u8, i8, u16, i16, u32, i32, u64, i64, f16, f32, f64, ...]` under Safe casting. No integer slot
holds both a uint64 and an int64 (u64 -> i64 is not Safe, i64 -> u64 is not Safe), and the Safe rule
lets any integer into f64, so a (uint64, int64) pair is compared as float64. Every integer above
2**53 is rounded first, so distinct values compare equal and orderings flip. The output is a
`bool` array, so nothing tells the user that precision was lost (unlike `add(u64, i64)`, whose
float64 dtype shows it). NumPy 2.x compares these pairs exactly. Only the 64-bit pair is affected:
uint64 against int8/16/32 also goes through f64 but stays correct, because a uint64 above 2**53
rounds to a value far above any int32.

## Trigger
```python
a = np.array([2**53, 2**53 + 1], np.uint64)
b = np.array([2**53 + 1, 2**53], np.int64)
jix.equal(jix.compact(a), jix.compact(b)).numpy()   # [True, True], expected [False, False]
jix.less(jix.compact(a), jix.compact(b)).numpy()    # [False, False], expected [True, False]
jix.equal(np.array([2**63 - 1], np.int64), np.array([2**63], np.uint64)).numpy()  # [True]
(jix.compact(np.array([2**60 + 1], np.int64)) == jix.compact(np.array([2**60], np.uint64))).numpy()  # [True]
jix.equal(jix.compact(np.array([2**62 + 1], np.int64)), np.uint64(2**62)).numpy()  # [True]
```
The same happens with compact arrays, numpy arrays passed directly (Plain), typed numpy scalars
and the dunder operators.

## Root cause
`define_op2!` (jix-py/src/ops/common/mod.rs:168-195) makes one same-type descriptor per table entry
with `CastKind::Safe` on both inputs, and `dispatch_args` takes the first entry both operands
Safe-cast to. For (u64, i64): the u64 slot is rejected because Int -> UInt is a down-rank
(dtype_promote.rs:81-83). The i64 slot is rejected because `P8.higher()` is `None`
(dtype_promote.rs:99-112). f16 is skipped (no f16 input), and f32 needs `P8.higher()`, so that is
rejected too. The f64 slot is accepted by the "Allow any precision to be cast to 64-bit
float/complex" short-circuit (dtype_promote.rs:118-120). That rule is a deliberate trade-off for
arithmetic, where the f64 result dtype makes the loss visible. Comparisons reuse it, but their
result is `bool` and an exact mixed-signedness comparison is cheap.

On intent: the py-ops context doc lists "u64 with any signed int -> f64, lossy above 2**53" as
intentional. It cites the promotion test (test_type_promotion.py:182), which checks only that
`add` returns float64, and its comment says "lossy for the top bit", which understates the loss.
No test or doc covers comparisons. The comparison docstrings promise "Safe casting rules", and
the maintainers already removed the same loss above 2**53 for `u64 + Python int`
(test_type_promotion.py:434-439). Comparing two integers and getting the wrong answer is a wrong
result, not a dtype choice. So I rate it medium (wrong results in a rare corner case: both values
above 2**53 and close together) and do not treat it as intended.

## Suggested fix
Give the comparison tables an exact (u64, i64) / (i64, u64) path before the f64 fallback. One way
is a mixed-type descriptor with `CastKind::None` on both inputs, backed by a small core kernel:
for `a: u64, b: i64`, `b < 0 || a > b as u64`, and similar for the other ops. Another way is to
lift both operands into i128 for these two pairs. Add test cases at 2**53 +- 1 and 2**63 +- 1 to
test_type_promotion.py for all six comparisons.
