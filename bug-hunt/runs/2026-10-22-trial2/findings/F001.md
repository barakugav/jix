# F001: Safe-API UB: a writable pull result can be reused as `out` of a larger read; `out` extent is never checked, so reads write past it

- Severity: critical  Verdict: confirmed  Category: unsound-api
- Location: jix/src/storage/buf.rs:282 (`check_out_buf`) (related: jix/src/storage/buf.rs:135 `is_writable`, jix/src/storage/buf.rs:309-317 `materialize_out_buf` pull branch, jix/src/array.rs:938-946 `to_ndarray_buf`, jix/src/storage/plain.rs:476, jix/src/ops/shape_ops/flip.rs:145, jix/src/ops/shape_ops/repeat.rs:195, jix/src/ops/shape_ops/tile.rs:262, jix/src/ops/shape_ops/tile.rs:285, jix/src/storage/compact.rs:411 and 477)
- Reachability: public Rust API (safe code only). Python is not affected: numpy `out=` is validated in jix-py/src/array.rs.
- Reported by: shape-ops-copy-ops

## What goes wrong
A pull read (`Array::to_ndarray_buf(index, ctx, None)`, or `ArrayStorage::read_data(.., None)` through
the public `Array::storage()`) of any materializing op (Flip, Repeat, Tile B/C, Roll wrap, Reshape,
Concatenate, Stack, elementwise ops) returns a `StridedBuf` backed by a `PoolBuf` sized to exactly that
region. `is_writable()` is true for it, and `data_ptr_mut()` returns `Some`. Safe code can pass it back
as `out` of another read that covers a larger region, uses a larger dtype, or reads a different array.
`check_out_buf` checks only the stride count and writability, never that the slice covers
`strided_span_bytes(region, out.strides, itemsize)`. Every storage then writes the full region into the
buffer: Plain (and Compact) copy through raw pointers in `NdCopier`, and Flip/Repeat/Tile first build
`out_buf.get_unchecked_mut(dst_off..)` with `dst_off` past the end. The result is a heap buffer
overflow from 100% safe code.

## Trigger
```rust
let small = Array::plain_ndarray(array![1u8, 2])?.flip(0);
let ctx = ReadContext::default();
let mut buf = small.to_ndarray_buf(&[0..1], &ctx, None)?;   // 1-byte pool buffer, strides [1]
let big = Array::plain_ndarray(array![1u8, 2, 3, 4])?;      // or `.flip(0)` on it
let ctx2 = ReadContext::default();
big.to_ndarray_buf(&[0..4], &ctx2, Some(&mut buf));         // accepted; writes 4 bytes into 1
```

## Root cause
`to_ndarray_buf` and `ArrayStorage::read_data` are safe, so they cannot assume anything about `out`
that safe code can violate. The unsafe constructors (`StridedBuf::from_raw_parts_mut`, buf.rs:85-98)
put the extent requirement on the caller. A pull result, however, is a writable `StridedBuf` that safe
code receives without promising anything, and nothing re-checks the extent when it comes back as `out`:
`check_out_buf` (buf.rs:282-297) does not get the region shape or itemsize. Every `read_data` impl and
the `to_ndarray_buf_slow_dyn` splitter (array.rs:1010+) trust `out` to cover the region. The
`get_unchecked_mut` in flip.rs:145, repeat.rs:195 and tile.rs:262/285, the raw-pointer copies in
NdCopier through `PtrMutNoalias::from_slice(dst)`, and the `get_unchecked_mut` in compact.rs:477 all
rely on that. Pool buffers are sized to the request exactly (`RawAlignedBytes::with_capacity_unchecked`
keeps `capacity == size`), so any larger region, larger itemsize, or wider stride overflows.

## Suggested fix
Check the extent at the points where `out` enters: in `check_out_buf`, pass the region shape and
itemsize and require `strided_span_bytes(region, out.strides(), itemsize) <= out.data().0.len()`. The
extra cost is one span computation per read. `out` must also not have a 0 stride on a dim longer
than 1. A pull result relabeled by Broadcast (broadcast.rs:151) has those aliasing strides and can come
back as `out` the same way. The alternative is to make pull results non-writable for safe callers, e.g.
expose them read-only and keep a writable `out` constructible only through the unsafe constructors.
`ArrayStorage::read_data` is public too, so the check has to be in `check_out_buf` (which every impl
calls), not only in `Array::to_ndarray_buf`.
