# F006: MapMultiple::new skips check_shape_overflow with the output itemsize (incomplete fix of K2), so a widening map_multiple pull read overflows the heap

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/ops/map.rs:237 (MapMultiple::new, map.rs:231-283) (related: jix/src/storage/buf.rs:312,
  jix/src/array.rs:1023, jix/src/array.rs:1058-1061, jix/src/ops/op1.rs:35, jix/src/ops/op2.rs:53,
  jix/src/ops/reduction.rs:166, jix/src/storage/elementwise_pipeline.rs:875-878)
- Reachability: public Rust API (`jix::ops::MapMultiple::new` / `jix::ops::map_multiple`, then
  `Array::to_ndarray_buf(.., None)`). Not exposed to Python (no MapMultiple use in jix-py/src).
- Reported by: concept-integer-width

## What goes wrong
K2 was fixed by moving the "shape * itemsize fits u64" guard into the constructors of the ops that
widen the itemsize: `Op1::new` (op1.rs:35, also used by `Map` and `cast`), `Op2::new` (op2.rs:53,
also used by `Map2` and the comparison ops) and `ReductionOp::new` (reduction.rs:166). The pull
allocation site itself, `materialize_out_buf` (buf.rs:310-316), still computes
`out_shape.product::<usize>() * itemsize` unchecked. `MapMultiple::new` (map.rs:231-283) is the one
dtype-changing constructor that was missed. It only checks that the output dtype is non-zero-sized
(map.rs:237) and that the input shapes match. So a widening closure over a lazily broadcast array is
accepted even when the byte size of the result overflows u64. A pull read then wraps the allocation
size in release builds. The first tile is written at full-shape strides into an 8-byte pooled
buffer, which is a heap buffer overflow. Release builds crash with SIGSEGV. Debug builds panic on the
multiplication.

## Trigger
```rust
let n: u64 = (1 << 61) + 1;          // n * 1 fits u64, so broadcast's check passes
let a = Array::compact_ndarray(&array![7u8])?.broadcast(&[n]);
let m = jix::ops::map_multiple(vec![a], |xs: &[u8]| xs[0] as f64);   // accepted; n * 8 overflows
let ctx = m.read_ctx();
m.to_ndarray_buf(&[0..n], &ctx, None)  // (2^61 + 1) * 8 wraps to 8 bytes
```
The fixed-length-array form (`[a]`, `|xs: [u8; 1]| xs[0] as u64`) is accepted too. Control: the
same trigger through `Map::new_array(a, |x: u8| x as f64)` is rejected with
`InvalidShapeOperation`.

## Root cause
- jix/src/ops/map.rs:231-283: `MapMultiple::new` never calls
  `check_shape_overflow(shape, size_of O)`. Every other constructor that changes the element type
  calls it (op1.rs:35, op2.rs:53, reduction.rs:166). This constructor breaks the invariant that the
  K2 fix relies on: every constructible array has shape * itemsize <= u64::MAX.
- jix/src/storage/buf.rs:312 (and elementwise_pipeline.rs:875-878, pick_output_layout :891): the
  pull allocation size is still an unchecked `product * itemsize`. The strides from
  `strides_for_layout_order` describe the full shape. So the guard at construction is the only
  thing that keeps the allocation and the strides consistent, and one missed constructor is enough
  to cause memory corruption. array.rs:1058-1061 then builds `StridedBuf::from_slice_mut` over the
  8-byte slice with no length check and pushes the first tile into it.
- Separate from this finding: the u64-only check does not protect 32-bit targets, where `usize`
  wraps at 4 GiB (already noted in K2).

## Suggested fix
Add `check_shape_overflow(arrays.shape(0), Dtype::new_ref::<O>().itemsize() as _)?` to
`MapMultiple::new`, next to `check_dtype_size_nonzero` (guarded by `narrays > 0`, as the shape check is). For defense in depth, make the size
computation in `materialize_out_buf` / `materialize_pipeline_out_buf` checked (`checked_mul` plus
`usize::try_from`, returning `Err`). Then a future constructor that misses the check cannot turn
into heap corruption, and 32-bit targets are covered too.
