# F012: Op2::shape assumes its children's shapes are still equal (`assert_unchecked`); a safe user ArrayStorage whose shape changes makes safe code UB (SIGSEGV in release)

- Severity: medium  Verdict: confirmed  Category: unsound-api
- Location: jix/src/ops/op2.rs:182 (related: jix/src/ops/op2.rs:41-53 the only real check, in `Op2::new`; jix/src/util/mod.rs:550-555 `assert_unchecked_eq!`; jix/src/ops/cmp.rs:435 Greater/GreaterEqual build `Op2::new(b, a, ..)`; jix/src/ops/cmp.rs:987 ApproxEq; jix/src/ops/map.rs:120 Map2; jix/src/storage/core_trait.rs:56 safe `pub trait ArrayStorage`; jix/src/array.rs:1605 safe `Array::from_storage`; same pattern on `dtype()`: jix/src/ops/into_type.rs:88, :103)
- Reachability: public Rust API (needs a user `ArrayStorage` impl; not reachable from Python or from any built-in storage, whose shapes are fixed)
- Reported by: elementwise-ops-cmp-clamp-approx

## What goes wrong
`Op2::shape` returns `a.shape()` after `assert_unchecked_eq!(a.shape(), b.shape())`, which is
`debug_assert_eq!` plus `std::hint::assert_unchecked`. The two shapes are compared for real only once,
in `Op2::new`. `ArrayStorage` is a safe, unsealed public trait and `Array::from_storage` is safe, so a
user storage (it can forward `read_data`/`dtype`/`spec`/`info` to a jix storage and use the public
`jix::ops::IntoType` for `element_type_change`) may report a different `shape()` later. Then a plain
`.shape()` call on any Op2-based array (Add, Sub, Mul, Div..., Pow, Maximum/Minimum, bitwise ops,
Equal/Less/Greater/..., ApproxEq, Map2) executes `assert_unchecked(false)`: UB from safe code. Debug
builds panic in the debug_assert; in release LLVM uses the false fact, and in the repro it turns an
empty shape slice into an 8-element one and reads through its dangling pointer (SIGSEGV).

## Trigger
User storage `Shifty` wraps a `Compact<i32>` and returns `&self.alt` from `shape()` once a shared
`AtomicBool` is set.
- Smallest: `let sum = jix::ops::Add::new_array(shifty /* inner shape [3] */, a /* [3] */)?;`
  (or `a.greater(shifty)`), set the flag (`alt = [7]`), call `sum.shape()`.
- Release crash: child 1 = `Shifty` over a `[1; 8]` compact array with `alt = vec![]`, child 2 = a
  storage returning the constant `&[1u64; 8]` static. Build `Add`, set the flag, then
  `arr.shape().iter().product::<u64>()`.

loop of the test closure: the slice really is `(ptr 0x8, len 0)` (the control prints exactly that for
the same storage without Op2), but after the assume the compiler uses `len == 8` from the constant
other child and dereferences the dangling pointer.

## Root cause
op2.rs:180-184 turns a property that was checked once at construction (op2.rs:41-53) into a permanent
optimizer assumption, but the property depends on `ArrayStorage::shape()` of arbitrary child storages
staying constant, which a safe trait cannot promise (nothing in the `ArrayStorage` docs even states
it). The `assert_unchecked` buys essentially nothing: `shape()` returns only `a`'s slice. This is one
instance of the library-wide trust in safe `ArrayStorage` impls (context doc R3): into_type.rs:88/103
do the same with `dtype()` stability, and Where / SubDtype trust user `read_data` buffers for bounds.

## Suggested fix
Drop the `assert_unchecked` in `Op2::shape` (keep `debug_assert_eq!` if wanted), or store the shape
(a `DimArray<u64>`) in `Op2` at construction and return that. Same for into_type.rs:88/103 (a plain
`debug_assert`, or re-check the dtype where it matters).
For the class as a whole, either make `ArrayStorage` an `unsafe trait` whose docs state the invariants
(stable shape/dtype, `read_data` buffers valid for the requested region) or seal it.
