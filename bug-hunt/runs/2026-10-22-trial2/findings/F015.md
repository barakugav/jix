# F015: f64 -> f16 conversion double-rounds through f32 (cast, asarray(dtype=f16), Python floats with f16 arrays)

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/cast.rs:59 (related: jix/src/ops/cast.rs:280 (Complex<f64> -> Complex<f16> per component), jix/src/ops/cast.rs:554 (test oracle `CastTo<f16>` uses the same formula), jix-py/src/ops/common/operand.rs:425 (`Scalar::cast` to F16 for Python floats))
- Reachability: public Rust API and Python API
- Reported by: dynamic-python-differential

## What goes wrong
`Cast<f16>` is generated for every source type as `f16::from_f32(value as f32)`. For an f64 source
this rounds twice: f64 -> f32 (ties-to-even) and then f32 -> f16 (ties-to-even). When the first
rounding lands exactly on an f16 halfway point, the second one breaks the tie to even, which can be
the wrong neighbour: the result is 1 f16 ulp off the correctly rounded value that numpy
(`astype(np.float16)`, `np.float16(x)`) produces. It affects `Array::cast::<f16>()` of f64 data,
`Complex<f64> -> Complex<f16>`, Python `jix.cast(f64, np.float16)` / `jix.asarray(f64, dtype=np.float16)`,
and every binary/ternary op that mixes an f16 array with a Python float (the float is converted with
`Scalar::cast(F16)` -> core `Cast<f16>`): add, maximum, where, etc. About 4-7 in 100000 random f64
values convert wrongly. The codebase otherwise avoids exactly this hazard (cast.rs:213, 245 disable
the i64/u64 -> f32 SIMD path because it "would round twice through f64").

## Trigger
x = 1 + 2^-11 + 2^-40 (strictly above the midpoint 1 + 2^-11 between f16 neighbours 1.0 and
1 + 2^-10; `x as f32` rounds to exactly that midpoint).
- Rust: `Array::compact_ndarray(&array![x]).unwrap().cast::<f16>()` -> 1.0 (expected 1.0009765625);
  `<f64 as Cast<f16>>::cast(x)` -> 1.0; `Complex{re: x, im: -x}` -> (1.0, -1.0).
- Python: `jix.add(np.zeros(2, np.float16), x)`, `jix.maximum(...)`, `jix.where(c, x, a)`,
  `jix.cast(np.array([x]), np.float16)`, `jix.asarray(np.array([x]), dtype=np.float16)` -> 1.0
  (numpy: 1.0009765625).

## Root cause
cast.rs:59 `(@scalar_to f16, $value:expr) => { f16::from_f32(($value) as f32) }` is used for all
sources. For integer sources it is fine (every integer below the f16 overflow threshold is exact in
f32), but f64 has 53 significand bits and f32 only 24, so `as f32` can create an exact f16 tie that
was not there. f16 casts have no SIMD bulk path (`bulk=("disabled")`), so the scalar path is the
only one. The test oracle (cast.rs:554 `impl_cast_to_f16!`) uses the same formula, so the unit tests
agree with the bug. No intentional-behavior note covers this (py-ops.md lists it only as a
suspicion).

## Suggested fix
Special-case f64 -> f16 with a single correct rounding, e.g. round to f32 with round-to-odd and then
`f16::from_f32` (f32 has >= 11 + 2 bits, so this is exact): `let y = x as f32; if y.is_finite() &&
y as f64 != x && y.to_bits() & 1 == 0 { y = f32::from_bits(if (y as f64).abs() < x.abs() {
y.to_bits() + 1 } else { y.to_bits() - 1 }) }; f16::from_f32(y)`. Do NOT switch to
`half::f16::from_f64`: in half 2.7.1 it is not correctly rounded either (with F16C it does
`f as f32` + vcvtps2ph; its software fallback, used by jix's no-std `half`, drops the low 32
mantissa bits from the sticky bit - 482 wrong of 1e6 in the repro sweep). Fix the test oracle at
cast.rs:554 the same way (or compare against an exact reference) so the unit tests can catch it.
