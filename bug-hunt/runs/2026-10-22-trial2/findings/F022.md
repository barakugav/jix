# F022: Dim lengths > i64::MAX are cast `as i64` in parse_basic_index, flatten and core DimSlice::resolve, so such dims cannot be indexed, x[-2**63] overflows, and flatten raises

- Severity: low  Verdict: confirmed  Category: overflow
- Location: jix-py/src/ops/shape_ops.rs:317 (related: jix-py/src/ops/shape_ops.rs:318 (`i + len`
  overflow), :309 and :370 (ellipsis / trailing fill `end: Some(shape as i64)`), :333-341 (slice
  path), :821 (`flatten`: `size as i64`); jix/src/ops/shape_ops/slice.rs:365-367 (core
  `DimSlice::resolve`: `idx + dim_len as i64`, `0..=dim_len as i64`); jix-py/src/array.rs:192-193
  (`Array.parse_index` casts the i64 endpoints back `as u64`))
- Reachability: Python API (`a[...]`, `Array.numpy(index=...)`, `jix.slice`, `jix.flatten`) and
  public Rust API (`Slice::new_array` / `Array::slice` with explicit bounds)
- Reported by: py-ops-shape-ops, shape-ops-copy-ops

## What goes wrong
jix shapes are u64, and `check_shape_overflow` (jix/src/error.rs:186) only bounds
`prod(shape) * itemsize`. A 1-byte dtype (u8 / i8 / bool) can therefore have a dim of up to
`u64::MAX` as a lazy repeat / tile / broadcast view and read small sub-regions of it. F009 relies
on the same fact. The Python index parser takes `len = shape[dim] as i64`, which is negative for
these dims. Every integer or slice index on the dim then fails the `>= len` check, including
`x[0]`, `x[-1]`, `x[0:2]` and even `x[:]`. The IndexError reports a negative "size". `x[-2**63]`
computes `i + len` with `len == -1`, which panics with "attempt to add with overflow" in debug
builds. Release builds wrap here and still raise IndexError. `jix.slice` on another dim of such an
array also fails, because the ellipsis / trailing fill hands core `Slice` `end = shape as i64`.
Core `DimSlice::resolve` has the same cast, so it rejects every explicit endpoint on a huge dim,
`0..2` included, and `-2..` overflows in debug builds. `jix.flatten` casts the element count
`as i64`. For sizes in (i64::MAX, u64::MAX) it raises "shape must be non negative or -1", while
`jix.reshape(y, -1)` works. No silent wrong value was found: every path ends in an error (or a
debug panic), because the final check is against a negative length.

## Trigger
```python
K = (2**64 - 1) // 3
x = jix.repeat(np.arange(3, dtype=np.uint8), K)       # shape (2**64-1,)
x[0]; x[-1]; x[0:2]; x[:]                              # IndexError ... size -1
x[-2**63]                                              # PanicException (debug), IndexError (release)
jix.slice(jix.insert_dim(x, 0), 0)                     # RuntimeError from core Slice
y = jix.repeat(np.array([0, 1], np.uint8), 2**62 + 1)  # shape (2**63+2,)
jix.flatten(y)                                         # ValueError; reshape(y, -1) works
```
Rust: `Array::compact_ndarray(&array![0u8,1,2])?.tile(3074457345618258603, 0)` (len 2^63+1), then
`Slice::new_array(t, (0u64..2,).into())` returns Err, and `(-2i64..,)` panics at slice.rs:365.

## Root cause
`parse_basic_index` (jix-py/src/ops/shape_ops.rs:317, :333) and `DimSlice::resolve`
(jix/src/ops/shape_ops/slice.rs:365-367) do their bounds arithmetic in i64 after a lossy
`u64 as i64` of the dim length. `SliceItem` endpoints are i64, so the parser also emits
`Some(shape as i64)` for filled dims (:309, :370) instead of `None`. `Array.parse_index`
(array.rs:192-193) happens to undo that cast with `as u64`, so `__getitem__` survives the fill, but
`jix.slice` hands the negative end to core. `flatten` (:821) builds the reshape target through
`ItemOrTuple<i64>`. Only `size == u64::MAX` survives that round trip, because it becomes `-1` and
is inferred.

## Suggested fix
Keep `len` as u64 in `parse_basic_index`. Resolve a negative index as
`len.checked_sub(i.unsigned_abs())` and a non-negative one as `i as u64 < len`. Have
`ParsedBasicIndex` carry `Range<u64>`, or emit `None` endpoints for filled dims. In core
`DimSlice::resolve`, resolve endpoints the same way (or in i128) instead of using `dim_len as i64`.
In `flatten`, call core `Reshape` with the u64 size directly instead of going through the i64
`reshape` argument.
