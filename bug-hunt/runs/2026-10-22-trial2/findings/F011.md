# F011: An 8 KB Strict-valid archive that declares a 34 GB block aborts the process (Rust and Python) on its first read, with an allocation failure instead of an error

- Severity: medium  Verdict: confirmed  Category: resource
- Location: jix/src/archive/array.rs:497-506 (the only bound on the block size: its element count fits u32) (related: jix/src/archive/block.rs:373-381 (block_size only checked > 0 and divides nitems), jix/src/storage/compact.rs:395-398 (full-block scratch allocated before any decode), jix/src/codec/mod.rs:276-279 (second full-block tmp when filters are on), jix/src/storage/block.rs:180 (`block_size * itemsize` used as the buffer length), jix/src/util/buf_pool.rs:45 + jix/src/util/aligned_vec/raw.rs:205-210 (`handle_alloc_error` aborts), jix-py/src/archive.rs:91 (Python `read_array`); companion of F005, which covers the 32-bit wrap of the same product)
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file*` with `ArchiveValidation::Strict`, then any read) and Python API (`jix.read_array(path, validation="strict")`, then `a[1:2].numpy()`)
- Reported by: codec-archive-codec-pipeline

## What goes wrong
The per-block element count `block_size` and the itemsize come from the untrusted header. Load-time
validation only requires the block product to fit u32 and the itemsize to fit u16. Nothing ties
`block_size * itemsize` (up to about 2^32 * 65535 = 2.8e14 bytes) to the data in the file. The
first read of any element allocates one full block of scratch (`read_data_slow`), plus a second one
in `Decoder::decode` when filters are on. These go through `BufferPool::get` ->
`RawAlignedBytes::with_capacity_unchecked`, which calls `handle_alloc_error` when the allocator
returns null. That aborts the whole process, including a Python interpreter that only called
`read_array`. Strict validation, which the docs recommend "whenever the archive's origin is
untrusted or unverified" (archive/mod.rs:43-45), never returns an Err for this file.

## Trigger
Write `Array1::from_elem(1 << 21, [0u8; 128])` with `block_shape [2^21]` and no filters. In the
metadata before the first zstd frame, patch the four 4-byte uleb128 varints `80 80 80 01` (2^21:
shape, block_shape, nitems, block_size) to `FF FF FF 7F` (2^28 - 1). The varint lengths do not
change, so every length prefix stays valid. The result is an 8331-byte file (8339 bytes from
Python, with a struct dtype). `read_from_reader(.., Some(len), .., Strict)` returns Ok with shape
`[268435455]` and block bytes 34_359_738_240. Then call `a.to_ndarray_sub::<Ix1>(&[1..2], &ctx)`.

  47-bit x86_64 user address space, so a crafted file can make the allocation fail on any such
  machine.

## Root cause
`ArrayBlockTableStorageBase::read_from` (archive/array.rs:497-506) and `BlockTable::read_content`
(archive/block.rs:373-381) validate the block's element count, but not its byte size against
anything the file actually contains. `tune` / `into_spec` (storage/params.rs:321-424, 492-525) add
only `check_shape_overflow` (u64 product). The read path then trusts that one block's bytes can be
allocated. `read_data_slow` allocates `full_buf_len` before decoding anything
(storage/compact.rs:395-397). The aligned fast path and `Decoder::decode`'s filter tmp
(codec/mod.rs:276-278) do the same. The pool allocates infallibly
(util/buf_pool.rs:45 -> util/aligned_vec/raw.rs:205-210, `handle_alloc_error`), so the result is
an abort, not an `Err`.

## Suggested fix
Two complementary fixes:
1. Make block buffers fallible. Add a `try_get` / `try_allocate_buf` that returns
   `Err(OutOfMemory/InvalidArchive)` on a null allocation, and use it for the block scratch in
   `read_data_slow`, `Decoder::decode` and `materialize_out_buf`. This also covers a legitimately
   huge block read on a smaller machine.
2. Reject implausible blocks early. Under Strict (O(nblocks)), read each block's zstd frame
   content size (`ZSTD_getFrameContentSize`) and require it to equal `block_size * itemsize`, or
   bound `block_size * itemsize` by the block's compressed length times zstd's maximum ratio. At
   minimum, check a block's declared content size before allocating its scratch in `read_block`.
   On 32-bit, combine this with F005's `isize::MAX` bound in `tune`.
