# F018: Python numpy(out=x) never checks that x overlaps a buffer the array reads: `&mut [u8]` over memory a live `&[u8]` input covers (UB) and order-dependent wrong values, also without any explicit asarray

- Severity: medium  Verdict: confirmed  Category: memory-safety
- Location: jix-py/src/array.rs:603-627 (related: jix-py/src/array.rs:218-288 `check_output_array`, jix-py/src/array.rs:469-485 docstring warning, jix/src/storage/elementwise_pipeline.rs:278-284 and :411-417 `PtrMutNoalias` over the output chunk, jix/src/storage/plain.rs:471-476 `&[u8]` src + `copy_from`, jix/src/storage/buf.rs:221-239 `copy_from` -> NdCopier with `PtrNoalias`/`PtrMutNoalias`, jix-py/src/ops/common/operand.rs:177-191 zero-copy Plain over a numpy buffer)
- Reachability: Python API
- Reported by: pipeline-driver

## What goes wrong
`Array.numpy(out=x)` builds a `&mut [u8]` (`std::slice::from_raw_parts_mut`, array.rs:606) and a
writable `StridedBuf` (array.rs:619) over `x`, then reads the whole lazy chain into it. Nothing
checks whether `x` shares memory with a `Plain` leaf of that chain. Such leaves are zero-copy views
over numpy buffers, made by `jix.asarray`, and also by the implicit numpy-to-jix conversion of every
operator and `jix.*` function. During the read, `Plain::read_data` holds a `&[u8]` over the same
bytes (plain.rs:471), and the element-wise driver passes a `noalias` `&mut [u8]` for each output
chunk to the `#[inline(never)]` inner loop (elementwise_pipeline.rs:280). Non-lazy shape views go
through `copy_from`/NdCopier (buf.rs:232-233), whose contract is "no overlap". So this is UB under
Rust's aliasing rules. In practice the result is silently wrong, and which values are wrong depends
on the visit order and the SIMD lane width (case C below: the first 64 elements are right, after
that the values double over and over). NumPy's ufuncs detect an overlapping `out=` and buffer
through a temporary. Users write `np.add(x, 1, out=x)` as the normal in-place idiom, so they will
expect the jix equivalent to work.

The docstring (array.rs:469-485) calls this undefined behavior, which is why I did not mark it
`intended`:
- The docstring describes the hazard too narrowly ("built by `jix.asarray()` over the very NumPy
  array being passed as `out`"). Case B below never calls `asarray`, and its input is a *view*
  (`x.T`) of `out`, not the same array. The operator wraps it zero-copy by itself.
- A pure-Python API that can be driven into UB and silent corruption, when an overlap check is
  cheap, is unreasonable on its own merits. The primer's checklist names this exact pattern as a
  target.

## Trigger
```python
x = np.arange(16, dtype=np.float32).reshape(4, 4)
(jix.asarray(x).T + 0).numpy(out=x)                       # A
c = jix.compact(np.ones((4, 4), np.float32))
(c + x.T).numpy(out=x)                                    # B: no asarray anywhere
y = np.arange(100, dtype=np.int64)
(jix.asarray(y[:-1]) * 2).numpy(out=y[1:])                # C: shifted 1-d
jix.asarray(x).T.numpy(out=x)                             # D: no element-wise op (Plain push copy)
```

The hunter's shifted case (`(b + 1).numpy(out=y[1:])` over `arange`) only looked right because,
for `y = arange`, an overwritten `y[i]` equals `y[i-1] + 1`, which is the original value. Case C,
with `* 2`, shows the corruption. Miri was not run: it cannot run the PyO3 extension. A Rust-only
version would have to call the unsafe `Plain::new` / `StridedBuf::from_raw_parts_mut` in breach of
their own contracts, so it could not serve as a regression test. The UB follows directly from
`slice::from_raw_parts_mut` (array.rs:606), whose result is live while plain.rs:471 builds a
`&[u8]` over the same bytes.

## Root cause
`numpy()` (array.rs:603-627) is the unsafe caller of `slice::from_raw_parts_mut` and
`StridedBuf::from_raw_parts_mut`. Both require exclusive access to the destination bytes for the
duration of the read. `check_output_array` (array.rs:218-288) checks the dtype, shape, writeability,
alignment, and negative or zero strides, but not overlap. The Python `Array` keeps no record of
which numpy buffers its chain borrows, so the binding cannot check either. The core relies on
non-overlap in its noalias inner loops (elementwise_pipeline.rs:278-284, 411-417) and in NdCopier
(buf.rs:221-239), and its safe Rust API gets that guarantee from borrowck. Python bypasses
borrowck through raw pointers.

## Suggested fix
Make the Python `Array` (or a core visitor on `ArrayStorage`) report the byte ranges of the
`Plain` leaves it borrows. In `numpy(out=)`, intersect `out`'s span with each of them, as
`np.may_share_memory` does. On overlap, either decode into a fresh temporary and copy it into
`out`, as NumPy does, or raise ValueError. Remove the UB warning from the docstring after that, or
at least widen it to cover implicit conversion and views of `out`.
