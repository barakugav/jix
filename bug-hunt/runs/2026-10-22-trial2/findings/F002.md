# F002: numpy bool arrays with bytes other than 0/1 are wrapped zero-copy and read as Rust `bool` (UB); reductions, comparisons, bitwise ops and where return wrong results

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix-py/src/ops/common/operand.rs:184 (related: jix/src/storage/plain.rs:108-115,
  jix/src/storage/plain.rs:421, jix/src/dtype.rs:338, jix/src/ops/reduction.rs:980,
  jix/src/ops/reduction.rs:994, jix/src/ops/reduction.rs:1101, jix/src/ops/reduction.rs:2882,
  jix/src/ops/reduction.rs:2949, jix/src/ops/where_op.rs:277-283, jix-py/src/ops/as_array.rs:61)
- Reachability: Python API (every function that accepts a numpy array). From Rust only through the
  `unsafe` `Plain::new`, whose documented safety contract does not mention element validity.
- Reported by: reduction-fold-loops, elementwise-ops-cmp-clamp-approx

## What goes wrong
`Operand::from_any_with_params` wraps every n-d numpy array zero-copy as `Plain` storage and never
checks the bytes. The jix bool dtype is "a single byte with value 0 or 1" (jix/src/dtype.rs:338).
NumPy has no such rule: `u8_arr.view(bool)`, `np.frombuffer(buf, dtype=bool)` and `np.memmap` all
produce bool arrays holding any byte value, and NumPy reads nonzero as True. Every jix bool consumer
then reads those bytes as typed Rust `bool`. A `bool` with value 2 is immediate UB, and Miri reports
it. In practice the results are silently wrong: `all`, `min`, `sum`, `mean`, `argmax`, `any`,
`equal`, `&` and `where` all disagree with NumPy. `jix.compact` stores the invalid bytes, so every
later read of the compressed array is affected too. I found no memory corruption on this path. The
damage I saw is wrong values, but the compiler is entitled to do anything.

## Trigger
```python
raw = np.array([2, 1, 4, 1, 2, 2, 1, 8] * 5, dtype=np.uint8)
b = raw.view(np.bool_)                       # all truthy for NumPy
jix.all(b), jix.sum(b), jix.argmax(b), jix.min(b), jix.mean(b)
jix.any(np.frombuffer(bytes([2, 4] * 20), dtype=np.bool_))
m = np.array([[2, 1, 4], [1, 2, 1]], np.uint8).view(np.bool_); jix.all(m, dim=0); jix.sum(m, dim=0)
x = np.array([2, 2, 0, 0, 2, 1] * 16, np.uint8).view(bool)
y = np.array([1, 0, 2, 1, 2, 2] * 16, np.uint8).view(bool)
jix.equal(x, y); jix.asarray(x) & jix.asarray(y); jix.where(x, np.arange(96, dtype=np.int32), -1)
```
0-d inputs are not affected, because they go through `item()`, which normalizes the value
(operand.rs:99-153).

## Root cause
operand.rs:184 calls `Plain::new` and gives the numpy buffer the jix dtype returned by
`dtype_from_numpy` (operand.rs:98). Nothing checks that the bytes are valid for that dtype. The
public contract makes this easy to miss. `Array::plain_ndarray_ptr` requires "Elements accessed by
the data pointer must be valid for the specified dtype" (plain.rs:421). `Plain::new`, which the
wrapper actually calls, lists only pointer validity and readability in its `# Safety` section
(plain.rs:108-115). Downstream, the bool kernels assume 0/1:
- the reduction fold loops read typed `bool` (reduction.rs:980/982/994/999/1101/1103);
- `All` computes `state & item` and `Any` computes `state | item` (2882/2949);
- the comparison and bitwise kernels and `where` (where_op.rs:277-283, 305) do the same.
Struct dtypes with a bool field are affected the same way.

## Suggested fix
In `Operand::from_any_with_params`, do not wrap a bool numpy array (or a struct dtype that contains
a bool field) zero-copy without checking it. One option is to scan the array as `u8` and, when some
byte is above 1, use a normalized copy (`arr.view(np.uint8) != 0`) or raise ValueError. The other is
to always normalize bool inputs. Also add the element-validity requirement to `Plain::new`'s
`# Safety` section. Separately, archive load of a bool dtype has no 0/1 validation either (see the
elementwise-ops context doc, R4). That path is not covered by this fix.
