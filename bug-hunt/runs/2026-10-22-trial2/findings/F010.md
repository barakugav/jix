# F010: Concatenate::new sums concat-dim lengths unchecked: overflow panics (debug) or wraps to a tiny wrong shape (release)

- Severity: medium  Verdict: confirmed  Category: overflow
- Location: jix/src/ops/shape_ops/concatenate.rs:111 (related: jix/src/ops/shape_ops/concatenate.rs:114, jix-py/src/ops/shape_ops.rs:903)
- Reachability: public Rust API (`Concatenate::new` / `new_array` / `ops::concatenate`) and Python API (`jix.concatenate`)
- Reported by: py-ops-shape-ops

## What goes wrong
`Concatenate::new` adds up the inputs' lengths on the concat dim with a plain `+=`. It calls
`check_shape_overflow` only after the loop. When the lengths add up past `u64::MAX`, a debug build
panics with "attempt to add with overflow", even from the `Result`-returning constructor. In
Python that shows up as `pyo3_runtime.PanicException`.

Release builds have overflow checks off, so the sum wraps. For example, 2*(2^63+2) becomes 4. The
wrapped shape then passes `check_shape_overflow`, and `borders` ends up out of order
(`[2^63+2, 4]`). The result is an `Ok` array with a silently wrong shape (`[4]`) whose data is the
first 4 elements of input 0. If there are more than 32 inputs, the out-of-order `borders` also
breaks the `partition_point` lookup (concatenate.rs:234), which needs `borders` sorted.

## Trigger
Each input needs a concat-dim length near 2^63, which takes a 1-byte dtype (u8/bool) and a lazy
view (broadcast/repeat/tile), so no memory is used.
- Rust: `a = compact([7u8]).broadcast(&[2^63+2])`, `b = compact([9u8]).broadcast(&[2^63+2])`,
  `Concatenate::new_array((a, b), 0)`.
- Python: `y = jix.repeat(np.array([0, 1], np.uint8), 2**62 + 1)` (length 2**63+2), then
  `jix.concatenate([y, y])`.

Expected: an `Err` (`InvalidShapeOperation`, "shape has overflowed") / a regular Python exception.

## Repro
- `jix/tests/repro_2026_10_22_trial2__f010.rs` (asserts `Err`; fails while the bug exists)
  - `cargo test --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_22_trial2__f010 -- --nocapture`
    -> `panicked at ./src/ops/shape_ops/concatenate.rs:111:13: attempt to add with overflow`
  - same with `--release` ->
    `expected Err, got Ok with shape [4], data = Ok([7, 7, 7, 7], shape=[4], ...)`
- `bug-hunt/runs/2026-10-22-trial2/repros/F010.py` (run with `.venv/bin/python`, debug extension):
  `y.shape = (9223372036854775810,)`, then
  `panicked at .../concatenate.rs:111:13: attempt to add with overflow`,
  `BUG: raised pyo3_runtime PanicException attempt to add with overflow`, exit 1.

## Root cause
concatenate.rs:111 `shape[dim] += shape_i[dim];` is unchecked. The overflow guard at
concatenate.rs:114 (`check_shape_overflow(&shape, itemsize)`) only checks the product of the
already-summed shape, so it never sees a sum that has wrapped. Nothing upstream limits a single
dim: `check_shape_overflow` allows any length up to `u64::MAX` for itemsize 1, and Broadcast,
Repeat and Tile produce such dims. The Python wrapper (jix-py/src/ops/shape_ops.rs:868-903) checks
only ndim and dtype before calling `Concatenate::new_array`. The context doc lists this as an
unverified suspicion, not an intentional behavior.

## Suggested fix
Use `shape[dim] = shape[dim].checked_add(shape_i[dim])` and on `None` bail with
`InvalidShapeOperation` (the same error kind `check_shape_overflow` uses), before pushing to
`borders`.
