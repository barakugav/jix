# F024: numpy operand on the left of an operator with a jix.Array never reaches jix's reflected op (object ndarray of whole jix arrays; comparisons raise)

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/array.rs:124 (the `#[pyclass]` of `Array`: there is no `__array_ufunc__ = None` and no `__array_priority__`) (related: jix-py/src/array.rs:832 `__radd__` and the other reflected dunders, jix-py/src/array.rs:1103-1131 comparison dunders, jix-py/src/array.rs:393 `__bool__`, jix-py/python/tests/test_op2.py:75-77)
- Reachability: Python API
- Reported by: dynamic-python-differential

## What goes wrong
For `ndarray OP jix.Array`, Python calls `ndarray.__add__` (etc.) first. numpy defers (returns
NotImplemented) only if the other operand sets `__array_ufunc__ = None` or has a higher
`__array_priority__`. `jix.Array` has neither, so numpy treats it as an opaque Python object:
it builds a 0-d object array, broadcasts it against the ndarray and runs the object loop. The
result is a numpy `object` ndarray of the ndarray's shape whose every element is a whole lazy
jix Array (`a[i] + j`), so the dtype, shape and values are all wrong and nothing signals it. For
comparisons the object loop calls `bool()` on each element array, and `Array.__bool__` raises
ValueError. jix already defines `__radd__`, `__rsub__`, ... and `jix.add(ndarray, Array)` is
correct, so Python would call the right code if numpy deferred. With a numpy scalar on the left
the result is a jix Array, but numpy first turns the scalar into an untyped Python number, so
the result dtype differs from `jix OP scalar`: `np.int16(3) + int8 jix` is int8, while
`int8 jix + np.int16(3)` is int16. `test_op2.py:75-77` notes the scalar effect and works around
it with `jix.add`. Mixing numpy data with jix arrays in operations is a documented use
(`jix-py/docs/module.md:89`), and the result depends on which side the numpy operand is on, so
users will see this as a bug. It is not listed as intentional in py-core.md, py-ops.md or
KNOWN.md.

## Trigger
```python
a = np.array([1, 2, 3], np.int32)
j = jix.compact(np.array([10, 20, 30], np.int32))
a + j    # object ndarray shape (3,), a[0]+j etc.; expected jix Array int32 [11, 22, 33]
a < j    # ValueError: the truth value of a jix.Array is ambiguous
np.int16(3) + jix.compact(np.int8([1, 2, 3]))   # int8; reflected jix op gives int16
```
This affects all 17 binary operators: + - * / // % & | ^ << >> < <= > >= == !=.

## Root cause
`jix-py/src/array.rs:124-128` declares the class without the NumPy binop-deferral protocol. In
numpy's `binop_should_defer` (used by `ndarray.__add__` and the scalar binops), an operand
without `__array_ufunc__` and with the default priority does not defer. numpy then calls the
ufunc with the jix Array coerced to `np.asarray(j)`, which is `array(Array(...), dtype=object)`.
The reflected dunders at array.rs:832ff are therefore never reached when a numpy object is on
the left.

## Suggested fix
Add a class attribute `__array_ufunc__ = None` to `Array` (a `#[classattr]` returning
`py.None()`). numpy then returns NotImplemented from `ndarray.__op__` and from numpy scalar
binops, so Python falls through to jix's `__r<op>__` and reflected comparisons. A side effect:
`np.add(ndarray, jix_array)` and in-place `ndarray += jix_array` would raise TypeError instead
of producing object arrays. Optionally also add an `__array__` method so `np.asarray(j)`
materializes. Add `ndarray OP Array` cases to test_op2.py / test_cmp.py.
