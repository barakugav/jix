# F017: Contiguous inner-loop lane count ignores element width: wide element types overflow a 2 MiB thread stack and abort

- Severity: low  Verdict: confirmed  Category: resource
- Location: jix/src/storage/elementwise_pipeline.rs:688-690 (related: jix/src/util/mod.rs:802-807
  (`prev_power_of_two(0) == 1`); jix/src/storage/elementwise_pipeline.rs:691-694 (the strided arm,
  capped by `LanesInfo`); jix/src/ops/common.rs:49-55 (`LanesInfo::LANES`, 128 bytes per lane
  array); jix/src/storage/elementwise_pipeline.rs:619-626 (`[T; LANES]` chunk returned by value and
  stored); jix/src/storage/elementwise_pipeline.rs:665 (runtime `dispatch!`, one monomorphized copy
  per SIMD level); jix/src/dtype.rs:1186-1197 (`[T; N]` is `Dtyped` up to `u16::MAX` bytes))
- Reachability: public Rust API (`map`, and any element-wise op whose `T` is a wide `Dtyped`, e.g.
  `[u8; 60000]` or a large `#[derive(Dtyped)]` struct). Not reachable from Python: the bindings only
  dispatch element-wise ops over scalar dtypes (`jix-py/src/ops/common/dispatch.rs:63-70`).
- Reported by: pipeline-driver

## What goes wrong
When every operand and the output are contiguous, `inner_loop_per_level` sets the lane count to
`used_simd_registers * prev_power_of_two(S::u8s::LEN / P::MAX_ITEMSIZE)`. The formula is meant to
limit the working set to about 8 SIMD registers (4 on x86). When an element is wider than one register
(more than 64 bytes with AVX-512, 32 with AVX2, 16 with SSE/NEON), the quotient is 0, and
`prev_power_of_two(0)` returns 1. LANES therefore stays at 8 (4 on x86) for every element width.
Every node in the fused tree then returns a `[T; 8]` by value: the leaf read, each `Map`/`Op1`
result, the `transmute_copy` copies, and the chunk stored by `inner_loop_impl`. Stack use grows by
`8 * size_of::<T>()` per temporary, with no cap. The strided loop caps the same arrays at 128 bytes
per lane array through `LanesInfo`, so it uses one lane for elements over 128 bytes. The contiguous
loop has no such cap. In a release build, a two-map pipeline over 60000-byte elements needs about
2.8 MiB of stack. The same pipeline over a strided view of the same data needs about 79 KiB. The
default stack for a spawned thread is 2 MiB, and the contiguous case aborts the process with a stack
overflow. This is an abort, not a catchable panic.

## Trigger
Release build, x86_64 host (AVX-512 here). The pipeline runs on a thread with Rust's default 2 MiB
spawned-thread stack:
```rust
let data = Array1::from(vec![[1u8; 60000]; 32]);
let a = Array::plain_ndarray_view(data.slice(s![..16])).unwrap();   // contiguous input
a.map(|x: [u8; 60000]| x).map(|x: [u8; 60000]| x).to_ndarray::<Ix1>()
```
In debug builds the threshold is lower. The hunter saw 16384-byte elements overflow a 2 MiB thread,
which is also the stack `cargo test` gives each test. Debug builds are stack-hungry on the strided
path too, though: the strided control at 60000 bytes needs about 6.7 MiB in debug. So the 8x lane
factor accounts for only part of the debug numbers.

## Repro
`jix/tests/repro_2026_10_22_trial2__f017.rs`. Each case runs in a child process, so the abort shows
up as a test failure. The parent re-executes the test binary with `--exact child_*`.

In the debug build both default-stack tests fail, the strided control included, because of
general debug-build stack bloat. The release run is the one that isolates the defect: same data, same
op chain and same thread stack, and only the contiguous path aborts.

## Root cause
elementwise_pipeline.rs:688 divides the register width by `MAX_ITEMSIZE`. When that quotient is 0,
the result should be an element count below one register. Instead, `prev_power_of_two` (util/mod.rs:802-807)
turns 0 into 1, so the "8 registers" budget becomes "8 elements" of any size. The const block only
asserts `lanes <= 512` and a power of two, and nothing bounds `lanes * size_of::<T>()`. Wide `T`
is a supported dtype (dtype.rs:1186-1197 accepts `[T; N]` up to 65535 bytes, and
`#[derive(Dtyped)]` structs have no size limit). The strided arm at :691-694 applies `LanesInfo`
(ops/common.rs:49-55) for exactly this reason, but the contiguous arm does not.

## Suggested fix
Bound the contiguous lane count by bytes as well as by registers. For example, when
`P::MAX_ITEMSIZE > S::u8s::LEN`, use `const_min(<T as LanesInfo>::LANES, ...)`, or compute
`prev_power_of_two(max(1, used_simd_registers * S::u8s::LEN / P::MAX_ITEMSIZE))`. Then a
wide-element tree uses 1 lane (about one copy of `T` per temporary), as the strided path does.
`LanesInfo` looks only at `T`, not at `MAX_ITEMSIZE`. A byte budget based on `P::MAX_ITEMSIZE`
also covers wide intermediates.
