# F028: Multi-cell fold feeds a cell's items to the order-sensitive ArgMax/ArgMin `update` out of stream order (multi-dim argmax picks the wrong tie / NaN; latent, crate-internal)

- Severity: low  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/reduction.rs:1114 (`fold_multi_cell_impl` folds with `update_state` in walk order) (related: jix/src/ops/reduction.rs:1640 `ArgMax`/`ArgMin::update` "Items come in stream order: a tie keeps the earlier one"; jix/src/ops/reduction.rs:689 logical operand excluded from the dim sort; jix/src/ops/reduction.rs:547 tiles swept row-major over the reduced dims; jix/src/ops/reduction.rs:642 non-first tiles continue with `update_state`, not `merge_states`; jix/src/ops/reduction.rs:50 `update_state` docs state no ordering requirement; jix/src/util/nd_iter_unordered.rs:103 stride sort)
- Reachability: crate-internal. `ReductionOp`, `ArgMaxKernel` and `ArgMinKernel` are `pub(crate)`. Public Rust `argmax`/`argmin` and Python `jix.argmax`/`jix.argmin` are `single_dim`, and with one reduced dim the walk is always ascending. The driver behavior itself can be seen through the public `reduce_unordered`, but that op requires a commutative closure, so its output is not wrong.
- Reported by: reduction-fold-loops

## What goes wrong
In the multi-cell path (kept dim innermost), each run folds one item into each cell with `update_state(prev, item, idx)`. The order of a cell's runs is the order of the `NdIterUnordered` outer walk plus the tile sweep, and neither is ascending in stream position:
(a) inside a tile, the outer dims are sorted by memory stride, and the logical-index operand is excluded from that sort;
(b) across tiles, tiles are swept row-major over tile coordinates. Tile (0,0) can therefore hold stream position `1*N1 + 0` before tile (0,1) holds position `0*N1 + b`, which is smaller.

`ArgMax::update` / `ArgMin::update` keep the earlier-*visited* item on a tie, and also among NaNs. A multi-dim argmax/argmin therefore returns a later tied maximum, or a later NaN, instead of the first. The one-cell path is not affected, because it merges partials with the index-aware `merge_states`.

## Trigger
Both triggers use a multi-dim `ReductionOp::new(storage, ArgMaxKernel {}, [0, 1])` (or `ArgMinKernel`).
1. Permuted memory, one tile. Plain i32 input of shape `[2, 2, 3]` with byte strides `[24, 48, 4]`, so k is innermost, then r0, with r1 outermost. Maxima are tied at `(r0=0, r1=1)` (position 1) and `(r0=1, r1=0)` (position 2). The walk visits positions 0, 2, 1, 3. The result is 2; expected 1. The same holds for ArgMin, and for NaN at positions 1 and 2.
2. C-order memory, several tiles. Compact i32 input of shape `[4, 4, 2]` with `block_shape([2,2,2])` and `read_size((32,32))` (8 items, giving `[2,2,2]` tiles). Maxima are tied at position 2 `(0,2)` and position 4 `(1,0)`. The visit order is 0,1,4,5,2,3,6,7,... The result is 4; expected 2.

## Root cause
`ArgMax::update` (reduction.rs:1638-1646) uses a non-strict comparison. It assumes items arrive in ascending stream position, so it never looks at `idx` to break a tie. The `ReductionOpKernel::update_state` contract (reduction.rs:48-50) does not promise that order, and the driver does not provide it:
- `reduce_tile_impl` passes `affects_dim_order = [true, true, false]` (reduction.rs:686-691). This deliberately lets memory strides, not the logical index, choose the outer dim nesting.
- `read_data_impl` sweeps tiles row-major over tile coordinates (reduction.rs:547). With two or more reduced dims split across tiles, this order is not stream order.
- In the multi-cell path, every non-first visit of a cell goes through `update_state` (reduction.rs:642, 1114), including the first visit of a later tile. It does not use the index-aware `merge_states`.

There is no UB: a cell's first visit is still always position 0, so the `INIT` keyed on `base_item_idx == 0` stays correct. The existing test `multi_dim_argmax_reports_the_true_stream_position` covers only a 0-d output, which takes the one-cell path, so it does not catch this.

## Suggested fix
Make the per-item fold index-aware for the kernels that use indices. One way: `ArgMax`/`ArgMin::update` break ties by the lower `idx`, like `merge_states` does (`b_better || (!a_better && idx < state.0)`). Another: for `NEEDS_INDICES` kernels, have `fold_multi_cell_impl` call `merge_states(prev, init_state(item, idx))`. Also remove the "lanes see items in ascending stream position" assumption from the docs, or state in `update_state`'s docs that order is unspecified. Add a regression test with permuted reduced dims and with C-order multi-tile reduced dims.
