# F007: With len=None (the Python default for file-like readers), Owned::read_section allocates and zero-fills the section size declared in the untrusted TOC before reading any of it: a 106-byte BytesIO aborts the interpreter

- Severity: medium  Verdict: confirmed  Category: resource
- Location: jix/src/archive/block.rs:433 (related: jix/src/archive/common.rs:116, jix/src/archive/common.rs:262-269, jix/src/archive/block.rs:346-348, jix/src/archive/array.rs:110-117, jix-py/src/archive.rs:96, jix-py/src/archive.rs:143)
- Reachability: Python API (`jix.read_array(file_like)` with default arguments, Strict validation) and public Rust API (`Array::read_from_reader(reader, None, ..)`)
- Reported by: codec-archive-archive-io

## What goes wrong
With `len=None`, `ArchiveReader::new` sets `total_size = u64::MAX`, so `check_section_bounds`
accepts any section whose `offset + size` does not overflow. `Owned::read_section` then runs
`vec![MaybeUninit::<T>::zeroed(); size / size_of::<T>()]` before it reads a single byte of the
section. The allocation size comes straight from the file.
- A size the allocator refuses, such as 2^44, aborts the process ("memory allocation of N bytes
  failed", SIGABRT). In Python this kills the interpreter, and no `except` can catch it.
- A size that fits, such as 1 GiB, is allocated and fully zero-written. Only then does
  `read_exact` fail with `UnexpectedEof`. Here a 106-byte input grew peak RSS by 1023 MiB in both
  debug and release builds.

Both TOC rows are affected: block_data (read first) and blocks_loc.

The context doc lists "`len=None` skips section bounds checks" as intended, and that intent is
not disputed here. But skipping the check against a caller-supplied length is no reason to trust
the declared size for an up-front allocation. An out-of-range section should give the same
`UnexpectedEof` error that a moderately oversized one already gives. Python users never opt into
this. `len` is optional, the docstring's own in-memory example `jix.read_array(buf)` omits it,
and the docstring presents the default `strict` validation as the choice for untrusted archives.
Passing `len=len(data)` turns the same file into a clean `RuntimeError`.

## Trigger
1. `jix.write_array(jix.compact(np.arange(8, dtype=np.uint8)), buf)` gives a valid 106-byte archive.
2. Locate the TOC at `4 + 3 x (uleb128 len + message)`. Overwrite the size field (bytes 8..16) of
   row 1 (block_data) with `2**44` as LE u64. The same works for row 0 (blocks_loc) with
   `12 * 2**40`, since `size_of::<BlockLocation>() == 12`.
3. `jix.read_array(io.BytesIO(data))`, or in Rust `Array::read_from_reader(Cursor::new(data), None,
   ArrayParams::default(), ArchiveValidation::Strict)`.

Expected: an ordinary error (`UnexpectedEof` / `InvalidArchive`), with memory bounded by the bytes
that actually exist. Actual: the process aborts. With a 2^30 size, 1 GiB is committed before the
error.

## Root cause
- `jix/src/archive/common.rs:116`: `len=None` sets `total_size = u64::MAX`.
  `check_section_bounds` (`:262-269`) therefore places no bound on `section.size`.
- `jix/src/archive/block.rs:430-433` (`Owned::read_section`) sizes the destination
  `Vec` from `section.size` and fills it with zeroes up front. `MaybeUninit` has no `IsZero`
  specialization, so every byte is written (the fill is the K4 fix from #87).
  `read_section_into` (`common.rs:240-242`) then calls `read_exact` into that buffer. The
  stream's real length is only discovered after the allocation.
- `jix/src/archive/block.rs:346-348`: block_data is read first, then blocks_loc. The
  `blocks_loc.len() == nblocks` check (`:366-371`) runs only after the allocation, even though
  `nblocks` is already known from the header.
- `jix-py/src/archive.rs:96,143`: the binding forwards `len=None` for file-like objects. It never
  derives a length from the stream, even though the stream is required to be seekable.

## Suggested fix
In `Owned::read_section`, do not pre-size the buffer from untrusted input when the bound is
unknown. Read through `reader.take(section.size)` with `read_to_end` (growth is bounded by the
bytes that actually arrive), then check that the length read equals `section.size`. An
alternative is to fill in fixed-size chunks. When `len` is `Some`, the current pre-sized read is
already bounded and can stay. In the same function, `try_reserve` would turn the remaining huge
cases into an error instead of an abort.

Optionally, `read_content` could check `blocks_loc_section.size == nblocks * 12` before reading.
The Python binding could also default `len` to the stream's remaining size, using
`seek(0, SEEK_END)` and then restoring the position.

Related sibling (not part of this finding): `ArchiveReader::read_slice` (`common.rs:161,210`)
resizes to the untrusted uleb128 message length before reading, and it does so even when `len` is
given. The same bounded-read approach fixes it.
