# F013: NdCopier::copy trusts that its `dtype` matches the one given to `new`; scalar routes only debug_assert it, so a mismatch reads and writes past the documented span

- Severity: low  Verdict: confirmed  Category: unsound-api
- Location: jix/src/util/nd_copy.rs:89 (related: jix/src/util/nd_copy.rs:47-53, jix/src/util/nd_copy.rs:90, jix/src/util/nd_copy.rs:97-102, jix/src/util/nd_copy.rs:111-116, jix/src/util/nd_copy.rs:127-131, jix/src/util/nd_copy.rs:360, jix/src/storage/elementwise_pipeline.rs:513-517, jix/src/storage/elementwise_pipeline.rs:529-555, jix/src/storage/elementwise_pipeline.rs:571-585)
- Reachability: crate-internal (`NdCopier` is `pub(crate)`; every current caller passes the same dtype to `new` and `copy`; the public `jix::__private::bench_util::nd_copy` (util/bench_util.rs:11-28) passes one `dtype` to both)
- Reported by: util-nd-copier

## What goes wrong
`NdCopier::new(dtype)` fixes the element type `T` from `(itemsize, alignment)` (nd_copy.rs:30-39).
`copy()` takes a second `dtype` (nd_copy.rs:62). The scalar routes (`scalar_fn::<T>`) use it only in
`debug_assert_eq!`s (89-90). Every byte count after that comes from `size_of::<T>()`: the
single-element move (100-101), the contiguity flags (115-116), the iterator layout (127-131) and the
inner loops. `copy_untyped` instead takes the item size from `copy()`'s argument (360).
`copy()`'s Safety section (47-53) sizes the required byte range with "itemsize" and never says that
`copy()`'s dtype must equal `new()`'s. So a caller that sizes its slices from the dtype it passes
to `copy()`, while the copier was built from a wider dtype, gets an out-of-bounds read of `src` and
an out-of-bounds write of `dst` in release. Only the debug_assert stops this, and only in debug.
Today nothing triggers it, so this is a latent hazard. The API is shaped for exactly this slip:
`Staging` builds its copier once in `new(.., dtype, ..)` (elementwise_pipeline.rs:513-517), takes
the dtype again on every `fill_from` / `write_to`, and sizes its `PtrNoalias` / `PtrMutNoalias`
spans from that later argument (elementwise_pipeline.rs:547-549, 573-575).

## Trigger
Crate-internal only: a copier built from `u64::DTYPE` (8,8) and `copy(..., &u32::DTYPE)`. The
src/dst slices are sized per the Safety doc from the 4-byte itemsize, and src_strides ==
dst_strides:
- `shape=[1]`, strides `[4]`, 4-byte slices: the 1-d single-element path (97-102) moves 8 bytes.
  That is 4 bytes past both spans.
- `shape=[4]`, strides `[4]`, 16-byte slices: the stride 4 != `size_of::<u64>()`, so this is the
  strided `inner_loop::<u64, _, false, false>`, with 8-byte moves at offsets 0, 4, 8 and 12. The
  last one touches bytes 16..20, 4 bytes past both spans. (The hunter's "copy_nonoverlapping 32
  bytes against 16" would need strides `[8]`, which a caller sizing for u32 would not pass. The
  real overrun is 4 bytes at the tail.)
- `shape=[2,2]`, strides `[8,4]`, 16-byte slices: the `NdIterUnordered` path overruns the same way,
  at bytes 16..20.
No current call site does this. All of these pass the same dtype value to both calls:
storage/buf.rs:229/231, storage/compact.rs:392/414/481, array.rs:1334/1435,
ops/shape_ops/tile.rs:176, repeat.rs:155, flip.rs:138, ops/sub_dtype.rs:157/163,
elementwise_pipeline.rs:233/365 with fill_from/write_to (`operands[i].dtype` / `output_dtype` ==
`operands[0].dtype`, elementwise_pipeline.rs:211-212, 337-338) and util/bench_util.rs:20.

## Repro
`NdCopier` is `pub(crate)`, so the repro runs in a scratch copy of the crate
(`scratch/crate-F013`). One helper is added to `src/util/bench_util.rs`:
`nd_copy_split_dtype(src, dst, shape, src_strides, dst_strides, new_dtype, copy_dtype)`, which
calls `NdCopier::new(new_dtype).copy(.., copy_dtype)`. A binary driver
`repros/F013_internal_bin.rs` (saved as `src/bin/f013.rs`) puts the 4- and 16-byte slices at the
start of 8-aligned 64-byte buffers. The src tail is filled with 0xAA and the dst tail with 0xEE.
The driver asserts the correct behavior: no dst byte outside the span changes. It exits 1 while the
bug exists. An inline-test form of the same checks is in `repros/F013_internal.rs`. It was not run,
because a full `--lib` test build did not fit the shared disk.

With debug_asserts off, which matches release:

The `aa` bytes in dst were read from past the end of the src span (src's 0xAA tail). They were
then written past the end of the dst span: 4 bytes out of bounds on each side, in all three
routes. Inside the span the values are correct, so only the overrun shows. Logs:
`scratch/F013_nda.log`.

## Root cause
`copy()` has two sources of truth for the element size. `scalar_fn` uses `size_of::<T>()` (fixed
at `new`) and checks it against `copy()`'s `dtype` only with `debug_assert_eq!` (nd_copy.rs:89-90).
`copy_untyped` uses `copy()`'s `dtype` (nd_copy.rs:360). The Safety contract (47-53) states spans in
terms of an unspecified "itemsize" and lists neither "`dtype` must have the same
(itemsize, alignment) as the dtype given to `new`" nor which of the two itemsizes the spans are
measured with.

## Suggested fix
Make the copier the only source of truth. Store the itemsize in `NdCopier` (or keep the dtype) at
`new`, and drop the `dtype` parameter from `copy()`. `Staging::fill_from` / `write_to` should then
size their spans from the Staging's own dtype, not from a separate argument. Short of that,
promote the two `debug_assert_eq!`s at 89-90 to `assert_eq!`s on itemsize (cheap: once per
`copy`). Then add the precondition to `copy()`'s Safety section. Note that the alignment assert
must not be promoted as-is, because of K8 (i686 `align_of::<u64>() == 4` vs dtype alignment 8).
