# F015: 32-bit: section sizes and uleb128 message lengths are truncated with `as usize`; Owned reads panic (assert_eq / capacity overflow) and a malformed archive loads silently, where 64-bit returns Err

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/archive/block.rs:430 (related: jix/src/archive/common.rs:240, jix/src/archive/common.rs:161, jix/src/archive/common.rs:264)
- Reachability: public Rust API (`Array::read_from_reader`, `read_from_file`, `read_from_file_section`); Python API (`jix.read_array` with a file-like reader, or a path with an explicit `len`) on the shipped 32-bit wheels (x86, armv7)
- Reported by: codec-archive-archive-io

## What goes wrong
`Owned::read_section` sizes its buffer as `section.size as usize / size_of::<T>()`. On 32-bit a
section size >= 2^32 truncates, the buffer is shorter than the section, and `read_section_into`
hits `assert_eq!(buf.len() as u64, section.size)` - a panic in release builds too. A size in
(isize::MAX, 2^32) does not truncate but makes `vec!` panic with "capacity overflow". 64-bit
builds return `Err(Io: failed to fill whole buffer)` for the same files. Separately,
`try_read_message` truncates the uleb128 message length with `length as usize` before
`read_slice`, so on 32-bit a length prefix of `L + 2^32` is read as `L` and a malformed archive
loads successfully, while 64-bit rejects it. No memory unsafety: the asserts and later
validation still bound everything; `Mmap::read_section` is not affected because `len` is only used
after `end <= mmap.len()` (a usize).

## Trigger
A valid 106-byte archive of `array![1u8, 2, .., 8]`, written with `write_to`, then patched:
- block_data TOC row (second `Section`) size = 2^32 + 1, read with
  `Array::read_from_reader(Cursor::new(bytes), None, ArrayParams::default(), ArchiveValidation::Strict)`
  (also with `len = Some(1 << 40)`): panic `assertion left == right failed, left: 1, right: 4294967297` at common.rs:240.
- block_data size = 2^31: panic `capacity overflow` (alloc raw_vec).
- blocks_loc TOC row size = 2^32 + 8 (a multiple of `size_of::<BlockLocation>() == 12`): panic at
  common.rs:240, `left: 0, right: 4294967304`.
- FileMetadata length prefix rewritten to `L + 2^32` (5-byte uleb128, section offsets shifted
  by +4): loads `Ok(())` on 32-bit with `len = None` and with the exact `len = Some(110)`.
- Without crafting: a genuine archive whose data section is over 2 GiB, opened with
  `read_from_file` on 32-bit, panics instead of returning an error (it cannot fit in a 32-bit
  address space either way).

## Root cause
- jix/src/archive/block.rs:430 `let len = section.size as usize / size_of::<T>();` assumes the
  section size fits in usize. `check_section_bounds` (common.rs:264) only bounds it by the
  caller's `len` (`u64::MAX` for `None`), never by `usize`/`isize::MAX`.
- jix/src/archive/common.rs:240 turns the resulting length mismatch into a release-mode panic.
- jix/src/archive/common.rs:161 `self.read_slice(length as usize)` truncates the uleb128 length.

## Suggested fix
Convert with `usize::try_from(section.size)` (and `isize::MAX` bound, e.g. via
`Layout::array::<T>`) in `Owned::read_section`, returning `InvalidArchive`/an io error on
failure; likewise `usize::try_from(length)` in `try_read_message`. Ideally also bound the message
length by the reader's remaining limit (`Take::limit()`) before allocating, which fixes the
related 64-bit eager 4 GiB allocation for the same inputs.
