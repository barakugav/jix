# F001: Struct layout validation sums field ends in unchecked u16; a field list that runs past 65535 wraps and validates against a tiny itemsize, so SubDtype reads up to 64 KiB past the buffer (crafted .jix -> SIGSEGV in release; also from 100% safe Rust)

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/dtype.rs:673 (related: jix/src/dtype.rs:671, jix/src/dtype.rs:682, jix/src/dtype.rs:704, jix/src/dtype.rs:479-481, jix/src/dtype.rs:492, jix/src/dtype.rs:500, jix/src/util/mod.rs:64-67, jix/src/archive/schema/conversions.rs:113, jix/src/ops/sub_dtype.rs:76-101, jix/src/ops/sub_dtype.rs:140, jix/src/ops/sub_dtype.rs:154, jix-py/src/dtype.rs:205)
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file*` on an untrusted .jix; `Dtype::from_fields`, `Dtype::new_struct`), Python API (`jix.read_array` on an untrusted .jix)
- Reported by: types-dtype-layout

## What goes wrong
`is_aligned_struct`, `is_packed_struct` and `from_fields::determine_itemsize_and_alignment` add
each field's itemsize into a `u16` running offset with `+=` and round it with
`Idx::ceil_to_multiple` (`div_ceil(m) * m`). None of this arithmetic is checked. In release builds
the sum wraps mod 65536, so a field list whose running end passes 65535 validates against a tiny
itemsize. The result is a `Dtype` that breaks contract C1: fields lie far outside
`[0, itemsize)`. `SubDtype` trusts field offset and size without re-checking them against the
parent itemsize. Its pull path returns `tmp.with_offset(65535)` and its push path does
`get_unchecked(65535..)` over a buffer that holds 1 byte per element, so the field read goes up
to 64 KiB past the allocation. Debug builds hit an overflow panic instead of returning
`InvalidArchive` or `InvalidArgument`.

## Trigger
- Crafted archive: write a valid archive of `array![1u8, 2, 3, 4]`. In its BlockTableHeader,
  replace the dtype with
  `Struct{a: U8 shape [65535] @0, b: U8 shape [2] @65535}, itemsize 1, alignment 1`, then
  shift the two TOC section offsets by the change in length. Call
  `Array::read_from_reader(.., ArchiveValidation::Strict)?.dtype_sub_field::<[u8; 2]>("b").to_ndarray()`,
  or in Python `jix.dtype_sub_field(jix.read_array(path), "b").numpy()`. The aligned check
  computes `65535 + 2 = 65537`, which wraps to 1 and equals the itemsize.
- Public constructors: `Dtype::from_fields(vec![("a", 0, u8[65535]), ("b", 65535, u8[2])])` and
  `Dtype::new_struct(<same>, &[], 1, align 1)` both return `Ok` with itemsize 1.
- Ceil-only wrap: `Dtype::from_fields(vec![("a", 0, u16), ("b", 2, u8[65533])])` returns `Ok`
  with itemsize 0, alignment 2 and is_aligned = true, because `ceil_to_multiple(65535, 2)` gives
  65536, which wraps to 0. Arrays of an itemsize-0 dtype are rejected, so this form is mostly
  inert. It can still be nested as a field of a valid outer struct.
- Safe code only, with no file: `Dtype::from_fields` (above) plus a user `ArrayStorage` (a safe,
  public trait). The storage forwards `read_data` / `shape` / `spec` / `info` to
  `Array::plain_ndarray(array![1u8, 2, 3, 4])` and reports `dtype()` as the jix-certified
  1-byte struct. Its buffers really are 1 byte per element, so the storage misreports nothing.
  `.dtype_sub_field::<[u8; 2]>("b").to_ndarray()` then reads 64 KiB past a 4-byte `Vec`.

## Root cause
The validators assume a running sum of field ends that fit in `u16`. That holds only if the
input already respects C1, and the validators exist to enforce C1. The relevant code:
- `jix/src/dtype.rs:673` / `:704`: `expected_offset += dtype.itemsize();` in `is_aligned_struct` /
  `is_packed_struct` (used by `new_struct`, and therefore by `Dtype::from_proto` at
  `archive/schema/conversions.rs:113` and by `dtype_from_numpy` at `jix-py/src/dtype.rs:205`).
- `jix/src/dtype.rs:671` / `:682`, and `:479` / `:492` in `from_fields`: `ceil_to_multiple`, which
  is `div_ceil(m) * m` with only a `debug_assert!(m > 0)` (`util/mod.rs:64-67`).
- `jix/src/dtype.rs:481` / `:500`: the same unchecked add in
  `from_fields::determine_itemsize_and_alignment`.

`from_proto` limits each offset and itemsize to `u16`, but nothing limits their sum. Downstream,
`SubDtype::new` (`ops/sub_dtype.rs:76-101`) checks only that the field exists and has a nonzero
size. `read_data` then offsets into the parent buffer by the field offset with no bounds check
(`sub_dtype.rs:140` `with_offset`, `:154` `get_unchecked`) and copies `field.itemsize` bytes per
element.

## Suggested fix
Do the layout arithmetic in `u32` / `u64`, or with `checked_add` / `checked_mul`, in all three
validators and in `ceil_to_multiple`'s callers here. Reject the layout (return false /
`InvalidArgument`) when any field end or the rounded total exceeds `Itemsize::MAX`. As defense in
depth, `SubDtype::new` could assert `offset + field.itemsize <= parent.itemsize`, which keeps the
unsafe offset local to the code that justifies it.
