# F009: `ArrayStorage` is a safe, unsealed trait, but jix's unsafe code trusts its `read_data` buffers: a user storage with no `unsafe` causes out-of-bounds reads (pull, default elementwise pipeline) and uninitialized reads (push, `to_ndarray_sub` `assume_init`)

- Severity: medium  Verdict: confirmed  Category: unsound-api
- Location: jix/src/storage/core_trait.rs:132-134 (default `read_as_elementwise_pipeline`) and jix/src/array.rs:806 (`assume_init`). Related: jix/src/storage/core_trait.rs:56 (`pub trait ArrayStorage`: safe, unsealed, no `# Safety` section); jix/src/storage/elementwise_pipeline.rs:813-816 (`OperandTyped::new_input` precondition) and :837-860 (`read_bulk` raw reads); jix/src/array.rs:791-805 (uninit `out` buffer); jix/src/storage/buf.rs:386-390 (`read_data_and_map_strides` push branch drops the inner result and returns `out.view_mut()`); jix/src/ops/shape_ops/broadcast.rs:144-165 (pull from inner, then `copy_from` over the outer shape); jix/src/ops/sub_dtype.rs:150 (`get_unchecked`); jix/src/array.rs:1617 (safe `Array::from_storage`)
- Reachability: public Rust API. It needs a user `ArrayStorage` impl that breaks the documented `read_data` contract. No `unsafe` is needed, and Python and the built-in storages do not reach it.
- Reported by: storage-core-buf-contract

## What goes wrong
`ArrayStorage` is a safe public trait, and nothing seals it. `Array::from_storage` is also safe. A user crate can implement the trait without `unsafe`: it forwards `dtype`/`spec`/`info` to a jix storage and uses the public `jix::ops::IntoType` for `element_type_change`. Several pieces of jix's own `unsafe` code then rely, for memory safety, on what that impl's `read_data` returns.

The trait docs state a contract: pull returns a buffer valid for the region, and push writes the region into `dst`. But a safe trait's contract cannot discharge an `unsafe` precondition, so a buggy impl makes safe calls UB:
- **Pull:** the default `read_as_elementwise_pipeline` checks only the dtype. It then wraps the pull buffer in `unsafe OperandTyped::new_input`, and the pipeline reads every element of the region with raw pointers. In the repro, the region is 3 or 2^22 elements and the buffer holds 4 bytes, so these reads run past it.
- **Push:** `to_ndarray_sub` passes an `ndarray::Array::uninit` buffer as `out`. It then calls `assume_init` without checking that anything was written.

This is the same trust boundary as K25 (fixed in c009869 by removing `Op2::shape`'s `assert_unchecked`) and as K4 (a safe user `Read` impl, fixed by zero-filling). This finding covers the `read_data` buffer part, which trial2 section 6.A left open.

## Trigger
User storage `Short<S>`:
- `shape()` returns a user `Vec` (`[3]` or `[1 << 22]`).
- `dtype`/`spec`/`info` forward to an inner 1-element `Plain`.
- `read_data` ignores `index` and `out`, and returns `self.inner.read_data(&[0..1], ctx, None)`.

The two calls:
1. Pull: `(-Array::from_storage(Short { inner: plain[1.0f32], shape: [n] })).to_ndarray::<Ix1>()`. The `Neg` pipeline uses the default `read_as_elementwise_pipeline`.
2. Push: `Array::from_storage(Short { inner: plain[7u8], shape: [3] }).to_ndarray::<Ix1>()`. This takes the `small_read` path, which pushes into the uninit ndarray and then calls `assume_init`.

## Root cause
The `read_data` contract (core_trait.rs:71-107) is stated only as prose on a safe trait, yet unsafe code relies on it:
- **core_trait.rs:132-134.** The default pipeline establishes `OperandTyped::new_input`'s precondition ("`data` must be a valid view of `dtype` elements", elementwise_pipeline.rs:813) from `check_dtype` alone. Nothing compares the returned `StridedBuf`'s slice length with the region's span at the returned strides.
- **array.rs:791-806.** `to_ndarray_sub` relies on every storage's push path writing every element before `assume_init`.
- **buf.rs:386-390.** The push branch of `read_data_and_map_strides` assumes that the inner storage wrote through `inner_out`.
- **Other consumers.** Broadcast push (`copy_from` from the inner pull view, broadcast.rs:157-163), SubDtype's `get_unchecked` (sub_dtype.rs:150), Flip/Repeat/Tile, Where, and reduce_tile also use child pull buffers without a bounds check.

There is no `from_storage`-time check that could help, because the lie happens at read time.

## Suggested fix
Pick one policy and apply it everywhere:
1. **Make the trait unsafe.** Change it to `pub unsafe trait ArrayStorage` with a `# Safety` section covering stable `shape`/`dtype`/`spec`, pull buffers that cover the region at their strides with initialized valid bytes, and push writing every element of the region into `out`. This matches what the code already assumes. Sealing the trait also works, if user storages are not a goal.
2. **Validate at the trust boundary.** For pull results, check `strided_span(region, strides, itemsize) <= data.len()` before `OperandTyped::new_input`, `copy_from` or `get_unchecked`. This is O(ndim), and `check_out_buf` already does the same for `out`. Only safe code can produce a `StridedBuf` from existing buffers, so a span check covers bounds. For push, either zero-fill the `to_ndarray_sub` allocation before the read (the same approach as the K4 fix; zero is a valid value of every `Dtyped` type), or check that the returned buffer is `out` (same data pointer) and error otherwise.
