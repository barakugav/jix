# F016: write_array docstring advertises gzip.GzipFile as a supported writer, but every write to one fails ("Negative seek in write mode")

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/archive.rs:160-162 (related: jix/src/archive/block.rs:214, jix/src/archive/block.rs:231, jix/src/archive/block.rs:170-176, jix-py/src/archive.rs:1153)
- Reachability: Python API (`jix.write_array(array, <gzip.GzipFile opened for writing>)`)
- Reported by: codec-archive-archive-io

## What goes wrong
The `write_array` docstring lists `gzip.GzipFile` as an example of a "seekable binary file-like
object" it accepts. The archive writer cannot be used with any forward-only writer:
`BlockArchiveWriter::start` writes a zeroed TOC placeholder and skips forward over the
block-locations section, and `finalize` then seeks BACKWARDS to fill in the locations
(`block.rs:214`) and the TOC (`block.rs:231`). A write-mode `GzipFile` (which reports
`seekable() == True`) only supports forward seeks, so every `write_array` to one raises
`RuntimeError: IO error: OSError: Negative seek in write mode`. This happens for every array:
compact arrays, lazy views, and empty arrays alike. The error is clean (no corruption or crash),
but the documented example never works. If the caller keeps the `with gzip.GzipFile(...)` block
open past the exception, a truncated, unreadable gzip stream is left behind. No test covers it: the
only GzipFile test (`test_with_gzip_file`, jix-py/src/archive.rs:1153) checks raw `PyWriter`
writes, not `write_array`.

## Trigger
```python
import gzip, io, numpy as np, jix
with gzip.GzipFile(fileobj=io.BytesIO(), mode="wb") as g:
    jix.write_array(jix.compact(np.arange(10, dtype=np.float32)), g)
```

## Root cause
The docstring (jix-py/src/archive.rs:160-162) only requires `.write()`, `.seek()` and
`.tell()`. The archive layout (header, TOC, block locations, block data), however, is written with
placeholders that `BlockArchiveWriter::finalize` (jix/src/archive/block.rs:211-243) patches by
seeking back to `blocks_loc_offset` and `toc_offset`. So the writer actually needs random-access
seek, which `GzipFile` (and any other compressing or streaming wrapper) does not provide in write
mode.

## Suggested fix
The simplest fix is to remove `gzip.GzipFile` from the docstring and say that the writer must
support backward seeks (random access). Users can then write to an `io.BytesIO` and gzip the bytes
afterwards. The alternative is to support forward-only writers by buffering the locations and TOC
and writing them after the data, as a trailer or a back-pointer. This changes the format and would
need a matching reader change. Add a `write_array` + GzipFile test either way, asserting whichever
behavior is chosen.
