# F010: Float base ** integer exponent uses powi: error grows with |n| (tens to thousands of ulps) and representable subnormal results come back as exactly 0

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/op2.rs:1199-1203 (related: jix/src/ops/op2.rs:1155-1165 trait doc, jix/src/ops/op2.rs:1214-1223 f16 x int, jix/src/ops/op2.rs:1236-1243 `float_power`, jix-py/src/ops/op2.rs:625-627 dispatch pairs `(f32, i32)` / `(f64, i32)`)
- Reachability: public Rust API and Python API (`arr ** <python int>`, `jix.power(float_arr, int_arr_or_scalar)`)
- Reported by: elementwise-ops-op2-arith-div-pow

## What goes wrong
`impl Pow for [f32, f64] x [i8, u8, i16, u16, i32]` computes `a.powi(b as i32)`. On x86_64 this is
compiler-builtins `__powisf2` / `__powidf2`: square-and-multiply in the float type, with a negative
power computed as `1 / a^|n|`. As a result:
(1) the rounding error grows with |n|, about 0.7 ulp per unit of |n|. Measured maximum vs numpy
over random bases: 3 ulps at n=5, 6 at n=10, 36 at n=50, about 75 at n=100, about 790 at n=1000,
and 6375 (f32) / 8254 (f64) at n=10000. numpy stays at 1 ulp.
(2) when `a^|n|` overflows to inf but the true `a^-|n|` is a representable subnormal, the result
is `1/inf = 0`.
Neither case sets a status bit, because `float_power` (op2.rs:1236) only classifies non-finite
results. The same values through the float-exponent impl (`powf`) are correct, so in jix
`x ** -1074` and `x ** -1074.0` give different answers. Python routes `float_arr ** <int>` to
the `(f32, i32)` / `(f64, i32)` pairs, so this affects the common `arr ** 3` spelling (`** 2` is
diverted to Square).

## Trigger
- Rust: `Array::compact_ndarray(&array![2.0f64, 10.0]).unwrap().pow(Array::compact_ndarray(&array![-1074i32, -309]).unwrap())` -> `[0.0, 0.0]`, expected `[5e-324, 1e-309]`.
- Rust f32: `2.0f32 ** -130i32` -> 0 (expected 7.34684e-40); `1.0135511f32 ** 100i32` -> 3.8420584 (expected 3.842073, 61 ulps); `(1 + f32::EPSILON) ** (1 << 24)` -> 7.3853374 (expected 7.3890553, 7797 ulps).
- Python: `jix.compact(np.array([2.0])) ** -1074` -> `[0.]` vs `** -1074.0` -> `[5e-324]`; `jix.power(jix.compact(np.float32([2])), np.int16(-130))` -> `[0.]`; `jb ** 100` over bases in 1 +- 0.08 -> up to 72 / 77 ulps (f32 / f64).

## Root cause
op2.rs:1201 picks `powi` for speed. Rust documents `powi` as having non-deterministic
precision. compiler-builtins evaluates it as repeated squaring, so error compounds about once per
squaring and multiply, and it computes negative powers as a reciprocal of the positive power,
which overflows before the reciprocal is taken. The trait doc names `powi` (op2.rs:1156), but it
also says "Float values follow f32::powf" (op2.rs:1162), and the Python `power` docstring says
float bases behave "as numpy". Neither holds for integer exponents. Nothing in the context doc's
"Intentional behaviors" covers accuracy. The tests that would notice use only integer-valued bases
with exponents 0-4 and rtol 1e-6 (jix-py/python/tests/test_op2.py:431-446), or check only status
bits (op2.rs:3120-3197).

## Suggested fix
Compute the float x int impls with `powf(b as Self)`. `i32 -> f64` is exact, and `i32 -> f32` is
exact for |b| <= 2^24. For larger |b| use f64 `powf` and round once, or note that past 2^24 any
base except +-1 overflows or underflows anyway. Alternatively keep a fast path for small |n|
(e.g. |n| <= 4). For f16 x int, f32 `powf` and one rounding is enough. Add a test that compares
against `powf` for large |n| and for subnormal results.
