# F005: check_section_bounds adds section offset + size unchecked: a crafted TOC panics instead of returning InvalidArchive (debug: add overflow; release: capacity overflow in the heap reader), also from default Python read_array

- Severity: medium  Verdict: confirmed  Category: error-handling
- Location: jix/src/archive/common.rs:264 (related: jix/src/archive/block.rs:423-433, jix/src/archive/block.rs:458-473, jix/src/archive/block.rs:346, jix-py/src/archive.rs:106-120)
- Reachability: Python API (`jix.read_array(path)` with default arguments, Strict validation) and public Rust API (`Array::read_from_reader` / `read_from_file` / `read_from_file_section` / `read_from_file_mmap`)
- Reported by: storage-compact-read-path, codec-archive-archive-io

## What goes wrong
`ArchiveReader::check_section_bounds` evaluates `section.offset as u64 + section.size <= total_size`
with a plain `+`. When a TOC section has `offset + size > u64::MAX`, a debug build panics on the add.
A release build wraps to a small value, so the check passes. The heap reader (`Owned::read_section`)
then allocates `vec![MaybeUninit::zeroed(); section.size as usize]`. On 64-bit, a wrapped sum
needs `size >= 2^63 + 1 > isize::MAX`, so the allocation always panics with "capacity overflow".
The bad file is never rejected with `InvalidArchive`. In Python the panic arrives as
`pyo3_runtime.PanicException`. That is a `BaseException`, so the `except Exception` code that is
supposed to handle untrusted files does not catch it. The read panics; it does not corrupt memory.
`Owned` allocates and reads only into its own correctly-sized `Vec`. The mmap reader re-checks
with `checked_add` against the mapping and returns `Err` in release.

This is the part of K5's suggested fix that was not applied. The K5 fix in 5b3a9f5 added checked
arithmetic only to `Mmap::read_section`. The pilot write-up also suggested making
`check_section_bounds` use `checked_add`, and this finding covers that missing piece.

## Trigger
1. Write any small array, e.g. `Array::compact_ndarray(&array![1u8, 2, 3, 4, 5, 6, 7, 8])` -> `write_to`.
2. Find the TOC at `4 + 3 x (uleb128 len + message)`. Overwrite row 1 (block_data,
   `{offset: i64, size: u64}` LE) with either:
   - `{offset: i64::MAX, size: 2^63 + 2}` (the sum wraps to 1), or
   - `{offset: 1, size: u64::MAX}` (the sum wraps to 0).
3. Call `Array::read_from_reader(Cursor::new(bytes), Some(len), ArrayParams::default(),
   ArchiveValidation::Strict)`, or in Python `jix.read_array(path)` (by default `len` is the file
   size and validation is Strict).

Expected: `Err(InvalidArchive "section is out of archive bounds")`.

## Root cause
- `jix/src/archive/common.rs:262-269`: `0 <= section.offset && section.offset as u64 + section.size
  <= self.total_size` uses an unchecked `+`. It is the only bound on a section before
  `Owned::read_section` allocates.
- `jix/src/archive/block.rs:423-433`: `Owned::read_section` trusts that check and computes
  `len = section.size as usize / size_of::<T>()`. It then allocates `vec![..; len]` before any read.
  Once the check has wrapped, `len` exceeds `isize::MAX` bytes and the allocation panics.
- `jix/src/archive/block.rs:458-473`: `Mmap::read_section` has the correct checked version, against
  `mmap.len()`. It runs after `check_section_bounds`, so the debug build still panics first.
- The section is read at `block.rs:346` (block_data first, then blocks_loc at `:347-348`). Both
  rows are affected. For blocks_loc the size must also be a multiple of `size_of::<BlockLocation>()`.

32-bit (by reading the code, not run): the release add wraps the same way. `section.size as usize`
then truncates, so the allocation is small, and the `assert_eq!(buf.len() as u64, section.size)` in
`read_section_into` (`common.rs:243`) panics. The result is again a panic, not UB.

With `len=None` (`total_size = u64::MAX`), the debug build still panics on the same add. Skipping the
bounds check against `len` is intended. An overflowing `offset + size` should still be an error, and
the checked add fixes that case too. Huge but non-overflowing sizes with `len=None` are a separate
issue: allocation happens before validation.

## Suggested fix
In `check_section_bounds`, use checked arithmetic:
`u64::try_from(section.offset).ok().and_then(|o| o.checked_add(section.size)).is_some_and(|end| end <= self.total_size)`.
Optionally, cap `section.size` to `isize::MAX` / `usize` before allocating in `Owned::read_section`
(or use `try_reserve`), so a huge size with `len=None` becomes an error rather than a panic or abort.
