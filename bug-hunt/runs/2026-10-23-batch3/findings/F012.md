# F012: Derived structs with a zero-length array field (or a zero-sized array field whose shape product exceeds u16) write to .jix but cannot be read back; Dtype::set_shape panics on such dtypes in debug

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix/src/archive/schema/conversions.rs:125 (related: jix/src/archive/schema/conversions.rs:35, jix/src/archive/schema/conversions.rs:167, jix/src/dtype.rs:1186, jix/src/dtype.rs:857, jix/src/archive/block.rs:141)
- Reachability: public Rust API (`#[derive(Dtyped)]` + `Array::compact_ndarray` + `write_to` / `read_from_reader`; `Dtype::set_shape`)
- Reported by: types-dtype-layout (twice: the round-trip failure and the set_shape overflow)

## What goes wrong
The `[T; N]` `Dtyped` impl (dtype.rs:1186) builds dtypes that no runtime constructor accepts:
`[T; 0]` gives inner shape `[0]`, and a zero-sized `T` lets `[[T; 300]; 300]` carry shape
`[300, 300]` whose product (90000) does not fit `Itemsize = u16`. Inside a derived `#[repr(C)]`
struct with a nonzero itemsize, arrays of such a type pass `check_dtype_size_nonzero`, so they can
be created and written. `to_proto` (conversions.rs:167) emits the field shape unchanged, but
`from_proto` rejects it on read, so the library writes archives it refuses to open. Separately,
`Dtype::set_shape` (a pub method returning `Result`) multiplies the current shape with unchecked
`product::<Itemsize>()` (dtype.rs:857): debug builds panic with "attempt to multiply with overflow"
for `[[Empty; 300]; 300]` and `[[Empty; 256]; 256]`; in release 65536 wraps to 0 and the call
returns the misleading "current shape has zero elements" error.

## Trigger
```rust
#[derive(Copy, Clone, Dtyped)] #[repr(C)] struct WithZeroLen { a: u32, z: [u32; 0] }
#[derive(Copy, Clone, Dtyped)] #[repr(C)] struct Empty {}
#[derive(Copy, Clone, Dtyped)] #[repr(C)] struct WithBigZst { a: u32, z: [[Empty; 300]; 300] }

let a = Array::compact_ndarray(&ndarray::arr1(&[WithZeroLen { a: 7, z: [] }]))?;
let mut buf = Cursor::new(Vec::new());
a.write_to(&mut buf)?;                                    // Ok
Array::read_from_reader(Cursor::new(buf.into_inner()), None,
    ArrayParams::default(), ArchiveValidation::Strict);   // Err(InvalidArchive)
// same with WithBigZst
let mut d = <[[Empty; 300]; 300] as Dtyped>::DTYPE;
d.set_shape(&[2]);                                        // debug: panic
```

## Root cause
- dtype.rs:1186-1197: `[T; N]::DTYPE` asserts only `N < u16::MAX`; it accepts `N == 0` and never
  checks that the accumulated shape product fits `Itemsize` (it cannot overflow the itemsize when
  `T` is zero-sized, so the `itemsize *= n` const-eval overflow check does not catch it).
- The write path (archive/block.rs:141 -> `Dtype::to_proto`, conversions.rs:167) serializes
  whatever dtype it is given, with no check that `from_proto` will accept it.
- conversions.rs:35 (`try_shape_product` over u16) and conversions.rs:125 (`set_shape`, which
  rejects a zero dim at dtype.rs:852-856) reject those shapes on read. The two sides disagree.
- dtype.rs:857: `self.shape().iter().cloned().product::<Itemsize>()` is unchecked; the comment at
  dtype.rs:858-860 assumes every non-`[T; N]` dtype has a valid shape, but the `[T; N]` impl
  itself can produce a product > u16::MAX.

## Suggested fix
Make the writer and reader agree. Simplest: reject these dtypes where they are built or written -
in the `[T; N]` impl add a const assert that `N > 0` (or document `[T; 0]` as unsupported) and that
the shape product fits `Itemsize` (track it with `checked_mul` in const eval), or have
`ArrayParams`/the archive writer validate the dtype recursively (every field shape nonzero and its
product fits u16) before writing. Alternatively, relax `from_proto` to accept zero-element and
large-product shapes on zero-itemsize field dtypes. In `set_shape`, compute the current product
with `try_shape_product()` / `checked_mul` and return an error instead of panicking.
