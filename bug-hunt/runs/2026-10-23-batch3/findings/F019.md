# F019: jix.power(x, 2) / x ** 2 is routed to Square and silently drops the documented float Overflow report

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/op2.rs:688 (related: jix-py/src/ops/op2.rs:635-662 SQUARE_TABLE, jix/src/ops/op1.rs:375-419 Square kernels, jix/src/ops/op2.rs:1199-1259 float Pow + float_pow_error, jix-py/src/ops/op2.rs:553-557 power docstring)
- Reachability: Python API
- Reported by: elementwise-ops-op2-arith-div-pow

## What goes wrong
`jix.power` swaps its dispatch table for `SQUARE_TABLE` whenever the exponent is the Python scalar
2 / 2.0 (also `np.int32(2)`, and `x ** 2` via `Array.__pow__`). For float bases (f16/f32/f64) the
Square kernel is a plain `x * x` with no status parameter, whereas the Pow kernel reports Overflow
for finite operands with an infinite result. So whether the read raises/warns depends only on how
the exponent was spelled: `power(x, 2)` returns `inf` silently, while `power(x, 3)`,
`power(x, <array of 2>)` and numpy's `np.power(x, 2)` all report "overflow". This contradicts the
`jix.power` docstring ("For a float base, as numpy: ... finite operands with an infinite result
`over`"), which makes no exception for an exponent of 2. Values are identical (powi(2)/powf(2.0) is
the correctly rounded x*x), and integer bases are unaffected (neither kernel reports anything for a
non-negative exponent), so only the float error report is lost.

## Trigger
```python
y = jix.compact(np.array([1e200, 3.0]))          # also float32 1e30, float16 300.0
with jix.errstate(over="raise"):
    jix.power(y, 2).numpy()                       # -> array([inf, 9.]), no error
    jix.power(y, 3).numpy()                       # -> FloatingPointError: overflow encountered
```
With default modes (`over='warn'`), `power(y, 2)` emits no warning while `power(y, 3)` warns.

## Root cause
The shortcut (introduced in 5a03a22, #71) assumes Square is a drop-in replacement for Pow with
exponent 2; the comment above `SQUARE_TABLE` (jix-py/src/ops/op2.rs:635) checks only that the dtype
promotion is identical. But `Square` is a status-less op1 trait (jix/src/ops/op1.rs:375-384, float
impls 387-392 and f16 at 404-419), while float `Pow` routes every non-finite result through
`float_power` -> `float_pow_error` (jix/src/ops/op2.rs:1199-1259), which sets Overflow. The error
semantics therefore differ for float bases. The Python errstate tests do not catch it because
`_errors_match_numpy` always passes the exponent as an array (test_errstate.py:246-271), so the
scalar-2 shortcut is never exercised. (The 0.5 -> Sqrt shortcut matches numpy 2.5, which also gives
`[nan, -0.0]` for `power([-inf, -0.0], 0.5)`, so it is not part of this finding.)

## Suggested fix
Restrict `SQUARE_TABLE` to the integer pairs (where Square and Pow agree exactly), letting float
bases fall through to the Pow kernel; or give Square a status-taking float kernel that flags
Overflow for a finite input with an infinite result (which would also make `jix.square` match
`np.square`, which warns "overflow encountered in square"). Add a scalar-exponent case to
`test_float_power_errors_match_numpy`.
