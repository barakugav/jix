# F014: read_uleb128 has no length cap: an 11-byte length prefix panics in debug (shift overflow) and is silently accepted in release

- Severity: low  Verdict: confirmed  Category: overflow
- Location: jix/src/archive/common.rs:184 (related: jix/src/archive/common.rs:170 unbounded `for i in 0..`, jix/src/archive/common.rs:157 caller `try_read_message`, jix/src/archive/array.rs:447 / :457 and jix/src/archive/block.rs:311 the three message reads of every archive)
- Reachability: public Rust API (`Array::read_from_reader`, `read_from_file`, `read_from_file_mmap`) and Python API (`jix.read_array`)
- Reported by: codec-archive-archive-io

## What goes wrong
`ArchiveReader::read_uleb128` reads continuation bytes with no limit on how many and ORs in
`u64::from(b & 0x7F) << (i * 7)`. From the 11th byte on (i = 10, shift 70), a debug build
panics with "attempt to shift left with overflow". The Python bindings in this environment are a
debug build, so the panic surfaces there as `pyo3_runtime.PanicException`. Release builds,
including the shipped wheels, mask the shift (70 & 63 = 6) and accept the overlong prefix. A
valid archive whose length prefix is rewritten in an 11-byte form loads without error, and higher
groups are OR-ed into low bits, so different byte strings decode to the same length. The writer
uses prost's `encode_length_delimited`. Its reader counterpart, prost's `decode_varint`, rejects
varints longer than 10 bytes and a 10th byte above 1. jix's reader is laxer than its own format's
encoder. Release does not gain any reachable effect from this beyond a canonical encoding, since
any length can already be written canonically. The practical impact is the debug panic plus lax
parsing.

## Trigger
- Hunter's file: `b"jix1" + [0x80]*10 + [0x00]` (15 bytes), read with
  `Array::read_from_reader(Cursor::new(bytes), Some(15), ArrayParams::default(), ArchiveValidation::Strict)`
  or `jix.read_array(path)`.
- A valid archive (`compact_ndarray(&array![1u8..=8])` + `write_to`) with its one-byte
  FileMetadata length `L` replaced by `[L | 0x80, 0x80 x 9, 0x00]`. The two TOC section offsets
  are shifted by +10 so that only the varint encoding differs.

  assertion fails.

## Root cause
`for i in 0..` at common.rs:170 has no upper bound. The shift at common.rs:184 is unchecked: it
is valid only for `i * 7 < 64`, which means at most 10 bytes. Nothing rejects an 11th byte, and
nothing checks that the 10th byte contributes only bit 63 (`b & 0x7F <= 1`). No other validation
covers this: `ArchiveReader::new` checks only the magic, and the length is used directly by
`read_slice` (common.rs:161).

## Suggested fix
Limit the loop to 10 bytes. Return `io::ErrorKind::InvalidData` ("varint too long") when the 10th
byte has the continuation bit set or `b > 1`. Or use checked math (`checked_shl` plus an overflow
check) and error on overflow. This matches prost's `decode_varint`.
