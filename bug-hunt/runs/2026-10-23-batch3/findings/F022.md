# F022: Owned::read_section transmutes Vec<MaybeUninit<T>> to Vec<T>, relying on Vec layout that std does not guarantee (latent; no current rustc config breaks it)

- Severity: low  Verdict: confirmed  Category: unsafe-hygiene (latent unsoundness)
- Location: jix/src/archive/block.rs:439 (related: doc comment jix/src/archive/block.rs:413; callers jix/src/archive/block.rs:346,348)
- Reachability: public Rust API / Python API: the line runs on every non-mmap archive read (`Array::read_from_file`, `read_from_file_section`, `read_from_reader`, Python `read_array(mmap=False)`). The trait itself (`BlockTableStorageRead`) is `pub(crate)`, and no input changes the outcome.
- Reported by: codec-archive-archive-io

## What goes wrong
`Owned::read_section` zero-fills a `Vec<MaybeUninit<T>>`, reads the section bytes into it, and
returns `std::mem::transmute::<Vec<MaybeUninit<T>>, Vec<T>>(data)`. `Vec` is `repr(Rust)`, and std
does not guarantee that two instantiations with different type arguments share a field order.
The `transmute` docs use this case (`Vec<&T>` to `Vec<Option<&T>>`) as their example of code that
"relies on the unspecified data layout of `Vec` ... and could cause Undefined Behavior". The
`MaybeUninit` docs say the same about containers of `MaybeUninit<T>`. The contents are fully
initialized (zeroed, then `read_exact`), so the only hazard is the `Vec` header layout.

The hazard is latent only. The hunter suggested that `-Zrandomize-layout` would turn this into
UB, but it does not with the current toolchain. rustc's layout-randomization seed for `Vec<T>`
does not depend on `T`, because `T` reaches `Vec` only through `PhantomData<T>`, and
`RawVecInner` is not generic over `T`. So `Vec<T>` and `Vec<MaybeUninit<T>>` are shuffled the
same way. Miri does not flag it either.

## Trigger
Any Owned archive read, for example `Array::compact_ndarray(..)?.write_to(&mut cursor)` followed by
`Array::read_from_reader(cursor, None, ..)`. This hits line 439 with `T = u8` (block data) and with
`T = BlockLocation` (block table). It would misbehave only on a compiler where
`Vec<MaybeUninit<T>>` and `Vec<T>` lay out `ptr` / `cap` / `len` differently. The ptr, cap and len
would then be swapped, which means an invalid free or out-of-bounds access.

  - `cargo test --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_23_batch3__f022 -- --nocapture`
    gives `test owned_read_section_round_trip ... ok`. It passes, which is expected for a latent issue.
  - `python jix/run_miri.py --all-features --test repro_2026_10_23_batch3__f022` gives `test owned_read_section_round_trip ... ok`, with no UB reported.
- Layout probe (standalone, no jix): `bug-hunt/runs/2026-10-23-batch3/scratch/f022-layout/`
  (source also saved as `scratch/f022-layout-probe.rs`). It reads each `Vec<T>`'s three words
  and prints where ptr, cap and len sit. Results on rustc 1.101.0-nightly (2026-10-20):
  - Plain build: every T gives `["cap","ptr","len"]`.
  - `RUSTFLAGS="-Zrandomize-layout -Zlayout-seed=$s" cargo +nightly run -Zbuild-std`, seeds 1-7:
    the order does change between seeds, for example seed 2 gives `["len","cap","ptr"]` and seed
    4 gives `["len","ptr","cap"]`. So randomization does reach std's `Vec`. Within any one seed,
    though, `Vec<u8>`, `Vec<MaybeUninit<u8>>`, `Vec<u64>`, `Vec<Loc>`, `Vec<MaybeUninit<Loc>>`,
    `Vec<String>` and `Vec<Option<&u8>>` all had the same layout.

## Root cause
At jix/src/archive/block.rs:439, the code assumes that `Vec<A>` and `Vec<B>` have the same
layout whenever `A` and `B` have the same size and alignment. Only the element type is
layout-compatible: `MaybeUninit<T>` is `repr(transparent)`. The container is not guaranteed to
be. Today the assumption holds only because of how rustc implements `Vec` and layout
randomization.

## Suggested fix
Use the sanctioned conversion:
`let mut v = ManuallyDrop::new(data); unsafe { Vec::from_raw_parts(v.as_mut_ptr().cast::<T>(), v.len(), v.capacity()) }`
(this works on MSRV 1.89; `Vec::into_raw_parts` is not needed). Another option is the safe
`data.into_iter().map(|x| unsafe { x.assume_init() }).collect()`, which reuses the allocation
through in-place collect. Update the doc comment at :413 to match.
