# F024: Array::to_ndarray_buf pull mode copies the whole region for large reads of lazy views (broadcast, permute/slice over Plain, collapsed pipelines) that read_data(None) returns in O(1); a huge broadcast aborts

- Severity: low  Verdict: confirmed  Category: questionable-semantics (resource / pathological cost; values are correct)
- Location: jix/src/array.rs:975 (the `small_read` bypass only checks `plain_read()`) (related: jix/src/array.rs:1034 `materialize_out_buf` in `to_ndarray_buf_slow_dyn`, jix/src/storage/buf.rs:327-341 `materialize_out_buf` pull branch, jix/src/ops/shape_ops/broadcast.rs:156 Broadcast pull view, jix/src/ops/shape_ops/broadcast.rs:187 and permute_dims.rs:156 `with_cleared_flags`, jix/src/storage/elementwise_pipeline.rs:891 `pick_output_layout` collapse, jix/src/array.rs:867-869 and core_trait.rs:78-80 "cheapest buffer it can" docs)
- Reachability: public Rust API (`Array::to_ndarray_buf(.., None)`). Not the Python API: jix-py only calls `to_ndarray_buf` in push mode (jix-py/src/array.rs:631). No crate-internal caller uses the Array-level pull; internal pulls go through `storage.read_data` directly.
- Reported by: concept-push-pull

## What goes wrong
`to_ndarray_buf_checked` sends a region to the block-splitting slow path when it has more than
`read_size.min` items and the storage is not PLAIN_READ (array.rs:975). In pull mode the slow path
calls `materialize_out_buf`, which allocates `prod(region) * itemsize` pooled bytes. It then pushes
every piece into that buffer. Only Plain and Scalar (and InsertDim/RemoveDim over them) keep
PLAIN_READ. Broadcast, PermuteDims, Slice and every element-wise pipeline clear it. Their own pull
`read_data(None)` returns a cheap view instead: 0 strides for Broadcast, the re-strided Plain memory
for PermuteDims, and stride-0 collapsed dims for a pipeline. Through the public Array entry point, a
large pull of these views becomes an O(region) copy, and a pipeline runs its kernel on every element
instead of once per distinct input element. The values are right. What fails is the documented
promise that pull returns "the cheapest buffer it can ... possibly with broadcast/stride-0 dims".
The result is also inconsistent: a `Scalar` (PLAIN_READ) of the same shape gives a 0-stride view,
while the equivalent `broadcast` copies. When the region does not fit in memory, the infallible
pool allocation aborts the process. `read_data(None)` on the same storage returns a 4-byte view.

## Trigger
```rust
let b = Array::compact_ndarray(&array![[1.5f32]])?.broadcast(&[4096, 4096]);
b.to_ndarray_buf(&[0..4096, 0..4096], &ctx, None)   // strides [16384, 4], 64 MiB copy
b.storage().read_data(&[0..4096, 0..4096], &ctx, None) // strides [0, 0]
```
The same happens for `-b` (pipeline), for `plain_ndarray_view(&2048x2048).permute_dims(&[1, 0])`
(16 MiB copy instead of a view), and for `.broadcast(&[1 << 20, 1 << 18])` (aborts:
`memory allocation of 1099511627776 bytes failed`, SIGABRT).

## Root cause
The splitting heuristic in `to_ndarray_buf_checked` (array.rs:972-982) was written for push reads
and for storages whose pull has to materialize anyway (Compact, Flip, Repeat...). For those,
splitting bounds the intermediate leaf buffers. In pull mode the slow path must own a destination
for all pieces, so it allocates the full region (array.rs:1034). The only exception is the
`plain_read()` bypass. That flag means "read is a plain strided copy" and is cleared by Broadcast
(broadcast.rs:187), PermuteDims (permute_dims.rs:156) and the pipeline ops, although their pull is a
view. Nothing in the slow path knows which dims the storage would have collapsed, unlike the
pipeline's own `pick_output_layout` (elementwise_pipeline.rs:891).

## Suggested fix
In pull mode, skip the split when the storage can answer with a view. One option is a spec flag
like "pull is a view", propagated by Broadcast, PermuteDims, Slice, InsertDim and RemoveDim when
the inner has it, and set by pipelines whose region collapses. Another option: give the slow path's
pull allocation stride 0 and extent 1 on dims the storage reports as broadcast, and read only one
piece along them, as `pick_output_layout` does. At least, document that an oversized pull through
`Array::to_ndarray_buf` materializes the region. Optionally, return an `Err` instead of aborting
when the pull allocation is unreasonably large.
