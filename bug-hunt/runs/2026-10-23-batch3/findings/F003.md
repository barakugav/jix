# F003: A Strict-valid .jix array of bool (or of a struct with a bool field) whose bytes are not 0/1 decodes into typed Rust `bool`: UB from safe code (Miri-confirmed), and where / cast / not / sum / any return inconsistent results

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/storage/block.rs:201 (related: jix/src/codec/mod.rs:270-327,
  jix/src/archive/block.rs:394-398, jix/src/archive/array.rs:514-539, jix/src/element_type.rs:82,
  jix/src/storage/compact.rs:326, jix/src/storage/compact.rs:342,
  jix/src/storage/elementwise_pipeline.rs:849-854, jix/src/util/mod.rs:793, jix/src/dtype.rs:338,
  jix/src/ops/transmute.rs:52-54, jix/src/archive/mod.rs:42-45, jix-py/src/archive.rs:117-125)
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file` /
  `read_from_file_section` / `read_from_file_mmap`, then `into_typed::<bool>()` or a `Dtyped`
  struct) and Python API (`jix.read_array(path)`, also with `mmap=True`), with the default
  `ArchiveValidation::Strict`
- Reported by: storage-compact-read-path

## What goes wrong
Archive loading validates the header, the sizes and the block locations, but never the decoded
values. `BlockTable::read_block` (block.rs:201) decompresses a block and runs the filters straight
into the destination buffer. When the file declares a bool dtype, or a struct or inner-shape dtype
with a bool field, the file's bytes become Rust `bool` values. jix defines bool as "a single byte
with value 0 or 1" (dtype.rs:338). Any other byte is an invalid value, and the first typed read of
it is UB. Miri reports this in the bool -> i32 cast kernel. The same library treats this as a
soundness requirement elsewhere: `transmute_elements` is `unsafe` precisely because of `bool`
(transmute.rs:52-54). The `ArchiveValidation::Strict` docs (archive/mod.rs:42-45) say it is the
mode to use "whenever the archive's origin is untrusted or unverified". In practice the kernels
disagree with each other. Byte 2 is false in `where`, `cast`, `sum` and `any`, byte 255 is true,
and `numpy()` returns the raw bytes.

## Trigger
1. Write `[0u8, 1, 2, 255]` as a u8 archive (`Array::compact_ndarray(..).write_to(..)`, or
   `jix.write_array(jix.compact(np.array([0,1,2,255], np.uint8)), path)`).
2. Patch the one header byte that encodes the scalar kind from U8 (5) to Bool (14). It is the only
   byte that differs from a 4-element bool archive of the same length. The block bytes are left
   untouched.
3. Rust: `Array::read_from_reader(.., ArrayParams::default(), ArchiveValidation::Strict)?
   .into_typed::<bool>()?`, then `to_ndarray()`, `where_condition(a, x, y)`, `a.cast::<i32>()`,
   `!a`, `a.sum(0)`. Python: `a = jix.read_array(path)`, then `a.numpy()`, `jix.where(a, x, y)`,
   `jix.cast(a, "int32")`, `jix.sum(a)`, `jix.any(a[2:3])`.

A struct dtype works the same way: write `#[repr(C)] struct { a: u8, b: u8 }` with `b` = 2 and
255, then patch the field `b` scalar kind to bool and read it as `struct { a: u8, b: bool }`.

## Root cause
- `BlockTable::read_content` takes the dtype from the file (archive/block.rs:394-398) and checks
  only the codec, filters, sections, sizes and (in Strict mode) block locations.
  `ArrayBlockTableStorageBase::read_from` (archive/array.rs:514-539) adds the geometry checks.
  Nothing anywhere inspects decoded element values.
- `Array::into_typed::<bool>()` checks only that the dtype matches (element_type.rs:82). It cannot
  know about the values.
- Every compact or mmap block read goes through `BlockTable::read_block` (compact.rs:326, 342),
  which calls `Decoder::decode` (block.rs:201). That writes the decompressed and unfiltered bytes
  verbatim into `dst` (codec/mod.rs:270-327). The byte-shuffle and bit-shuffle filters only permute
  bits, so the attacker controls every output byte.
- The typed kernels then read the bytes as `bool`: the elementwise pipeline reads `[bool; N]`
  (elementwise_pipeline.rs:849-854, util/mod.rs:793), and so do `where` (where_op.rs:277-284),
  the reductions and the bool `Not`. LLVM may assume the value is 0 or 1, so different kernels
  look at different bits, which explains the contradictory results above.
- This is the archive-load half of the bool-validity question. K15 covers only the numpy-ingest
  path (jix-py operand.rs). Its fix would not touch this path, and K15's own write-up says so.

## Suggested fix
Validate or normalize bool bytes at the single decode choke point, `BlockTable::read_block`, after
`decode` succeeds and before the block reaches any cache or caller. Do this only for dtypes that
contain a bool: scalar bool, an inner shape of bool, or a struct with a bool field at any depth.
Precompute the bool byte offsets within one element once, at load time in `read_content` (for
example in `DecoderCodecConfig`), so other dtypes pay nothing. Two options:
- normalize each such byte to `(b != 0) as u8`. This matches NumPy's nonzero-is-true and also
  repairs files that the K15 path has already written.
- reject the block with `InvalidArchive`.

Either way the check must run in both Strict and Minimal mode, because Minimal may panic but must
not be UB (codec-archive context, "Intentional behaviors").
