# F011: Dtype::new_struct (and so the archive reader) accepts duplicate struct field names that from_fields rejects

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/dtype.rs:578-629 (`new_struct`, no name check before the `fields` collect at 606) (related: jix/src/dtype.rs:459-467 `from_fields` duplicate check; jix/src/archive/schema/conversions.rs:113 archive `from_proto` -> `new_struct`; jix/src/ops/sub_dtype.rs:85 first-match field lookup; jix-py/src/dtype.rs:37-71 `dtype_to_numpy`)
- Reachability: public Rust API (`Dtype::new_struct`, `Array::read_from_reader` / `read_from_file` on a crafted archive); Python API (`jix.read_array` on a crafted archive)
- Reported by: types-dtype-layout

## What goes wrong
`Dtype::from_fields` rejects a field list with a repeated name ("duplicate field name `x` in struct
dtype"), and the docs of both constructors say names should be unique. `Dtype::new_struct`, the
explicit-layout constructor, never checks names, and it is the constructor the archive reader uses
for every struct dtype. So a `.jix` file whose struct dtype has two fields named `x` loads without
error. `dtype_sub_field("x")` takes the first match, and nothing can select the second field. In
Python, `read_array` succeeds but the array is unusable: `arr.dtype` and `arr.numpy()` both raise
numpy's `ValueError: name already used as a name or title`. The error comes at first use instead of
as `InvalidArchive` at load. No UB and no wrong value for a reachable field. The defect is that two
constructors that should agree validate differently, and malformed archive metadata gets through.

## Trigger
- Rust, direct: `Dtype::new_struct(vec![("x".into(),0,u8::DTYPE),("x".into(),1,u8::DTYPE)], &[], 2, Alignment::new(1).unwrap())` returns `Ok` (itemsize 2). The same list passed to `from_fields` returns `Err`.
- Archive: `array![0x0201u16, 0x0403]` relabeled as that dtype (`transmute_elements_dyn`, sound because all fields are u8), then `write_to` and `read_from_reader(.., ArchiveValidation::Strict)`. The read returns `Ok`, and `dtype_sub_field::<u8>("x")` gives `[1, 3]`. Bytes 2 and 4 cannot be selected. A purely safe route is to byte-patch the field name in any struct archive (the hunter's `jix/tests/hunt_2026_10_23_batch3__types_dtype_layout_2.rs` does this).
- Python: `jix.write_array` of a numpy array with dtype `[("xa","u1"),("xb","u1")]`, then rename `xb` to `xa` in the header bytes (`b"\n\x02xb"` -> `b"\n\x02xa"`), then `jix.read_array(BytesIO(data))`.

## Root cause
The uniqueness check exists only in `from_fields` (jix/src/dtype.rs:460-467, a `HashSet` over the
names). `new_struct` (jix/src/dtype.rs:578-629) validates shape, itemsize, alignment and the
aligned/packed layout, but not names. `Dtype::from_proto` (conversions.rs:84-114) adds no check of
its own and relies on `new_struct`. jix-py's `dtype_from_numpy` (jix-py/src/dtype.rs:208) also calls
`new_struct`, but numpy already rejects duplicate names, so that caller is not affected.

## Suggested fix
Move the duplicate-name check into a helper and call it from `new_struct` too, for example right
after the fields are collected at dtype.rs:606. `from_proto` already maps `new_struct` errors to
`InvalidArchive`, so the archive path then fails at load with a clear message. Add a `new_struct`
test next to `from_fields_duplicate_names_errors` (dtype.rs:1447).
