# F008: Writing an archive into an append-mode (O_APPEND) file or file object returns Ok but leaves the TOC as zeros, so the archive cannot be read back

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/archive/block.rs:229-235 (TOC patch in `BlockArchiveWriter::finalize`) (related: jix/src/archive/block.rs:163-176 (`start` writes the zero TOC placeholder, then seeks forward over the locations section), jix/src/archive/block.rs:212-218 (locations patch), jix/src/archive/block.rs:236-240 (final seek sets a position that is not EOF), jix/src/archive/array.rs:286-329 / :392-410 (`write_to` / `write_to_with` accept any `Write + Seek`), jix-py/src/archive.rs:160-165 and :231-235 (`write_array` on a file-like, `append` ignored), jix-py/src/archive.rs:216-218 (the path branch avoids O_APPEND on purpose))
- Reachability: public Rust API (`Array::write_to`, `write_to_with` with a `File` opened with `OpenOptions::append(true)`) and Python API (`jix.write_array(arr, f)` with `f = open(p, "ab")`)
- Reported by: codec-archive-archive-io

## What goes wrong
`BlockArchiveWriter` assumes that each write lands at the position it last sought to. `start` writes
a zero TOC placeholder and seeks forward past the block-locations section. `finalize` seeks back to
write the locations and then the real TOC. On an append-mode stream every write goes to EOF and
seeks are ignored for writes. The block data lands where the locations belong, the locations and
the real TOC are appended after it, and the zero placeholder TOC stays where readers look for it.
`write_to` / `write_array` return success. Every later read of that archive fails with
`block locations length 0 does not match N blocks`, so the data is lost. In Python, `f.tell()` after
`write_array` also reports a position short of EOF (235 vs a 267-byte file), because the final seek
in `finalize` targets `block_data_offset + len`. Offsets recorded with `tell()` for packed arrays
are therefore wrong too. The read fails loudly (an error, never wrong values): an all-zero TOC only
passes validation for 0-block arrays, and those read back correctly as empty.

## Trigger
Rust:
```rust
let mut f = OpenOptions::new().create(true).append(true).open(&p)?;
Array::compact_ndarray(&array![1i32, 2, 3, 4, 5])?.write_to(&mut f)?; // Ok(())
Array::read_from_file_section(&p, 0, len, ArrayParams::default(), ArchiveValidation::Strict)
// -> Err("block locations length 0 does not match 1 blocks")
```
Python, using the documented "pack two arrays into one file" pattern with a file object (for file
objects `write_array` ignores `append=`, so `"ab"` is how a user would append):
```python
jix.write_array(jix.compact(a), p)
off = os.path.getsize(p)
with open(p, "ab") as f:
    jix.write_array(jix.compact(np.arange(6, dtype=np.int16) * 7), f)  # returns None
jix.read_array(p, offset=off)  # RuntimeError: block locations length 0 does not match 1 blocks
```

## Root cause
The writer uses seek-then-write (block.rs:173-176, :212-218, :229-235) and never checks that a
write landed at the expected offset. `Write + Seek` alone does not promise this: std documents
that an append-mode `File` sends every write to EOF whatever the seek position. Python's `"ab"`
objects behave the same way and still report `seekable() == True`. The developers know about the
hazard. The path branch of `write_array` opens without O_APPEND and seeks to the end by hand, for
exactly this reason (jix-py/src/archive.rs:216-218). Writers that users pass in are not checked,
and neither the Rust docs (`write_to`: "any destination implementing `Write` + `Seek`") nor the
Python docstring (`write_array`: "any seekable binary file-like object ... an open file handle")
mention the requirement. There is also a smaller related problem. A Rust append-mode `File` on an
existing file reports position 0 until its first write, because std does not seek to EOF on open,
so `ArchiveWriter::new` would record a wrong `base_offset` as well.

## Suggested fix
Detect the case and return an error instead of `Ok`. In `finalize`, after writing the locations
and the TOC, compare `stream_position()` with `seek target + bytes written`. On an append-mode
stream it reports EOF instead, so return an `Err` such as "writer does not honor seek (opened in
append mode?)". A similar check right after the seek in `start` and the first data write catches
the problem earlier. Also document in `write_to` / `write_to_with` / `write_array` that the writer
must not be in append mode. A more robust alternative is a format with a trailing footer, which
needs no seek-back, but that is a format change.
