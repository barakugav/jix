# F006: Archive message length (uleb128) is allocated and zero-filled before it is checked against the archive length, so an 11-byte file aborts the process (Rust and Python)

- Severity: medium  Verdict: confirmed  Category: resource
- Location: jix/src/archive/common.rs:210 (related: jix/src/archive/common.rs:152-163 (`try_read_message`, `length as usize` at :161), jix/src/archive/array.rs:446-458 (FileMetadata and ArrayHeader reads), jix/src/archive/block.rs:310-312 (BlockTableHeader read), jix/src/archive/block.rs:423 (sections, unlike messages, ARE checked against the limit before allocating), jix-py/src/archive.rs:91-146)
- Reachability: public Rust API (`Array::read_from_file`, `read_from_file_section`, `read_from_reader`, `read_from_file_mmap`) and Python API (`jix.read_array(path)` with default arguments, and file-like readers)
- Reported by: codec-archive-archive-io

## What goes wrong
`ArchiveReader::try_read_message` decodes an untrusted u64 length with `read_uleb128` and passes
it to `read_slice(length as usize)`. `read_slice` first runs `self.tmp_buf.resize(len, 0)` and only
then `read_exact`. The length is never compared with `self.reader.limit()`, the archive bytes that
are left. The `Take` limit makes `read_exact` fail, but only after the allocation and zero-fill.
Every message goes through this path: FileMetadata (the first bytes after the magic), ArrayHeader
and BlockTableHeader. It happens for every read entry point, for Strict and Minimal validation,
and even when the caller passes the exact archive length.

The effect depends on the size:
- A length above `isize::MAX` panics with "capacity overflow". In Python that is a
  `PanicException`, a `BaseException`.
- A length that cannot be allocated, such as 2^44, makes `handle_alloc_error` abort the process.
  No caller can catch that, in Rust or Python.
- A length that fits in RAM, such as 256 MiB, is allocated and zero-filled. That memory is
  committed before the EOF error comes back.

The section reader already checks sizes against the archive length before it allocates
(`check_section_bounds`, block.rs:423), so the message path is the odd one out.

## Trigger
File bytes = `b"jix1" + uleb128(1 << 44)` (11 bytes), then
`Array::read_from_file(&path, ArrayParams::default())`, or Python `jix.read_array(path)`.
Variants: `uleb128(1 << 63)` (14 bytes) gives a capacity-overflow panic, and `uleb128(1 << 28)`
(9 bytes) zero-fills 256 MiB and then returns `Err(Io "failed to fill whole buffer")`. A valid
FileMetadata followed by a bad ArrayHeader length works the same way.
Expected: an `Err` (InvalidArchive / UnexpectedEof) with no allocation larger than the archive.
For comparison, a small bad length, such as `b"jix1" + b"\x64"`, already gives
`RuntimeError: IO error: failed to fill whole buffer` in Python.

## Root cause
`try_read_message` (common.rs:160-161) trusts the decoded length:
`let msg_bytes = self.read_slice(length as usize)?;`.
`read_slice` (common.rs:209-211) runs `tmp_buf.resize(len, 0)` before `read_exact`. Nothing
between them compares `length` with `self.reader.limit()`. That limit is `len` minus the bytes
already consumed, or `u64::MAX` when `len` is `None`. The context doc already lists the uleb128
message length as "Trusted / NOT validated", but nothing makes it safe to trust. The protobuf
messages involved are tiny: FileMetadata is 2 fields and the headers are a few hundred bytes at
most.

On 32-bit there is also a truncation: `length as usize` at :161 reads `2^32 + k` as `k`. That
mis-frames the stream, but later checks reject it, so it does not add a separate failure.

## Suggested fix
In `try_read_message`, reject `length > self.reader.limit()` with an
`UnexpectedEof` / InvalidArchive error before calling `read_slice`. Also use `usize::try_from`
instead of `as usize`. To cover `len = None` (limit `u64::MAX`), add one of these:
- a sanity cap on header message size (for example 16 MiB), or
- an incremental read (`(&mut self.reader).take(length).read_to_end(&mut tmp_buf)` and then
  check the byte count), so memory grows only with the bytes that actually arrive.
