# F002: Archive read keeps the caller's block_shape_fixed_dims, so tune rescales the file's block shape and blocks are decoded with the wrong geometry (silently wrong values, panic, or every read failing; write_to then persists a corrupt Strict-valid file)

- Severity: high  Verdict: confirmed  Category: wrong-result
- Location: jix/src/archive/array.rs:537 (related: jix/src/storage/compact.rs:200, jix/src/storage/params.rs:349-393, jix/src/storage/compact.rs:296, jix/src/storage/compact.rs:395, jix/src/storage/block.rs:162, jix/src/archive/array.rs:398-405, jix-py/src/archive.rs:100, jix-py/src/array.rs:1658-1678)
- Reachability: public Rust API (`Array::read_from_file`, `read_from_file_section`, `read_from_reader`, `read_from_file_mmap`) and Python API (`jix.read_array(..., params=...)`, also with `mmap=True`)
- Reported by: storage-compact-read-path

## What goes wrong
When an archive is read with `ArrayParams` whose `block_shape_fixed_dims` has any `false` entry,
`ArrayBlockTableStorageBase::new` re-tunes the file's block shape. The spec block shape then no
longer matches the geometry of the stored blocks, and `read_data` takes block indices, grid,
in-block offsets and strides from that spec. There are three outcomes:
- Same block volume, different shape: every block decodes fine but is scattered with the wrong
  shape. The values are silently wrong (3584 of 4096 elements in the repro).
- Different volume: every read of a valid file fails with `InvalidBufferSize`.
- Same volume with a larger spec grid: the bounds-checked `blocks_loc` index panics
  (`PanicException` in Python).

`write_to` / `write_array` of such an array copies the blocks verbatim and writes the drifted
block shape into the header. The new file passes Strict validation, and reading it back with
default params gives the permuted data. The corruption is silent and persisted.

## Trigger
Rust:
```rust
let src = Array2::from_shape_fn((64, 64), |(i, j)| (i * 64 + j) as i32);
// write with block_shape [8, 32] (write_to), then:
let mut p = ArrayParams::new();
p.block_shape_fixed_dims(&[false, false]).block_size(1024);
let a = Array::read_from_reader(Cursor::new(bytes), None, p, ArchiveValidation::Strict)?;
a.into_typed::<i32>()?.to_ndarray::<Ix2>()?   // Ok, but row 1 = [128, 129, ...]
```
The spec block shape becomes [4, 64] while the stored blocks are [8, 32].

Python:
```python
jix.write_array(jix.compact(src, params={"block_shape": [8, 32]}), path)
jix.read_array(path, params={"block_shape_fixed_dims": [False, False], "block_size": 1024}).numpy()
```

Other triggers:
- 1-D, shape [100], block [16], read with `block_shape_fixed_dims(&[false])` and the default
  `block_size`: `InvalidBufferSize: got 400, expected 64`.
- Shape [64, 300], block [32, 5] (120 blocks), read with [False, False] and block_size 1024:
  the spec is [1, 160] (128 blocks), and the read panics with "index out of bounds: the len is
  120 but the index is 120" at storage/block.rs:162.
- The same params reused on two machines, simulated with block_size 1024 and then 2048, with
  `block_shape [8, 1]` and fixed dims `[true, false]`: the read fails with `InvalidBufferSize`.

## Root cause
- `read_from` validates the header geometry against the `BlockTable` (archive/array.rs:462-535).
  It then sets only `params.block_shape = Some(<file block shape>)` (archive/array.rs:537) and
  passes the caller's other fields, including `block_shape_fixed_dims` and `block_size`, to
  `Self::new`.
- `new` calls `params.into_spec(...)` (compact.rs:200), which calls `tune`. With any `false`
  fixed-dim, `fixed_block_shape` is false (params.rs:349). `block_size` defaults to L1
  (params.rs:351-353), and the non-fixed dims are rescaled from 1 (params.rs:372-393).
- The result becomes the spec block shape. Nothing compares it with `blocks.block_size` or with
  the header shape, although `read_data` treats the spec block shape as the storage geometry:
  compact.rs:296 and the grid at compact.rs:311-315 for fast path 1, and the block strides and
  `full_buf_len` from compact.rs:390 onwards for `read_data_slow`.
- `read_block` catches only a volume mismatch (block.rs:189-195). It does not catch a
  same-volume reshape, and its index (block.rs:162) is out of bounds when the spec grid is larger.
- `write_to_with` on a compact source writes `storage.0.block_shape()`, the drifted spec, into
  the header next to the original blocks (archive/array.rs:398-405). The header still satisfies
  every check at read time when the volume and nblocks happen to match.
- Side effect: the 2^30-byte block bound is enforced only by `tune` (params.rs:405-414), on the
  rescaled shape. A file whose own block exceeds it is accepted at load time when its geometry
  drifts. Reads still fail with `InvalidBufferSize` before any allocation of that size, so no
  further impact was found here.

Users are expected to pass these params on read. The Rust `read_from_*` docs say `params`
"control how the array is read" (see `ArrayParams`). The Python `read_array` docstring points to
`jix.compact()` for `params`. There, `block_shape_fixed_dims` is described as controlling how
DOWNSTREAM ops rescale the block shape, so a reader has a legitimate reason to pass `False`.
Neither doc says it can change how existing blocks are decoded. No existing test reads an
archive with non-default fixed dims.

## Suggested fix
In `read_from` (archive/array.rs:537), the file's geometry must win. Either:
- override `block_shape_fixed_dims` to all-true for tuning and build the spec, then restore the
  caller's flags only as propagation hints, or
- reject a non-all-true `block_shape_fixed_dims` with `InvalidArgument`.

Also add a check in `ArrayBlockTableStorageBase::new` that
`prod(spec.block_shape) == blocks.block_size` and that the grid size equals `blocks.nblocks()`,
or better, take the block shape from the caller instead of re-tuning it. This also protects the
`compact_with` double-tune path.
