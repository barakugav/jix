# F020: 32-bit: check_out_buf runs check_region_size (`r.end - r.start`) before the index is validated; a reversed range panics (debug) or gets the wrong error kind (release)

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/error.rs:278 (related: jix/src/storage/buf.rs:288, jix/src/ops/op1.rs:60, jix/src/ops/op2.rs:108, jix/src/ops/map.rs:300, jix/src/ops/cmp.rs:814, jix/src/ops/shape_ops/insert_dim.rs:163, jix/src/ops/shape_ops/remove_dim.rs:160, jix/src/ops/shape_ops/permute_dims.rs:124, jix/src/ops/where_op.rs:161, jix/src/ops/sub_dtype.rs:123)
- Reachability: public Rust API (direct `ArrayStorage::read_data` call, 32-bit targets only). Not reachable from Python or from the `Array`-level entry points, which call `check_get_range` first (array.rs:757, 853, 950).
- Reported by: concept-push-pull

## What goes wrong
`ArrayStorage::read_data` is a safe public trait method, and its contract (core_trait.rs:87-89) says it must reject an index with `start > end` itself. `check_out_buf` (buf.rs:282) starts with `check_region_size` (error.rs:274). On 32-bit targets that function computes `r.end - r.start` for every range without checking `start <= end`. Nine storages call `check_out_buf` before they validate the ranges: Op1, Op2, MapMultiple, Clamp, InsertDim, RemoveDim, PermuteDims, Where and SubDtype. The last four call only `check_get_range_ndim`, which checks ndim but not the bounds. So for these storages, the leaf storages that would reject a reversed range never run. On i686 a debug build panics with "attempt to subtract with overflow". A release build wraps to a huge product and returns `InvalidShapeOperation` ("read region ... does not fit in memory") instead of `InvalidIndex`. This causes no memory unsafety: in release the wrapped size only produces an error, and every path downstream still calls `check_get_range`. 64-bit builds compile the check out (`cfg!(target_pointer_width = "32")`), so they return `InvalidIndex`.

## Trigger
On i686, any of the following, where `a = Array::compact_ndarray(&array![1i32, 2, 3, 4])`:
- `(-a.view()).storage().read_data(&[3..1], &ctx, None)`
- `(a.view() + a.view()).storage().read_data(&[3..1], &ctx, None)`
- `a.view().insert_dim(0).storage().read_data(&[0..1, 3..1], &ctx, None)`
- `where_condition(c, a.view(), a.view())`, `a.view().clamp(a.view(), a.view())`, `remove_dim` and `permute_dims` views read the same way.

## Root cause
`check_region_size` (error.rs:274-288) assumes the ranges are already validated, but `check_out_buf` (buf.rs:288) calls it first, before checking anything else. The leaf storages (Compact compact.rs:278, Plain plain.rs:454, Scalar scalar.rs:103) and most shape ops call `check_get_range` before `check_out_buf`. The element-wise ops (op1.rs:60, op2.rs:108, map.rs:300, cmp.rs:814) and InsertDim (insert_dim.rs:163) call `check_out_buf` first and validate later, or leave validation to their child. RemoveDim, PermuteDims, Where and SubDtype (remove_dim.rs:136, permute_dims.rs:123, where_op.rs:160, sub_dtype.rs:122) only call `check_get_range_ndim` first.

## Suggested fix
Make `check_out_buf` call `check_get_range(array_shape, index)` first. It already takes `array_shape`, and that call would replace its own index-ndim check. All impls would then validate the same way, and `check_region_size` would only ever see valid ranges. Another option is to make `check_region_size` itself robust, for example with `r.end.checked_sub(r.start)` mapped to an `InvalidIndex` error.
