# F033: Zero-element arrays are rejected on input when a dim of length > 1 has a negative stride, though no element is ever addressed (gap in the K80 fix)

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/storage/plain.rs:519 (related: jix-py/src/ops/common/operand.rs:473-477, jix-py/src/array.rs:251-255, jix/src/storage/plain.rs:245, jix/src/storage/plain.rs:282)
- Reachability: public Rust API (`Array::plain_ndarray(_with)`, `plain_ndarray_ref(_with)`, `plain_ndarray_view(_with)`, `compact_ndarray(_with)`) and Python API (`jix.asarray`, `jix.compact`, any op with a numpy operand, `Array.plain()`)
- Reported by: concept-degenerate-shapes

## What goes wrong
The K80 fix made the ndarray and numpy input paths ignore the stride of a dim of length <= 1, because
such a dim is never stepped. It left out arrays with zero elements. In such an array no dim is ever
stepped, so every stride is irrelevant. Both input paths still check the sign of the stride on every dim
of length > 1. A reversed view sliced down to empty, such as `a[::-1][:, 1:1]`, is therefore rejected
with "Negative strides are not supported".

NumPy flags this array C_CONTIGUOUS, so `np.ascontiguousarray(x)` returns `x` itself and the usual
workaround does not help. ndarray reports `is_standard_layout() == true`. jix's own `numpy(out=x)`
accepts the same array, because `check_output_array` returns early for any shape containing 0
(array.rs:251-255). The input and output paths therefore disagree on one buffer. No values are wrong and
nothing is unsafe: valid input gets a clean error. Generic code that reverses an axis and then takes an
empty slice fails only in this corner case.

## Trigger
Python: `x = np.arange(12.0).reshape(4, 3)[::-1][:, 1:1]` gives shape (4, 0), strides (-24, 8), and
C_CONTIGUOUS True. Each of `jix.asarray(x)`, `jix.compact(x)`, `jix.asarray(np.ascontiguousarray(x))`
and `jix.asarray(np.zeros((4, 0))) + x` raises
`ValueError: Negative strides are not supported`. `jix.compact(np.zeros((4, 0))).numpy(out=x)` is
accepted.

Rust: `let base = Array2::<f64>::zeros((4, 3)); let v = base.slice(s![..;-1, 1..1]);` gives shape
[4, 0], strides [-3, 0], and standard layout. `Array::plain_ndarray_view(v)`,
`Array::plain_ndarray_ref(&v)` and `Array::compact_ndarray(&v)` all return `Err(InvalidArgument)`.
The owned form fails the same way: `Array2::zeros((4, 3))`, then `invert_axis(Axis(0))`, then
`slice_collapse(s![.., 1..1])`, then `Array::plain_ndarray(owned)`.

## Root cause
- `strides_from_ndarray` (plain.rs:516-527) skips the sign check only per dim (`if len <= 1`). It
  never looks at whether the whole shape is empty. The Python twin in `plain_from_numpy`
  (operand.rs:470-479) has the same per-dim test.
- The two input paths and the output path use different rules for the same array.
  `check_output_array` returns early for any shape containing 0 (array.rs:251-255). The input paths
  have no such early return.
- Nothing downstream needs these strides when the array has no elements. The `Plain::new` and
  `plain_ndarray_ptr` safety contracts (plain.rs:108-115, 407-413) only require memory to be valid
  for the index combinations that exist, and an empty shape has none. Empty reads also return before
  any pointer math (`NdCopier::copy`, jix/src/util/nd_copy.rs:67-68).

## Suggested fix
In both `strides_from_ndarray` and `plain_from_numpy`, check first whether any dim has length 0. If one
does, return `itemsize` (or the C-order strides) for every dim without checking the signs, the same way
length <= 1 dims are handled today. Extend `negative_strides_are_an_error` (plain.rs) and
`test_negative_strides_raise_value_error` (test_bad_input.py) with an empty reversed view.
