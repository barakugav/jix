# F020: Struct dtypes nested 33+ levels are written to .jix without error but can never be read back (prost decode recursion limit)

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix/src/archive/schema/conversions.rs:129 (`Dtype::to_proto`, recursive at :160, no depth check) (related: jix/src/archive/block.rs:141 writer header, jix/src/archive/common.rs:162 `M::decode` with prost's default `RECURSION_LIMIT = 100`, jix/src/archive/block.rs:318-320 header decode mapped to `Error::io`, jix/src/dtype.rs:175 docs promise "arbitrary nesting", jix-py/src/dtype.rs:203 numpy dtype conversion accepts any depth)
- Reachability: public Rust API (safe: nested `#[derive(Dtyped)]` structs + `compact_ndarray` + `write_to`), Python API (`jix.write_array` of a nested numpy structured dtype)
- Reported by: py-core-numpy-wrap-dtype

## What goes wrong
`Dtype::to_proto` serializes nested struct dtypes recursively with no depth limit, so `write_to` /
`write_to_file` / Python `write_array` succeed for any nesting depth. The reader decodes the
`BlockTableHeader` with prost, whose default decode recursion limit is 100 message levels. Each
struct level costs 3 levels (Dtype -> DtypeStruct -> Field -> Dtype) plus the header itself, so a
dtype nested 33 or more struct levels deep produces a file that `read_from_reader` /
`read_from_file` / `read_array` always reject, in both `Strict` and `Minimal` validation (the
header is decoded before validation is consulted, block.rs:318). The data is effectively lost
to jix: the writer is more permissive than the reader (same class as K53). The error also comes
back with kind `Io` ("IO error: failed to decode Protobuf message: ... recursion limit reached")
rather than `InvalidArchive`, which points the user at their storage rather than the dtype.
Depth 32 round-trips.

## Trigger
Rust (safe): `#[derive(Copy, Clone, Dtyped)] #[repr(C)] struct S1 { a: u8 }`, then
`struct S2 { a: S1 }` ... `struct S33 { a: S32 }`;
`Array::compact_ndarray(&Array1::from(vec![S33; 4]))?.write_to(&mut Cursor)` -> `Ok`;
`Array::read_from_reader(Cursor::new(&bytes), None, ArrayParams::default(), Strict)` -> `Err`.

Python: `d = np.dtype('u1'); for _ in range(33): d = np.dtype([('a', d)])`;
`x = np.arange(1, 5, dtype=np.uint8).view(d)`; `jix.write_array(x, b)` succeeds;
`b.seek(0); jix.read_array(b)` raises `RuntimeError`.

## Root cause
The format has an implicit nesting cap (prost 0.14 `RECURSION_LIMIT = 100`, not overridable
without the `no-recursion-limit` feature, which jix does not enable - jix/Cargo.toml:27), but
nothing on the write side enforces it: `Dtype::to_proto` (conversions.rs:129-171) recurses into
every field dtype (:160), `BlockArchiveWriter::start` (block.rs:141) writes the result, and no
`Dtype` constructor (`from_fields`, `new_struct`, derive, `dtype_from_numpy`) bounds nesting depth.
The reader (common.rs:162) then fails inside prost before `Dtype::from_proto` runs, and
block.rs:320 wraps the `DecodeError` as `Error::io`.

## Suggested fix
Define a maximum struct nesting depth (e.g. 32, with headroom below prost's limit, or compute it
from the limit: `(100 - header levels) / 3`) and enforce it in one place: preferably in the Dtype
constructors (`from_fields` / `new_struct`, so derive, numpy and archive paths all inherit it),
or at least in `BlockArchiveWriter::start` before anything is written, returning a clear error.
Optionally map a header `DecodeError` to `InvalidArchive` instead of `Io`.
