# F037: Float add/sub/mul/square and the sum/prod/mean reductions never report `invalid` or `over`, while divide reports the same conditions; under default modes `inf / inf` raises but `inf - inf` is a silent NaN

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/ops/op2.rs:590 (related: jix/src/ops/op2.rs:610 f16 add/sub/mul, jix/src/ops/op2.rs:633-644 the `impl_arith!` instantiations, jix/src/ops/op1.rs:389-394 and 411-415 float/f16 Square, jix/src/ops/reduction.rs:1520-1528 Sum update/merge, jix/src/ops/reduction.rs:1606-1614 Product update/merge, jix/src/ops/op2.rs:1148-1156 `float_div_error`, jix/src/error.rs:301-302 InvalidOperation definition, jix-py/src/error.rs:38-51 errstate doc)
- Reachability: public Rust API and Python API
- Reported by: concept-arith-semantics

## What goes wrong
A NaN result from non-NaN operands is what `ArithmeticErrorKind::InvalidOperation` is defined to mean (error.rs:301), and an infinite result from finite operands is what `Div`, `Pow` and `Exp` report as `Overflow`. The float Add, Sub and Mul kernels (`impl_arith!`, op2.rs:588-593, f16 at 607-611), float Square (op1.rs:389-394, 411-415), and every reduction take no `ArithmeticOpStatus`. The `Sum` and `Product` traits fold through the status-less `Add::add` / `Mul::mul` (reduction.rs:1522/1527, 1608/1613), and `Mean` goes through Sum. So these ops never report either condition. The modes then give different outcomes for the same IEEE condition:
- Default modes (`invalid` = raise/Error): `inf / inf` fails the read, but `inf - inf`, `inf + -inf`, `0 * inf`, `sum([inf, -inf])` and `mean([inf, -inf])` return NaN with no error and no warning.
- `errstate(all='raise')` / every mode set to Error: `1e308 + 1e308`, `-1e308 - 1e308`, `1e200 * 1e200`, `square(1e200)`, `sum([1e308, 1e308])`, `prod([1e200, 1e200])` and f16 `sum` of 1000 x 100.0 all return inf silently. `1e308 / 1e-308` raises.

numpy reports every one of these: it warns under default modes and raises under `errstate(all='raise')`. The issue is not only that numpy differs. errstate's documented purpose (jix-py/src/error.rs:38-42: "An operation that hits an error ... the mode decides what else happens") is to let a user catch NaN or inf generation, and it silently covers only some ops. jix's own default is stricter than numpy's (`invalid` raises), and that default applies to divide and not to subtract.

Partly related, already triaged:
- K60 (intended): `power(x, 2)` is routed to Square, which drops Pow's Overflow. Its resolution note says "x ** 2 on floats is a plain square, without the Pow overflow report". K60 covers only the Pow-to-Square routing. It does not cover add/sub/mul, the InvalidOperation default-mode asymmetry, or the reductions.
- batch3 and batch5 raised the Overflow half as an open question ("is it deliberate?"). There is no KNOWN entry.

The hunter's extra sub-claim, that a Python float scalar narrowed to an f16/f32 array dtype becomes inf without a report (jix-py/src/ops/common/operand.rs:384-385), is covered by documented intended behavior. py-ops context: "an untyped float next to an f16 array stays f16 (can overflow to inf, by design)". elementwise-ops context: "Casts never set a status". It is not part of this finding.

## Trigger
Python:
```python
x = jix.compact(np.array([np.inf]))
(x / x).numpy()                       # FloatingPointError: invalid operation encountered
(x - x).numpy()                       # array([nan]), no warning (default modes)
with jix.errstate(all="raise"):
    (jix.compact(np.array([1e308])) + jix.compact(np.array([1e308]))).numpy()   # array([inf])
    jix.sum(jix.compact(np.array([1e308, 1e308]))).numpy()                       # array(inf)
    jix.sum(jix.compact(np.full(1000, 100.0, np.float16))).numpy()               # array(inf, float16)
```
Rust: `(a - b)` with `a = b = [inf]` under the default `read_ctx()` gives `Ok([NaN])` while `a / b` gives `Err(Arithmetic, "invalid operation encountered")`. `Array::compact_ndarray(&array![1e308f64, 1e308])?.sum(0)` read with every `ArithmeticErrorMode` set to `Error` gives `Ok(inf)`.

## Root cause
- Commit 98b2ed3 (#81, "Add kernel errors for many ops") added status reporting to divisions, remainders, sqrt, ln, exp, trig and pow. For add/sub/mul/square it only made the integer kernels wrap. The float arms of `impl_arith!` (op2.rs:588-593, 607-611) and Square (op1.rs:389-394, 411-415) remained plain `a op b` in status-less traits (`define_scalar_op2_trait!` Add/Sub/Mul at op2.rs:338-370 declare no `(status)`).
- The reduction kernel traits (`Sum::update` / `merge_states`, `Product`, and Mean via Sum, reduction.rs:1462-1528, 1550-1614) have no status parameter at all, so a reduction cannot report anything.
- None of this is documented as an exception. The trait docs for Add/Sub/Mul and Square mention only integer wrapping. The `errstate` doc and `set_arithmetic_error_mode` (codec/mod.rs:424-427) describe the modes as applying to element-wise operations in general. No context doc "Intentional behaviors" entry or KNOWN entry covers float add/sub/mul or the reductions. K60 covers only the `power(x, 2)` routing.

## Suggested fix
Either make the behavior consistent or document it.
- Consistent: give the float Add/Sub/Mul/Square kernels a status the same way Div does. The fast path stays a plain `a op b`. Only when the result is non-finite (one vector compare per chunk in the SIMD body) call a cold classifier: NaN result with non-NaN operands sets InvalidOperation, an inf result with finite operands sets Overflow. For reductions, track per output whether any input was non-finite, and classify the finalized value the same way, or thread a status through `Sum`/`Product::update`.
- Document instead: if the hot kernels are meant to stay status-free, say so in the Add/Sub/Mul/Square and Sum/Product/Mean docs and in the `jix.errstate` docstring ("add, subtract, multiply, square and reductions never report errors"). Then add a KNOWN entry so later runs stop raising it.
