# F018: jix.log(f16, base) for a valid base near 1 rounds a finite result to +-inf with no Overflow report (no warning, no error under over='raise')

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix-py/src/ops/op1.rs:369-371 (related: jix-py/src/ops/op1.rs:366 (`ln_base_inv`), jix/src/ops/map.rs:16 (`Array::map`, no status channel), jix/src/ops/cast.rs:20-22 (scalar `Cast::cast`, no status), jix/src/ops/op1.rs:539-556 (f16 `float_op1!` kernels report this case, the K106 fix), jix-py/src/array.rs:1461 (`Array.log`))
- Reachability: Python API (`jix.log(a, base=...)`, `Array.log(base=...)`); the Rust core has no log-with-base
- Reported by: py-ops-arith-wrappers

## What goes wrong
For a base other than e / 2 / 10, `jix.log` computes `ln(x)` in f64, multiplies by `1 / ln(base)`
and narrows the result to the input dtype inside `Array::map`, whose closure has no
`ArithmeticOpStatus`, using the scalar `Cast`, which never reports. For f16 input and a base with
`|ln(base)| < ~2.5e-4` (base in about (0.99975, 1.00025)), ordinary inputs have a true result
beyond f16's range (e.g. 69081 for x = 1000, base = 1.0001), and it becomes +-inf with no Overflow
report: no RuntimeWarning by default and no FloatingPointError under `jix.errstate(over="raise")`.
The same quotient computed as `jix.divide(jix.log(x16), ln_base)` reports it. So do the f16
`exp` / `tan` / `power` kernels, which since the K106 fix check for a finite wide result that
rounds to an infinite f16. numpy reports it as well ("overflow encountered in divide" for
`np.log(x16) / f16`, "overflow encountered in cast" for the f64 result cast to f16). The result
value (inf) is the correctly rounded one; only the report is missing. f32 / f64 cannot reach it:
`|ln(x)| <= ~745` and `|ln(base)| >= ~1.1e-16` for any f64 base != 1 bound the result far below
f32's max.

Not every jix op reports a float overflow: plain add / sub / mul / square (K60, intended) and
casts (intentional per the elementwise-ops context doc) do not. That is why the hunter's "every
other f16 op" overstates it. But `log` with a base is a transcendental op, a division by
`ln(base)`, so it belongs with Div / Pow / the `float_op1!` kernels, which all report.

## Trigger
```python
h = np.array([1000.0, 65504.0], dtype=np.float16)
with jix.errstate(over="raise"):
    jix.log(h, base=1.0001).numpy()   # [inf, inf], no error; true [69081.0, 110904.2]
    jix.log(h, base=0.9999).numpy()   # [-inf, -inf], no error
```
The same happens through `jix.compact(h).log(base=1.0001)`.

## Root cause
jix-py/src/ops/op1.rs:369-371 does the final narrowing step,
`res.map(move |x: f64| <f64 as Cast<T>>::cast(x * ln_base_inv))`, through `Array::map`
(jix/src/ops/map.rs:16, `F: Fn(S::Item) -> R`). That map has no status argument, and
`Cast::cast` (jix/src/ops/cast.rs:20-22) does not report out-of-range float narrowing, so
nothing can tell errstate that a finite f64 result became an infinite f16. The K107 / #92 fix
moved the multiplier to f64 so it can no longer overflow on its own. It left the result's
narrowing unchecked, which is the same pattern the K106 fix closed in the f16 `float_op1!`
kernels (jix/src/ops/op1.rs:543-552: `status.set_if(Overflow, r.is_infinite() &&
r32.is_finite())`).

## Suggested fix
Do the narrowing in a step that can report. Either add a status-aware map to the core (for
example `map_with_status(|x, status| ...)` built on the same Op1 kernel machinery) and set
`Overflow` when `r.is_infinite() && (x * ln_base_inv).is_finite()`, or make "log with a runtime
base" a core Op1 kernel with an f64 parameter whose f16 / f32 impls do the same check as
`float_op1!`. Keep the single f64 computation and the single cast, so the K92 rounding fix holds.
