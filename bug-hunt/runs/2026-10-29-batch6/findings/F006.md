# F006: dtype_from_numpy recurses once per struct nesting level with no depth limit: a deeply nested numpy struct dtype segfaults the interpreter (native stack overflow) instead of raising

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix-py/src/dtype.rs:203 (the self-call inside the field-map closure of `dtype_from_numpy`, jix-py/src/dtype.rs:101) (related: jix-py/src/dtype.rs:45 `dtype_to_numpy` self-call, jix-py/src/ops/common/operand.rs:87, jix-py/src/ops/as_array.rs:78, jix/src/dtype.rs:891 and :1075 recursive `Dtype` eq / drop)
- Reachability: Python API
- Reported by: py-core-numpy-wrap-dtype

## What goes wrong
`dtype_from_numpy` converts a numpy struct dtype by calling itself once per field, so its
recursion depth equals the nesting depth of the struct, and nothing bounds it. Each level also
goes through pyo3 / rust-numpy calls (`names()`, `get_field()`, `PyErr` plumbing), about 6 KB
of stack per level in the debug wheel. jix-py runs on the calling Python thread's stack, and
Rust's stack-overflow guard handler is not installed in an extension module, so the overflow is
a plain SIGSEGV that kills the interpreter. No Python exception is raised. numpy builds, copies
and assigns the same dtype without trouble. For its own recursive operations (repr, `.descr`,
`str(x)`) numpy raises a catchable `RecursionError` instead. Every path that wraps a numpy
operand reaches this: `jix.asarray(x)`, `asarray(..., dtype=d)` / `jix.cast`, and any op that
takes a numpy operand (for example `jix.where`).

## Trigger
```python
d = np.dtype('u1')
for _ in range(1400):
    d = np.dtype([('a', d)])
x = np.zeros(2, dtype=d)
jix.asarray(x)        # main thread, 8 MiB stack, debug wheel -> SIGSEGV
```
On a thread started after `threading.stack_size(1 << 20)`, depth 200 is enough, through
`jix.asarray(x)`, `jix.asarray(np.zeros(2, 'u1'), dtype=d)` or `jix.where(mask, x, x)`. In
every case numpy's `x.copy()` succeeds first.

Under gdb (depth 1400, main thread) the fault is in
`PyAnyMethods::len <- extract_sequence<String> <- PyArrayDescr::names <- jix::dtype::dtype_from_numpy
<- dtype_from_numpy::{closure#5} <- map_try_fold ...`. The backtrace is 16312 frames deep, about
11-12 frames per nesting level.

The debug wheel was the only one tested. A release wheel has smaller frames, so the depth needed
is higher (not measured), but the recursion is just as unbounded.

## Root cause
`dtype_from_numpy` (jix-py/src/dtype.rs:193-206) maps every field through a closure that calls
`dtype_from_numpy(&field_dtype)` (line 203), with no depth counter and no
`Py_EnterRecursiveCall`-style guard. `dtype_to_numpy` (line 45) has the same shape. Once a
deep `Dtype` exists, the core `Dtype` `PartialEq` / `Clone` / `Drop` (jix/src/dtype.rs:891, 1075)
also recurse. These are only reachable after `dtype_from_numpy` succeeds, or from an archive,
whose protobuf decode recursion limit bounds the depth.

No realistic untrusted source carries such a dtype. A `.npy` header's descr is parsed with
`ast.literal_eval`, and the parser's nesting limit keeps it to roughly 60-100 struct levels.
Deeper dtypes need pickle or deliberate construction. This is why the severity is low rather
than medium: the process crashes, but only on a pathological, hand-built input. That matches
how the other native-stack-overflow findings were rated (K30, K72: low).

## Suggested fix
Thread a depth argument through `dtype_from_numpy` (and `dtype_to_numpy`) and return
`ValueError("Unsupported struct dtype: nested more than N levels")` past a small cap (for
example 32, the same cap the archive decoder should apply), checked before recursing. A cap at conversion time also
bounds every later recursive walk of the core `Dtype` that starts from Python. Optionally, also
enforce the same cap in `Dtype::new_struct` so the core rejects deep dtypes from every source.
