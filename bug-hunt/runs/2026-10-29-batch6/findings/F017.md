# F017: An untyped Python float or complex next to a bool/u8/i8/u16/i16 operand is cast to f32 / complex64 at dispatch with no range check: i8 + 1e300 -> inf, u8 * 1e-46 -> 0, u8 / 1e39 -> 0 (exact 2.55e-37 fits in f32), u8 / 1e-46 raises 'divide by zero'. An out-of-range Python int raises OverflowError instead

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/common/operand.rs:164 (related: jix-py/src/ops/common/operand.rs:332-361
  (`check_int_in_bounds` returns Ok for every Float / Complex value),
  jix-py/src/ops/common/operand.rs:385 and :387-389 (`Scalar::cast` to F32 / ComplexF32 converts
  the value as is), jix-py/src/ops/common/dtype_promote.rs:96 (an untyped float passes any float
  slot), jix-py/src/ops/common/dispatch.rs:198-228 (first Safe entry wins, f16 entries skipped, so
  f32 comes before f64), jix-py/src/ops/common/dispatch.rs:242, :254, :302-311 (where / stack /
  concatenate promotion picks F32 before F64, then the same `Operand::cast`),
  jix-py/src/ops/op2.rs:42-45 and :215-217 (docstrings: operands are cast to "the smallest type
  that can represent both without information loss"), jix-py/src/ops/op2.rs:207-210 (divide
  docstring: an infinite quotient of finite operands is reported as `over`))
- Reachability: Python API (every dispatched op, e.g. `+ - * /`, `jix.add/subtract/multiply/divide/maximum/...`,
  `jix.where`, `jix.stack`, `jix.concatenate`). Not reachable from Rust: core ops need both
  operands to have the same element type, so the caller casts explicitly.
- Reported by: py-ops-dispatch-promotion

## What goes wrong
If no operand is a typed float, dispatch puts an untyped Python float (or complex) into the first
float slot its partner Safe-casts to. For bool/u8/i8/u16/i16 that slot is f32 (or complex64).
Such a value is out of range when it is finite and above f32::MAX (about 3.4e38), or nonzero and
below the smallest f32 subnormal (about 1.4e-45). `Operand::cast` turns it into +-inf or 0 with no
check and no report: only Python ints are range-checked (operand.rs:164-166). The kernel then
sees an inf or 0 operand, so nothing downstream reports anything either.

The f32 result dtype is intended and documented (`i8 + 1.5 -> f32`). For `i8 + 1e300`, inf is
also the correctly rounded f32 result. Converting the scalar first loses more than the dtype
alone would, though:
- `uint8 [255, 200] / 1e39` gives [0, 0]. The exact 2.55e-37 and 2e-37 are normal f32 numbers.
- `uint8 [100] * 1e-46` gives 0. The exact 1e-44 is representable in f32 (subnormal).
- `uint8 / 1e-46` and `jix.divide(True, 1e-46)` raise FloatingPointError "divide by zero
  encountered" (`divide` defaults to 'raise'), although the divisor is nonzero. The divide
  docstring promises that an infinite quotient of finite operands is reported as `over`, which
  only warns by default.

The handling is also inconsistent: `int8 + 300` raises OverflowError ("Python integer 300 out of
bounds for i8"), while `int8 + 1e300` silently becomes inf in a dtype that jix chose, not the
user. Since #82 the precision test says the f32 default exists because "in f16 ... 1e10
overflows to inf. f32 holds both apart" (test_type_promotion.py:376-380), so overflowing an
untyped float in the chosen dtype is treated there as a defect. The change only moved the limit
to 3.4e38. NumPy 2 computes all of these in float64 and gets the exact values.

## Trigger
```python
i8 = jix.compact(np.array([1, 2], np.int8)); u8 = jix.compact(np.array([1, 2], np.uint8))
i8 + 1e300                      # float32 [inf, inf]          numpy f64 [1e300, 1e300]
i8 * 1e39                       # float32 [inf, inf]
u8 * 1e-46                      # float32 [0, 0]              numpy [1e-46, 2e-46]
jix.compact(np.array([255, 200], np.uint8)) / 1e39   # float32 [0, 0]  exact 2.55e-37, 2e-37 (normal f32)
u8 / 1e-46                      # FloatingPointError: divide by zero encountered
i8 + 1e300j                     # complex64 [1+infj, 2+infj]
jix.where(jix.compact(np.array([True, False])), u8, 1e300)   # float32 [1, inf]
jix.stack([jix.compact(np.array(1, np.uint8)), 1e300])       # float32 [1, inf]
i8 + 300                        # OverflowError (contrast)
i8 + np.float64(1e300)          # float64 [1e300, 1e300] (control: typed scalar picks f64)
```

There were no warnings at any errstate setting: `jix.errstate(all="raise")` still returns inf for
`i8 + 1e300`. The int32 / uint32 and wider ints are not affected (they take the f64 slot), and
neither are typed np.float64 scalars.

## Root cause
`Operand::cast` (operand.rs:155-172) runs `check_int_in_bounds` only for untyped scalars, and
that check returns Ok for every Float / Complex value (operand.rs:332-337). `Scalar::cast` then
converts the f64 with `cast_to::<f32>` (operand.rs:385, and :387-389 for complex). That is Rust
`as`, which saturates to +-inf and flushes tiny values to 0. In the cases above the 32-bit target
was not set by any operand. It comes from the dispatch tables listing f32 before f64, from
`is_cast_allowed` letting an untyped float into any float slot (dtype_promote.rs:96), and from the
f16 skip (dispatch.rs:199-208). jix's casts never report a status (an intentional core design), so
nothing flags the conversion.

Intended, and not part of this finding:
- The f32 / complex64 result dtype itself (test_type_promotion.py:22-24, 323-329).
- An untyped float next to the user's own f16 / f32 array keeping that array's dtype. NumPy 2
  (NEP 50) does the same, with an "overflow encountered in cast" warning.
- Precision rounding of in-range values, e.g. 0.1 -> f32.

Same root as F005 (comparisons with a Python float run in f32), which this batch confirmed
separately. F017 covers arithmetic, where / stack / concatenate, and the out-of-range values.

## Suggested fix
Add a float counterpart of `check_int_in_bounds` in `Operand::cast`. When an untyped Float /
Complex scalar is converted to F32 / ComplexF32 (or F16), raise OverflowError if a finite
component becomes inf, or a nonzero component becomes 0 (e.g. "Python float 1e300 out of range for
f32"), like Python ints. Do this at least when jix picked the 32-bit default, meaning no operand
was a typed float. Alternatively, never let an untyped float narrow below f64 unless a typed
float operand sets the precision; the f16 skip already does this one level down. Add the repro
cases next to test_python_float_default_keeps_f32_precision.
