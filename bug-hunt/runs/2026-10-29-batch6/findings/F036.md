# F036: f32/f16 base ** i32 exponent rounds the exponent to f32, so odd exponents above 2^24 become even and a negative base gives the wrong sign ((-1)^odd = +1)

- Severity: medium  Verdict: confirmed  Category: wrong-result
- Location: jix/src/ops/op2.rs:1209 (related: jix/src/ops/op2.rs:1211, jix/src/ops/op2.rs:1234, jix/src/ops/op2.rs:1237, jix-py/src/ops/op2.rs:625-627 dispatch pairs (f16, i32), (f32, i32))
- Reachability: public Rust API (`Array::pow`, `jix::scalar::Pow::pow`) and Python API (`jix.power` / `**` with an int32 array or `np.int32` exponent; int8/int16/uint8/uint16 exponents promote to the same pair)
- Reported by: concept-arith-semantics

## What goes wrong
`impl Pow for [f32, f64] x [i8, u8, i16, u16, i32]` evaluates `a.powf(b as Self)`. For an f32
base and an i32 exponent with |b| > 2^24, `b as f32` rounds to a nearby float, and every f32 that
large is even, so the parity of an odd exponent is lost. The f16 x int kernel does the same through
`a.to_f32().powf(b as f32)`. A negative base then gives a result with the wrong sign: (-1)^odd comes
out +1.0 instead of -1.0, (-2)^odd +inf instead of -inf, (-0.5)^odd +0.0 instead of -0.0. No error
flag marks the -1 case. jix's own f64 ** i32 kernel is exact (i32 -> f64 is lossless) and gives the
right sign, and numpy (which evaluates float32 ** int32 in float64) agrees with it. This is a
regression from #90 (K51 fix): the old `powi(b as i32)` kept the parity.

## Trigger
Rust: `Array::compact_ndarray(&array![-1.0f32, -0.5, -2.0])?.pow(Array::compact_ndarray(&array![16777217i32; 3])?)`
(also with an f16 base, and with the exponent -16777217).
Python: `jix.power(jix.compact(np.float32([-1, -0.5, -2])), np.int32(16777217))`, or a typed int32
exponent array; same for float16 bases.

## Root cause
op2.rs:1209 `_ => a.powf(b as Self)` and op2.rs:1234 `_ => a.powf(b as f32)` convert the integer
exponent to f32 before the power. `i32 -> f32` is exact only for |b| <= 2^24; past that the value,
and in particular its parity, changes, and powf's sign rule for a negative base depends on the
exponent being an odd integer. The #90 change replaced `powi(b as i32)` (op2.rs:1202 before
4d11918), which used the exact integer, with this; the batch3 F010 suggestion had called out that
`i32 -> f32` is exact only up to 2^24. The status classification (op2.rs:1211, 1237) uses the same
rounded exponent but stays correct, since it only tests `y < 0` and finiteness. No test covers
|b| > 2^24 for f32/f16 bases (`float_pow_errors` and the pow test at op2.rs:2005-2013 use small
exponents).

## Suggested fix
For f32 (and f16) bases, evaluate a non-trivial integer exponent in f64:
`((a as f64).powf(b as f64)) as f32` (f16: `f16::from_f64(f64::from(a).powf(b as f64))`), at least
when `b.unsigned_abs() > 1 << 24`. Or keep the f32 powf and restore the sign: if `a < 0` and `b` is
odd, `p = p.copysign(-1.0)`. Add a regression test with exponents +-(2^24 + 1) and bases -1, -2,
-0.5 for f32 and f16.
