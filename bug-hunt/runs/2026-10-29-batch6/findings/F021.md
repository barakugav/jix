# F021: asarray / cast / compact with dtype= convert numpy scalars with numpy's C cast instead of jix's Cast, so a float numpy scalar casts differently from the same value as a 0-d or 1-d array (and a complex numpy scalar casts to float instead of raising TypeError)

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/as_array.rs:65-72 (related: jix-py/src/ops/mod.rs:93-96 `jix.cast`, jix-py/src/array.rs:1661 `jix.compact`, jix-py/src/ops/mod.rs:97-185 `cast_impl`, jix/src/ops/cast.rs:62-70 and the `cast_int_float_concrete` test at cast.rs:682-697)
- Reachability: Python API (`jix.asarray(x, dtype=)`, `jix.cast(x, dtype)`, `jix.compact(x, dtype=)` with `x` a numpy scalar, `np.generic`)
- Reported by: py-core-numpy-wrap-dtype

## What goes wrong
The K96 fix (#92) made `asarray` pass every value that is not a `jix.Array` or an ndarray
through `numpy.asarray(value, dtype=dtype)`, so that numpy range-checks untyped Python ints.
numpy scalars (`np.float64(...)`, `np.float32(...)`, `np.complex128(...)`) are not ndarrays, so
they take this path too. Their cast is then numpy's C cast, not jix's lazy `Cast`, although the
docstring says the dtype cast is jix's lazy cast (see `jix.cast()`). For float -> int the two
disagree on every out-of-range, inf or NaN value. jix's `Cast` saturates and sends NaN to 0
(pinned by `cast_int_float_concrete`). numpy's cast is platform-dependent: on x86 the cvtt
instruction gives INT_MIN, other values wrap, and numpy emits a RuntimeWarning. A 0-d or 1-d
ndarray holding the same value goes through `cast_impl` and saturates silently. So the result
for one value depends on its container, and the numpy-scalar result depends on the platform.
A second consequence: `np.complex128(1+2j)` with `dtype=float64` gives 1.0 with a
ComplexWarning. The same value as a 0-d array raises the TypeError that the docstring promises
for complex -> float casts.

## Trigger
On x86_64 (`np scalar` | `0-d ndarray` | `1-d ndarray`):
- `jix.cast(np.float64(3e9), np.int32)` -> -2147483648 + RuntimeWarning | 2147483647 | [2147483647]
- `jix.cast(np.float64('nan'), np.int32)` -> -2147483648 + RuntimeWarning | 0 | [0]
- `jix.cast(np.float64(-1.5), np.uint8)` -> 255 | 0 | [0]
- `jix.cast(np.float32(300.7), np.uint8)` -> 44 | 255 | [255]
- `jix.cast(np.float64(1e10), np.uint32)` -> 1410065408 | 4294967295 | [4294967295]
- `jix.cast(np.float64('inf'), np.int64)` -> -9223372036854775808 + RuntimeWarning | 9223372036854775807
- `jix.asarray(...)` and `jix.compact(..., dtype=)` give the same results.
- `jix.cast(np.complex128(1+2j), np.float64)` -> 1.0 + ComplexWarning | TypeError
- Even wrapping the scalar first changes the result: `jix.cast(jix.asarray(np.float64(3e9)), np.int32)` -> 2147483647.

## Root cause
`as_array.rs:65-66` decides whether a value has its own dtype with
`value.is_instance_of::<Array>() || value.is_instance_of::<numpy::PyUntypedArray>()`.
`np.generic` is typed but is not a `PyUntypedArray`, so `as_array.rs:67-72` runs
`numpy.asarray(value, dtype=np_dtype)`. That casts the scalar with numpy's own rules before jix
sees it. Then `dtype_from_numpy(np_dtype) == array.dtype()` makes `cast_impl` a no-op
(ops/mod.rs:98-100). The K96 write-up (bug-hunt/runs/2026-10-27-batch5/findings/F012.md,
"Suggested fix") said to exclude `np.generic` from this path and keep `cast_impl` for typed
sources (jix arrays, numpy arrays and scalars). The fix left the scalar exclusion out. The #92
test `test_python_ints_are_range_checked_at_the_dtype` checks only `np.int64(300) -> uint8`.
For int -> int, numpy's cast and jix's `as` cast both wrap, so that test cannot see the
difference.

## Suggested fix
Treat `np.generic` as a typed source. Add `|| value.is_instance(numpy_items(py)?.generic.bind(py))?`
to `value_is_array` at as_array.rs:65-66. operand.rs:43-48 already uses the same
`numpy_items().generic` check. Typed scalars then take the `Operand` 0-d path and `cast_impl`,
the same as 0-d ndarrays. The #92 int test still
passes, because jix's int -> int cast also wraps (300 -> 44).
