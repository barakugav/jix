# F001: PyWriter::write hands write() a memoryview over Rust memory; views derived from it (b[:], memoryview(b), b.cast, np.frombuffer(b), PickleBuffer(b)) outlive the buffer - use-after-free from pure Python

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix-py/src/archive.rs:419 (related: jix-py/src/archive.rs:439, jix-py/src/archive.rs:234, jix/src/archive/block.rs:87, jix/src/array.rs:1469)
- Reachability: Python API (`jix.write_array(array, file_like)`)
- Reported by: py-core-archive-errstate, concept-python-boundary

## What goes wrong
For a Python file-like destination, `PyWriter::write` wraps the borrowed Rust slice `buf` in a
read-only memoryview (`PyMemoryView_FromMemory`, archive.rs:419-429), calls the user's `write()`, then
calls `release()` on that memoryview and discards the result (archive.rs:439). The comment at
archive.rs:433-438 claims this "ensur[es] Python can't hold a reference into `buf`", but in CPython
`release()` only invalidates that one memoryview object: a slice `b[:]`, `memoryview(b)` or
`b.cast('B')` is a new memoryview on the same managed buffer and stays valid; `np.frombuffer(b)`
keeps the raw data pointer (numpy 2.5 does not hold a buffer export, so `release()` succeeds and the
ndarray still points at `buf`); an object that does hold an export (`pickle.PickleBuffer(b)`) makes
`release()` raise BufferError, which is ignored, so even the original memoryview stays live. `buf` is
the compact array's own block data (large blocks bypass the 8 KiB BufWriter, block.rs:87), the
BufWriter's internal buffer (small writes), or the lazy encoder's reused `tmp_block_compressed`
(array.rs:1469). All of it is reused or freed after `write_array` returns, so safe Python code ends
up reading reused or freed Rust heap memory (stale bytes, garbage, SIGSEGV).

## Trigger
A seekable writer whose `write(b)` keeps a derived view, e.g.
`self.views.append(b[:])` (or `np.frombuffer(b, np.uint8)`) and returns `len(b)`, with `seek`/`tell`
implemented. Then:
`a = jix.compact(np.random.default_rng(0).random(1 << 18)); jix.write_array(a, w); del a; gc.collect()`
and read `bytes(w.views[i])` for the largest chunk. For stale-but-not-freed data, write a lazy source
`a * 1.0` and compare each kept view with a `bytes(b)` copy taken inside `write()`.

## Repro
`bug-hunt/runs/2026-10-29-batch6/repros/F001.py`, run with
`.venv/bin/python bug-hunt/runs/2026-10-29-batch6/repros/F001.py`. It asserts that every kept view
either raises ValueError or still holds the written bytes; the crashing step runs in a child process.
Output:

```
plain     : 15 writes, 0 views still live after write_array, 0 of them now hold different bytes than were written
slice     : 15 writes, 15 views still live after write_array, 14 of them now hold different bytes than were written
frombuffer: 15 writes, 15 views still live after write_array, 14 of them now hold different bytes than were written
AssertionError: views outlived the Rust buffer passed to write(): slice: 14 stale views; frombuffer: 14 stale views; child slice: exit status -11; child frombuffer: exit status -11
```

(`plain` = keeping the original memoryview, the documented-safe case: it is released correctly.) The
child processes read a 43 KB view of a freed 2 MiB compact array and die with SIGSEGV (exit -11);
with a 512 KiB array they instead read back garbage. A separate check showed `pickle.PickleBuffer(b)`
leaves even the original memoryview live (release() raised BufferError, ignored).

## Root cause
The `unsafe` block at archive.rs:419 lends Rust memory with a lifetime bounded by the call to an
arbitrary Python callable. Its soundness depends on Python code not retaining any view - a property
`release()` cannot enforce (it does not reach derived memoryviews or pointer-holding consumers such
as numpy), and the one failure `release()` can report (BufferError on live exports) is swallowed by
`let _ =` at archive.rs:439. The user-facing docstring of `write_array` (archive.rs:150-195) states
no such restriction. Mitigating context: Python's io docs say a `write()` implementation "should
only access b during the method call", and CPython's own BufferedWriter has the same hazard with
custom raw objects (bpo-15994) - hence high rather than critical: the trigger is a writer that
breaks that convention, but it is pure safe Python and reaches a use-after-free.

## Suggested fix
Hand `write()` a Python-owned object: `PyBytes::new(py, buf)` (one memcpy per write of at most one
compressed block or 8 KiB, negligible next to zstd). If zero-copy must stay, at minimum propagate a
failed `release()` as an error and document the restriction in the `write_array` docstring - but
that still leaves slices/casts/numpy views dangling, so the copy is the real fix.
