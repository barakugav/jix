# F041: BlockTable documents in-bounds block locations as an invariant that Minimal validation does not establish; BlockTable::new only debug_asserts it, so debug builds panic at load where release builds load

- Severity: low  Verdict: confirmed  Category: questionable-semantics (latent hazard)
- Location: jix/src/storage/block.rs:129 (related: jix/src/storage/block.rs:73-78 and :105 (documented invariant / `new` precondition), jix/src/archive/block.rs:384-402 (check only under Strict), jix/src/archive/block.rs:415 (calls `new` with unchecked locations), jix/src/storage/block.rs:198 and jix/src/archive/block.rs:87 (the only consumers, both checked slicing))
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file_section` / `read_from_file_mmap` with `ArchiveValidation::Minimal`) and Python API (`jix.read_array(..., validation="minimal")`). The load-time panic appears only in debug builds (including the dev Python extension). Shipped wheels are release builds.
- Reported by: concept-untrusted-archives

## What goes wrong
`BlockTable` lists "every block's location satisfies `offset + len <= block_data.len()`" as a struct
invariant (storage/block.rs:78), and `BlockTable::new` documents it as a precondition
(storage/block.rs:105). `read_content` checks the locations only under `ArchiveValidation::Strict`
(archive/block.rs:384-402) and then calls `new` with the unchecked table in Minimal mode
(archive/block.rs:415). `new` only `debug_assert!`s the invariant (storage/block.rs:129-132), so
the outcome depends on the build profile. A debug build panics at LOAD, while a release build loads
the file, serves every intact block, and panics only when the bad block is read (checked slice at
storage/block.rs:198). Panics are allowed by Minimal's "trusted input" contract, so today this is a
profile inconsistency, not a crash or UB. The real hazard is that the struct advertises an invariant
that the Minimal path does not hold. Code that trusts it (an unchecked `get_unchecked` sub-slice of
`block_data`, a precomputed span for an mmap read, a size computed from the locations) would turn a
Minimal-mode file into UB.

## Trigger
Write a `u32` array of shape `[64]` with `block_shape [16]` (4 blocks) to a `Cursor`. Set the 4th
`BlockLocation.len` to `u32::MAX`; its bytes are at `TOC + 32 + 3*12 + 8`, where the TOC is the
`[Section; 2]` whose first entry is `{offset: TOC+32, size: 48}`. Read the archive with
`ArchiveValidation::Minimal`, then read elements `0..48` (blocks 0-2, which are intact).

## Root cause
`BlockTable::new` (storage/block.rs:113-145) is written as if its callers always pass validated
locations: it documents the in-bounds condition as a precondition and guards it with a debug-only
assert. `read_content` deliberately skips that validation in Minimal mode
(archive/block.rs:384-386), so in that mode the precondition is not met. The invariant still holds
in practice only because every current consumer (`read_block` at storage/block.rs:198,
`write_content` at archive/block.rs:87) re-checks it implicitly with safe slicing. No current unsafe
code relies on it (grep of `block_data` / `block_location` in jix/src and jix-py/src).

## Suggested fix
Make the documented contract match Minimal mode. Drop the location condition from the
`BlockTable` invariants and from `new`'s doc, saying instead that locations are in bounds only after
Strict validation and every access must be checked. Remove the per-block `debug_assert!`, or keep it
only for the in-memory builders. Optionally have `read_block` / `write_content` use
`block_data.get(offset..).and_then(|s| s.get(..len))` and return `InvalidArchive`. That costs O(1)
per block and turns a Minimal-mode bad location into an `Err` in every build instead of a panic.
