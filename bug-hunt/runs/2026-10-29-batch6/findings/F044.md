# F044: Free-threaded builds: numpy(out=) validates one read of out's shape/strides but writes with a second read, and plain_from_numpy reads shape and strides separately; a concurrent `.shape =` / `.strides =` turns into an out-of-bounds write/read or a panic

- Severity: low  Verdict: plausible  Category: memory-safety (data race / TOCTOU hardening)
- Location: jix-py/src/array.rs:617 (related: jix-py/src/array.rs:218-306 check_output_array, array.rs:602, array.rs:647, array.rs:653, jix-py/src/ops/common/operand.rs:424, operand.rs:465, operand.rs:471, operand.rs:482)
- Reachability: Python API, free-threaded wheels only (3.14t / 3.15t; the module is `#[pymodule]` with pyo3 0.30's default `gil_used = false`)
- Reported by: concept-threads-send-sync

## What goes wrong
`numpy(out=)` checks `out`'s ndim, shape, data pointer and strides in `check_output_array`
(array.rs:218-306). Each check re-reads the live `PyArrayObject` fields through rust-numpy's
`shape()` / `strides()`. `numpy()` then reads the strides a second time (array.rs:617,
`np_arr.strides()[..out_shape.len()]`) and the data pointer a second time (array.rs:653). It sizes
a `&mut [u8]` from `strided_span_bytes(read_shape, strides)` (array.rs:647) and writes through it
while detached (array.rs:660). The layout that gets written was never validated as a whole.
`plain_from_numpy` has the same pattern. It reads ndim (operand.rs:424), shape (465) and strides
(471) separately, so a `Plain` can pair one layout's shape with another layout's strides. That
mismatch lasts as long as the jix array, so every later read of it over-reads. On a GIL build no
Python code runs between these reads, so the window does not exist there. On a free-threaded build
another thread can run `out.shape = ...` or `out.strides = ...` in between. Both setters are
deprecated in NumPy (2.5 / 2.4) but still accepted.

## Trigger
On 3.14t: `a = jix.compact(np.arange(8, dtype=np.int32).reshape(4, 2))`, `big = np.full(16, -1,
np.int32)`, `out = big[:8].reshape(4, 2)` (strides (8, 4)). Thread B loops
`out.shape = (2, 4); out.shape = (4, 2); out.shape = (8,)` while thread A loops `a.numpy(out=out)`.
- If (2, 4) lands between array.rs:602 and :617, jix writes read_shape (4, 2) with strides
  (16, 4). The span is 3*16 + 4 + 4 = 56 bytes, so rows 2-3 land in bytes 32..55 of the 32-byte
  view (here `big[8:14]`; for a standalone `out` that is a heap overflow).
- If `(8,)` lands in the window, `strides()[..2]` panics, giving a PanicException instead of a
  ValueError.

`jix.asarray(x)` with the same toggling of `x.shape` can build a Plain with shape (4, 2) and strides
(16, 4), which over-reads 24 bytes on every read. A shape change from (8,) to (4, 2) between
operand.rs:465 and :471 pairs shape (8,) with stride 8: span 60 bytes.

## Repro
`bug-hunt/runs/2026-10-29-batch6/repros/F044.py`, run with `.venv/bin/python <path>`. Part 1 runs on
any build and checks the facts the argument depends on. Part 2 is the race, with canary words after
the view. It asserts the correct outcome: success with correct contents, or a ValueError, and the
canary is never written or read. It can fail only on a free-threaded interpreter. None is installed
here, and building jix-py for one is outside the hunt rules, so the race itself was not run.

Output on the installed GIL build (CPython 3.13.16, NumPy 2.5.4):
```
after x.shape = (2, 4): strides (16, 4) data ptr unchanged: True dims array reallocated: True
validated shape (4, 2) + re-read strides (16, 4): span 56 bytes of a 32-byte view
numpy(out=): 3 ok, 1997 ValueError, canary intact
asarray: all reads consistent
GIL build: no Python code runs between the reads, so the race window does not exist here
PASS
```
Reading the code confirms that the GIL build has no window. After the dtype equivalence check in
`check_output_array`, nothing up to array.rs:653 calls Python or allocates a Python object. The
operand.rs:424-482 path is the same.

## Root cause
The layout is never captured once. `check_output_array` returns `()` instead of the shape/strides
it validated. `numpy()` then calls `np_arr.strides()` again, on the assumption that the
`PyArrayObject` metadata cannot change in between. That holds while the GIL is held. On 3.14t it
fails as soon as another thread holds a reference to the same ndarray. `plain_from_numpy` makes the
same assumption across its three reads.

Severity is low, not critical/high. Mutating an ndarray's metadata while another thread uses it is
a user-side data race that NumPy does not support: its thread-safety docs warn that concurrent
mutation of a shared array can crash the interpreter. NumPy cannot defend against it either. The
repro shows that `x.shape = ...` swaps in a newly allocated dims/strides array and frees the old
one, while it updates `nd`, `dimensions` and `strides` non-atomically. So any concurrent reader
(NumPy's own iterator setup included) can see a torn or freed layout, even with a single
"snapshot" read. jix's two-read structure widens that window and, worse, separates what is
validated from what is used.

## Suggested fix
Hardening only; it narrows the window but cannot close it:
- Have `check_output_array` copy `out`'s shape and strides into local `DimArray`s once and
  return them along with the data pointer. Validate that copy and use it at array.rs:617/653, so
  `[..out_shape.len()]` can no longer panic.
- In `plain_from_numpy`, copy ndim, shape and strides once (reading `nd` once and slicing both
  arrays with it) before validating.

Also document that an `out=` array, or a NumPy array wrapped by `asarray`, must not have its
shape or strides changed, or be resized, by another thread while jix uses it. On free-threaded
builds, that requirement is the real contract.
