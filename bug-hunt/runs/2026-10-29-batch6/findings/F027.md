# F027: Test comparators are weaker than documented: assert_array_matches ("bit-for-bit") and same_value / assert_same_elements ignore the sign of zero, assert_array_matches never matches NaN, bool8 compares by truthiness; f32 max/min reductions use a 0.1 tolerance and the reduction proptests never draw empty shapes

- Severity: low  Verdict: confirmed  Category: test-infra
- Location: jix/src/util/test_util.rs:899 (related: jix/src/util/test_util.rs:886-888 (doc), jix/src/util/test_util.rs:1358 (`same_value`), jix/src/util/test_util.rs:1363 (`assert_same_elements`), jix/src/scalar/bool.rs:43-48 (`bool8: PartialEq`), jix/src/ops/reduction.rs:3491-3509 (`ReductionCompare`), jix/src/ops/reduction.rs:3568 (`reduction_shape_strategy`))
- Reachability: crate-internal (test infrastructure only; no library behavior is wrong today)
- Reported by: util-test-infra

## What goes wrong
`assert_array_matches` says it compares "each element bit-for-bit" (test_util.rs:886-888), and
`ReductionCompare`'s exact arm says the same (reduction.rs:3491). But it passes `|a, b| a == b`
(test_util.rs:899), so it accepts -0.0 for +0.0, never accepts a NaN (so NaN propagation can't be
property-tested through it), and accepts any non-zero `bool8` byte for `bool8::TRUE` (bool.rs:43-48
compares truthiness). `same_value` (test_util.rs:1358), which every SIMD-body test except op2's
`div_rem_simd_bodies_all_levels` uses through `assert_same_elements`, also treats +0.0 == -0.0. So
those tests feed in the `0.0, -0.0` edge cases (test_util.rs:1328) but can't see a sign-of-zero
difference between SIMD and scalar code. They also can't see a NaN sign or payload difference
(that part is documented) or a non-canonical `bool8` output byte. The reduction tests also compare
f32 `max`/`min` with rtol 1e-3 / atol 0.1 (reduction.rs:3505-3509), although these ops return one
of the input elements, and `reduction_shape_strategy` never draws a zero-length dim or a 0-d shape.
That is how K62 (an empty float sum returned -0.0) got past the proptests. This is a gap that
could let library bugs through. I found no library bug that it hides today.

## Trigger
- `assert_array_matches(&compact([-0.0f64, 1.0]), &array![0.0, 1.0])` passes.
- `assert_array_matches(&compact([NaN, 1.0]), &array![NaN, 1.0])` panics.
- `assert_array_matches(&compact([bool8(2), bool8(0xFF)]), &array![TRUE, TRUE])` passes.
- `same_value(&-0.0f32, &0.0f32)` is true, and `assert_same_elements([0.0f32; 4], |_| -0.0, ..)` passes.
- The f32 `ReductionCompare` accepts 1.0 for `max([1.0, 1.05]) = 1.05`.
- 20000 draws of `reduction_shape_strategy` contain no zero-length dim and no 0-d shape.

shared tree, so the current kernels are correct.

## Root cause
The comparators use `PartialEq`, but the docs describe a bit comparison. IEEE `==` ignores the
sign of zero and never matches NaN, and `bool8`'s `PartialEq` deliberately compares truthiness.
`same_value` adds NaN == NaN but keeps `==` for everything else. `ReductionCompare` picks the
tolerance by dtype, not by op, so `max`/`min` share the tolerance of `sum`/`mean`. And
`reduction_shape_strategy` was copied from `shape_strategy` without its "Zero-length dims" arm.

## Suggested fix
- Make `assert_array_matches` and `same_value` compare bytes, for example through `Dtyped` bytes or
  `to_bits`. Treat any two NaNs as equal only where a NaN payload or sign is documented as free.
- Keep a separate comparator that accepts either signed zero for the ops that document "either may
  be returned" (`Maximum` / `Minimum`, cmp.rs:30 and :84).
- Compare `max`/`min` reductions exactly, with the same +-0 allowance.
- Add a zero-length and 0-d arm to `reduction_shape_strategy`.
- Fix the doc at test_util.rs:886-888 and reduction.rs:3491 if the `PartialEq` behavior is kept.
