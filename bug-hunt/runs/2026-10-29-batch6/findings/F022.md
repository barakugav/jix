# F022: File-like adapters flatten every Python exception from read()/write()/flush() into RuntimeError (KeyboardInterrupt/SystemExit/OSError lose their type), and BufWriter's Drop calls write() again after it raised

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix-py/src/archive.rs:498 (`py_to_io_err`) (related: jix-py/src/archive.rs:307, 431, 458 (call sites);
  jix/src/error.rs:42 (`Error::io` keeps only the message); jix-py/src/util.rs:74 (Io -> RuntimeError);
  jix-py/src/archive.rs:234-256 (`BufWriter` passed by value into `write_array_impl`);
  jix-py/src/archive.rs:110 vs 119/124 (missing file: FileNotFoundError vs RuntimeError))
- Reachability: Python API
- Reported by: py-core-archive-errstate, concept-python-boundary

## What goes wrong
`py_to_io_err` turns the `PyErr` raised by a user file-like's `read()`/`write()`/`seek()`/`tell()`/`flush()`
into `io::Error::other(e.to_string())`. Core wraps it as `ErrorKind::Io` with only the message, and
`IntoPyResult` maps it to `RuntimeError`, with no `__cause__`. So a `KeyboardInterrupt` (Ctrl-C) or
`SystemExit` raised inside a user's `write()`/`read()` surfaces as `RuntimeError('IO error: KeyboardInterrupt: ')`:
an `except Exception` around `write_array`/`read_array` swallows Ctrl-C and `sys.exit()`, and `except OSError`
no longer catches a disk-full / EIO error (errno lost). Separately, `write_array_impl` owns the
`BufWriter<PyWriter>`; on the error return its `Drop` runs `flush_buf`, which calls the Python `write()` again
with the still-buffered bytes after it already raised (any second error is silently dropped). The same root
cause (core `Io` errors -> RuntimeError) makes one missing file raise two exception types depending on `len=`.
No memory-safety or data-correctness impact: the operation fails in every case, only the exception type and an
extra write() call are wrong.

## Trigger
- `jix.write_array(jix.compact(np.random.default_rng(0).random(1 << 16)), w)` where `w.write` raises
  `KeyboardInterrupt()` / `SystemExit(2)` / `OSError(28, ...)` / `ValueError` on its 2nd call.
- A writer whose `flush()` raises `ValueError`.
- `jix.read_array(r)` where `r.read` raises `KeyboardInterrupt()` / `OSError(5, ...)` on its 2nd call.
- `jix.read_array("/nonexistent/missing.jix", len=100)` (also with `mmap=True`) vs without `len=`.

## Root cause
- `jix-py/src/archive.rs:497-500`: `io::Error::other(e.to_string())` discards the `PyErr` object (type,
  errno, traceback). pyo3 already supports round-tripping a `PyErr` through `io::Error`
  (`From<PyErr> for io::Error` / `From<io::Error> for PyErr` downcasts it back), but even that would not
  survive core, because `jix_core::Error::io` (`jix/src/error.rs:42-44`) keeps only `format!("IO error: {err}")`,
  and `jix-py/src/util.rs:74` maps `ErrorKind::Io` to `RuntimeError`.
- `jix-py/src/archive.rs:234-256`: `write_array_impl` takes the `BufWriter` by value and returns early via
  `into_py_result()?`; `BufWriter::drop` then calls `flush_buf` -> `PyWriter::write` again (std's Drop flushes
  unless a panic is in progress). Core's `write_to_with` takes `&mut W` and does no retry (the error kind is
  `Other`, not `Interrupted`), so the extra call is from the Drop.
- Missing file: with `len=None` jix-py calls `path.metadata()?` itself (archive.rs:110), and pyo3 maps that
  `io::Error` (NotFound) to `FileNotFoundError`; with `len=` given, the open happens in core
  (`read_from_file_section` / `read_from_file_mmap`, archive.rs:119/124) and comes back as `RuntimeError`.
- Not covered by the documented "non-arithmetic core errors surface as RuntimeError" (py-core context
  Intentional behaviors): these are Python exceptions raised by user code, not core errors, and the existing
  RuntimeError tests (`test_bad_input.py:160-167`) only cover jix's own over-reporting checks.

## Suggested fix
Stash the first `PyErr` inside `PyReader`/`PyWriter` (e.g. `Option<PyErr>` field, return a placeholder
`io::Error`), and in `read_array`/`write_array` re-raise the stashed `PyErr` when the core returns `Err`
(it takes precedence over the core message; optionally chain the core error). Keep the `BufWriter` in the
caller and on error discard its buffer (`BufWriter::into_parts`) instead of letting `Drop` flush it. For
path I/O, either open the file in jix-py for every `len=` case, or map core `ErrorKind::Io` to `OSError`
(ideally carrying the `io::ErrorKind`) so a missing file is `FileNotFoundError` regardless of `len=`.
