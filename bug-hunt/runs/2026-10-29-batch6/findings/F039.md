# F039: A Python read that raises FloatingPointError drops the warnings recorded in the same read: an 'over' RuntimeWarning that comes with an 'invalid' error is silently discarded

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix-py/src/array.rs:674 (related: jix-py/src/array.rs:1670 `jix.compact`, jix-py/src/archive.rs:253 `write_array_impl`, jix-py/src/error.rs:187 `configure_context_error_modes` drops the leftover warnings, jix/src/error.rs:341-378 `ArithmeticErrorModes::check_op_status` records the warning and then returns the Err, jix/src/codec/mod.rs:436-453 `ReadContext::take_warnings` / `check_op_status`)
- Reachability: Python API
- Reported by: concept-arith-semantics

## What goes wrong
The core records every Warn-mode kind as a warning in the `ReadContext` and then returns the
first Error-mode kind as `Err`, so after a failed read the warnings are still in the context. The
Rust API keeps them: a caller that owns the context can still call `ctx.take_warnings()` after the
`Err`. The Python read paths (`Array.numpy()`, `jix.compact()`, `jix.write_array()`) return the
`Err` with `?` before they call `take_warnings()`. The context goes back to the array's cache with
the warning still in it, and the next read's `configure_context_error_modes` drops it. So a user
who set `over='warn'` gets no overflow warning when the same read also raises for `invalid` (or
`divide`), even though the overflow happened. The errstate docs say that 'warn' "emits a
RuntimeWarning". numpy emits the overflow warning and then raises.

## Trigger
```python
with jix.errstate(over="warn", invalid="raise", divide="ignore"):
    (jix.compact(np.array([1e308, 0.0])) / jix.compact(np.array([0.5, 0.0]))).numpy()
```
Element 0 overflows (1e308 / 0.5 = inf) and element 1 is invalid (0 / 0). `jix.compact(x)` and
`jix.write_array(x, io.BytesIO())` on the same lazy `x` do the same thing. So does a multi-block
input (`block_shape=[8]`, overflow in the first block, 0/0 in the last).

## Root cause
`jix/src/error.rs:357-367` pushes a warning for each Warn kind and keeps the first Error kind,
returning it at line 377. The warnings are left in `ReadContext::warnings`
(`jix/src/codec/mod.rs:450-452`). In the bindings:
- `numpy()`: `self.arr.to_ndarray_buf(...).into_py_result()?;` (array.rs:674) returns before
  `context_guard.take_warnings()` (675).
- `compact()`: `.compact_with(...).into_py_result()?;` (array.rs:1670) returns before
  `context.take_warnings()` (1671).
- `write_array_impl`: `.write_to_with(...).into_py_result()?;` (archive.rs:253) returns before
  `context.take_warnings()` (256).
The `ContextGuard` drop puts the context back in the cache (array.rs:1782-1788), and the next
`read_ctx()` calls `configure_context_error_modes`, which does `drop(context.take_warnings())`
(jix-py/src/error.rs:187).

## Suggested fix
At each of the three sites, keep the read's `Result`, call `take_warnings()` whether it succeeded
or not, emit the warnings once the GIL is held, and only then propagate the error. For example,
return `(result, warnings)` from the detached closure and run
`emit_warnings(py, warnings)?; result?`. (numpy also stops at the first raising kind in the order
divide, over, under, invalid, so a warning for a kind after the raising one is not emitted. Matching
that exactly would mean `check_op_status` stops collecting warnings after the first Error kind.
That part is optional.)
