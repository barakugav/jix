# F005: Comparing a bool/u8/i8/u16/i16 operand with a Python float (or complex) runs in float32 and returns wrong booleans

- Severity: medium  Verdict: confirmed  Category: wrong-result (questionable-semantics)
- Location: jix-py/src/ops/common/dtype_promote.rs:96 (related: jix-py/src/ops/common/dispatch.rs:198-228
  (first Safe-castable entry wins, f16 entries skipped); jix-py/src/ops/cmp.rs:57, 100, 142, 182,
  222, 262 (the six comparison tables list f32 before f64); jix-py/src/ops/cmp.rs:599-607 (isclose
  table: f16, f32, f64, Complex<f32>, Complex<f64>); jix-py/src/ops/common/operand.rs:164-168
  (only Python ints are range-checked, the float is rounded to f32 silently);
  jix-py/src/array.rs:1156-1176 (the dunder comparison operators call the same functions))
- Reachability: Python API (`jix.equal/not_equal/less/less_equal/greater/greater_equal/isclose`
  and `==`, `!=`, `<`, `<=`, `>`, `>=` on `jix.Array`). Not reachable from Rust: core comparisons
  need both operands to have the same element type, so the caller casts explicitly.
- Reported by: py-ops-dispatch-promotion

## What goes wrong
An untyped Python float has precision `None`, and `CastKind::Safe` lets it into ANY float slot
(dtype_promote.rs:96). A bool/uint8/int8/uint16/int16 operand Safe-casts into f32, the f16 entries
are skipped when no operand is f16, and the comparison tables list f32 before f64, so the comparison
runs in f32: the Python float is rounded to f32 first. Whenever that rounding lands on or crosses an
array value, the boolean result is wrong, and since the output dtype is bool the precision loss is
invisible (unlike `i8 + 1.5 -> float32`, whose dtype shows it). A Python complex goes to
Complex<f32> in equal/not_equal the same way. Python bool scalars (typed P1) and typed numpy
int8/int16 scalars take the same path. NumPy 2.5.4 and Python's own int-vs-float comparison give
the exact answer for all of these. This is the K26 class (u64 vs i64 compared in f64, fixed in
c009869 with exact kernels even though the u64+i64 -> f64 arithmetic promotion is intentional);
and the f16 skip in #82 was introduced precisely so that `equal(i8, 1.0001)` stops being True
(test_type_promotion.py:376-380), which only moved the cliff from f16 to f32.

Not affected: int32/uint32 and wider ints (they go to the f64 slot), typed float64 scalars,
array-array comparisons, and f16/f32 arrays against a Python float (numpy 2 also compares those in
the array's float type).

## Trigger
```python
a = jix.compact(np.array([0, 1, 3], np.int16))
jix.equal(a, 1.00000001)        # [F, T, F]   exact [F, F, F]
jix.less(a, 3 * 0.1 * 10)       # [T, T, F]   exact [T, T, T]   (3.0000000000000004)
jix.less(a, 1e-50)              # [F, F, F]   exact [T, F, F]
jix.greater(a, -1e-50)          # [F, T, T]   exact [T, T, T]
img = jix.compact(np.array([30000, 65535], np.uint16))
jix.greater(img, 65534.999)     # [F, F]      exact [F, T]
jix.equal(img, 30000.0001)      # [T, F]      exact [F, F]
jix.equal(a, complex(1.00000001, 0))  # [F, T, F]  exact [F, F, F]
jix.equal(True, 1.00000001)     # True        exact False
jix.equal(np.int8(1), 1.00000001)     # True  exact False
jix.isclose(jix.compact(np.array([1], np.uint8)), 1.00000001, rtol=0, atol=0)  # [T]  exact [F]
```

## Root cause
`define_op2!` builds one same-type descriptor per table entry with `CastKind::Safe` on both inputs,
and `dispatch_args` (dispatch.rs:198-228) returns the first entry both operands Safe-cast to. For
(int16 array, Python float): the integer slots reject the float (Float > Int rank), the f16 slot is
skipped (dispatch.rs:199-208, no f16 input), and the f32 slot accepts both - int16 because
`P2.higher() = P4 <= P4` (dtype_promote.rs:116-123), the float because an untyped precision passes
any float slot (dtype_promote.rs:96). `Operand::cast` (operand.rs:164-168) then rounds the f64 value
to f32 with no check (only ints are range-checked). The same-type f32 slot is a fine result dtype
for arithmetic, but for a comparison it silently changes the question being asked.

## Suggested fix
For comparisons (and isclose), do not let an untyped Python float/complex narrow below 64 bits:
e.g. treat an untyped float as P8 when dispatching the comparison tables (so int16 vs float picks
f64, where every <=32-bit int is exact), or keep the f32 kernel but compare the array against the
f64 scalar exactly (compare against the f32 floor/ceil of the scalar, as for the K26 exact
kernels). Keep f16/f32 arrays vs a Python float as they are (numpy 2 compares those in the array's
type). Add the repro's cases to test_type_promotion.py next to
test_python_float_default_keeps_f32_precision.
