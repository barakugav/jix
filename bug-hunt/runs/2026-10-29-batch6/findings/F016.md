# F016: Vec/slice MapMultiple scratch calls Vec::set_len over uninitialized items and then assigns through IndexMut, building a &mut [T] over uninitialized memory (latent; strict Miri flags it)

- Severity: low  Verdict: confirmed  Category: memory-safety
- Location: jix/src/util/arr_sequence.rs:453-462 (Vec impl) (related: jix/src/util/arr_sequence.rs:577-586 (the `&[Array<S>]` impl, same body); jix/src/ops/map.rs:376 (the only caller, `MapMultiplePipeline::read_bulk`); jix/src/array.rs:1399-1407 and jix/src/util/buf_pool.rs:116-118 (the same "slice over uninitialized bytes" pattern on crate-internal `u8` buffers))
- Reachability: public Rust API (`jix::ops::map_multiple` with a `Vec<Array<S>>` or a `&[Array<S>]` sequence, read through any materialization)
- Reported by: util-nd-arr-sequence

## What goes wrong
`read_bulk_as_iter` for the `Vec<Array<S>>` and `&[Array<S>]` sequences reuses a `Vec<S::Item>`
scratch. Each call does `clear()`, `reserve(narrays * M)`, then `set_len(narrays * M)` before any
element is written (the `clippy::uninit_vec` lint that warns about this is silenced with `#[allow]`).
That breaks `Vec::set_len`'s documented safety precondition ("the elements at old_len..new_len must be
initialized"), which is library UB. The slots are then filled with `tmp_buf[item_idx * narrays + arr] =
item`. Each of those stores goes through `<Vec<T> as DerefMut>::deref_mut`, which creates a
`&mut [S::Item]` that also covers every slot not yet written. The Rust Reference treats a reference to an
invalid (uninitialized) value as UB, though the opsem rules for that are not final. Miri's strict mode
(`-Zmiri-recursive-validation`) reports exactly this. Today the results are correct and no build
miscompiles it, because:
(1) `S::Item: Dtyped` is `Copy` and has no `Drop`, so the assignment never drops or reads the old slot;
(2) each `inner.read_bulk::<M>` returns all `M` items, so all `narrays * M` slots are written before the
shared slices are handed out;
(3) on a panic mid-fill, only a `Vec<Copy>` is dropped, and that reads nothing.
So this is a latent hazard: an unsafe precondition that is violated, but nothing depends on it yet.

## Trigger
```rust
let a = Array::plain_ndarray(array![1i32, 2, 3]).unwrap();
let b = Array::plain_ndarray(array![10i32, 20, 30]).unwrap();
let m = jix::ops::map_multiple(vec![a, b], |xs: &[i32]| xs[0] + xs[1]);
let ctx = m.read_ctx();
let mut dst = [0u8; 12];
m.to_ndarray_slice(&[0..3], &mut dst, &ctx).unwrap();   // -> [11, 22, 33]
```
The same happens with `map_multiple(&arrays[..], ...)`. A fixed-size `[Array<S>; N]` or tuple sequence
does not have the problem, because it builds its items with `array_from_fn_inline`.

## Root cause
arr_sequence.rs:453-456 (and 577-580) call `Vec::set_len` to make uninitialized capacity indexable, so
that the fill loop at 460-463 (584-587) can scatter items with `tmp_buf[i] = item`. The SAFETY comment
at 448-450 covers only the exclusivity of the `UnsafeCell` borrow, not the initialization requirement
of `set_len`. The `#[allow(clippy::uninit_vec)]` at 453 / 577 silences the lint that flags exactly this
pattern.

## Suggested fix
Fill the slots through `tmp_buf.spare_capacity_mut()` (a `&mut [MaybeUninit<S::Item>]`) with
`slots[item_idx * narrays + arr].write(item)`, and call `set_len(narrays * M)` only after the loop, then
drop the `#[allow]`. Since every slot is written exactly once, the `set_len` is then sound. Another
option is to keep the scratch as `Vec<MaybeUninit<S::Item>>` and convert the fully written prefix to
`&[S::Item]` with a pointer cast. The crate-internal `u8` buffers (array.rs:1401 `AlignedBytes::set_len`
+ `as_mut_slice`, and `PoolBuf::as_mut_slice`, buf_pool.rs:116-118, over a fresh allocation) use the
same "slice over uninitialized bytes" pattern by design (pool buffers are documented as uninitialized,
buf_pool.rs:37). Fixing those means changing the crate-wide `StridedBuf` / `PoolBuf` model, so it is a
separate, larger change.
