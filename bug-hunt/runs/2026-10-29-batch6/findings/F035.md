# F035: jix-py rejects padding-free numpy struct dtypes whose field names are not in offset order (e.g. numpy multi-field views x[['b','a']]) with a misleading "padding between fields" error

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/dtype.rs:190-209 (related: jix/src/dtype.rs:655-683 `check_fields` and its message at 668-673, jix/src/dtype.rs:480-482 `from_fields` sorts by offset, jix/src/dtype.rs:528-530 `new_struct` doc "fields must be given in offset order")
- Reachability: Python API (`jix.asarray`, `jix.compact`, any op / `dtype=` argument that converts a numpy dtype)
- Reported by: concept-dtype-layout

## What goes wrong
`dtype_from_numpy` collects struct fields in numpy's `names` order and hands them unchanged to
`Dtype::new_struct`, which (as documented) requires the fields in offset order. numpy allows any
`names` order, and creates such dtypes itself: the multi-field view `x[['b','a']]` of
`[('a','<i4'),('b','<f4')]` has `names=['b','a'], offsets=[4,0], itemsize=8`. That layout has no
padding at all (fields tile [0, 8) back to back) and is a valid packed (or, with `align=True`,
aligned) C layout - `Dtype::from_fields` with the same field list accepts it because it sorts by
offset first. jix-py instead raises `ValueError: ... field `b` is at offset 4, expected 0: padding
between fields is not supported, add an explicit padding field instead`. The rejection is clean
(no memory-safety impact), but the message blames padding the dtype does not have and tells the
user to add a padding field, which cannot fix it; the real constraint (field order) is never named.

## Trigger
```python
x = np.zeros(3, dtype=[('a', '<i4'), ('b', '<f4')])
jix.asarray(x[['b', 'a']])
# also: np.dtype({'names': ['b', 'a'], 'formats': ['<f4', '<i4'], 'offsets': [4, 0]})  (with or without align=True)
```

## Root cause
jix-py/src/dtype.rs:190-206 builds the field list in `names` order and :208 calls
`Dtype::new_struct`, whose contract (jix/src/dtype.rs:528-530) is offset order. `check_fields`
(jix/src/dtype.rs:655-683) walks the fields in the given order and reports any offset mismatch as
"padding between fields", so an out-of-order but gap-free list gets the padding message. The
intentional-behavior note "only C-aligned or C-packed layouts" covers layouts with gaps / overlaps,
not a gap-free layout whose names are merely listed out of order.

## Suggested fix
Either (a) sort the collected fields by offset in `dtype_from_numpy` before `new_struct` (the jix
dtype then lists the fields in offset order, so `.numpy()` returns names `['a','b']`; numpy treats
that as a different dtype, `x[['b','a']].dtype != x.dtype`, so the dtype round trip in
`_assert_same`-style checks would not hold for this input - the bytes do), or (b) keep rejecting
but detect the case (offsets not increasing) and say so, e.g. "struct dtype fields must be listed
in offset order; field `b` at offset 4 comes before offset 0". In either case `check_fields` should
distinguish "offset < expected" (out of order / overlap) from "offset > expected" (gap) so the Rust
`new_struct` error is accurate too.
