# F010: #[derive(Dtyped)] panics on a raw-identifier field (`r#type`); the recorded field name would also be "r#type", not "type"

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix-macros/src/lib.rs:147-148 (related: jix-macros/src/lib.rs:156-157, 165-166 (same pattern for the offset / end-offset consts); jix-macros/src/lib.rs:202 (`stringify!(#field_names)` records the field name); jix/src/dtype.rs:891-905 (`Dtype::eq` compares field names, which gates `into_typed` / `dtype_sub_field`))
- Reachability: public Rust API (`jix::dtype::Dtyped` derive, a compile-time failure; no runtime effect)
- Reported by: types-dtyped-derive, concept-dtype-layout

## What goes wrong
The derive names its per-field helper consts with `format!("field_{i}_{}_dtype", f_name)` and then
`syn::Ident::new(&var_name.to_uppercase(), ..)`. `Display` for a raw `syn::Ident` keeps the `r#`
prefix, so a field `r#type` gives the string "FIELD_0_R#TYPE_DTYPE". `Ident::new` panics on that, and
the derive fails with an unhelpful "proc-macro derive panicked" error. A valid `#[repr(C)]` struct with a
field named after a keyword (`type`, `match`, `ref`, ... - common when mirroring a C struct or NumPy
record) therefore cannot derive `Dtyped`, and the only workaround is to rename the field.
A second defect sits behind the panic. The field name is recorded with `stringify!(#field_names)`
(lib.rs:202), and that keeps the prefix (`stringify!(r#type)` == "r#type", checked with rustc). So with
only the panic fixed, the derived dtype would have a field "r#type". That dtype would never equal an
archive's or numpy's struct dtype with a field "type" (field names are part of `Dtype::eq`), so
`into_typed::<S>()` would fail on such arrays, and `dtype_sub_field("type")` would not find the field.
There is no memory-safety impact: offsets and sizes are unaffected, and the failure is at compile time.

## Trigger
```rust
#[derive(Copy, Clone, jix::dtype::Dtyped)]
#[repr(C)]
struct S { r#type: u32, x: u32 }
```
Any raw identifier triggers it, including a non-keyword one such as `r#len`.

## Repro

["type", "x"] and equals `Dtype::from_fields([("type", 0, u32), ("x", 4, u32)])`. While the bug exists

Latent second defect: `rustc --edition 2024` on `println!("{:?}", stringify!(r#type))` prints
`"r#type"`.

## Root cause
lib.rs:147, 156 and 165 build identifiers by formatting a `syn::Ident` through `Display`, which keeps
the `r#` raw prefix, and then pass the result to `Ident::new`, which panics on an invalid identifier.
lib.rs:202 turns the ident into the runtime field name with `stringify!`, which also keeps the prefix.
Neither place calls `syn::ext::IdentExt::unraw()`.

## Suggested fix
Use `f_name.unraw()` (from `syn::ext::IdentExt`) both when building the helper-const names and for the
recorded field name: emit `#field_name_strs` as string literals of `ident.unraw().to_string()`
instead of `stringify!(#field_names)`. Alternatively, name the helper consts by index only
(`FIELD_0_DTYPE`), because the index already makes them unique. Add a derive test with an `r#type` field.
