# F003: Plain::read_data (and jix-py numpy(out=)) take a `&[u8]` / `&mut [u8]` over the whole strided span, gap bytes included; element-disjoint views whose spans interleave then alias, which is UB from safe Rust and from Python (Miri)

- Severity: high  Verdict: confirmed  Category: memory-safety
- Location: jix/src/storage/plain.rs:468 (related: jix/src/storage/plain.rs:458, jix/src/storage/buf.rs:254-255, jix/src/storage/buf.rs:74, jix/src/storage/buf.rs:97, jix/src/storage/elementwise_pipeline.rs:283, jix/src/storage/elementwise_pipeline.rs:751, jix/src/array.rs:866, jix-py/src/array.rs:651, jix-py/src/array.rs:665, jix/src/util/mod.rs:109)
- Reachability: public Rust API (safe: `Array::plain_ndarray_ref` / `plain_ndarray_view` + `to_ndarray_slice`) and Python API (`jix.asarray(...)` + `numpy(out=)`)
- Reported by: concept-aliasing-lifetimes, concept-python-boundary

## What goes wrong
`Plain::read_data` turns its base pointer into
`std::slice::from_raw_parts(src_ptr, src_span)`, with
`src_span = strided_span_bytes(out_shape, self.strides, itemsize)` (plain.rs:458-468). For a
non-contiguous view, that slice covers every byte from the first to the last element, gap bytes
included, and those bytes are not elements of the view. The slice then lives on: as the pull
`StridedBuf` (an `OperandData::Input` of the element-wise pipeline for the whole run,
elementwise_pipeline.rs:751), or as `PtrNoalias::from_slice(src)`, a protected argument of
`NdCopier::copy` (buf.rs:254). ndarray lets safe code hold element-disjoint views whose spans
interleave (`multi_slice_mut`, `split_at` on an inner axis, ...). So the shared slice jix creates
can cover bytes that a live `&mut [u8]` exclusively borrows: the `buf` argument of
`to_ndarray_slice` (array.rs:866), which jix then writes through `PtrMutNoalias`. That is an
aliasing violation (UB) on the Rust abstract machine, reachable without any `unsafe` and without
breaking any documented contract. jix-py adds the mirror image: `numpy(out=)` builds
`&mut [u8]` over the whole span of `out` (jix-py/src/array.rs:647-659), and that span covers the
elements of an asarray'd input that shares no element with `out`. The values are always correct
(the bytes actually touched are disjoint), so tests never notice it, and no miscompile is known
with today's codegen. But Miri reports UB, and the `noalias` contracts that `PtrNoalias` /
`PtrMutNoalias` exist to assert are false.

## Trigger
Safe Rust (u8, 3x4, values 0..12):
```rust
let mut big = Array2::<u8>::from_shape_fn((3, 4), |(r, c)| (r * 4 + c) as u8);
let (mut row, col) = big.multi_slice_mut((s![1, 1..4], s![.., 0])); // {5,6,7} vs {0,4,8}
let a = Array::plain_ndarray_ref(&col).unwrap();   // span [0, 9) contains bytes 5..8
let out = row.as_slice_mut().unwrap();             // &mut [u8] over bytes 5..8
a.to_ndarray_slice(&[0..3], out, &ReadContext::default()).unwrap();
// also: a.map(|x: u8| x + 1).to_ndarray_slice(...)   (element-wise pipeline)
```
Python: `x = np.arange(12, dtype=np.uint8).reshape(3, 4)`, then
`jix.asarray(x[:, 0]).numpy(out=x[:, 1])`, `jix.asarray(x[:, 0]).numpy(out=x[1, 1:4])` or
`(jix.asarray(x[:, 0]) * np.uint8(2)).numpy(out=x[:, 1])`. In each, `np.shares_memory(src, out)`
is False, so the numpy() docstring ("out must not overlap memory the array itself reads from",
jix-py/src/array.rs:502-508) permits it. Same root cause, not run (no Miri for Python / threads):
two GIL-released reads into `big[:, 0]` and `big[:, 1]` from two threads (two live overlapping
`&mut [u8]`), or a read of `jix.asarray(x[:, 0])` while another thread writes `x[:, 1]` (the same
thing in safe Rust: `to_ndarray()` of a Plain over `col` while another thread writes through
`row`, since ArrayViewMut is Send).

## Root cause
jix models every buffer it reads or writes as a byte slice that spans the whole strided region:
`StridedBufData::Slice(&[u8])` / `SliceMut(&mut [u8])` (buf.rs:51-56), built with
`strided_span_bytes` (util/mod.rs:109) in `Plain::read_data` (plain.rs:468),
`StridedBuf::from_raw_parts(_mut)` (buf.rs:74, 97) and jix-py `numpy` (array.rs:651). Every kernel
then gets `PtrNoalias` / `PtrMutNoalias` over those spans. A Rust reference asserts things about
ALL bytes it covers (no mutation for `&`, exclusivity for `&mut`). For a strided view that it
borrows from someone else, jix only has rights to the element bytes, never to the gaps. The Plain
safety contracts (plain.rs:108-115, 407-413) and the safe `plain_ndarray_ref` / `plain_ndarray_view`
promise only element-wise readability, and ndarray hands out the gap bytes to other safe views. So
nothing upstream makes the span claim true. KNOWN K31 (intended) covers `out` overlapping memory
the array READS. It does not cover element-disjoint views, nor the safe Rust API, which the
storage-core context doc assumed could only reach this via unsafe constructors.

## Suggested fix
Do not materialize references over memory jix does not own. Give `StridedBuf` a raw-pointer variant
for borrowed external memory, e.g. `Raw { ptr: NonNull<u8>, span: usize, PhantomData<&'a [u8]> }`
(and a `RawMut` one), use it in `Plain::read_data`, `StridedBuf::from_raw_parts(_mut)` and the
jix-py numpy(out=) path (which should then skip its `&mut [u8]` over the whole span). Kernels that
consume such buffers should get plain raw pointers, or noalias wrappers only over spans jix owns
(pool / staging buffers), instead of `PtrNoalias::from_slice` over the span. Contiguous
views (span == elements) could keep the slice fast path. If noalias over external strided inputs
must stay for performance, the alternative is to stage non-contiguous Plain inputs and external
`out`s through pool buffers. Either way, also make the numpy() docstring say what the contract is
in terms of `np.may_share_memory`, if anything is still required.
