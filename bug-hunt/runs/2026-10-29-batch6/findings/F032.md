# F032: The Safety sections of Plain::new, plain_ndarray_ptr and compact_nd_ptr leave out two things the implementation needs: no writes to the memory during a read or while a lent pull view is alive, and a strided span (gap bytes included) that nobody writes or uniquely borrows. Calls that meet the documented contract are UB (Miri)

- Severity: low  Verdict: confirmed  Category: unsound-api
- Location: jix/src/storage/plain.rs:108-115 (`Plain::new` Safety) (related: jix/src/storage/plain.rs:407-413 (`Array::plain_ndarray_ptr` Safety), jix/src/array.rs:299-305 (`Array::compact_nd_ptr` Safety), jix/src/storage/plain.rs:458-471 (span `&[u8]` built and lent as the pull view), jix/src/array.rs:991-993 (`to_ndarray_buf` returns that view directly for `plain_read` storages), jix/src/util/mod.rs:531-533 (`SendSyncPtr` makes Plain Send + Sync), jix/src/storage/buf.rs:59-64 (`StridedBuf::from_raw_parts` states the rule, K59), jix/src/archive/array.rs:185-191 (the mmap constructor states the matching rule), jix-py/src/ops/common/operand.rs:485 (jix-py relies on `Plain::new` for numpy buffers))
- Reachability: public Rust API (the unsafe constructors, used as their docs allow)
- Reported by: concept-aliasing-lifetimes, concept-threads-send-sync

## What goes wrong
The three public unsafe constructors require only this: the pointer is valid and non-dangling
for the array's lifetime, every element at `strides` is readable, and (for `plain_ndarray_ptr` and
`compact_nd_ptr`) the elements are valid dtype values. None of them says the memory must not be
written. But `Plain::read_data` builds `slice::from_raw_parts(src_ptr, src_span)`, a `&[u8]` over
the whole strided span, gaps included (plain.rs:458-468). In pull mode it lends that slice to
the caller as a `StridedBuf<'a>` that lives as long as the borrow of the array (plain.rs:471).
`Array::to_ndarray_buf(.., None)` returns it unchanged for `plain_read` storages
(array.rs:991-993). jix therefore needs three things the docs do not state:
1. No write to the region while a lent view is alive, even from the same thread. The owner
   writing through its own pointer, which is still valid, invalidates the view.
2. No concurrent write during a read. Plain is Send + Sync through `SendSyncPtr`, so another
   thread writing the buffer races with jix's non-atomic reads.
3. The gap bytes between elements must be dereferenceable, and nobody may write or uniquely
   borrow them during a read. This is the unsafe-API face of F003.

`StridedBuf::from_raw_parts` got the matching sentence in the K59 fix ("The memory must not be
mutated during 'a"). The mmap constructor states its rule too (archive/array.rs:185-191). The
Plain constructors are the remaining gap.

## Trigger
(1), single thread, no race, every documented requirement met:
```rust
let mut data = vec![1u8, 2, 3];
let p = data.as_mut_ptr();
let a = unsafe { Array::<Plain<&(), Ty<u8>>>::plain_ndarray_ptr(
    p.cast_const(), [3u64], &[1], u8::DTYPE, ArrayParams::default()) }.unwrap();
let ctx = ReadContext::default();
let view = a.to_ndarray_buf(&[0..3], &ctx, None).unwrap(); // lent &[u8] over data
unsafe { p.write(9) };                                    // owner updates its buffer
let first = unsafe { view.data_ptr().read() };            // UB: view's tag was invalidated
```
(2): `data: Vec<AtomicU32>` wrapped with `plain_ndarray_ptr(data.as_ptr().cast(), [4], &[4], u32::DTYPE, ..)`.
Then `std::thread::scope(|s| { s.spawn(|| data[1].store(100, Relaxed)); arr.to_ndarray::<Ix1>() })`.
(3): `plain_ndarray_ptr` over bytes 0, 4 and 8 of a buffer while byte 5 is written by other code
or held through a live `&mut` during `to_ndarray_slice`. The safe-code version is F003.

## Root cause
plain.rs:108-115 and 407-413 copy only the "valid for reads" part of the requirements of
`slice::from_raw_parts`. They drop "must not be mutated for the duration of 'a". Here `'a` is
the read itself and also any pull view it lends. They also describe the readable region as
"reachable via data and strides for all index combinations", which leaves out the gap bytes that
`strided_span_bytes` covers. array.rs:299-305 (`compact_nd_ptr`) has the same omission, but only
for the duration of the call: the Plain it builds is dropped before it returns, so no view
escapes. jix-py's `plain_from_numpy` (operand.rs:485) calls `Plain::new` on numpy buffers that
other Python threads can write while jix reads with the GIL released. The context doc lists that
as undocumented NumPy-like behavior, not a separate bug.

## Suggested fix
Add to the Safety sections of `Plain::new` and `plain_ndarray_ptr`: "every byte from the first
to the last element (the strided span, gaps included) lies in one allocation, and none of it is
written, or borrowed through a `&mut`, while the array is being read or while a `StridedBuf`
returned by a pull read of it, or of a lazy view over it, is alive." Add the read-only version to
`compact_nd_ptr`, limited to the duration of the call. A note on `to_ndarray_buf` that a pull
view may borrow the storage's own memory would help too. If F003 is fixed by not building `&[u8]`
over spans, the gap-byte clause can shrink to the element bytes. The no-write-during-a-lent-view
clause still applies as long as pull returns a slice of the caller's memory.
