# F034: Span / size products over an empty region do not stop at the zero extent, so a valid empty region with large strides (or, on 32-bit, large extents) overflows: debug builds panic

- Severity: low  Verdict: confirmed  Category: panic
- Location: jix/src/util/mod.rs:111 (related: jix/src/storage/plain.rs:458, jix/src/ops/shape_ops/concatenate.rs:290, jix/src/storage/buf.rs:73, jix/src/storage/buf.rs:96, jix/src/storage/buf.rs:386, jix/src/storage/elementwise_pipeline.rs:901, jix/src/error.rs:276, jix-py/src/ops/common/operand.rs:471)
- Reachability: Python API (debug extension); public Rust API through the unsafe-but-contract-respecting `Array::plain_ndarray_ptr` and `StridedBuf::from_raw_parts(_mut)`; plus a 32-bit-only safe path (`broadcast` + `to_ndarray_buf`)
- Reported by: concept-degenerate-shapes

## What goes wrong
`strided_span_bytes` goes through the dims in order and adds `stride * (len - 1)` for each one.
It returns 0 only when it reaches a zero-length dim. In an empty region the other dims are never
stepped, so their strides can be anything, including values whose sum overflows `usize`. The
overflow happens before the zero dim is seen, and debug builds panic with "attempt to add with
overflow". `materialize_out_buf` (buf.rs:386) has the same ordering problem: it takes the `usize`
product of the extents. On 32-bit, `check_region_size` accepts an empty region whose non-zero
extents multiply past `usize::MAX`, because its byte size is 0, and that product then overflows.
Release builds wrap. Every overflowing value ends up multiplied by 0 or discarded by the early
`return 0`, so release builds return the correct empty result. This was checked on x86_64 and
i686 release. The impact is a debug-only panic: the dev Python extension and `cargo test` panic,
and shipped wheels behave correctly.

## Trigger
- Python (debug extension):
  `e = as_strided(np.zeros(1), shape=(3,3,0), strides=(2**62, 2**62, 8)); y = np.ones((3,3,2));
  jix.concatenate([y, e, y], 2).numpy()`. NumPy accepts any strides for a zero-element array.
  jix-py keeps the strides of dims longer than 1 unchanged (operand.rs:471). Concatenate reads the
  middle member with the empty sub-index `[0..3, 0..3, 0..0]`, which reaches
  `Plain::read_data -> strided_span_bytes`.
- Rust: `Array::plain_ndarray_ptr(ptr, [3,3,0], &[usize::MAX/2, usize::MAX/2, 4], u32::DTYPE, ..)`.
  The safety contract ("valid to read for all index combinations") holds trivially here. A
  `to_ndarray_buf(&[0..3, 0..3, 0..0], ..)` of this array panics, and so does `concatenate` with
  it. `StridedBuf::from_raw_parts_mut(NonNull::dangling(), &[3,3,0], &[usize::MAX/2,
  usize::MAX/2, 8], 8)` also panics, and its documented contract is met for an empty region.
- i686 only, safe API: `Array::compact_ndarray(&array![[[7u8]]]).broadcast(&[1<<20, 1<<20, 0])
  .to_ndarray_buf(&[0..1<<20, 0..1<<20, 0..0], &ctx, None)` gives "attempt to multiply with
  overflow" in `materialize_out_buf` (buf.rs:386).

## Root cause
`strided_span_bytes` (util/mod.rs:105-114) checks `len == 0` one dim at a time, inside the same
loop that accumulates offsets. The emptiness of the whole region is decided only after the
earlier dims have already been multiplied and added. `materialize_out_buf` (buf.rs:386) and
`pick_output_layout` (elementwise_pipeline.rs:901, the `small` test) both take a plain
`.product::<usize>()` of the extents. On 64-bit this cannot overflow, because every array
shape's zero-padded product fits in u64. On 32-bit, `check_region_size` (error.rs:276) bounds
only the true product, which is 0 for an empty region. `try_shape_product` returns that product,
not the zero-padded one, so the `usize` product of the non-zero extents is unchecked.

## Suggested fix
In `strided_span_bytes`, return 0 up front when `shape.contains(&0)`, and only then accumulate
offsets. Alternatively, keep the loop and use `wrapping_*` arithmetic, or check emptiness first.
In `materialize_out_buf` and `pick_output_layout`, short-circuit on a zero extent (for example
`if out_shape.contains(&0) { 0 } else { product }`), or compute the product with `checked_mul`
that stops at the first 0.
