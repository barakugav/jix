# F012: 32-bit: empty read regions skip the region-size bound, so reads of an empty region with huge other extents overflow usize in the stride / size math (debug panic; a gap in the K81 fix)

- Severity: low  Verdict: confirmed  Category: overflow
- Location: jix/src/error.rs:274-288 `check_region_size` (related: jix/src/error.rs:242-271
  `check_get_buffer_size`; jix/src/array.rs:873-874 `to_ndarray_slice` -> jix/src/util/mod.rs:141
  `default_strides_from_iter`; jix/src/storage/compact.rs:295 `Compact::read_data`;
  jix/src/storage/buf.rs:386-389 `materialize_out_buf` (pull), reached from
  jix/src/ops/shape_ops/broadcast.rs:140; jix/src/array.rs:775-783 the K81 fix in `to_ndarray_sub`,
  which bounds the zeros-as-1 product and so disagrees with the other read paths)
- Reachability: public Rust API (`Array::to_ndarray_slice`, `Array::to_ndarray_buf`, pull and push),
  32-bit targets only. Python is unaffected in practice: the shipped i686 / armv7 wheels are release
  builds, where the products wrap with no effect (see below).
- Reported by: types-dims-errors

## What goes wrong
`check_region_size` (32-bit only) and `check_get_buffer_size` bound a read region by its TRUE
byte product `prod(extents) * itemsize`. For an empty region that product is 0, so the checks
accept any extents for the other dims, e.g. `[0..0, 0..2^20, 0..2^20]`, whose non-zero extents
multiply to 2^40 > usize::MAX on 32-bit. The code after the checks multiplies the full region shape
in `usize` without a check: `default_strides` in `to_ndarray_slice`, the `nitems` product in
`Compact::read_data` (computed before its `nitems == 0` early return), and the size product and
`strides_for_layout_order` in pull-mode `materialize_out_buf` (used by Broadcast's empty-read path,
and so by any op over a Broadcast). On i686 debug each of these panics with 'attempt to multiply
with overflow'. In release they wrap, but every wrapped size product contains the zero factor and
the wrapped strides belong to an empty region that is never accessed: the repro passes in an i686
release build, and I found no memory or value consequence. The K81 fix bounded the zeros-as-1
product only inside `to_ndarray_sub`, so on i686 `to_ndarray_sub` returns a clean
`Err(InvalidShapeOperation)` for the same region where `to_ndarray_slice` / `to_ndarray_buf` panic
(debug) or return `Ok` (release). On 64-bit there is no issue: `check_shape_overflow`
(error.rs:186) proves the zeros-as-1 byte product of the array shape fits in u64 = usize, and a
region's `max(extent, 1)` never exceeds the matching array dim's `max(dim, 1)`.

## Trigger
i686 debug build, `BIG = 1 << 20`:
```rust
// to_ndarray_slice (push into a packed 0-byte buffer)
let b = Array::compact_ndarray(&array![[[7u8]]])?.broadcast(&[1, BIG, BIG]);
b.to_ndarray_slice(&[0..0, 0..BIG, 0..BIG], &mut [], &b.read_ctx());
// Compact pull
let a = Array::compact_fn((BIG, BIG, 0u64), |_| 0u8)?;
a.to_ndarray_buf(&[0..BIG, 0..BIG, 0..0], &a.read_ctx(), None);
// Broadcast pull (also through an element-wise op: `.map(|x: u8| x.wrapping_add(1))`)
let b = Array::compact_ndarray(&array![[[7u8]]])?.broadcast(&[BIG, BIG, 1]);
b.to_ndarray_buf(&[0..BIG, 0..BIG, 0..0], &b.read_ctx(), None);
```
The product order matters for `Iterator::product`: a leading zero extent short-circuits to 0 without
overflow, so the zero extent has to come after the huge ones for the product sites
(`default_strides` multiplies from the last dim backwards, so there the zero must come first).

## Root cause
`check_region_size` (error.rs:276-280) and `check_get_buffer_size` (error.rs:247-251) bound
`prod(extents) * itemsize`, which `try_shape_product` computes exactly (its zeros-as-1 guard
only checks against u64 overflow, util/mod.rs:215-225). On 32-bit the downstream code needs more:
every intermediate product of the region extents (strides, `product::<usize>()` before an
emptiness check) must fit in `usize`, which only the zeros-as-1 product bounds. K16's fix put the
bound in the shared helper but measured the wrong quantity for empty regions; K81's fix corrected
the quantity only locally in `to_ndarray_sub` (array.rs:775-783). The prior F016 write-up's claim
that `to_ndarray_slice` / `to_ndarray_buf` "return early for empty regions" does not hold: the
stride / size products run before any emptiness check.

## Suggested fix
Make `check_region_size` (32-bit) bound the zeros-as-1 product, as `to_ndarray_sub` now does:
`index.iter().map(|r| (r.end - r.start).max(1)).chain([itemsize]).try_shape_product()` must be
`<= isize::MAX`. Then `to_ndarray_sub` can call the shared helper again. `to_ndarray_slice`
calls `default_strides` before `check_out_buf` runs, so either call `check_region_size` there
first or compute its strides after the check. Alternatively, return early for empty regions
before any stride / size math in `to_ndarray_slice`, `Compact::read_data` and
`materialize_out_buf`, but the helper fix covers every path at once.
