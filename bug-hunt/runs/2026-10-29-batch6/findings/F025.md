# F025: jix.Array binary dunders never return NotImplemented: a foreign operand's reflected op (even with `__array_ufunc__ = None`) is never tried, `a == None` raises ValueError, unsupported operand types raise ValueError instead of TypeError

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/array.rs:880 (`__add__`, and every binary dunder through `__rrshift__` at
  array.rs:1149 and `__rpow__` at array.rs:1014) (related: jix-py/src/array.rs:1156-1183
  comparison dunders `__lt__`..`__ne__`; jix-py/src/ops/common/operand.rs:85 `np.asarray(other)`
  fallback in `Operand::from_any_with_params`; jix-py/src/dtype.rs:174 object/str/void dtype ->
  ValueError; jix-py/src/array.rs:1518 `__array_ufunc__ = None`; KNOWN K37, the numpy-on-the-left direction)
- Reachability: Python API
- Reported by: py-core-array-surface-util

## What goes wrong
Every binary and comparison dunder of `jix.Array` takes `other: &Bound<PyAny>`, so pyo3's
argument extraction never fails and pyo3 never returns `NotImplemented`. The dunder forwards
straight to the op, and `Operand::from_any_with_params` (operand.rs:85) runs `np.asarray(other)`
on anything that is not a jix array, Python scalar or ndarray. For None, a str, a `Fraction`, or
any user object that gives an object or unicode dtype, and `dtype_from_numpy` raises
`ValueError: Unsupported dtype: dtype('O')` (dtype.rs:174). Python therefore never tries the
right operand's reflected method, never uses the identity fallback for `==` / `!=`, and never
raises its standard `TypeError: unsupported operand type(s)`. jix relies on this protocol itself:
it sets `__array_ufunc__ = None` (array.rs:1518) so that numpy defers to jix's reflected ops
(the K37 fix). jix does not honor the same NEP 13 opt-out when it is the left operand. numpy,
torch and JAX all defer here, so no third-party type with reflected operators (units, uncertainty
or symbolic types, a user wrapper) can appear on the right of a jix array. The error is also the
wrong exception class (ValueError rather than TypeError), so `except TypeError` duck-typing code
does not catch it.

## Trigger
```python
import fractions, numpy as np, jix
class Foo:
    __array_ufunc__ = None
    def __radd__(self, o): return "Foo.__radd__"
a = jix.compact(np.array([1, 2, 3], np.int32))
a + Foo()                       # ValueError: Unsupported dtype: dtype('O')
np.array([1, 2, 3]) + Foo()     # 'Foo.__radd__'
a == None                       # ValueError (numpy: array([False, False, False]))
a == "x"                        # ValueError: Unsupported dtype: dtype('<U1')
a * fractions.Fraction(1, 2)    # ValueError (expected TypeError)
a + object()                    # ValueError (expected TypeError)
```
This affects all binary arithmetic, bitwise and comparison dunders, both the forward and the
reflected variants (for example `Foo() + a` with no `Foo.__add__` also raises ValueError rather
than TypeError).

## Root cause
The dunders at jix-py/src/array.rs:880-1183 have signature
`fn __op__(slf, other: &Bound<PyAny>) -> PyResult<Self>`. With this signature they can only
return a jix Array or raise, never `NotImplemented`. The operand conversion they share
(operand.rs:29-85) treats "anything else" as an array-like via `np.asarray`, and the unsupported
dtype that results is reported as a ValueError (dtype.rs:174). Nothing checks the right operand
for `__array_ufunc__ = None`, which is the NEP 13 opt-out that jix itself uses at array.rs:1518.
No test, docstring or context doc marks this behavior as intended.

## Suggested fix
Have the dunders, but not the named methods or `jix.add` and friends, return `NotImplemented`
when the other operand is foreign:
(1) `type(other).__array_ufunc__ is None` and `other` is not a jix Array, or
(2) `Operand::from_any` fails because the converted numpy dtype is object, str, bytes or void
(and `other` was not itself an ndarray).
In pyo3, return a small enum, `Array | NotImplemented`, with `IntoPyObject` (or
`PyResult<Py<PyAny>>` returning `py.NotImplemented()`), so the stubs stay typed. Lists and
numeric sequences must keep working. Separately, consider raising TypeError rather than ValueError
for object/str operands in the function forms.
