# F024: errstate restores a construction-time snapshot of OS-thread-local modes, so asyncio tasks whose with-blocks exit out of order leave the thread in a non-default mode for good

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/error.rs:113-124 (related: jix-py/src/error.rs:19-21, jix-py/src/error.rs:138-140, jix-py/src/error.rs:173-174, jix-py/src/array.rs:174)
- Reachability: Python API
- Reported by: py-core-archive-errstate

## What goes wrong
The error modes live in a `thread_local!` `Cell` (error.rs:19-21). `ErrState::new` snapshots the
current modes and installs the new ones (error.rs:113-124), and `__exit__` writes that snapshot
back (error.rs:138-140). That restores correctly only when blocks exit in strict LIFO order.
asyncio tasks share one OS thread, so two tasks that each `await` inside a `with jix.errstate(...)`
and exit first-in-first-out leave the thread in the FIRST task's mode for good, after every block
has exited. Since `divide`/`invalid` default to `raise`, the leaked mode is typically `ignore` or
`warn`, and a later `x // 0` anywhere on the thread silently returns 0. While both blocks are
active, a task that asked for `divide='raise'` also reads under the other task's `ignore` and gets
no error. numpy 2.x keeps errstate in a contextvar (each asyncio task has its own context), and the
same program leaves numpy at its default. The docstring promises that the context manager "restores
the previous modes on exit", and the op docs say errors are reported "as numpy". Neither says that
an out-of-order exit can leave the thread in another mode for good.

Scope notes:
- The generator variant from the report (a generator suspended inside `with errstate(divide='warn')`
  and closed after an enclosing `with errstate(divide='ignore')` exits) leaks `ignore` in numpy
  2.5.4 too. A contextvar token reset restores the value from before its own `set`, so that
  variant is not specific to jix, and the suggested fix would not change it.
- The reused-object variant (`es = errstate(...); with es: ...; with es: ...` applies nothing the
  second time) follows from the documented "applies on call, not on `__enter__`" behavior
  (context/py-core.md "Intentional behaviors"; error.rs:43-46 docstring), so this finding does not
  cover it.
- "Per thread" is documented and intended. What is not documented is the asyncio consequence: modes
  are shared across tasks and can stay set after every block has exited.

## Trigger
```python
async def worker(mode, entered, leave):
    with jix.errstate(divide=mode):
        entered.set(); await leave.wait()
# Task A enters with 'ignore', then task B enters with 'warn'; A exits first, then B.
# Afterwards: jix.geterr()['divide'] == 'ignore'; (x // jix.compact(np.zeros(2, np.int64))).numpy() -> [0 0]
```

## Root cause
error.rs:113-124 captures `prev` when the object is built, and error.rs:138-140 sets `MODES` to it
on exit. The code assumes nothing else changed `MODES` on this OS thread between the two points,
which holds only for LIFO nesting. asyncio tasks (and anything else that interleaves on one thread)
break that assumption. `configure_context_error_modes` (error.rs:173-174, called from
array.rs:174) then applies the leaked thread-wide modes to every later read.

## Suggested fix
Store the modes in a Python `contextvars.ContextVar`, as numpy 2.x does. Set it in `__enter__` and
keep the token, then `reset(token)` in `__exit__`. For the plain function-call form, call
`set` without a reset. Read the var in `configure_context_error_modes`, which already runs with the
thread attached, before the read starts. Each asyncio task then gets its own modes. Optionally,
reject entering the same errstate object twice, as numpy does.
