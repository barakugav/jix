# F002: #[derive(Dtyped)] output is not hygienic: names in the user's scope (size_of, align_of, assert!, BASE_OFFSET, ...) change the computed DTYPE and disable its checks, so code with no `unsafe` gets a wrong DTYPE (heap OOB read, uninitialized padding read, wrong field offsets)

- Severity: medium  Verdict: confirmed  Category: unsound-api
- Location: jix-macros/src/lib.rs:183-241 (related: lib.rs:184, 187, 192, 197, 200, 210, 220, 227-239, 262-263, 282; jix/src/storage/plain.rs:458-468, 473, 520-524; jix/src/util/nd_copy.rs:31-38; jix/src/ops/sub_dtype.rs:139)
- Reachability: public Rust API (`#[derive(jix::dtype::Dtyped)]`, a safe derive that emits an `unsafe impl`)
- Reported by: types-dtyped-derive

## What goes wrong
The derive emits `unsafe impl Dtyped` (lib.rs:282). The only justification for that impl is the
layout computed inside `const DTYPE = { ... }` and the asserts that follow it (lib.rs:183-241). All of
that code resolves names at the call site:
- `size_of` / `align_of` are unqualified (lib.rs:192, 197, 210, 227, 228, 230).
- `assert!`, `stringify!` and `concat!` are unqualified (lib.rs:227-239), and so is `std::borrow::Cow` (lib.rs:200).
- The block declares items (`BASE_OFFSET`, `FIELD_{i}_{NAME}_DTYPE/_OFFSET/_END_OFFSET`, `FIELDS`;
  lib.rs:184-204) in the same block where it re-emits the user's field types, so those names inside
  a field type resolve to the derive's own items.

A user item with one of these names changes the layout the derive computes. The asserts that should
catch a mismatch use the same shadowed names, so they still pass. The result is a DTYPE that
disagrees with the real Rust layout, in code that never wrote `unsafe`. Consumers trust DTYPE without
re-checking it:
- `Plain::read_data` sizes `from_raw_parts` with `DTYPE.itemsize` (plain.rs:458-468), while the
  strides come from the real `size_of::<T>()` (plain.rs:520-524).
- `NdCopier` reads whole elements as integers, picking the integer width from DTYPE (nd_copy.rs:31-38).
- `SubDtype` trusts the field offsets (sub_dtype.rs:139).

The results are heap out-of-bounds reads, reads of uninitialized padding (the K3 bug class, which #88
was meant to rule out at compile time), and silently wrong field views.

## Trigger
All three use only safe code:
1. A user `const fn size_of<T>() -> usize { 16 }` in the module, then
   `#[derive(Dtyped)] #[repr(C)] struct S { a: u8 }`. DTYPE.itemsize is 16, but `size_of::<S>()` is 1.
   Reading `Array::plain_ndarray_ref(&view).to_ndarray_slice(&[1..2], ..)` copies 16 bytes starting at
   element 1. With a 2-element allocation, that is a heap OOB read.
2. A user `macro_rules! assert { ($($t:tt)*) => { () }; }` in the module, then
   `#[derive(Dtyped)] #[repr(C)] struct Q { a: u8, b: u32 }`. This struct has 3 padding bytes. The
   derive accepts it with DTYPE `{a@0 u8, b@4 u32}`, itemsize 8, align 4, where it should fail with a
   compile error.
3. The most natural trigger: an ordinary user const named `BASE_OFFSET` used in a field type.
   - `const BASE_OFFSET: u16 = 3; #[repr(C)] struct P { a: [u8; 4 - BASE_OFFSET as usize], b: u32 }`.
     The real layout is a@0 `[u8; 1]`, 3 bytes of padding, b@4. The derive resolves `BASE_OFFSET` to
     its own `const BASE_OFFSET = 0`, so it lays out a@0 `[u8; 4]`, b@4 `u32`. Every size, alignment
     and padding assert passes (8 == 8, 4 == 4, 4+4 == 8). DTYPE claims the 3 padding bytes as field
     data, and the padded struct is accepted.
   - `const BASE_OFFSET: u16 = 4; struct UsesBaseOffset { a: [u8; BASE_OFFSET as usize + 1], b: [u8; 9 - BASE_OFFSET as usize] }`.
     The real layout is a@0 `[u8;5]`, b@5 `[u8;5]`. DTYPE says a@0 `[u8;1]`, b@1 `[u8;9]`, so field
     views are silently wrong.

Severity: medium, not the hunter's high. This is a real soundness hole: a safe derive becomes UB
because of a user's own name collision. But every trigger needs a user item whose name matches one of
the derive's internal names. Even then, the shadowed value has to slip past the size assert by
coincidence: for `BASE_OFFSET`, the re-resolved field sizes must still sum to the real `size_of`. That
is the same class as K50, K70 and K25 (safe user code makes jix's unsafe code UB), which were triaged
medium.

## Root cause
lib.rs:183-241 runs its layout computation with call-site hygiene, so it is not computing the layout
of the struct the user wrote. It assumes several things that the user's scope can change:
- that `size_of` / `align_of` / `assert!` mean the `core` ones;
- that the field types mean the same inside the `const DTYPE` block as at the struct definition. They
  do not, because the block declares its own `BASE_OFFSET`, `FIELDS` and `FIELD_*` items around them.

The asserts at lib.rs:227-239 run through the same shadowable names, so they cannot detect the
mismatch. Nothing at runtime re-checks `T::DTYPE` against `size_of::<T>()`, `align_of::<T>()` or
`offset_of!`. `new_struct_borrowed_unchecked` (jix/src/dtype.rs:634) is unchecked and does not run
`check_fields` / the no-padding validation. The `#[repr(transparent)]` arm (lib.rs:262-263) has the
same unqualified names, but it is not exploitable: the compiler already guarantees layout equality for
transparent structs.

## Suggested fix
- In the generated code, use absolute paths only: `::core::mem::size_of`, `::core::mem::align_of`,
  `::core::assert!`, `::core::stringify!`, `::core::concat!`, and `::core::borrow::Cow` or
  `#jix_crate::...` re-exports. This is what the bytemuck and zerocopy derives do.
- Do not declare named items in a scope that also contains user field types. Either compute
  everything inside a `const fn` / expression that has no local item declarations, or give the
  generated items `Span::mixed_site()` hygiene. Mixed-site hygiene keeps them invisible to user tokens
  and keeps user tokens resolving to user items.
- Also check each field offset against `::core::mem::offset_of!(Self, field)` and each field's
  `size_of` against its `DTYPE.itemsize()`. A cheaper alternative: call a checked const constructor
  that runs the `check_fields` / no-padding validation instead of `new_struct_borrowed_unchecked`.
  Either way, a wrong computation becomes a compile error instead of UB.
