# F023: read_array(file_like) and Array::read_from_reader leave the stream at an arbitrary position, so arrays written back-to-back with write_array(f) / write_to(&mut w) cannot be read back with successive reads

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/archive/block.rs:354-356 (core reads block_data, then the EARLIER blocks_loc section, and never seeks to the archive end) and jix-py/src/archive.rs:142 (an internal 8 KiB `BufReader` over the Python reader reads ahead and is dropped) (related: jix/src/archive/array.rs:145-161 `read_from_reader`, jix/src/archive/block.rs:244-248 writer `finalize` restores the stream to the archive end, jix/src/archive/common.rs:255-262 `seek_relative_to_base`)
- Reachability: Python API (`jix.read_array(f)` on any file-like) and public Rust API (`Array::read_from_reader(&mut r, ..)`)
- Reported by: py-core-archive-errstate

## What goes wrong
The write side is built for sequential streams: `finalize` patches the TOC and then explicitly
seeks back to the end of the block data (block.rs:244-248), so `write_array(a, f);
write_array(b, f)` packs archives back-to-back and leaves `f` at the end of each one. The read
side does not mirror this, in two independent ways:
1. Core: `read_content` reads the block_data section (the last one) and then the blocks_loc
   section (which sits before it), and returns there. After `Array::read_from_reader(&mut r, ..)`
   the reader is at the START of the block data, inside the archive (position 89 for an archive
   that ends at 115).
2. Python: `read_array` wraps the Python reader in `BufReader::new` (archive.rs:142) BELOW the
   core's `Take`, so the BufReader reads ahead up to 8 KiB past whatever the core consumed, even
   when the exact `len=` is passed, and is dropped without seeking the Python object back.
After one read, the stream position is therefore arbitrary: past the next archive's start for
small arrays, or inside the first archive for large ones. A second `read_array(f)` fails with a
clean error (`IO error: failed to fill whole buffer` or `invalid header magic`). `offset=` is
rejected for file-likes, and no API reports the length of an archive that was just read, so a
caller must record every archive's start offset at write time. This also affects the "custom
container format" use that the `write_to` docs advertise, where other data follows an archive
in a stream. `np.save`/`np.load` (and `pickle`) on a packed stream read back sequentially.

## Trigger
Python: `buf = io.BytesIO(); write_array(jix.compact(np.arange(10, dtype=np.int32)), buf);
write_array(jix.compact(np.arange(5.0)), buf); buf.seek(0); read_array(buf); read_array(buf)`.
Rust: `a.write_to(&mut c)?; b.write_to(&mut c)?; c.set_position(0);
Array::read_from_reader(&mut c, None, ..)?; Array::read_from_reader(&mut c, None, ..)`.

## Root cause
The reader treats the stream position after a read as don't-care. `read_content`
(block.rs:347-357) seeks with `seek_relative_to_base` to each section in the order block_data,
blocks_loc, and nothing afterwards moves to `base + end of the last section`.
`read_from_reader` (array.rs:145-161) consumes the reader by value and adds no final seek. In
jix-py the `BufReader` is placed under the `Take` (archive.rs:142-143), so even a final seek
inside the core would only fix the BufReader's logical position. The Python object's position
is left where the last buffer fill ended, unless the BufReader is seeked with a real `seek`
(which discards the buffer and seeks the inner reader) before it is dropped. Nothing documents
the position after a read. The docs show only the record-offsets pattern
(jix-py/src/archive.rs:64-70, jix/src/archive/array.rs:307-325).

## Suggested fix
After a successful read, seek the reader to `base + max(section.offset + section.size)` (the end
of block_data for writer-produced files) with a real `seek`, not `seek_relative`. Do this in
the core (`read_content` or `ArrayBlockTableStorageBase::read_from`). In jix-py, also make sure
the Python object ends there: either seek the `BufReader` with `SeekFrom::Start` before dropping
it, or drop it and call `f.seek(end)` on the Python object. Otherwise, document that the stream
position after `read_array` / `read_from_reader` is unspecified, and add a test either way.
Applying the fix also to the error path (leaving `f` at the archive start) would be a bonus.
