# F009: #[derive(Dtyped)] accepts a bare #[repr(packed)] (= repr(Rust, packed), field order unspecified) and assumes declaration order; when rustc reorders (e.g. -Zrandomize-layout) the DTYPE field offsets are wrong and dtype_sub_field reads the wrong bytes

- Severity: low  Verdict: confirmed  Category: wrong-result (latent: relies on unspecified layout)
- Location: jix-macros/src/lib.rs:127 (related: jix-macros/src/lib.rs:189-197 offset computation, jix-macros/src/lib.rs:227-239 the only layout asserts, jix-macros/src/lib.rs:29 docs that advertise bare `#[repr(packed)]`, jix-macros/tests/derive_external.rs:76-91 the test that has to allow `clippy::repr_packed_without_abi`)
- Reachability: public Rust API (any downstream crate deriving `Dtyped` on a `#[repr(packed)]` struct, then `dtype_sub_field` / `dtype_sub_field_dyn`, or writing a `.jix` that another program reads by field)
- Reported by: types-dtyped-derive

## What goes wrong
The derive maps the sorted repr string `"packed"` to the same branch as `"C,packed"`
(lib.rs:127) and then computes each field offset as the running sum of `size_of` in declaration
order (lib.rs:189-197). It never compares the result with `offset_of!`. A bare `#[repr(packed)]`
is the Rust representation with packing. The Rust reference says `packed` on its own does not
guarantee field order, and clippy's `repr_packed_without_abi` lint warns about exactly this. The
derive's asserts (lib.rs:227-239) check only total size, alignment and "no padding". A packed
struct always has alignment 1 and a size equal to the sum of its field sizes, whatever the field
order, so a reordering passes every check. `P::DTYPE` then describes a different layout than the
real one, and `SubDtype` copies bytes from the wrong offsets. Every `Dtyped` type accepts every bit
pattern, and the claimed fields still tile the element, so the result is silently wrong values,
not UB. The whole element still round-trips correctly. Only field access, and any consumer that
interprets the stored DTYPE (Python, another build), is wrong.

The hazard is latent with today's stable rustc (1.97). The layout code sorts packed fields by
(packed alignment = 1, niche size, niche offset), and `Dtyped` fields have no niches, so the stable
sort keeps declaration order. Reordering happens with `-Zrandomize-layout`, the nightly flag
designed to catch code that relies on unspecified layouts. A future change to rustc's
field-ordering heuristics could cause it too.

## Trigger
```rust
#[allow(clippy::repr_packed_without_abi)]
#[derive(Copy, Clone, Dtyped)]
#[repr(packed)]
struct P { a: u8, b: u32, c: u16, d: u64 }

let arr = Array::compact_ndarray(&array![P{a:1,b:2,c:3,d:4}, P{a:5,b:6,c:7,d:8}])?;
arr.view().dtype_sub_field::<u32>("b").to_ndarray::<Ix1>()  // expect [2, 6]
```
The user crate is compiled with `-Zrandomize-layout` (nightly), and jix is built normally. The hunter reports that a
RUSTFLAGS-wide `-Zrandomize-layout` cannot build jix itself, because jix's own
`size_of::<Dtype>() <= 32` const assert fails. This verifier did not re-run that.

## Root cause
jix-macros/src/lib.rs:127 treats `repr(packed)` like `repr(C, packed)`. That is right for the C
representation, which fixes declaration order, but not for the Rust representation, whose field
order is unspecified. The offsets at lib.rs:189-197 are derived, not measured, and nothing ties
them to the real layout. The size/alignment/padding asserts at lib.rs:227-239 cannot detect a
permutation of the fields of a packed struct. The `Dtyped` safety contract (D3: field offsets
equal the Rust layout) therefore rests on unspecified compiler behavior.

## Suggested fix
Either reject bare `packed` in the derive and require `#[repr(C, packed)]` (this also removes the
clippy allow in derive_external.rs), or emit `assert!(offset_of!(Self, <field>) ==
<FIELD_OFFSET> as usize)` for every named field inside the generated `const DTYPE` block.
`offset_of!` is const and stable since 1.77 (MSRV is 1.89) and works on packed fields. Better
still, take the offsets from `offset_of!` directly. The extra asserts also harden the `repr(C)`
path.
