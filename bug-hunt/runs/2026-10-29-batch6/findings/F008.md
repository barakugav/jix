# F008: Deep type-erased op chains (every Python op result) recurse once per op level on read and on drop, so `x = x + 1` in a loop overflows the native stack (SIGSEGV kills the interpreter)

- Severity: medium  Verdict: confirmed  Category: resource
- Location: jix/src/storage/core_trait.rs:139 (default `read_as_elementwise_pipeline` does a pull `read_data`) (related: jix/src/storage/any.rs:57 (`ArrayStorageAny::read_data` forwards to the inner op, no `read_as_elementwise_pipeline` override); jix/src/storage/any.rs:22 (nested `Arc<dyn AnyInner>`, recursive drop); jix/src/ops/into_type.rs:101 (IntoType forwards the pipeline request to the Any node); jix/src/ops/op2.rs:115-131 (Op2 builds child pipelines before its own `to_buf`); jix-py/src/ops/common/dispatch.rs:13,75,102-103 (every op input is `IntoType<ArrayStorageAny, Ty<T>>`); jix-py/src/ops/op2.rs:17 (every result is `.into_any()`))
- Reachability: Python API (any loop of ops followed by a read, or by dropping the result); public Rust API via `Array::into_any` / `into_typed`
- Reported by: concept-composition

## What goes wrong
jix-py type-erases every op input and output, so a lazy chain built in a Python loop is a linked list
`Any(Add(IntoType(Any(Add(IntoType(Any(...)), Scalar))), Scalar))`. Reading it recurses once per op level
on the native stack: `Op2::read_data` -> `read_as_elementwise_pipeline` -> `IntoType` -> the default
`read_as_elementwise_pipeline` of `ArrayStorageAny` -> pull `read_data` -> next `Op2::read_data` -> ... down to
the leaf, before any level runs its `to_buf`. Dropping the chain also recurses, once per nested
`Arc<dyn AnyInner>`. Nothing limits the depth, so an ordinary NumPy-style loop (`for _ in range(n): x = x * a + b`,
then one read at the end) overflows the stack. In Python that is a SIGSEGV that kills the whole interpreter.
Python's recursion limit does not apply, so there is no `RecursionError`. In Rust it is a "has overflowed its
stack" abort. It is not memory corruption: the guard page catches the overflow, and only O(1) region buffers
are live at a time. The only cost is stack.

## Trigger
Python: `x = jix.asarray(np.array([1.0, 2.0])); for _ in range(5000): x = x + 1.0`, then `x.numpy()` (read), or
the same loop with 100000 iterations, then `del x` (drop).
Rust: `x = (x.into_typed::<f64>()? + ones).into_any()` repeated 10,000 times, then
`x.into_typed::<f64>()?.to_ndarray()` on an 8 MiB thread. Dropping a 100,000-deep chain fails the same way.

Measured thresholds on an 8 MiB stack (Linux main-thread default, `ulimit -s 8192`):
- Python, installed debug extension: read works at n=1800 and segfaults at n=2000 (about 4.3 KB per level).
  Drop works at n=30000 and segfaults at n=50000.
- Rust release: read works at n=6500 and aborts at n=7000 (about 1.2 KB per level). A release wheel crashes
  at about the same depth. On a 1 MiB Windows main thread or a 512 KiB macOS secondary thread it crashes
  at a few hundred levels (estimated from the per-level cost).
- With `ulimit -s 65536` the same Python read (n=5000) and drop (n=100000) succeed, which confirms the crash
  is stack exhaustion.

## Root cause
Evaluation is purely recursive over the storage tree. That is fine for a statically typed pipeline, whose
depth is bounded by the source code. But `ArrayStorageAny` (any.rs:47-90) lets a runtime loop build a tree
of unbounded depth. It does not override `read_as_elementwise_pipeline`, so each type-erased level falls
back to the default (core_trait.rs:129-141). That default does a pull `read_data` of the inner
`dyn ArrayStorage` (any.rs:57). That call is the next `Op2::read_data` (op2.rs:103-117), which first builds
its children's pipelines (op2.rs:126-131) and so recurses again. The drop glue of `ArrayStorageAny`
(`Arc<dyn AnyInner>`, any.rs:22) is recursive in the same way. jix-py's dispatch (dispatch.rs:13, 75,
102-103) and result wrapping (`.into_any()`, op2.rs:17) guarantee that every Python op adds one such level.
Neither the Python layer nor the core has a depth guard or an automatic materialization.

## Suggested fix
Bound the depth of type-erased chains. Track a `depth` in `AnyMeta` (1 + max of the children's depths),
and have jix-py (or `into_any`) materialize the operand with `compact()` once it passes a threshold, for
example 256. Alternatively, raise a clean `RecursionError`/`MemoryError` instead of crashing. For the drop,
give `ArrayStorageAny` a `Drop` that unlinks nested `Arc`s iteratively (take the inner `Arc` when the
refcount is 1 and push it on a heap `Vec`). A depth bound also fixes the drop. As a stopgap, document that long
op loops should call `x = x.compact()` periodically.
