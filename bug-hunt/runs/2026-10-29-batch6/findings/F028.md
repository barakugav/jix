# F028: Python assert_array_matches checks neither dtype nor 0-d shape, and its sub-range draw still skips the K21 cases (start == len, zero-length dims) although K21 is fixed

- Severity: low  Verdict: confirmed  Category: test-coverage
- Location: jix-py/python/tests/tests_util.py:299 (related: jix-py/python/tests/tests_util.py:278, jix-py/python/tests/tests_util.py:303, jix/src/util/test_util.rs:873, jix/src/util/test_util.rs:970, jix/src/util/test_util.rs:1010, jix-py/python/tests/test_cmp.py:194)
- Reachability: test infrastructure only (no library code involved)
- Reported by: util-test-infra

## What goes wrong
`assert_array_matches` says it mirrors the Rust helper, but it compares with
`np.testing.assert_allclose(a, b, rtol, atol)` and the default `strict=False`. As a result:
(1) dtype is never checked. The Rust helper does `into_typed::<T>().unwrap()`, which fails on a
dtype mismatch. K75 (two-bound `clamp` of bool returned uint8) passed `test_clamp_both[bool_]`
for this reason. (2) A 0-d operand on either side is broadcast, not shape-checked. A reduction
that returns `(1,)` or `(1,1)` instead of `()`, or `()` instead of `(n,)` with equal elements,
passes. (3) The sub-range check draws one range (Rust draws 16). `sub_range_strategy` takes
`start` from `[0, size-1]`, so a slice that starts at the dim length (`a[n:n]`, `a[n:]`) is never
drawn. Rust draws both ends from `0..=len`. The check is also skipped entirely when any dim is
zero-length. Both exclusions are exactly the K21 cases. The comment at :303 justifying them
("jix rejects slice(0, 0) on zero-length dimensions") has been stale since K21 was fixed in
c009869. Only the fixed list in test_getitem.py:70-75 covers those cases, and only on plain
compact arrays, not on lazy op results.

Not a defect: NaN == NaN at matching positions (`equal_nan=True`) still requires the NaN
positions to match. -0.0 == +0.0 behaves the same as the Rust `==` helper.

I found no library bug hiding behind these gaps today. I ran the whole Python suite with
`assert_array_matches` patched to also require equal shape and dtype (3 hypothesis examples per
test, via a `-p` plugin outside the tree). It gave 8 failures and 2205 passes. All 8 failures
are reduction tests that intentionally build the reference in float64 or float32 and compare
with a tolerance: test_sum[float32/complex64/bool], test_mean[float32/complex64],
test_product/var/std_concrete. There was no shape mismatch. This matches the hunter's sweep of
46 ops x 14 dtypes.

## Root cause
- tests_util.py:299 uses `np.testing.assert_allclose` without `strict=True`. numpy's
  `assert_array_compare` accepts `x.shape == () or y.shape == ()` as compatible and never
  compares dtypes.
- tests_util.py:278 draws `start` from `st.integers(0, size - 1)`. The Rust version at
  test_util.rs:876 draws both ends from `0..=len`.
- tests_util.py:303-304 skips the sub-range check for any zero-length dim. The skip was a
  workaround for K21, which is now fixed.

## Suggested fix
Pass `strict=True` to `assert_allclose`, or check `actual.shape` and `actual.dtype` explicitly
before the value comparison. In the 8 reduction tests that use a wider-precision reference, cast
the reference to the expected result dtype, or add an `expected_dtype=` parameter. Draw `start`
from `[0, size]` and remove the zero-length skip and its comment. Draw several sub-ranges per
call (Rust uses 16).
