# F031: assert_read_rejects_invalid_index tries only 3 of the invalid-index classes and runs on only 4 storages (permute_dims, remove_dim, sub_dtype, where); no library bug hides behind the gap today

- Severity: low  Verdict: confirmed  Category: test-coverage
- Location: jix/src/util/test_util.rs:1379-1394 (the index set) (related: its only call sites jix/src/ops/shape_ops/permute_dims.rs:191-192, jix/src/ops/shape_ops/remove_dim.rs:239-240, jix/src/ops/sub_dtype.rs:222-225, jix/src/ops/where_op.rs:477; the shared validator it guards jix/src/storage/buf.rs:308-315 `check_out_buf` -> jix/src/error.rs:213 `check_get_range`; the narrower older tests jix/src/storage/buf.rs:516-540 `reversed_index_is_invalid_index` and jix/src/error.rs:483-492; K61)
- Reachability: test infrastructure only (`pub(crate)` helper, `#[cfg(test)]`). The contract it checks is public: `ArrayStorage::read_data` is a safe public trait method that has to reject any index.
- Reported by: util-test-infra

## What goes wrong
The helper builds 1 + 2*ndim invalid indices: one with ndim+1 ranges, then for each dim `0..len+1`
and `1..0` (test_util.rs:1385-1394). It never tries fewer ranges than ndim, the empty index for
ndim > 0, more ranges than NDIM_MAX, an empty range past the end (`len+1..len+1`,
`u64::MAX..u64::MAX`), huge ends (`0..u64::MAX`, `len..u64::MAX`), other reversed ranges
(`u64::MAX..0`), or a valid empty range in one dim combined with an invalid range in another. Only
4 tests call it, on PermuteDims, RemoveDim, SubDtype and Where. Compact, CompactMmap, Plain,
Scalar, the element-wise ops, the reductions and the other shape ops are never passed to it. The
only other invalid-index read test, buf.rs:516-540, tries one reversed range on Op1, Op2 and
PermuteDims.

The missing classes are the ones a likely regression would get through. Suppose someone adds an
"empty region, nothing to read" early return before `check_out_buf`. That passes all three of the
helper's classes: the ndim+1 index fails the length test, `0..len+1` is not empty, and `1..0` is
not `start == end`. But it accepts `len+1..len+1`, `u64::MAX..u64::MAX` and `[0..0, 0..len+1]`. A
pull-mode view impl could then compute `base + start * stride` with `start = u64::MAX`.

Today every storage is correct. Every leaf and op `read_data` calls `check_out_buf` first
(`check_get_range` comes before any `end - start`, which was the K61 fix). The forwarding wrappers
(Transmute, IntoType, Any, MaybeCompact, the compact wrappers, View/Box/Arc/&dyn, the cmp ops over
Op2) pass the index on to such an impl. So this is a coverage gap that could let a future
regression through, not a live bug.

## Trigger
Not a library trigger. Coverage: grep shows 4 call sites. The helper's set for a shape `[5, 6, 7]`
has 7 indices. The repro's wider set for the same shape has 86 indices, each read in pull and push mode.

## Repro
`jix/tests/repro_2026_10_29_batch6__f031.rs`. It runs the wider set in pull and push mode,
catching panics, and asserts that every read returns `ErrorKind::InvalidIndex`. It covers 77
arrays:
- the hunter's 36 chains, plus View, a transposed (non-C) Plain, Scalar, Scalar+Compact, product,
  min, max, argmin, std, all, any, reduce_unordered (Reduce), map2, map_multiple, real, imag,
  read_from_file (TypeDyn) and read_from_file_mmap (CompactMmap);
- the same kind of chains on a zero-length-dim base `(0, 6, 7)`, a 0-d base and an 8-d (NDIM_MAX)
  base, where the ndim+1 and 16-range indices exceed `DimArray` capacity.

`Fold` (not exported from `jix::ops`, and its `.fold` method is commented out at
reduction.rs:3428-3446) and `FnStorage` (internal to `compact_fn`) are not reachable from the
public API, so the repro leaves them out.

```
cargo test --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_29_batch6__f031 -- --nocapture
test every_storage_rejects_every_invalid_index_class ... ok
bug-hunt/tools/cargo-i686 test --manifest-path jix/Cargo.toml --all-features --test repro_2026_10_29_batch6__f031 -- --nocapture
test every_storage_rejects_every_invalid_index_class ... ok
```

It passes on x86_64 and on i686, so no library bug sits behind the gap. The test asserts the
correct behavior, so it can serve as the wider regression test. A failing repro is not possible
here because the defect is in a `pub(crate)` test helper, not in library behavior.

I did not run a mutation build. The disk has 1.5 GB free, too little for a scratch copy of the
crate. The early-return example above follows directly from the helper's three classes.

## Root cause
The helper was added with the K61 fix (#90) to pin one bug: a reversed range that reached
`end - start` before validation on Op1/Op2/.../PermuteDims/Where/SubDtype. It was sized for that
bug, so it only got the `1..0`, `0..len+1` and ndim+1 cases. It was then called only from the ops
K61 named, not from every storage.

## Suggested fix
Extend the index list in `assert_read_rejects_invalid_index` with the classes above: fewer ranges,
an empty index, `NDIM_MAX + 1` ranges, `len+1..len+1`, `u64::MAX..u64::MAX`, `u64::MAX..0`,
`0..u64::MAX`, `len..u64::MAX`, and a valid `0..0` in another dim. Call it from every storage's
test module, including Compact, CompactMmap, Plain, Scalar, the op1/op2/cast/cmp/clamp/map
families, the reductions and every shape op. Run it on a zero-length-dim base, a 0-d base and an
8-d base too, or drive it from one table-driven test like the repro.
