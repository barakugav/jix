# F042: Float reductions depend on the host's detected CPU cache sizes: the same numpy array, or the same .jix file, sums to different f32 values on machines with different L1d/L2

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix/src/storage/params.rs:453-459 (related: jix/src/storage/params.rs:349, jix/src/storage/params.rs:366-368, jix/src/util/cpu_cache.rs:57, jix/src/archive/array.rs:546-551, jix/src/ops/reduction.rs:437-441, jix/src/ops/reduction.rs:824-829, jix/src/ops/reduction.rs:843-856)
- Reachability: public Rust API (`Array::read_from_reader` / `read_from_file*`, `plain_ndarray*`, `compact_ndarray`, then `.sum(..)`) and Python API (`jix.asarray(x).sum()`, `jix.read_array(path).sum()`, `jix.compact(x).sum()`), all with default params
- Reported by: concept-threads-send-sync (raised as an open question in the pilot run's REPORT.md, section F)

## What goes wrong
`ArrayParams::tune` derives two defaults from `cpu_cache::cache_sizes()`. That function is
process-global state read from sysfs or sysctl. The defaults are `block_size = L1d`
(params.rs:366-368) and `read_size = (max(L1d/2, L2/16, block_size), L2/2)` (params.rs:453-459).
`read_size` is not part of the archive: `jix/schema/proto` has no such field, and
`read_from` only fixes the block shape (archive/array.rs:546-551). So every reader recomputes
`read_size` from its own host.

The reduction driver sizes its tiles with `read_shape_heuristic(read_size)` (reduction.rs:437-441).
It folds each tile pairwise, then merges tiles one after another (`merge_states(prev, state)`,
reduction.rs:824-829). The tile size therefore sets how the f32 additions are grouped. The result
of `sum()` (and of any other order-sensitive float fold) then depends on the machine that runs it,
not only on the data or the file. Within one process the result is stable, because the detection is
cached in a `OnceLock`. Across machines the last bits differ, so golden-value tests are flaky and
results cannot be reproduced bit for bit.

Nothing documents this. The params docs (params.rs:178, 204, 328) say only that the defaults are
"chosen automatically according to the CPU cache sizes", which reads as a performance setting.
`ReductionOpKernel::merge_states` (reduction.rs:71-77) allows regrouping "up to float accuracy",
but it is a crate-internal trait doc and does not say that the grouping depends on the host. The
pilot run left this as an open question, and KNOWN.md and the context docs do not mark it as
intended.

From reading the code (not run): there is a second dependence on the host. On contiguous data the
one-cell fold's lane count is `8 * u8s::LEN / size_of::<State>` for the SIMD level detected at run time
(reduction.rs:843-856, `fearless_simd::Level::new()`). For f32 that is 32 lanes on SSE2/SSE4.2/NEON,
64 on AVX2 and 128 on AVX-512. So two hosts with the same cache sizes but different SIMD levels
also group the additions differently.

## Trigger
Python: `x = np.random.default_rng(1).standard_normal(3_000_000).astype(np.float32)`.
- `jix.asarray(x).sum()`.
- `jix.write_array(jix.compact(x, params={'block_size': 48*1024}), path)` once, then
  `jix.read_array(path).sum()` on each host.

The only thing that changes is the L1d/L2 that sysfs reports.

The results span up to 4 ulps. Each value is within float accuracy of the exact sum. The defect is
that the result cannot be reproduced across machines, not that it is inaccurate.

## Root cause
The default `read_size` (params.rs:453-459) and the Plain/compact `block_size` (params.rs:366-368)
come from the detected cache sizes (params.rs:349, cpu_cache.rs:57). The reduction couples its
float grouping to them. `tile_shape` comes from `read_shape_heuristic` (reduction.rs:437). Each
tile is folded with `fold_pairwise` over that tile's run only, and successive tiles are merged in a
linear chain (reduction.rs:824-829). Tile boundaries along the reduced stream therefore move with
the host's cache sizes. The lane count of the leaf fold also depends on the runtime SIMD level
(reduction.rs:843-856).

## Suggested fix
Separate the float grouping from the I/O tiling. Fold each reduced stream in fixed chunks keyed by
absolute stream position, for example a constant power-of-two chunk with a fixed lane count. Combine
the chunks with a position-keyed pairwise or cascade stack, so that any tiling that splits the
stream at chunk multiples gives the same tree. Make the driver round its reduced-dim tile extents
to that chunk. If cross-host reproducibility is not a goal, document in the `sum`/`mean`/`prod` docs
(Rust and Python) that float results may differ in the last bits between machines and params.
Optionally also offer a deterministic mode: a fixed `read_size` and lane count, set by a param or
an environment variable.
