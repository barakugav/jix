# F038: A write_to_file / write_array that fails part-way leaves a partial, unreadable .jix file; the retry then raises FileExistsError, and a failed append leaves garbage bytes in the file

- Severity: low  Verdict: confirmed  Category: error-handling
- Location: jix/src/archive/array.rs:281-283 (related: jix-py/src/archive.rs:212-226, jix-py/src/archive.rs:241-257, jix/src/archive/array.rs:391-430, jix/src/archive/block.rs:129-215, jix/src/codec/mod.rs:446-453)
- Reachability: public Rust API (`Array::write_to_file`), Python API (`jix.write_array` with a path, both `append=False` and `append=True`)
- Reported by: concept-arith-semantics

## What goes wrong
A lazy view is written to disk as it is computed. The header and TOC placeholder go first, then the
blocks, compressed one at a time. The TOC is patched only at the end
(`BlockArchiveWriter::start` / `finalize`, archive/block.rs:129-215). Each block read checks its
arithmetic status (`ReadContext::check_op_status`, codec/mod.rs:446-453). Under the default modes,
divide-by-zero and invalid raise, so `write_array(a // b, path)` with a zero in `b` fails after
part of the archive is on disk. Neither the Rust nor the Python wrapper cleans up after the `Err`.
When the `BufWriter` is dropped it flushes its buffer, so the bytes reach the file anyway:
- For a new path (`create_new`), a corrupt file stays behind and cannot be read ("block locations
  length 0 does not match 200 blocks"). Retrying at the same path, even after the user fixes the
  modes with `jix.errstate(divide="ignore")`, raises `FileExistsError`. That is the obvious
  recovery, and it does not work.
- With `append=True`, the failed array's bytes stay after the arrays already in the file (60258
  bytes in the repro). The earlier and later arrays can still be read by offset. The file now holds
  an unparseable section.

## Trigger
Use int32, `block_shape=[1000]`, 200000 elements. `a = 1..=200000`, and `b` is all ones except
`b[-1] = 0`, so the zero is in the last block only. Call `q = a // b` in Python or `a / b` in Rust.
- Python: `jix.write_array(q, p)` raises FloatingPointError. Then
  `with jix.errstate(divide="ignore"): jix.write_array(q, p)` raises FileExistsError.
- Python append: `jix.write_array(small, p2)`, then `jix.write_array(q, p2, append=True)`.
- Rust: `q.write_to_file(&path)` returns `Err(Arithmetic)` and leaves `path` behind.

## Root cause
- `write_to_file` (jix/src/archive/array.rs:281-283) creates the file with `create_new` and returns
  the `Err` from `write_to`. It does not remove the file it just created.
- Python `write_array` (jix-py/src/archive.rs:212-226) works the same way. It creates the file with
  `create_new`, or opens it and seeks to the end for append. Then `write_array_impl`
  (:241-257) returns `?` on the error, without removing the new file or truncating back to the
  original length.
- The streamed writer (archive/array.rs:391-430, archive/block.rs) cannot finish an archive that
  failed part-way, so the left-behind bytes are always a corrupt section.
- The context docs list `create_new` as intended (codec-archive.md "Intentional behaviors";
  `test_archive.py:43`). They say nothing about failed writes. `test_errstate.py:108-120` checks only
  that `write_array(q, "q2.jix")` raises, not what is left on disk. The partial file is not
  documented behavior. Because of `create_new`, it blocks the natural retry.

## Suggested fix
In `write_to_file` and in Python `write_array` with a path, record whether the file was created and,
for append, its starting length. On `Err`:
- If the file was created, drop the writer and `remove_file(path)`.
- For append, `set_len(original_len)`.

Another option is to write to a sibling temp file and rename it into place on success. That covers
only the new-file case, not append. Either way, document what is left on disk when a write fails.
