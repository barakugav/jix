## What goes wrong
#107 fixed K168 by ANDing `diff.is_finite()` into `no_inf` (cmp.rs:230). For finite operands of
opposite sign with `|a| + |b| > T::MAX`, the result is now always false. The documented
definition is `|a - b| <= max(atol, rtol * max(|a|, |b|))` (cmp.rs:161-163, 548-549, and the
Python docstring). Its NaN / infinity rules cover only NaN or infinite operands. Exactly,
`|a - b| = |a| + |b|`, which is finite. The formula therefore holds whenever atol = inf, rtol = inf,
or `rtol >= 1 + min(|a|,|b|) / max(|a|,|b|)`. That bound includes every rtol >= 2 and part of
the 1 < rtol < 2 range that K168 was about. In all these cases jix now returns false.

Before #107 these pairs were true, because `inf <= inf` held. So the fix swapped one wrong answer
for another in the overflow regime instead of computing the right one. The result is also
inconsistent: with atol = inf or rtol >= 2, every finite pair is close except those whose
difference overflows. In f16 that starts at ordinary magnitudes (+-40000; 50000 vs -20000).
Through Python, any f16 `atol` >= 65520 casts to inf and triggers it too.

This is not documented as intended. The commit message only says "Do not report far-apart floats
as close when their difference overflows". K168's suggested fix offered
`| atol.is_infinite() | rtol.is_infinite()` to avoid the atol / rtol = inf part. The Rust test
reference was changed the same way (`if diff.is_infinite() return false`, cmp.rs:1084), so
`approx_eq_edge_cases` asserts the current behavior for MAX / MIN with tol = INFINITY. The Python
reference (`_ref_isclose_scalar`) was not changed, and its tolerances are capped at 0.5, so it
never reaches this regime. Severity is low because every trigger needs a tolerance large enough
to accept (almost) any finite pair, together with operands whose difference overflows.

## Trigger
- f64 / f32: `a = [MAX]`, `b = [-MAX]`, with any of (rtol=0, atol=inf), (rtol=inf, atol=0),
  (rtol=2, atol=0) or (rtol=3, atol=0). `a = [MAX]`, `b = [-MAX/4]`, rtol=1.5 (needs only 1.25).
- f16: `[40000]` vs `[-40000]` with rtol=2 or 3, or atol=inf (Python: `atol=1e6`). `[50000]` vs
  `[-20000]` with rtol=1.5 (needs 1.4).
- Expected `[true]` in every case. Actual `[false]`. Non-overflowing pairs (1 vs -1, MAX vs MAX/2)
  are unaffected, and K168 itself (MAX vs -MAX, rtol=1.5 -> false) stays fixed.

## Root cause
`impl_approx_eq` (cmp.rs:224-231) evaluates the formula in `T`. When `a - b` overflows, `diff`
becomes +inf and stops carrying the information the comparison needs. #107 handles that by
declaring such pairs never close (`& diff.is_finite()`, cmp.rs:230). That is only right when the
right-hand side is finite and smaller than the exact `|a| + |b|`. It is wrong when atol / rtol are
infinite, or when `rtol * max(|a|,|b|)` legitimately exceeds `|a| + |b|`.

## Suggested fix
When `diff` is not finite and both operands are finite, compare at half scale instead of returning
false. Halving is exact at these magnitudes, so compute
`diff_h = |a*0.5 - b*0.5|` (finite) and test
`close_h = (diff_h <= atol*0.5) | (diff_h <= (largest*0.5) * rtol)`. Then
`close = select(diff.is_finite(), close, close_h)`, which is still branchless. This gives the exact
answer for K168 and for this finding. A minimal alternative is
`& (diff.is_finite() | atol.is_infinite() | rtol >= 2)`, which still misses 1 + min/max <= rtol < 2.
Update `ref_approx_eq` to the exact formula (e.g. compute in a wider type, or at half scale) and add
rtol = 2, rtol = inf and atol = inf cases with MAX vs -MAX and MAX vs -MAX/4.
