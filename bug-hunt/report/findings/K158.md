# K158: Every element-wise op deep-copies the cache-id set of everything below it (#100), so a left-deep lazy chain of n ops holds about n^2/2 ids: memory grows quadratically with chain depth (about 120 MB at 4000 ops, 740 MB at 10000)

- Severity: low  Verdict: confirmed  Category: resource
- Location: jix/src/storage/params.rs:827-848 `ArraySpecDynamic::add_cache_id` (`Arc::make_mut`
  at :834) and jix/src/storage/params.rs:860-893 `add_cache_ids_from_impl` (shallow clone of the
  first input's set at :875, then `Arc::make_mut` at :880 for the next input) (related:
  jix/src/ops/elementwise/op1.rs:37-39 clone + add_cache_id, jix/src/ops/elementwise/op2.rs:84-85,

  that resets the set, jix/src/storage/any.rs:107 the type-erased node shares the Arc)
- Reachability: Python API (`x = x + base` or `x = x + 1` in a loop: every Python op result is a

## What goes wrong
Since #100 every `ArraySpecDynamic` carries `arrays_to_cache_potentially`, an
`Arc<ArrayCacheIdSet>` with the cache id of every storage the array reads at its own index. An
element-wise op starts from its first input's set (Op1 clones the whole dynamic spec; Op2 / Map /
Select / MinMax share the first input's Arc in the copy branch at params.rs:875), then mutates it
to merge the other inputs and add its own id. The input still holds the same Arc, so the first
`Arc::make_mut` deep-copies the whole set, O(k), to add one or two ids. Every op therefore owns a
private copy of all ids below it, and a left-deep chain of n ops holds sum(k) = n^2/2 ids at about
15 bytes each (HashMap entries), built with O(n^2) inserts. Before #100 an op's footprint did not
depend on depth. The sets only steer the optional read cache, so this memory buys nothing for
correctness. Shape ops that call `with_cache_scope` (transpose, slice, reshape, ...) reset the set,
which is why a chain broken by a transpose stays linear.

## Trigger
Python: `base = jix.asarray(np.arange(16, dtype=np.float32).reshape(4, 4)); x = base; for i in
range(n): x = x + base` (or `x = x + 1`). Rust: `x = (x.into_typed::<f32>()? +
base.clone().into_typed::<f32>()?).into_any()` in a loop, with `base: ArrayAny`.

## Root cause
The per-node set is a flat, owned, copy-on-write `HashMap` (params.rs:614-619), and every
element-wise constructor mutates a set it shares with its input (params.rs:834, :880), so
copy-on-write always fires. Practical bound: reads of type-erased chains overflow the stack
past about 2k levels in debug / 7k in release (K116), so a readable chain wastes up to about
30 MB (debug) / 350 MB (release); chains can still be built far deeper (up to the 30-50k drop
limit of K116), costing several GB. Hence low severity: no crash or wrong result, a
pathological memory cost on a plausible user loop, not driven by untrusted input.

## Suggested fix
Avoid per-node full copies: share structure (a persistent set, e.g. an `Arc` linked list or HAMT
of child sets with the repeat detection done on merge), or keep only a bounded/top-level set and
compute `arrays_to_cache` once at the top-level read (one traversal of the expression) instead
of at construction. A cheap mitigation: stop propagating ids beyond a size cap (the cache is an
optimization, so dropping ids only loses caching).
