# K181: power() with a float base rejects a Python int exponent outside i32 ('out of bounds for i32') though the result dtype is float either way and the (float, float) slot holds it; every other op accepts any i64 int next to a float array

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/common/dispatch.rs:249 (related: jix-py/src/ops/elementwise/arith.rs:537-542 float pairs of the Pow table, jix-py/src/ops/common/operand.rs:165 / 416 `check_int_in_bounds`, jix-py/src/ops/elementwise/arith.rs:416 docstring, jix-py/python/tests/test_type_promotion.py:423-427, 531, 719, 726)
- Reachability: Python API
- Reported by: py-ops-dispatch-promotion
- Consolidated: found in run 2026-11-15-batch7-5 as F012; line numbers below are at that run's commit. Re-checked at main c705a54 (#107): still reproduces (K181.py: 5 checks fail, e.g. f64_arr ** 2**31 raises OverflowError). Current location: jix-py/src/ops/common/dispatch.rs:249.

## What goes wrong
The Pow table lists each float base's (float, i32) pair before its (float, float) pair, and an
untyped Python int always passes the Safe check into the i32 slot. When the value is outside
i32, `Operand::cast` raises OverflowError, and `dispatch_args` returns that error instead of
trying the next descriptor. So `f64_arr ** 2**31`, `f64_arr ** 10**10` and
`power(f32_arr, 2**31)` raise "Python integer 2147483648 out of bounds for i32". The i32 appears
nowhere in the user's inputs or result: the result dtype is the base dtype whichever slot is
used, and the (float, float) slot represents the exponent exactly (f64 up to 2**53; f32 rounds it
the way numpy does under NEP 50). The same value works as `float(2**31)`, as `np.int64(2**31)`
(a typed i64 skips the i32 slot), and in the all-untyped `jix.power(0.5, 2**31)` (P8 default).
A typed float base such as `np.float64(0.5)` raises.

It is unreasonable on its own merits, not only because numpy differs:
- Next to a float operand, every other op takes a Python int at any int64 value without a range
  check (`f64_arr + 2**31`, `maximum(f64_arr, 2**31)`; pinned by
  test_python_int_into_float_is_not_bounds_checked). power is the only op that rejects one.
- The policy's stated reason (test_type_promotion.py:423-427: the int "adopts the integer dtype
  dispatch picked for it... rather than silently wrapping the scalar") does not apply. A float
  base has no integer dtype for the int to adopt and no wrapping to avoid. The i32 slot is an
  internal kernel choice (powi), and the docstring says only that "a float base takes an integer
  or a float exponent".

Not part of this finding: an INTEGER base with a Python int exponent outside u32
(`int64_arr ** 2**32` raises "out of bounds for u32", while `np.int64(2**32)` gives [1, 1, 0]).
That is the same mechanism as the pinned `power(int_arr, -1)`
(test_power_negative_python_int_exponent_raises_for_integer_base, listed as intended in
context/py-ops.md), so it is intended.

## Trigger
```python
x = np.array([1.0, 0.5, -1.0])
f64 = jix.asarray(x)
f32 = jix.asarray(x.astype(np.float32))
f64**2**31  # OverflowError, numpy/expected float64 [1, 0, 1]
jix.power(f64, -(2**31) - 1)  # OverflowError, expected [1, inf, -1]
jix.power(f32, 2**31)  # OverflowError, expected float32 [1, 0, 1]
jix.power(np.float64(0.5), 2**31)  # OverflowError, expected 0.0
f64**10**10  # OverflowError, expected [1, 0, 1]
```
(also f16 bases; any |exponent| > 2**31 - 1.)

## Root cause
`dispatch_args` (dispatch.rs:225-254) selects on kinds only: an untyped Int passes
`is_cast_allowed(Safe)` into I32, so (f64, i32) at arith.rs:541 wins before (f64, f64) at 542.
The value is checked only afterwards, in `Operand::cast` -> `check_int_in_bounds`
(operand.rs:165, 416-446), and the error is returned with `?` (dispatch.rs:249) with no
fall-through. For every other table the only slot next to a float operand is a float slot, where
ints are not range-checked. Power is the one table that mixes an integer exponent slot into the
float-base pairs, so it is the only place a Python int next to a float array can fail.

## Suggested fix
In `power()` (arith.rs:545), when the base operand is a float and the exponent is an untyped
Python int outside i32, skip the (float, i32) pairs. For example, pre-convert the exponent to an
untyped float scalar for a float base only, so it picks (float, float). Keep the int-base
behavior unchanged. Or let a table opt in to falling through to the next descriptor on an
untyped-int range error. At the least, document the i32 limit in the power docstring and pin it
with a test.
