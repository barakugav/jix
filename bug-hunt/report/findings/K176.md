# K176: Layout-identical numpy struct dtypes (default vs align=True) become unequal jix dtypes, so cast, concatenate, stack and where between them raise TypeError, while `.dtype ==` and numpy(out=) call them the same

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/elementwise/casting.rs:56 (related: jix-py/src/ops/common/dtype_promote.rs:177, jix-py/src/dtype.rs:130, jix-py/src/dtype.rs:217, jix/src/dtype.rs:897, jix-py/src/array.rs:221, jix/src/dtype.rs:476-501)
- Reachability: Python API
- Reported by: py-core-dtype-surface
- Consolidated: found in run 2026-11-15-batch7-5 as F005; line numbers below are at that run's commit. Re-checked at main c705a54 (#107): still reproduces (K176.py: cast / concatenate / stack / where between layout-identical struct dtypes raise TypeError). Current location: jix-py/src/dtype.rs:217.

## What goes wrong
`dtype_from_numpy` copies numpy's reported alignment into `Dtype::new_struct`
(jix-py/src/dtype.rs:130, :217). numpy reports alignment 1 for every struct built without
`align=True`, even when the offsets also form a valid aligned layout. So
`P = [('a','<i4'),('b','<f4')]` becomes a packed jix dtype (alignment 1), and the same list with
`align=True` (`A`) becomes an aligned one (alignment 4). Names, offsets (0, 4) and itemsize (8) are
the same. Core `Dtype::eq` compares the alignment (jix/src/dtype.rs:897-903), and jix-py uses that
equality as its test for "same dtype". As a result the identity cast (casting.rs:56) and the
shared-dtype check in promotion (dtype_promote.rs:177) both refuse the pair. Every other Python-visible
notion of dtype identity accepts it: numpy (`P == A`, `can_cast(P, A, 'no')`), the jix arrays' own
`.dtype` (`jix.asarray(x).dtype == jix.asarray(y).dtype` is True), and jix's `numpy(out=)`
(`is_equiv_to`, array.rs:221), which accepts an out of either layout for the other. Python has no
retagging op (`transmute_elements_dyn` is not exposed), so the only workaround is to materialize
and `.view()` in numpy. No wrong values and no memory issue: each failing call raises a TypeError
whose message shows two dtypes that differ only in `alignment: 1` vs `alignment: 4`.

Cross-language angle: `#[derive(Dtyped)] #[repr(C)]` and `Dtype::from_fields` choose the aligned
layout whenever it is valid (jix/src/dtype.rs:489-494). A `.jix` file written from Rust therefore
reads back in Python with an `align=True` descr, and it cannot be concatenated, stacked, `where`d
or cast together with a numpy array built with the default (packed) dtype of the same fields. A
file read back in Python behaves the same way (checked: `read_array` of an aligned array, then
`concatenate([r, x])` with x packed, raises).

## Trigger
```python
P = np.dtype([("a", "<i4"), ("b", "<f4")])
A = np.dtype([("a", "<i4"), ("b", "<f4")], align=True)
x = np.zeros(2, P)
y = np.zeros(2, A)
jix.asarray(x, dtype=A)  # TypeError: Unsupported cast ... alignment: 1 } to ... alignment: 4 }
jix.cast(y, P)  # TypeError: Unsupported cast
jix.concatenate([x, jix.asarray(y)])  # TypeError: Op 'concatenate' does not support operands with dtypes [...]
jix.stack([jix.asarray(x), jix.asarray(y)])  # same, 'stack'
jix.where(np.array([True, False]), jix.asarray(x), y)  # same, 'where'
# meanwhile these succeed:
jix.asarray(x).dtype == jix.asarray(y).dtype  # True
jix.asarray(x).numpy(out=np.zeros(2, A))  # ok
```
Each op works when both operands share one layout (checked for P/P and A/A).

Before the checks, the script asserts that `jx.dtype == jy.dtype` and that `numpy(out=)` in either
direction succeed. Both pass.

## Root cause
jix keeps packed and aligned struct layouts apart on purpose. `Dtype::new_struct` documents that it
exists for offsets that are valid both ways (jix/src/dtype.rs:508-509), and
`test_struct_dtype.py::test_aligned_flag_is_preserved` checks that the flag survives a round trip.
Core equality including the alignment is also what `Ty<T>` relies on: the runtime dtype alignment
has to equal `align_of::<T>()`, e.g. jix/src/util/nd_copy.rs:117. The flaw is in jix-py, which uses
that strict core equality as its notion of Python dtype identity:
- `cast_impl` returns early only when `array.dtype() == dtype` (casting.rs:56). Any other struct
  target falls through to "Unsupported cast", even when only the alignment differs.
- `promotion_target` takes the no-cast path only when all array dtypes are equal under core `==`
  (dtype_promote.rs:177). Struct dtypes have no rank/precision, so `promotion_target_impl`
  returns None and the op raises.

The descr cached for Python (`.dtype`) and `check_output_array` (`is_equiv_to`) both use numpy's
looser equivalence, so the two halves of jix-py disagree.

## Suggested fix
Do not change core `Dtype::eq`, since `into_typed` soundness depends on it. In jix-py, add a "same
layout" test for struct dtypes: same fields (recursively up to alignment), same itemsize and same
inner shape. Then:
- In `cast_impl`, when source and target have the same layout, retag with
  `array.transmute_elements_dyn(dtype.clone())`, the same zero-copy path already used for
  same-size integer casts at casting.rs:64.
- In `promotion_target` / `operands_dtype_promotion`, when every array operand is a struct with
  the same layout, cast them all to one of them through that retag. numpy picks the aligned one
  (`np.concatenate([x, y]).dtype` is aligned).

Do not normalize in `dtype_from_numpy` (e.g. picking aligned whenever valid): that would break
`test_aligned_flag_is_preserved` and change what Python round trips report.
