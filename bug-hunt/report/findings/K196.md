# K196: An integer index outside i64 raises TypeError 'only integers, slices ... are valid indices' instead of IndexError, while a slice bound of the same size and an in-range out-of-bounds int raise IndexError, as the docstrings promise

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/shape_ops.rs:274-281 (related: jix-py/src/ops/shape_ops.rs:163-167 (jix.slice Raises), jix-py/src/array.rs:505-513 (Array.numpy Raises), jix-py/src/array.rs:183 (Array.__getitem__ / numpy(index) caller), jix-py/src/util.rs:21-46 (slice path))
- Reachability: Python API (`Array.__getitem__`, `Array.numpy(index)`, `jix.slice`)
- Reported by: py-ops-shape-ops
- Consolidated: found in run 2026-11-17-scan-106-107-b as F005; line numbers below are at c705a54 (#107). Re-run by hand at main c705a54 (#107): reproduces (K196.py: 7 failures, TypeError instead of IndexError). Current location: jix-py/src/ops/shape_ops.rs:274.

## What goes wrong
`parse_basic_index` classifies each index item as Ellipsis, slice, or int, and takes an int via
`item.extract::<i64>()`. Any extraction failure falls through to the catch-all
`TypeError("only integers, slices (`:`), and ellipsis (`...`) are valid indices")`, so a Python
int (or numpy integer such as `np.uint64(2**63)`) outside `[-2**63, 2**63)` is reported as an
unsupported index TYPE, with a message that is false for an int. The same magnitude as a slice
bound goes through `PySlice_Unpack` and raises IndexError (pinned by
`test_slice.py::test_slice_huge_bounds_raise`), and `a[2**63 - 1]` raises IndexError, so the
exception type flips at 2**63 for no semantic reason. The docstrings of `jix.slice` and
`Array.numpy` list IndexError for "Integer index out of bounds" and TypeError only for an
"Unsupported index item type". Code that guards indexing with `except IndexError` misses these
cases. Any `__index__` error (OverflowError, or an exception raised by a user `__index__`) is
also swallowed and replaced by this TypeError. Nothing is read out of bounds and no wrong data is
returned; only the exception type and message are wrong.

## Trigger
```python
a = jix.compact(np.arange(5))
a[2**63]
a[-(2**63) - 1]
a[2**100]
a.numpy(2**64)
jix.slice(a, 2**64)
jix.slice(jix.compact(np.arange(12).reshape(3, 4)), (0, 2**64))
a[np.uint64(2**63)]
```

## Root cause
jix-py/src/ops/shape_ops.rs:274-281: `if !item.is_instance_of::<PyBool>() && let Ok(i) =
item.extract::<i64>()` discards the extraction error and conflates "not an integer" with "an
integer that does not fit in i64". Not covered by the context doc's intentional behaviors (the
"Python int outside i64 always raises" entry is about op operands and OverflowError, and indexing
raises either way - only the exception type is at issue).

## Suggested fix
Classify by type first: if the item is an int / has `__index__` (and is not a bool), call
`extract::<i64>()` and map an OverflowError (or any failure) to
`IndexError("index {item} is out of bounds for dim {d} with size {len}")` (or
`"cannot fit 'int' into an index-sized integer"`, like Python lists); raise the TypeError only for
items that are not integers at all. Add `a[2**63]`, `a[-(2**63) - 1]`, `a[np.uint64(2**63)]` to
the IndexError tests in test_slice.py.
