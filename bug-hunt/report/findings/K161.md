# K161: Scalar::new and Plain::new run tune's padded-shape check though they never pad, so `y + 1` on a valid lazy array of ~2^63+ elements raises InvalidShapeOperation while `y + y` works

- Severity: low  Verdict: confirmed  Category: error-handling

- Reported by: storage-compact-params
- Consolidated: found in run 2026-11-15-batch7-2 as F002; line numbers below are at that run's commit. Re-checked at main c705a54 (#107): still reproduces (repro_k161: Scalar::new and plain_ndarray_ptr reject a valid lazy shape; K161.py: 4 of 4 scalar ops rejected). ## What goes wrong
`ArrayParams::tune` ends by rejecting a shape whose product, padded up to the block shape, overflows
u64. The comment gives the reason: the archive reader checks the same thing. `Scalar::new` and
`Plain::new` also build their spec with `into_spec` -> `tune`. Neither storage has blocks, and both
replace the tuned block shape with all-ones on the next line. So they compute the auto block shape
(from L1d) only to check it and throw it away. The padded product they check is irrelevant to them.
When the element product fits u64 but padding the inner dim to the auto block overflows, the
constructor returns `InvalidShapeOperation` for a lazy array that is otherwise valid.
`Broadcast::new` accepts the same shape: it only runs `check_shape_overflow`. Ops between two such
arrays also work (`y + y` reads back correctly). But in Python every scalar operand becomes a
`Scalar` of the broadcast shape, so any op with a Python scalar raises. Neither constructor's docs
list this error. No wrong values and no panic: the cost is a spurious error.

## Trigger
B = 2^31 + 1 (odd, so no power-of-two-multiple block dim divides it), A = (2^64 - 1) // B = 8589934588.
A * B fits u64 with less than B to spare, so padding B by a single item overflows.
- Python: `x = jix.asarray(np.full((1, 1), 7, np.uint8)); y = jix.broadcast(x, (A, B)); y + 1`
- Rust: `jix::__private::Scalar::new(1u8, &[A, B], ArrayParams::new().block_size(1 << 15))`, or
  `unsafe { Array::plain_ndarray_ptr(&v, &[A, B], &[0, 0], u8::DTYPE, params) }`. Pinning
  `block_size` gives a host-independent auto block of [1, 32768]. With default params the block is
  [1, L1d] (here [1, 49152]).
The same thing happens for empty shapes, since zero dims count as 1 in both products, e.g.
`(0, 2**32 - 1, 2**32 + 1)`.

## Root cause
The padded-shape check at params.rs:379-388 protects block storage: a written array must be readable
by the archive reader. It lives in `tune`, which every leaf runs through `into_spec`. Scalar.rs:52-59
and plain.rs:129-136 clear `block_shape` / `block_shape_fixed_dims` and so get an auto block shape.
They then overwrite it with all-ones. With all-ones the padded product equals the element product,
which `check_shape_overflow` has already bounded. So the check tests a geometry these storages never
use. Shapes from numpy or ndarray cannot reach it (fewer than 2^63 items and at most one partially
blocked dim, so padding stays below 2x). Only jix's u64 lazy shapes and zero-stride raw pointers can.
Writing or compacting such an array still fails correctly, because compaction re-tunes with the real
block shape (array/compact.rs:178). So the check in the leaf constructors protects nothing.

## Suggested fix
Do not run the block-geometry checks for non-blocked leaves. The simplest way is to skip the
padded-shape check in `into_spec` when the flags say `plain_read`, or to give `tune` a flag for
that. The alternative is for Scalar/Plain to tune with an all-ones block shape that is fixed in
every dim, so nothing is scaled and the padded product equals the element product. In that case
reset the fixed dims to all-false afterwards: K121's `combine_block_layout` behavior depends on
them, and the auto block reports them all-false today. Note that `block_size` / `read_size`
defaults would then change too. Add a test next to `scalar_rejects_overflowing_shape`
(params.rs:2191) for a shape that broadcasts fine and must also build a Scalar/Plain.
