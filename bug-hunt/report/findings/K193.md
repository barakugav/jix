## What goes wrong
#106 sends every top-level read whose storage is `ReadTiling::ZeroCopy`, `Fusable` or
`SinglePass` to one `read_data` over the whole region (read.rs:458). The entry points check only
the OUTPUT region against the OUTPUT itemsize. But a fused element-wise op pulls each leaf for the
whole region (core_trait.rs:123), and a SubDtype pulls its parent for the whole region
(sub_dtype.rs:98). Each leaf runs `check_out_buf`, which calls `check_region_size(index.size(), leaf_itemsize)`
(buf.rs:359). On 32-bit that check rejects region * itemsize > isize::MAX (error.rs:319-323),
even in pull mode and even for a Broadcast's 0-stride view, which allocates nothing
(broadcast.rs:130). So when the op narrows (output itemsize < input itemsize), a read whose result
fits easily returns `InvalidShapeOperation "read region of size ... with itemsize <leaf> does not
fit in memory"`. The same expression read in two halves works, and at #105 (a7b0656) the same
calls succeed: Op1 / Op2 / Map / SubDtype cleared their flags then, so the read was tiled and every
leaf pull was tile-sized. The documented error is "the region does not fit in memory"
(read.rs:260, 395; "the result" at :40, :127), but here the region fits.

## Trigger
i686, default params:

```rust
// (1) struct field (SubDtype, ZeroCopy since #106): 32 MiB u8 result, 2 GiB + 64 B virtual leaf
#[derive(Copy, Clone, Dtyped)] #[repr(C)] struct Rec64 { a: u8, rest: [u8; 63] }
Array::plain_ndarray(Array1::from_elem(1, rec))?.broadcast(&[(1 << 25) + 1])
    .dtype_sub_field::<u8>("a").to_ndarray::<Ix1>()
// (2) the same leaf through .map(|r: Rec64| r.a).to_buf_slice(..)       (Map, Fusable)
// (3) f64 col [2^14, 1] and row [1, 2^14], both broadcast to [2^14, 2^14]:
a.less(b).to_ndarray_sub::<Ix2>(..)              // 256 MiB bool8 result, 2 GiB per leaf
(a + b).cast::<u8>().to_buf_slice(..)           // 256 MiB u8 result
// (4) the jix-py shape of the same less: ArrayAny leaves broadcast with
//     Broadcast::new_array(..).into_any(), into_typed::<f64>(), less, into_any(), then
//     to_buf_strided_into, as PyArray::numpy() does (jix-py/src/array.rs:653).
```

Python on an x86 / armv7 wheel (argued, not run):
`jix.less(jix.asarray(np.arange(16384.)[:, None]), jix.asarray(np.arange(16384.)[None, :])).numpy()`.
The implicit broadcast is Any(Broadcast(Plain)), which is ZeroCopy. The op is Fusable, and Any
makes it SinglePass (any.rs:106-108), so `numpy()` takes the single read.

## Root cause
#106 replaced #105's `plain_read || nitems <= min_nitems` single-read rule with
`read_tiling() <= SinglePass` (read.rs:458). `ReadTiling::fused` (params.rs:1087-1094) makes an
element-wise op over ZeroCopy leaves Fusable, whatever its input and output itemsizes. The same
goes for SubDtype: `pulled_view` (params.rs:1107-1112, sub_dtype.rs:65-66) keeps it ZeroCopy.
The single-read rule assumes that a region that fits at the output itemsize fits at every node
below it. That holds only when no node is narrower than its inputs. The leaves still run the
32-bit region check meant for buffers that must be materialized. Broadcast applies it to its own
virtual region (broadcast.rs:130) rather than to the 1-element inner region it actually pulls.

## Suggested fix
Either:
- Make the region check cover only memory that is really needed. A Broadcast pull would check
  only its inner region (`inner_size`), and a SubDtype pull would rely on its inner's check, so a
  0-stride view never fails. First audit that no pipeline / cache code computes a leaf's
  `prod(size) * itemsize` in usize.
- Or, on 32-bit, keep the single read only when the region fits at the largest itemsize in the
  tree. Carry a max itemsize in `ArraySpecDynamic`, or fall back to the tiled path when
  `nitems * max_itemsize > isize::MAX`. This restores #105 behavior for these reads.

Add a 32-bit test like the repro's case (1). It is cheap: 32 MiB.
