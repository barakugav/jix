# K192: Select is classified ReadTiling::Fusable (#106), but its read_data pulls `condition` and `y` into region-sized temporaries, so a top-level read of `cond_op.select(x, y_op)` runs untiled and allocates them for the whole region

- Severity: low  Verdict: confirmed  Category: resource
- Location: jix/src/ops/elementwise/select.rs:109 (related: jix/src/ops/elementwise/select.rs:143-144, jix/src/array/read.rs:458, jix/src/storage/params.rs:1075-1076, jix/src/storage/params.rs:1087, jix/src/ops/elementwise/op2.rs:122-125, jix/src/storage/any.rs:106-108)
- Reachability: public Rust API (Python is not affected)
- Reported by: elementwise-ops-select-transmute-subdtype, py-ops-cmp-bitwise-select, concept-read-contract
- Consolidated: found in run 2026-11-17-scan-106-107-b as F001; line numbers below are at c705a54 (#107). Re-run by hand at main c705a54 (#107): reproduces (repro_k192: a push read of a 16384 KiB region allocates 20480 KiB; the tiled read of the same expression 160 KiB). Current location: jix/src/ops/elementwise/select.rs:109.

## What goes wrong
#106 gave Select `ReadTiling::fused([c, x, y])`, so it is `Fusable` whenever its inputs are ZeroCopy
or Fusable. The `Fusable` doc (params.rs:1075-1076) promises a tree that "streams from the source
memory into the destination, with no temporary". That is true when Select is a pipeline leaf
(its `read_as_elementwise_pipeline`), but Select's own `read_data` does not use the pipeline: it
pulls `condition` and `y` with `read_data_pull` (select.rs:143-144) and then pushes `x` into `out`.
When `condition` or `y` is an element-wise op, each pull materializes a pooled buffer as large as
the region. Because the Select is Fusable, `to_buf_strided_checked` (read.rs:458) takes the
single-read path for the whole request, so those temporaries are the size of the whole output
(+100% for `y`, +1/itemsize for `condition`) instead of tile-sized, and the read makes three passes
over memory instead of one per cache-sized tile. Values are correct. Before #106 (a7b0656) Select's
`spec()` called `with_cleared_flags()`, so the read was tiled; this is a #106 regression.

## Trigger
Rust, Plain f32 inputs of N = 4 Mi elements:
`p(&a).greater(p(&zero)).select(p(&a), p(&b) * p(&b))` (spec read_tiling = Fusable), read with
`to_buf_slice(&[0..N], &mut dst, &ctx)` into a preallocated `dst` (same for `to_ndarray`,
`to_buf_strided`, `to_buf_strided_into`). Any parent that forwards (Slice, PermuteDims, InsertDim,
RemoveDim, Transmute: `forwarded(Fusable) = SinglePass`) or pushes pieces (Stack, Concatenate,
Reshape, Roll: `pushed_pieces`) also reads it in one pass. Only `condition` / `y` that are
non-ZeroCopy matter; a Fusable `x` is pushed and streams. Block-wise writers (compact,
write_to_file) read block-sized regions and are not noticeably affected. Python is not affected:
`where()` (jix-py/src/ops/elementwise/select.rs:93) builds Select from type-erased ArrayAny
operands, which forward Fusable as SinglePass (any.rs:108), so any op operand makes Select Tiled.

## Repro
jix/tests/repro_k192.rs (tracking global allocator; asserts a push read
allocates at most a quarter of the region, i.e. tile-sized scratch only):

```
cargo test --manifest-path jix/Cargo.toml --all-features --test repro_k192 -- --nocapture
```

```
output 16384 KiB; select(a > 0, a, b*b) [Fusable] push read allocated 20480 KiB; same with erased cond/y [Tiled] 160 KiB
panicked at tests/repro_k192.rs:117:5:
push read of a 16384 KiB region allocated 20480 KiB (tiled read of the same: 160 KiB)
```

The baseline is the same expression with `condition` and `y` type-erased (`into_any().into_typed()`),
which makes Select Tiled, as it effectively was before #106. Both reads produce the reference values.
The hunter's test (hunt_..._elementwise_ops_select_transmute_subdtype_1.rs) also measured
`to_ndarray` peaking at 36 MiB vs 16 MiB for the fused control `a*b + a`.

## Root cause
`ReadTiling` is one level used for two things: how a parent may fuse the node, and whether a
top-level read of the node needs tiling. For Op1/Op2/Clamp/Map both agree because their
`read_data` runs their own pipeline (op2.rs:122-125). Select is fusable as a pipeline leaf, but its
`read_data` (select.rs:133-147) pulls `condition` and `y`, which is only temporary-free when those
are ZeroCopy. select.rs:109 applies `ReadTiling::fused` to all three inputs regardless.

## Suggested fix
Either classify Select as `fused(...)` only when `condition` and `y` are ZeroCopy and `Tiled`
otherwise (the pre-#106 behavior for that case), or make `Select::read_data` stream through its
own `read_as_elementwise_pipeline` when the element type is static (like Op2) and keep the
pull-and-mix path only for ZeroCopy `condition` / `y`. A TypeDyn `x` / `y` with a Fusable
`condition` would still need the first rule. Add Select cases to
`read_tiling_of_expressions` (params.rs:2313).

Severity note: rated low (not the hunter's medium) for consistency with K187 / K64: values are
correct, the extra memory is bounded by about (1 + 1/itemsize) x the region, no untrusted input is
involved, and only the Rust API is affected. It can still turn a read that fit into an OOM abort.
