## What goes wrong
#107 ("Keep the cached numpy dtype of an implicitly broadcast operand", the K180 fix) changed the
`Operand::PyArray` arm of `broadcast_operand` from `arr.get().arr.clone()` (no numpy at all, at
a7b0656) to building a new `PyArray` with `arr.get().numpy_dtype(py)?`. `numpy_dtype` does not just
return a cached descr: when none is cached it runs `dtype_to_numpy` and caches the result. So every
jix Array operand that gets broadcast in any op (all `define_op2` ops, multiply, power, divide,
remainder, isclose, clamp, bitwise_rotate_*, where) now has its numpy dtype computed eagerly, but
only `where` ever uses it; element-wise results are built with `PyArray::from_core` and drop it.
`dtype_to_numpy` raises whenever numpy's `(itemsize, alignment)` differs from jix's, which on i686
Linux is the case for every f8/i8/u8/c16 dtype (K8: jix alignment 8, numpy 4). Arrays from
`jix.compact`, `jix.asarray` without `dtype=`, `read_array`, reductions and every op result carry no
cached dtype, so on the x86 wheels the op itself now raises ValueError where it built fine before.

## Trigger
i686 Linux, release wheel, numpy for i686 (all of these built before #107):
- `x = jix.compact(np.zeros((2, 1))); y = jix.compact(np.zeros(3)); x + y` (x broadcast)
- `a = jix.compact(np.arange(5, dtype=np.int32)); (a > a.mean()).numpy()` - `a.mean()` is a 0-d f64
  jix Array with no cached dtype that is broadcast to (5,); the bool result itself converts fine on
  i686, so this worked end to end before #107 and now raises in `>`.
- likewise `jix.isclose`, `jix.maximum`, `jix.clamp`, `jix.where(c23, a, x)` with the f8 jix
  operand needing broadcast, and pipelines that only `compact()` / `write_array` the result or cast
  it to f32 before `.numpy()`.

K8's listed triggers (`.dtype`, `.numpy()`, indexing, shape ops, `where`, `out=`) do not include
element-wise ops; this is a new trigger. (For `where`, x's dtype was already computed at
select.rs:89; the new part is that a broadcast y, or a broadcast x in a scalar-condition `where`
that selects y, now also fails.)

## Repro
`bug-hunt/report/repros/K199.py` (x86_64 simulation; no i686 Python
interpreter is available, see K8.md). The only `dtype_to_numpy` branch that goes through Python is an
align=True struct dtype (it calls `numpy.dtype(...)`), so the script replaces `numpy.dtype` with a
function that raises the i686 error and runs each op with a struct operand. Each case asserts the
correct (pre-#107) behavior:

```
$ .venv/bin/python bug-hunt/report/repros/K199.py
[PASS] where, no broadcast (control)  (numpy.dtype calls: 0)
[FAIL] where, y broadcast  (numpy.dtype calls: 1): ValueError: numpy dtype itemsize or alignment mismatch: (8, 4) != (8, 8)  [simulated i686]
[PASS] equal, struct x, no broadcast (control)  (numpy.dtype calls: 0)
[FAIL] equal, struct x broadcast  (numpy.dtype calls: 1): broadcast computed the operand's numpy dtype: numpy dtype itemsize or alignment mismatch: (8, 4) != (8, 8)  [simulated i686]
exit=1
```

The `equal` cases show the element-wise path: without broadcasting, `equal` of a struct operand
reaches dispatch and raises its TypeError with no numpy call; with x broadcast, `dtype_to_numpy`
runs first (the dispatch error formatter, dispatch.rs:262-302, does not touch numpy, so the call
comes from broadcast.rs:54). On i686 the same call with an f8 operand, which dispatch accepts,
fails the same way. The i686 failure of `dtype_to_numpy` for f8 is K8's confirmed analysis
(numpy's `NPY_ALIGNOF(double) == 4` on i686, jix-py/src/dtype.rs:75-82 requires equality).

## Root cause
broadcast.rs:53-57 uses `PyArray::numpy_dtype`, which is "get or compute", to carry the dtype over,
while the stated intent of the fix (and the K180 problem: a cached descr with metadata being dropped)
needs only "get if cached". Computing it is unnecessary for every consumer except `where`, which
computes x's dtype itself anyway (select.rs:89) when it needs it.

## Suggested fix
Carry over only an already cached descr: add an accessor that returns
`Option<Py<PyArrayDescr>>` from the cache without calling `dtype_to_numpy`, and build the broadcast
`PyArray` with `from_core_impl(array, cached)` (or fall back to `Operand::Array` when nothing is
cached). Separately, K8's fix (relax the alignment equality in `dtype_to_numpy`) removes the i686
failure at the root.
