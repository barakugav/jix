# K187: 32-bit: a stepped Slice is classified ReadTiling::ZeroCopy even when its K156 fallback materializes the region, so an outer stepped Slice pulls its whole bounding box from it - a pull of 2 elements allocates and reads O(step) elements

- Severity: low  Verdict: confirmed  Category: resource
- Location: jix/src/ops/shape_ops/slice.rs:101-103 (related: jix/src/ops/shape_ops/slice.rs:153-161, jix/src/ops/shape_ops/slice.rs:170, jix/src/ops/shape_ops/slice.rs:182-216, jix/src/storage/params.rs:1073, jix/src/storage/params.rs:1098-1104, jix/src/storage/core_trait.rs:123)
- Reachability: public Rust API, 32-bit targets only (x86 / armv7). Not Python: Python slicing rejects any step other than 1 (jix-py/src/ops/shape_ops.rs:338-339).
- Reported by: storage-compact-params
- Relation to KNOWN: a new interaction of #106 (ReadTiling forwarding) with #107's K156 fix (the stepped-Slice fallback). It is distinct from K77: K77 makes one inner read per OUTPUT position, here the outer Slice makes the inner do one read per position of the outer's BOUNDING BOX, which is `step` times as many.
- Consolidated: found in run 2026-11-16-scan-106-107 as F004; line numbers below are at c705a54 (#107). Re-run by hand at main c705a54 (#107): reproduces on i686 (repro_k187: 3 tests fail, a 2-element pull makes a 262148-byte allocation). Current location: jix/src/ops/shape_ops/slice.rs:103.

## What goes wrong
Since #106 `Slice::new` gives every Slice, stepped or not, `inner.read_tiling().forwarded()`
(slice.rs:101-103). So a stepped Slice over a ZeroCopy inner (Plain, Scalar, a Broadcast of them,
another Slice) is ZeroCopy, and params.rs:1073 defines that as "a pull returns a view into existing
memory: no compute, no allocation". A stepped Slice keeps that promise only when its bounding box
passes `check_region_size` (slice.rs:153-160). If the box does not fit, the #107 K156 fix drops it
to the general path, which materializes the requested region and makes one inner read per stepped
position (slice.rs:182-216).
An outer stepped Slice trusts the flag (slice.rs:161) and pulls its whole bounding box,
`(n-1)*step+1` elements, from that inner Slice (slice.rs:170). The inner then allocates the whole
box and does `(n-1)*step+1` single-element reads, all to return n elements. Before #106 a stepped
Slice cleared its flags (`with_cleared_flags`, a7b0656 slice.rs:228), so the outer took its general
path: n cheap reads. Values stay correct. The cost grows with the outer step, and the outer box can
be anything up to isize::MAX bytes. A box near that size is an allocation a 32-bit process usually
cannot make, and `handle_alloc_error` (util/aligned_vec/raw.rs:160-161, 208-209) then aborts the
process for a 2-element read (argued, not run). On 64-bit an in-shape box always fits in usize and
`check_region_size` is a no-op there (error.rs:319-323), so the fallback never happens.

## Trigger
On i686 (Rust API):
```rust
let s2 = Array::plain_ndarray(ndarray::Array1::from_elem(1, 7u32))?
    .broadcast(&[1u64 << 33])
    .slice((SliceItem::new(None, None, 1 << 16),))   // shape [2^17], ZeroCopy (forwarded)
    .slice((SliceItem::new(None, None, 1 << 16),));  // shape [2]
s2.to_buf_strided(&[0..2], &s2.read_ctx())?;        // pull
```
The outer box is 2^16+1 elements (256 KiB) and fits. The inner Slice's box for that request is
2^32+1 elements, which does not fit in a 32-bit usize, so the inner falls back. Every pull of `s2`
reaches the slow path: `to_buf_strided`, an element-wise op with `s2` as a leaf (the pipeline pulls
its leaves, core_trait.rs:123; e.g. `(!s2).to_ndarray()`), reduction tiles. The push read
`to_buf_slice` is unaffected.

## Repro
jix/tests/repro_k187.rs. The test uses a tracking global allocator and
asserts that a 2-element read makes no allocation over 4096 B.

`bug-hunt/tools/cargo-i686 test --manifest-path jix/Cargo.toml --all-features --test repro_k187 -- --nocapture --test-threads=1`
(i686, debug): all 3 tests fail.
```
!s2 to_ndarray: max alloc 262148 B, 224.947129ms
push: max alloc 0 B, 51.914us; pull: max alloc 262148 B, 231.149287ms
[u32; 16] pull of 2 items: max alloc 67108928 B, 3.600290029s
```
262148 = (2^16+1) * 4 and 67108928 = (2^20+1) * 64, exactly the outer bounding box. The third
test is the hunter's scale: `[u32; 16]` broadcast to [2^27], then `[::64][::2^20]`. Its 2-item pull
takes 3.6 s, against about 50 us for the push read of the same region. The values are correct in
every case.
The same command on x86_64 (`cargo test ...`) passes all 3: max allocation 8 B / 48 B / 0 B, and
every read takes microseconds.

## Root cause
`ReadTiling::forwarded()` (params.rs:1098-1104) describes an op that forwards every read
re-strided. A stepped Slice does that only on the fast path. Its general path, the only path for
push reads and since #107 also for pulls whose box does not fit, is "pushed pieces" with a
materialized pull. The classification at slice.rs:101-103 ignores both `no_steps` and the
size-dependent fallback. The only consumer that relies on ZeroCopy to pull MORE than it needs is
the stepped-Slice fast path itself (slice.rs:161), so the mismatch shows up when two stepped
Slices are nested.

## Suggested fix
Option 1, the simple safe fix: on 32-bit, do not classify a stepped Slice as ZeroCopy. Keep
`forwarded()` for `no_steps` and use, for example, `pulled_copy()` for stepped Slices. Gate it on
`cfg(target_pointer_width = "32")`. On 64-bit the fallback cannot happen, and nested stepped Slices
over a Plain keep their zero-copy view.
Option 2: keep the classification and make slice.rs:161 also require that the inner can serve the
box as a view. That needs a way to ask the inner whether a given region is zero-copy, for example a
stepped inner Slice checking its own box with `check_region_size`.
