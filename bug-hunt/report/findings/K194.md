## What goes wrong
#107's K156 fix lets a stepped Slice pull its bounding box from a ZeroCopy inner only when
`check_region_size(box, itemsize)` passes, where `itemsize` is the Slice's own (slice.rs:153-161).
That assumes the inner serves the box at the same itemsize. Since #106, SubDtype over a ZeroCopy
parent is itself ZeroCopy (sub_dtype.rs:65-66, `pulled_view()`), and SubDtype pulls the same index
from its parent (sub_dtype.rs:98). The parent has the larger struct itemsize. So the Slice's check
passes at the field itemsize, and the parent's `check_out_buf` (e.g. broadcast.rs:130) then fails
at the parent itemsize. The read returns `Err` instead of falling back to the general per-position
path, which works. Before #106 (a7b0656) SubDtype cleared its flags, so this path was never taken
over it. The push read of the same view works. Values are never wrong: this is a spurious error.

## Trigger
On i686 (Rust API). `S16` is a `#[repr(C)]` Dtyped struct `{ a: u8, rest: [u8; 15] }`:
```rust
let s = Array::plain_ndarray(array![S16 { a: 7, rest: [0; 15] }])?
    .broadcast(&[(1 << 27) + 2])
    .dtype_sub_field::<u8>("a")
    .slice((SliceItem::new(None, None, 1 << 27),));          // shape [2]
s.to_buf_strided(&[0..2], &s.read_ctx())?;                    // pull -> Err
(s + Array::plain_ndarray(array![1u8, 1])?).to_ndarray()?;    // pipeline leaf pull -> Err
```
The box is 2^27 + 1 elements: 128 MiB at the 1-byte field itemsize (passes), 2 GiB + 16 B at the
16-byte parent itemsize (fails isize::MAX). Any pull of the Slice reaches it: `to_buf_strided`, an
element-wise op with the Slice as a leaf, reduction tiles. Only a parent whose box exceeds
isize::MAX bytes while the field box does not can trigger it, so in practice a broadcast or Scalar
parent (a real Plain parent of that size cannot exist on 32-bit).

## Root cause
slice.rs:153-161 decides whether the inner can serve the box as a view from two facts: the inner
is `ReadTiling::ZeroCopy`, and the box fits at the Slice's itemsize. The second fact is about the
Slice, not about every storage the box pull reaches. All ZeroCopy storages keep the itemsize of
their input (Plain, Scalar, Broadcast, PermuteDims, InsertDim / RemoveDim, Slice, Transmute, Any)
except SubDtype, which narrows it, and its pull of the full parent region is subject to the
parent's own `check_out_buf` at the parent itemsize (sub_dtype.rs:96-98, broadcast.rs:130). The
same mismatch is reached through any ZeroCopy shape op stacked on a SubDtype (e.g. PermuteDims of a
SubDtype under a stepped Slice).

## Suggested fix
Simplest: on 32-bit, do not classify SubDtype as ZeroCopy when its itemsize is smaller than its
parent's (e.g. `pulled_copy()` or Tiled under `cfg(target_pointer_width = "32")`), so the stepped
Slice takes its general path as before #106. Alternatively, carry the largest itemsize of the view
chain in the spec and have slice.rs:160 check the box at that itemsize, or give ZeroCopy storages a
way to answer "can you serve this region as a view" (K187's option 2), which would fix both K187
and K194.
