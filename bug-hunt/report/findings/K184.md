# K184: #106 reused FileMetadata field 2 with an incompatible wire type, so archives written by jix 0.0.7 no longer load (and 0.0.7 cannot read new ones)

- Severity: medium  Verdict: confirmed  Category: compatibility
- Location: jix/schema/proto/jix/v1/structure.proto:7 (related: jix/src/archive/schema/_proto_gen/jix.v1.rs:219-220, jix/src/archive/common.rs:49-53, jix/src/archive/common.rs:180-186, jix/src/archive/common.rs:267-272, jix/src/archive/array.rs:460-473, jix/src/archive/version.rs:9-17, jix/Cargo.toml:3)
- Reachability: public Rust API (`Array::read_from_file`, `read_from_file_with`, `read_from`, `read_from_file_mmap`), Python API (`jix.read_array`, with or without `mmap=True`)
- Reported by: codec-archive-archive-io
- Consolidated: found in run 2026-11-16-scan-106-107 as F001; line numbers below are at c705a54 (#107). Re-run by hand at main c705a54 (#107): reproduces (repro_k184: both archives written by jix 0.0.7 fail with InvalidArchive, the control that re-encodes only field 2 loads; K184.py: 3 checks fail, the reverse check included). Current location: jix/schema/proto/jix/v1/structure.proto:7.

## What goes wrong
Before #106 (1169965), FileMetadata field 2 was `uint64 lib_version_semver`, a varint. #106 kept
field number 2 for `Semver lib_version`, a length-delimited message. Every writer since #55 / 0.0.5
stored a non-zero `VERSION_U64` there (0.0.7 -> `7 << 16`), so the field is always on the wire.
prost rejects a known field that arrives with the wrong wire type, so the FileMetadata of every
archive written by the 0.0.7 release (#99) fails to decode in current main, and the 0.0.7 reader
fails the same way on every archive written by current main. The rest of the format is still
compatible: re-encode only field 2 and the 0.0.7 file loads with the right contents.

The failure looks like corruption: the magic is still `jix1`, the archive type is still `ARRAY_V1`
and the proto package is still `jix.v1`, and the error names an internal Rust type path. The
"(archive written by jix X, read by jix Y)" suffix that #106 added for this kind of failure never
fires, because it wraps only `read_body` (array.rs:461-473) and here `read_file_meta` (array.rs:460)
is what fails. Also, `jix/Cargo.toml` is still `0.0.7`, so both incompatible formats describe
themselves as "jix 0.0.7".

## Trigger
Write any array with jix 0.0.7 (2b229d2) and read it with current main (c705a54). The repro holds
the exact 113-byte file that a jix 0.0.7 build wrote for `array![[1i32, 2, 3], [4, 5, 6]]` with
`write_to_file` (built from `git archive 2b229d2` in a scratch copy, not a synthetic splice). Its
FileMetadata is `06 08 02 10 80 80 1c`: len 6, archive_type 2, then field 2 as a varint (458752 = 7 << 16).
In the other direction, write any array with current main and read it with jix 0.0.7.

## Root cause
structure.proto:7 (`Semver lib_version = 2;`) reuses a field number whose old type (`uint64`,
wire type varint) does not match the new one on the wire (message, wire type LEN). Protobuf
evolution rules allow reuse only for a wire-compatible type. The generated decoder
(`_proto_gen/jix.v1.rs:219-220`) therefore errors out when it meets the old varint, and
`ArchiveReader::try_read_message` (common.rs:180-186) turns that into `InvalidArchive`. The
repo's own `schema_buf_break.yaml` CI job (buf `breaking: use: [FILE]`, whose FIELD_SAME_TYPE /
FIELD_SAME_NAME rules flag this change) exists to catch exactly this. It must have been
skipped with the `schema-skip-breaking` label or ignored.
Nothing in the tree documents a compatibility break: the commit message says only "Store lib
version as Semver message instead of packed u64", and `todo.md:6` still lists "document archive
compatibility". A deliberate break would also be expected to bump the version or the magic.

Refutation attempts that failed: there is only one production reader of FileMetadata
(`array.rs:460`, behind every public entry point, both mmap and owned), and it has no lenient
fallback. The control shows the rest of the 0.0.7 layout (headers, TOC, block table, zstd blocks)
is still accepted, so this is not masked by some other, intended format change. The current
writer always emits field 2 (`common.rs:51`, `Some(lib_version())`), so no file escapes either way.

## Suggested fix
Give the new message a fresh number and retire the old one, e.g.
`reserved 2; reserved "lib_version_semver"; Semver lib_version = 3;`. Then new readers skip the
old varint as an unknown field, and 0.0.7 readers skip field 3 and still read new files (field 2
defaults to 0). Checked: a file written by current main, with only the tag byte of its field 2
changed from `0x12` to `0x1a` (field 3), loads in the real 0.0.7 binary
(`jix 0.0.7 read OK: shape [2, 3] values [1, 2, 3, 4, 5, 6]`), while the unpatched file fails.
Alternatively, keep `uint64 lib_version_semver = 2` beside a new field. Optionally,
decode FileMetadata errors with the same "(archive written by ..., read by ...)" context, and add a
regression test that loads a checked-in archive from the previous release.
