# K179: where() raises for an integer error in an element it does not select, but only for some spellings of a 0-d condition (Python bool / numpy 0-d skip the other branch, a jix 0-d array reads it); numpy's guard idiom where(b != 0, a // b, 0) always raises, and nothing documents either

- Severity: low  Verdict: confirmed  Category: questionable-semantics
- Location: jix-py/src/ops/elementwise/select.rs:68 (related: jix-py/src/ops/elementwise/select.rs:17-18 (docstring), jix-py/src/ops/elementwise/select.rs:89, jix-py/src/ops/common/operand.rs:88-150, jix/src/ops/elementwise/select.rs:139, jix/src/ops/elementwise/select.rs:142, jix-py/src/ops/elementwise/div_rem.rs:33)
- Reachability: Python API (`jix.where`); the Rust `Array::select` has no scalar shortcut, so it always reads both branches
- Reported by: py-ops-cmp-bitwise-select, py-ops-dispatch-promotion
- Consolidated: found in run 2026-11-15-batch7-5 as F008; line numbers below are at that run's commit. Re-checked at main c705a54 (#107): still reproduces (K179.py: the same all-False condition gives 2 outcomes; the guard idiom raises). Current location: jix-py/src/ops/elementwise/select.rs:72.

## What goes wrong
The #95 shortcut in `jix.where` (jix-py select.rs:68-75) returns the selected operand when the
condition is an `Operand::Scalar` holding a bool. The other operand is then not in the result at
all, so it is never read. Three spellings become such a Scalar: a Python bool, a numpy bool scalar,
and any 0-d numpy array (operand.rs:88-150 turns it into a typed Scalar via `.item()`). Every other
condition goes to core `Select` (select.rs:89): a 0-d jix Array (`jix.asarray(False)`,
`jix.compact(np.array(False))`), a shape-(1,) numpy array, or any bool array. `Select` reads `y`
(pull, core select.rs:139) and `x` (push, core select.rs:142) over the whole requested region. Since
#95 an integer error is always an Err. So a zero divisor in an element the condition does NOT pick
still raises ArithmeticError.

Two results:
1. The same all-False 0-d condition gives a value for `False`, `np.False_` and `np.array(False)`.
   It raises ArithmeticError for `jix.asarray(False)` and `jix.compact(np.array(False))`.
2. numpy's usual guard, `where(b != 0, a // b, 0)`, cannot work in jix: it always raises. numpy
   returns `[3, 0, 3]` with a RuntimeWarning.

No doc states either result. The where docstring (select.rs:17-18) only says a "scalar"
condition returns the selected operand. It does not say that a 0-d numpy array counts as a scalar
and a 0-d jix array does not, or that unselected elements are evaluated and their integer errors
raise. divide / remainder / power say a zero divisor (or a negative exponent) raises "when the
result is read", but not that this applies to elements `where` discards. There is no UB and no
wrong value. The defect is an error contract that depends on the Python type of the condition and
is undocumented.

## Trigger
```python
a = jix.compact(np.array([7, 8, 9], np.int32))
b = jix.compact(np.array([2, 0, 3], np.int32))
q = a // b
jix.where(np.array(False), q, a)  # -> [7 8 9]
jix.where(jix.asarray(False), q, a)  # -> ArithmeticError
jix.where(np.array([False]), q, a)  # -> ArithmeticError
jix.where(b != 0, q, 0)  # -> ArithmeticError (numpy: [3 0 3] + RuntimeWarning)
```
The same happens with `rounding_mode="trunc"` / `"euclid"`, `%`, and a negative integer power.

## Root cause
- jix-py select.rs:68-75 decides whether the unselected operand is evaluated at all based on the
  Operand variant of the condition. That variant reflects how the value was passed (Python/numpy
  scalar or numpy 0-d -> `Scalar`, operand.rs:88-150; jix Array -> `PyArray`, operand.rs:38-40),
  not what it is: a 0-d jix bool array is just as much a scalar condition.
- Core `Select::read_data_uncached` (jix/src/ops/elementwise/select.rs:138-142) reads both `x` and
  `y` over the full region with `?`. An integer kernel's `ArithmeticStatus` covers its whole read,
  so an error in an element the mask discards still fails the read. Integer errors are always Err
  since #95 (div_rem.rs:33 docs, pipeline.rs:245-310), and the old errstate "ignore" escape hatch
  is gone.
- Neither the where docstring (select.rs:17-18) nor the divide / remainder / power docstrings
  describe how `where` and integer errors interact. The tests (test_select.py:48-66) pin only
  `True` / `np.False_` returning the operand object.

## Suggested fix
Docs first. In `jix.where`, state that `x` and `y` are both evaluated over the whole output, so an
integer error in an element the condition does not select still raises ArithmeticError, and give
the workaround `a // jix.where(b != 0, b, 1)`. Also state which conditions count as "scalar":
Python bool, numpy bool scalar or 0-d numpy array, but not a 0-d jix Array. The same sentence
belongs in divide / remainder / power. To remove the inconsistency between spellings, take the
shortcut for a 0-d jix bool array too. That means reading its one element, which is cheap, but it
makes `where` read data eagerly. Making the guard idiom work needs per-element error masking in
`Select`: an `ArithmeticStatus` per lane, masked by the condition. That is a larger design change.
(Verified variants: `rounding_mode="trunc"` / `"euclid"`, `%`, and `a ** e` with a negative `e`
all behave the same; see scratch/verify_F008_variants.py.)
