# K197: numpy()'s GIL decision can never see ReadTiling::Fusable - every jix-py array is an ArrayAny, which demotes Fusable to SinglePass, so tiny fused reads over numpy memory always release the GIL

- Severity: low  Verdict: confirmed  Category: performance
- Location: jix-py/src/array.rs:631-639 (related: jix/src/storage/any.rs:105-108, jix/src/storage/params.rs:1098-1103, jix-py/src/array.rs:125, jix-py/src/ops/common/macros.rs:11,45,141, jix-py/src/ops/common/operand.rs:520)
- Reachability: Python API (`Array.numpy()`, `Array.__getitem__`, `__array__`, `plain()`)
- Reported by: concept-python-boundary
- Consolidated: found in run 2026-11-17-scan-106-107-b as F006; line numbers below are at c705a54 (#107). Re-run by hand at main c705a54 (#107): reproduces (repro_k197: a 16-byte fused read over numpy memory detaches, because jix-py sees SinglePass, not Fusable). K197.py measures it through GIL hand-off latency and was inconclusive on this host: its control, a read that is meant to detach, showed no latency either. Current location: jix-py/src/array.rs:633.

## What goes wrong
#106 replaced the `plain_read` test in `PyArray::numpy` with a spec-based one: stay attached when
the storage's `read_tiling()` is `ZeroCopy` or `Fusable` and the read cost is at most 4096, else
detach. `PyArray.arr` is always an `ArrayAny`, and the only constructor of `ArrayStorageAny`
(`Array::into_any` -> `AnyMeta::new`) rewrites the erased spec's tiling with `forwarded()`, which
maps `Fusable` to `SinglePass` (by design, so a parent does not try to fuse through the erased
storage; core pins this in `params.rs` `read_tiling_of_expressions`). So the spec jix-py reads
never says `Fusable`, the `ReadTiling::Fusable` arm is dead, and every element-wise or select
result over numpy / scalar memory - however small - detaches, exactly as before #106. Only the
`ZeroCopy` arm (Plain, Scalar, and shape views of them) takes effect. No correctness or safety
impact: detaching is always safe here. The cost is latency: in a multi-threaded GIL program each
tiny lazy read hands the GIL away and waits up to the switch interval (5 ms by default) to get it
back - the hand-off #106 set out to avoid for cheap in-memory reads.

## Trigger
```python
x = np.arange(16, dtype=np.float32)
(jix.asarray(x) + 1).numpy()  # 64 bytes, element_cost 3 -> read_cost 48, still detaches
```
In Rust: `(plain.into_any().into_typed::<f32>()? + plain2.into_any().into_typed::<f32>()?).into_any()`
reports `SinglePass`, while the same op before `into_any()` reports `Fusable`.

  `cargo test --manifest-path jix/Cargo.toml --all-features --test repro_k197 -- --nocapture`
  ```

  panicked at tests/repro_k197.rs:52:5:

  ```

## Root cause
`ReadTiling` on the erased spec answers "can a parent fuse through me", and `AnyMeta::new`
(jix/src/storage/any.rs:105-108) correctly demotes it for that question. jix-py
(jix-py/src/array.rs:633-636) uses the same flag to answer a different question - "does a
top-level read of this array stream straight from memory" - for which the erased storage's
answer is still its inner storage's (`ArrayStorageAny::read_data` just forwards). After the
demotion `SinglePass` covers both a fused op over memory and a compact decompression, so jix-py
cannot tell them apart. Both halves landed in the same commit (#106, 1169965), and no test reads
the jix-py decision.

## Suggested fix
Keep the erased storage's own tiling reachable and use it for the GIL decision: e.g. a
`#[doc(hidden)]` `ArrayStorageAny::inner_spec()` / `erased_read_tiling()` returning
`self.inner.storage().spec()` (recursing through nested `Any`), or store the pre-demotion tiling in
`AnyMeta`. jix-py then matches `ZeroCopy | Fusable` on that. Add a jix-py test (or a core test of
the helper) so the arm cannot silently go dead again.
