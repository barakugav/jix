## What goes wrong
`Owned::read_section` guards the allocation only with
`usize::try_from(section.size / size_of::<T>())` (block.rs:394-395), i.e. it checks the ELEMENT
count against `usize`, not the BYTE size against `isize::MAX`. On 32-bit that admits a u8 section of
up to u32::MAX bytes, or a `BlockLocation` section of up to 12 * u32::MAX bytes. The chunked loop
(block.rs:402-410) then doubles a `Vec<MaybeUninit<T>>` towards `len`; once the next step passes
isize::MAX bytes, `Vec::resize` panics with "capacity overflow" (alloc raw_vec) - an explicit panic,
so release builds panic too, and Python gets a `PanicException` instead of an `OSError` /
`RuntimeError`. By then 1 GiB (block_data) or 1.5 GiB (blocks_loc) has been read into memory for
nothing. The section bounds check does not stop it: since #107 `total_size` is the real stream
length for both `Some(len)` and `None` (common.rs:116-134), and the stream really is that large. A
genuine archive with more than 2 GiB of block data (written on a 64-bit host) read on a 32-bit wheel
hits the same panic; a file merely padded or sparse-extended past 2 GiB is enough as well. The
existing `"section size {} is too large"` error shows the intended outcome is a clean Err.

## Trigger
On i686: write `array![1i32, 2, 3, 4]` with `write_to`, patch the TOC's block_data size to
`2^31 + 4096` (or the blocks_loc size to `12 * 178956971 = 2^31 + 4`), `File::set_len` the file
sparsely so the section lies inside it, then `Array::read_from_file(path)`.

## Root cause
block.rs:394-395 bounds the element count by `usize::MAX`, but a `Vec<T>` can hold at most
`isize::MAX` BYTES; on 64-bit the two never differ in practice (a section must fit in the real
stream), on 32-bit any section between 2 GiB and 4 GiB (u8) or 2 GiB and 48 GiB (BlockLocation)
falls in the gap. The doubling `data.resize((start * 2).max(4096).min(len), ..)` (block.rs:404) is
infallible and panics on the overflowing capacity. Sections between 1 and 2 GiB pass the capacity
check but can still abort the process on allocation failure (`handle_alloc_error`) on a 32-bit
address space - not demonstrated here.

## Suggested fix
Check the byte size, not the element count: reject `section.size > isize::MAX as u64` (or use
`Layout::array::<T>(len)`) with the existing "section size ... is too large" InvalidArchive error,
and grow with `try_reserve` in the loop, mapping a failure to an Err - as
`BlockLocation::alloc_table` (storage/block.rs:34-44) already does on the writer side since #107.
