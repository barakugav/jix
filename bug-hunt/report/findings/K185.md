# K185: 32-bit: the #107 read-size cap (isize::MAX bytes) does not bound tiles or chunks, because scale_read_shape grows broadcast / tile dims to 2 * max (and compaction to at least 2 target blocks), so compact_with panics with "capacity overflow" and reductions fail with a spurious InvalidShapeOperation

## What goes wrong
#107 clamps `ReadSize` to isize::MAX bytes (params.rs:26-27), per its commit message "so read tiles
and compaction chunks fit in memory". But `scale_read_shape` grows any dim with a non-NONE
`ScaleWeight` (Broadcast and Tile mark their duplicated dims FULL) up to `2 * max_nitems`
(util/mod.rs:505-509, documented at params.rs:160-161), so a tile or chunk reaches
`2 * isize::MAX` bytes = 2^32 - 2 on 32-bit. Compaction additionally floors `max_chunk` at one
target block (compact.rs:226), so with 1 GiB target blocks (BLOCK_SIZE_BYTES_MAX) the weighted dim
doubles the chunk to 2 GiB even at the default read size. In `compact_into_builder_dyn` the chunk
bytes go straight to `chunk_buf.reserve` (compact.rs:262-264), which panics with "capacity
overflow" (raw.rs:33) - an explicit panic, so release builds panic too. In reductions,
`read_shape_heuristic` produces the same doubled tile, and the inner Broadcast's `check_out_buf`
rejects it: `sum` over a long broadcast dim returns InvalidShapeOperation "read region of size
[2147483648] ... does not fit in memory" although the user asked for a scalar and the pull read is
a zero-copy view. No UB: the #107 cap does keep the u64 -> usize conversions from wrapping.

## Trigger
i686 (any 32-bit target), debug or release:

```rust
// (a) compaction, 1 GiB source read size (below isize::MAX, so not clamped at all)
let a = Array::compact_ndarray_with(&array![1u8], ArrayParams::new().read_size((1, 1 << 30)))?;
let b = a.broadcast(&[1 << 31]);
b.compact_with(ArrayParams::new().block_shape(&[1 << 20])?, &b.read_ctx())  // panics
// (b) compaction, DEFAULT read size, 1 GiB target blocks: max_chunk = 1 block, doubled to 2
let b = Array::compact_ndarray(&array![1u8])?.broadcast(&[1 << 31]);
b.compact_with(ArrayParams::new().block_shape(&[1 << 30])?, &b.read_ctx())  // panics
// (c) reduction: Err instead of 2^31 + 5
Array::compact_ndarray_with(&array![1u8], ArrayParams::new().read_size((1, 1 << 30)))?
    .broadcast(&[(1 << 31) + 5]).sum(0).to_ndarray::<Ix0>()
// (d) the K153 budget, read_size (1, 1 << 33) (clamped to isize::MAX), n = 2^32 + 5: tile 2^32 - 2
```

## Root cause
The #107 fix bounds the input of the heuristic (`ReadSize.max`), not its output. `scale_read_shape`
(util/mod.rs:505-509) lets a weighted dim reach `max_nitems.saturating_mul(2)`, and compaction's
`max_chunk = (read_size.max / block_size_bytes).max(1)` (compact.rs:226) lets the doubling act on
a whole 1 GiB block. Nothing after the heuristic re-checks the result against isize::MAX: the
compaction chunk bytes (compact.rs:262) go to `reserve` unchecked, and the reduction tile
(common.rs:560-563) is only checked by the inner storage's `check_out_buf`, which turns an internal
tiling choice into a user-visible error.

## Suggested fix
Bound the heuristic's output, not just its input: in `scale_read_shape`, cap the weighted target at
`max(max_nitems, isize::MAX / itemsize)` (or pass a hard byte ceiling and clamp the final volume to
it), and in compaction cap the chunk at `isize::MAX / block_size_bytes` blocks (at least 1). With
the cap, (a), (c) and (d) complete; (b) needs a 1 GiB chunk, which is the minimum for 1 GiB blocks.
Additionally size `chunk_buf` with a checked conversion and return InvalidShapeOperation instead
of panicking in `reserve`.
