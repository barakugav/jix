# K195: A dim of length exactly PY_SSIZE_T_MAX accepts out-of-range slice bounds: PySlice_Unpack clamps them to the dim length, so a[2**100:] / a[n+1:] return empty and a[5:2**100] selects to the end

- Location: jix-py/src/util.rs:36 (related: jix-py/src/util.rs:39-45, jix-py/src/ops/shape_ops.rs:337-358, jix-py/src/array.rs:183)
- Reachability: Python API (`Array.__getitem__`, `Array.numpy(index)`, `jix.slice`)
- Reported by: py-ops-shape-ops, concept-python-boundary
- Consolidated: found in run 2026-11-17-scan-106-107-b as F004; line numbers below are at c705a54 (#107). Re-run by hand at main c705a54 (#107): reproduces (K195.py: 5 out-of-bounds slices accepted on a dim of length 2**63 - 1). Current location: jix-py/src/util.rs:36.

## What goes wrong
Python slicing in jix is strict: an out-of-bounds start or stop raises IndexError, and huge bounds
raise too (an intentional behavior, pinned by `test_slice.py::test_slice_huge_bounds_raise`).
`slice_unpack` resolves the slice with `PySlice_Unpack`, which clamps any explicit bound outside
`[PY_SSIZE_T_MIN, PY_SSIZE_T_MAX]` to those limits; it only undoes the clamp for an omitted stop.
`parse_basic_index` then checks `start_norm > len` / `stop_norm > len` on the clamped value. When
the dim length is exactly `PY_SSIZE_T_MAX`, a clamped bound equals `len` and passes, so the strict
contract silently breaks for that one length: a start past the end gives an empty selection, and a
stop past the end selects to the end. The returned region is in bounds, so this is not a memory
safety issue. `PY_SSIZE_T_MAX` is `sys.maxsize`: 2**63-1 on 64-bit, and 2**31-1 on the shipped
(untested) 32-bit wheels, where it is a plausible lazy broadcast length. For every other length
the error message quotes the clamped value (`slice start 9223372036854775807`), not the user's.

## Trigger
```python
import sys, numpy as np, jix

b = jix.broadcast(jix.asarray(np.zeros(1, np.uint8)), (sys.maxsize,))
jix.slice(b, (slice(2**100, None),))  # shape (0,), expected IndexError
jix.slice(b, (slice(sys.maxsize + 1, None),))  # shape (0,), expected IndexError
jix.slice(b, (slice(5, 2**100),))  # shape (sys.maxsize - 5,), expected IndexError
jix.slice(b, (slice(0, sys.maxsize + 1),))  # shape (sys.maxsize,), expected IndexError
b[2**100 :]  # numpy array of shape (0,), expected IndexError
```
`b[5:2**100]` through `__getitem__` is accepted and then fails with MemoryError (8 EiB) instead of
IndexError, per the hunter's run.

## Root cause
`slice_unpack` (jix-py/src/util.rs:36) uses `PySlice_Unpack`, whose output is already clamped to
the `Py_ssize_t` range, so an explicit bound past `PY_SSIZE_T_MAX` and an explicit bound equal to
it become indistinguishable. Lines 39-45 recover only the omitted-stop case (`stop is None`). The
strict check in `parse_basic_index` (jix-py/src/ops/shape_ops.rs:345-353) is correct for the value
it receives, but that value is no longer the user's bound; it can only reject the clamped value
when it differs from `len`, i.e. for every length except `PY_SSIZE_T_MAX`. Negative huge bounds
are not affected: `PY_SSIZE_T_MIN + len` is still negative for any `len <= PY_SSIZE_T_MAX`.

## Suggested fix
Do not take start / stop from `PySlice_Unpack`. Read `slice.start` / `slice.stop` directly, treat
`None` as the default, convert the rest with `__index__` (`PyNumber_Index`) and extract as `i64`
(or compare as a Python int against `len`), mapping an overflow to IndexError that quotes the
user's value. Alternatively keep `PySlice_Unpack` but, when a returned bound equals
`PY_SSIZE_T_MAX` / `PY_SSIZE_T_MIN` and the slice field is not None, re-check the original object
for overflow. Add a test with a lazy broadcast of length `sys.maxsize`.
