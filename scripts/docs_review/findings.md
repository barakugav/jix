# Findings

What the review agents found and did not fix, collected per unit as the units are committed.
Nothing here was changed in the code or the docs.

- **Possible code bugs** - the code does something other than what its docs describe, and the
  docs look like the intended behavior. The review is not a bug hunt; these were met in passing.
- **Needs the maintainer** - a doc and the code disagree and it is not clear which is right, or
  a question only the author can answer.
- **Docs, not fixed** - a docs problem outside the unit that found it, or one the gate does not
  let an agent fix (docs generated by a macro).

## overview

Needs the maintainer:

- `jix-py/docs/module.md:80` says an `Array` "wraps compressed array data". An array made with
  `jix.asarray` is plain, so this covers only the usual case.
- `jix-py/docs/module.md:89` calls `jix.asarray` a "zero-copy" view of "any array-like". A Python
  list or scalar has to be converted first (as the `asarray` docstring itself says), so
  "zero-copy" holds only for inputs that already are buffers.

## ops-div-rem

Needs the maintainer:

- `jix-py/src/ops/elementwise/div_rem.rs:163` `remainder` (and `Array.remainder`, `jix-py/src/array.rs:1026`) annotates `rounding_mode` with a string `"Literal['trunc', 'floor', 'euclid']"` in `#[pyo3(signature = ...)]`, which CLAUDE.md says to avoid (emitted as a quoted string without imports). `divide` instead takes `RoundingMode`, whose `INPUT_TYPE` is a proper `typing.Literal`; `remainder` could do the same with a `RoundingMode::Floor` default.

## ops-cmp

Needs the maintainer:

- `jix-py/src/ops/elementwise/cmp.rs:273` `jix.isclose` is called "analogous to `numpy.isclose`", but its formula `|a - b| <= max(atol, rtol * max(|a|, |b|))` differs from NumPy's `atol + rtol * |b|`; the core `ops::ApproxEq` doc warns about this, the Python doc does not.

Docs, not fixed:

- `jix/src/ops/elementwise/cmp.rs:634` `ApproxEq::new_array` doc line is over 100 columns (as are the macro-generated constructor docs in the same file).
- `jix-py/src/array.rs:1269` `__ge__` one-line doc is 107 columns.

## ops-bitwise

Needs the maintainer:

- `jix-py/src/ops/elementwise/bitwise.rs:378,424` `bitwise_rotate_left/right`: a `bool` array `a` (or an untyped Python int `a` with an array `b`) passes Safe casting to the first `(i8, u32)` entry, so it is rotated as `i8` and the output is `i8`, not "`a`'s dtype". Is accepting `bool` here intended?
- `jix-py/src/ops/elementwise/bitwise.rs:297,336` `bitwise_left_shift/right_shift`: `bool` inputs are accepted (Safe cast to `u8`) but are not in the "Supported dtypes" list.

Docs, not fixed:

- `jix-py/python/tests/test_bitwise.py:7` the module docstring says the logical ops cast "any non-complex input" to bool, but complex is accepted too (Unsafe allows Complex -> Bool), and lines 35 and 43 of the same file test it.
- `jix/src/ops/elementwise/op2.rs:352` the macro arm `fixed_lhs_type` fixes the type of the right-hand operand (`S2::Item`). This is an internal name.

## ops-bit-count

Needs the maintainer:

- `jix/src/ops/elementwise/bit_count.rs:416` the plain `//` comment above `swap_bytes_concrete` says single-byte types do not support `swap_bytes` and points to the `SwapBytes` doc. `SwapBytes` is implemented for `i8`/`u8` (a no-op) via `int_op1!` (`:52`), and the doc now says so; the comment should say `u8` is skipped because swapping is a no-op.

## ops-cast-complex-select

Needs the maintainer:

- `jix-py/src/ops/elementwise/casting.rs:21` "any cast involving struct dtypes is not supported" is too broad: a cast to the identical struct dtype is accepted as a no-op (`casting.rs:55-56`). Unsupported casts raise `TypeError` (`casting.rs:133-137`), which no `Raises:` section documents.

## ops-reduction-engine

Docs, not fixed:

- `jix/src/ops/reduction/common.rs:2051` the `//` comments of the `sum_multi_bulk_multi_tile_2d_reduce_outer` / `_reduce_inner` / `_3d_reduce_middle` tests describe the old layout ("bulks split the reduced dim ...; tiles split the non-reduced dim"). ## ops-reduction

Needs the maintainer:

- `jix/src/ops/reduction/min_max.rs:159,236,316,395`, `jix/src/ops/reduction/variance.rs:388,482` - Max, Min, ArgMax, ArgMin, Variance and StandardDeviation have `SUPPORTS_EMPTY = false`, so reducing an empty dim fails with `InvalidArgument` (the `Array` methods panic, the Python functions raise), but neither the Rust struct docs nor the `jix-py/src/ops/reduction.rs` docstrings mention it (only `Mean` does).
